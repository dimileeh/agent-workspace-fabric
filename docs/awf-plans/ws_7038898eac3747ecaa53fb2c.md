# Plan: Preserve Primary Failure Causality Across Stale and Recovery Paths

## Goal

Prevent later stale/recovery/cleanup/runtime-release faults from replacing the actionable root cause already recorded for a workspace. If a workspace already has durable primary failure evidence, AWF should keep the original `failure_reason`, operator-facing `failure_message`, primary reason code, validation/provenance identifiers, failing command/test/coverage evidence, and recovery guidance. Subsequent infrastructure faults should be recorded as secondary diagnostics only.

This plan intentionally does not rework the post-agent pre-commit repair/retry behavior from PR #239 or GitHub Actions failure evidence from PR #241.

## Current Code Context

- `src/awf/control/executor.py`
  - `_mark_failed()` sets `Workspace.failure_reason`, `Workspace.failure_message`, and transitions to `failed` with a reason code and optional payload.
  - The validation loop finishes `ValidationRun` rows with reason codes such as `PYTEST_TEST_FAILURE` or `COVERAGE_BELOW_THRESHOLD`, then calls `_mark_failed()` with `FailureReason.validation_failure` or related validation failure classes.
  - Stale callback handling (`_record_stale_action_skip()`, `_finish_validation_callback_if_terminal()`) already records ignored stale callbacks, but must not convert existing validation failures to callback reasons.

- `src/awf/control/worker.py`
  - `_fail_stale_active_execution()` currently transitions stale active workspaces to `failed` and writes `failure_reason = infrastructure_failure` plus a stale runtime message.
  - `_fail_stranded_workspace()` similarly writes `infrastructure_failure` for runtime stranding findings.
  - `_record_preserved_active_execution_after_restart()` handles worker reconnect / active execution preservation and currently does not mutate failure fields, but should be covered by regression tests.
  - `_record_terminal_runtime_release_failed()` already records terminal runtime release failures as events without mutating `failure_reason`; existing tests cover the coarse preservation behavior, but not validation/provenance detail preservation.

- `src/awf/service/controls.py`
  - `WorkspaceControlService.destroy_workspace()` currently writes `failure_reason = cleanup_failure` and `failure_message = <cleanup message>` when destroy cleanup fails. If the workspace had already failed with validation/provider/auth evidence, this can replace the root cause.

- `src/awf/service/workspaces.py` and `src/awf/service/metrics.py`
  - `workspace_failure_details_payload()` and failure analysis derive specific reason codes from the latest `workspace.state_changed` event whose `new_state` is `failed`. Any recovery path that emits a later `failed` transition must carry primary failure details in that latest event, or readiness/failure taxonomy can report the secondary infrastructure fault as the root cause.

- `src/awf/service/readiness.py`
  - `_failure_taxonomy_check()` treats generic failure groups/examples/clusters as release-blocking. Preserved validation failures with specific reason codes must remain classified/actionable even when secondary stale/cleanup diagnostics exist.

## Intended Files / Modules To Touch

### Production Code

- `src/awf/control/worker.py`
  - Add narrow helpers local to the worker for building a primary failure snapshot from a workspace plus latest failed validation run/state-event evidence.
  - Update `_fail_stale_active_execution()` so if the row already has primary failure evidence, it transitions using the preserved primary reason code and payload instead of writing `infrastructure_failure`; stale runtime data is attached under supplemental/secondary metadata and the existing stale events remain.
  - Update `_fail_stranded_workspace()` with the same preservation rule for runtime stranding failures.
  - Extend `_record_preserved_active_execution_after_restart()` event payload to include a primary-failure snapshot when present, while leaving current runtime preservation behavior unchanged.
  - Extend terminal runtime release failure event payloads, if needed, with a primary-failure snapshot; do not mutate workspace failure fields.

- `src/awf/service/controls.py`
  - Update destroy cleanup failure handling so existing primary failure evidence is preserved. The cleanup failure remains visible via operation failure (`CLEANUP_FAILED`), audit evidence, and supplemental event/payload metadata.
  - When cleanup failure moves a workspace back to `failed`, ensure the latest failed state event exposes the original primary reason code/message for metrics/readiness, with cleanup stored as secondary metadata.
  - Preserve existing behavior when no primary failure exists: cleanup failure still records `failure_reason = cleanup_failure` and bounded cleanup message.

- `src/awf/service/workspaces.py`
  - Touch only if the implementation needs `workspace_failure_details_payload()` to read a `primary_failure` payload from a later failed transition. Prefer shaping transition payloads so the existing top-level `reason_code`/`message` extraction remains valid.

- `src/awf/service/metrics.py`
  - Touch only if tests prove failure analysis still chooses a secondary fault after the worker/controls payload changes. Prefer preserving primary details at the event payload source.

- `src/awf/service/readiness.py`
  - No behavior change expected. Add/adjust tests only unless readiness cannot classify preserved validation failures through existing summary structures.

- `src/awf/db/enums.py`, `src/awf/service/doctor/reasons.py`, reason catalog files
  - No changes expected because this plan should reuse existing public reason codes such as `PYTEST_TEST_FAILURE`, `CLEANUP_FAILED`, `STALE_ACTIVE_EXECUTION`, `STRANDED_WORKSPACE`, and `TERMINAL_RUNTIME_RELEASE_FAILED`. Update reason catalog entries only if implementation introduces a new public reason code, which is a non-goal unless tests force it.

## Implementation Steps

1. Add tests 1-4 first and confirm they fail for the current overwrite paths.
   - Use existing helpers in `tests/unit/control/test_worker.py` such as `_create_active_execution`, `_RecordingRuntimeCleaner`, `_ActiveExecutionCandidate`, and `RuntimeSnapshot`.
   - Use existing control-service helpers in `test_controls.py` / `test_controls_lifecycle.py` for destroy cleanup failures.

2. Add a small primary failure snapshot helper.
   - Prefer local private helpers near the mutating code unless the same logic becomes duplicated across worker and controls.
   - Snapshot fields should include, where present: `failure_reason`, `failure_message`, primary reason code, latest failed validation run id/status/reason code/tier, validation coverage percent/threshold/reason code, failing test node IDs/evidence, and existing failure details/recovery guidance from the latest primary failed-state payload.
   - Do not add schema columns or migrations; use existing event payload JSON and `ValidationRun` rows.

3. Update worker stale/runtime failure paths.
   - In `_fail_stale_active_execution()` and `_fail_stranded_workspace()`, detect existing primary failure evidence before writing failure fields.
   - If no primary exists, keep current infrastructure classification.
   - If primary exists, do not overwrite `failure_reason` or `failure_message`; transition to failed with primary reason details and include the stale/runtime fault under a secondary key such as `secondary_failures` or `secondary_failure`.
   - Preserve claim clearing and cleanup semantics.

4. Update worker preservation/release diagnostics.
   - Add primary-failure context to active execution preservation and terminal runtime release failure events when available.
   - Keep terminal runtime release from changing workspace status or failure fields.

5. Update destroy cleanup failure handling.
   - Before setting `cleanup_failure`, check whether the workspace already has primary evidence.
   - If no primary exists, keep existing behavior.
   - If primary exists, leave `failure_reason` and `failure_message` unchanged, finish the destroy operation with `CLEANUP_FAILED`, add audit/cleanup diagnostics, and ensure any failed-state transition payload keeps primary reason/message at the top level with cleanup as secondary metadata.

6. Run the focused tests added so far, then add tests 5-8.
   - If readiness/failure analysis still sees secondary infrastructure as primary, adjust event payload extraction in `src/awf/service/workspaces.py` narrowly so primary payload fields win over secondary metadata.

7. Check reason catalog impact.
   - If all changes reuse existing reason codes, do not update catalog files.
   - If a new public reason code becomes unavoidable, update catalog/tests in the smallest possible way.

8. Create the implementation validation artifact during the implementation phase, after code and tests are complete, following the repository's plan-and-validate workflow and the AWF phase instructions in effect then.

## Risks

- The latest failed-state event currently drives failure details. If a secondary cleanup path emits a new `failed` transition without primary top-level reason details, metrics/readiness can still report the wrong root cause even when `Workspace.failure_reason` is preserved.
- Some paths may only have primary reason evidence in `ValidationRun` rows, not in the workspace failed-state event payload. The helper must handle that without inventing a new schema.
- Active-row tests with pre-existing `failure_reason` may model race states that are rare in normal execution but important for callback/recovery robustness.
- Preserving primary reason codes on later failed transitions may require updating tests that currently expect `CLEANUP_FAILED` or `STALE_ACTIVE_EXECUTION` on the latest state-change event. The secondary event/payload should retain those infrastructure reason codes so operators do not lose diagnostics.
- Adding too much validation payload to events could make event JSON noisy. Cap lists and include only the most useful provenance fields.

## Assumptions

- A non-null `Workspace.failure_reason` with an actionable `failure_message`, or a failed validation run tied to that workspace, is sufficient durable primary evidence.
- Existing `ValidationRun` rows are the source of truth for validation reason code, coverage metadata, failing test IDs/evidence, and validation provenance identifiers.
- Secondary stale/cleanup/runtime-release faults should remain visible to operators and tests, but should not change retry/readiness classification away from the original cause.
- Provider/auth/timeout evidence is already represented by existing failure reason codes/messages/details; preserving those fields and reason details is enough to keep them distinct from validation and infrastructure failures.
- No database migration is needed.

## Non-Goals

- Do not reimplement post-agent pre-commit repair/retry from PR #239.
- Do not reimplement GitHub Actions failure evidence in monitor repair prompts from PR #241.
- Do not redesign scheduler/provider/terminal-runtime lifecycle logic.
- Do not add broad failure taxonomy changes or new public reason codes unless tests prove unavoidable.
- Do not change coverage policy, dependency files, generated OpenAPI output, or unrelated docs.
- Do not introduce retries that hide stale/cleanup/root-cause failures.
