## 2. Architecture decisions (locked — implement exactly)

- **D1 Transport = httpx.** `BitBucketClient.__init__` takes an injected `httpx.AsyncClient` (+ auth
  config). Tests use `httpx.MockTransport`. A `BitBucketClient.from_env(...)` classmethod builds the
  production `AsyncClient` + auth (base_url `https://api.bitbucket.org`). **No curl, no shelling out.**
  AWF's `cli/` layer already uses httpx (`src/awf/cli/common.py`) — follow that pattern.
- **D2 Shared `_request` helper** with: exponential backoff honoring `Retry-After` on **HTTP 429**;
  full **cursor pagination** following BB's `next` links; **ETag / `If-None-Match`** conditional
  requests (304 → return cached body) where the endpoint emits an ETag (best-effort, verified per
  endpoint). ETag cache is **bounded** (small LRU / capped dict) and **keyed per
  `(method, repo, pr, resource)`**. Read **`X-RateLimit-NearLimit`** and proactively slow before 429.
  BB rate limits are **per user/token**, not per repo.
- **D5 merge-method mapping:** AWF `merge` ↔ BB `merge_commit`; AWF `squash` ↔ BB `squash`;
  BB `fast_forward` is **first-class** (NOT aliased to `rebase`). `merge_pr` sends BB strategy
  **values** (`merge_commit`, not `merge`). See the **merge-gate seam risk (#352)** in §7.
- **D6 Auth = explicit credential MODE.** `BITBUCKET_AUTH_MODE` ∈ `{basic, bearer}` (default
  `basic`). Basic = `email:api_token` (Atlassian user API token) → `BITBUCKET_API_TOKEN` +
  `BITBUCKET_EMAIL`. Bearer = `Authorization: Bearer <access_token>` → `BITBUCKET_API_TOKEN`. **App
  passwords are NOT supported.** Missing/invalid config → reason-coded error
  (`BITBUCKET_AUTH_NOT_CONFIGURED`), never a crash. **NEVER log the token/credentials** — route all
  logging through `common/redaction.redact_secrets`; redact the `Authorization` header in any
  error/log output. The token is registered as an extra secret for redaction.

## 4. The 10 methods → BB Cloud REST v2.0 (verify each against live docs first)

Base: `/2.0/repositories/{ws}/{repo}` where `ws=repo.owner`, `repo=repo.name`.

1. **`create_pull_request`** → `POST .../pullrequests`
   body `{title, source:{branch:{name:<head>}}, destination:{branch:{name:<base>}}, description}` →
   return `links.html.href`.
2. **`fetch_pr_status`** (assemble `PRStatus`; `base_behind_count` is **passed in**, not recomputed):
   - `GET .../pullrequests/{id}` → `state` (OPEN/MERGED/DECLINED/SUPERSEDED), `merge_commit`,
     `destination`/`source` (branch + commit), `destination.branch.merge_strategies` +
     `default_merge_strategy`.
   - `GET .../commit/{sha}/statuses?refname=<source_branch>` → CI checks (state SUCCESSFUL/FAILED/
     INPROGRESS/STOPPED) → neutral `CheckState` + `CheckTiming`/`checks`.
   - `GET .../pullrequests/{id}/comments` (paginated) → threads with each comment's `resolved` state
     → unresolved `ReviewThread`s (filter resolved/own-authored like GitHub).
   - Map BB `state`/`merge_commit`/`closed`/`merged` and `mergeable` (derive from conflict status)
     into `PRStatus`.
3. **`fetch_failing_check_logs`** → pipeline-lookup chain (statuses do NOT carry pipeline/step UUIDs):
   `GET .../commit/{sha}/statuses?refname=<source_branch>` (find FAILED) →
   `GET .../pipelines/?target.commit.hash=<sha>` (find pipeline) →
   `GET .../pipelines/{uuid}/steps/` (find failing step) →
   `GET .../pipelines/{uuid}/steps/{step_uuid}/log` (HTTP **Range** header, tail `log_tail_chars`).
   Use **singular** `/steps/{uuid}/log` (NOT `/logs/{uuid}`). External (non-Pipelines) failing
   statuses have no BB logs → fall back to `pytest_fallback_commands` (same evidence path as GitHub
   via `extract_ci_failure_evidence`). Redact logs with `redact_ci_log`.
4. **`rerun_failed_workflow_jobs`** → `POST .../pipelines/` with a reconstructed
   `pipeline_pullrequest_target` (source, destination, destination commit, commit hash, PR id,
   selector). **No failed-only rerun API exists (UI-only)** → this reruns the WHOLE pipeline; emit
   reason code `BITBUCKET_PIPELINE_FULL_RERUN`. If the PR pipeline target cannot be safely
   reconstructed (custom/manual pipeline, required variables) → emit conservative
   `BITBUCKET_PIPELINE_NOT_RERUNNABLE` and do NOT trigger a wrong pipeline.
5. **`resolve_thread`** → `POST .../pullrequests/{id}/comments/{comment_id}/resolve`
   (**POST resolves; DELETE REOPENS — never DELETE**). `thread_id == comment_id`. (Signature is
   `resolve_thread(*, thread_id)` — no repo/pr in the Protocol; thread BB context must be encoded in
   `thread_id` or carried on the client. **Resolve during impl:** encode `repo/pr/comment` into the
   neutral `thread_id` string when `fetch_pr_status` builds threads, and parse it back here — same
   approach GitHub uses a node-id for. Document the encoding.)
6. **`post_comment`** → `POST .../pullrequests/{id}/comments` body `{content:{raw: <body>}}`.
7. **`create_issue`** → `POST .../issues`. If the issue tracker is **DISABLED (404)** → fall back to
   posting the content as a **PR comment**, return that comment URL, emit
   `BITBUCKET_ISSUE_TRACKER_DISABLED`. Never crash the NotifyHuman path; always return a usable URL.
   **Signature caveat:** Protocol `create_issue(*, repo, title, body)` has **no PR context**. The
   fallback needs a PR id. **Resolve during impl:** prefer threading PR context onto the
   `BitBucketClient` instance (set per-monitor) or document the limitation and, if no PR context is
   reachable, still emit the reason code and return the issue-tracker-disabled error URL without
   crashing. (Confirm what call sites pass — `create_issue` is used by the defer path in
   `pr_monitor_runner`; check whether a PR-scoped client is feasible.)
8. **`fetch_repo_merge_methods`** → from the **PR object's** `destination.branch.merge_strategies` +
   `default_merge_strategy` (the **repo** object does NOT expose merge settings). Map BB→AWF (D5).
   Signature is `(*, repo)` with no PR — **resolve during impl** the same PR-context way as #5/#7
   (carry last-known PR or fetch via a cached PR object). Map `merge_commit→merge`, `squash→squash`;
   `fast_forward` has no AWF name — see §7.
9. **`fetch_branch_pull_request_allowed_merge_methods`** → from the PR object's
   `destination.branch.merge_strategies` (NOT branch-restrictions, which are permissions/merge-
   checks). May be `None`/absent → return `None`.
10. **`merge_pr`** → `POST .../pullrequests/{id}/merge` `{merge_strategy, close_source_branch}` →
    return merge commit hash (`merge_commit.hash`). Translate AWF method → BB strategy **value**
    (`merge`→`merge_commit`, `squash`→`squash`). `delete_branch` → `close_source_branch`.

## 5. New reason codes (end-to-end, added to `service/doctor/reasons.py` + regenerated catalog)
- `BITBUCKET_AUTH_NOT_CONFIGURED` — auth mode/token/email missing or malformed.
- `BITBUCKET_PIPELINE_FULL_RERUN` — documents that rerun retriggers the whole pipeline (no
  failed-only API).
- `BITBUCKET_PIPELINE_NOT_RERUNNABLE` — PR pipeline target could not be safely reconstructed.
- `BITBUCKET_ISSUE_TRACKER_DISABLED` — issue tracker off; fell back to PR comment.

Reason codes flow exception → log field → event → policy. Catch **specific** exceptions
(`httpx.HTTPStatusError`, `httpx.RequestError`, `json.JSONDecodeError`, `BitBucketClientError`) —
never bare `Exception`.

## 7. Risks, assumptions, non-goals

### Risks
- **Merge-gate seam (#352) — likely a real bug to surface, NOT silently break.**
  `runtime/pr_monitor_runner/merge_loop.py` hardcodes GitHub's method vocabulary:
  `_MERGE_METHOD_PREFERENCE = ("squash", "merge", "rebase")` and `_KNOWN_MERGE_METHODS` filter the
  methods returned by `fetch_repo_merge_methods` / `fetch_branch_*`. BB `fast_forward` (and BB's
  `merge_commit` value if not mapped) would be **filtered out**, and a `fast_forward`-only repo would
  resolve to **no allowed methods** → merge can't proceed. Per the task: **flag it, don't silently
  break.** Plan: have BitBucketClient map `merge_commit→merge`, `squash→squash` (both round-trip
  through the GitHub-named gate), and surface `fast_forward` honestly; if the gate cannot express
  `fast_forward`, document the limitation + flag the #352 seam in the PR body, and have `merge_pr`
  refuse to merge with a wrong strategy (conservative reason code) rather than mis-merge. Investigate
  `merge_loop` during impl and record the verdict in the validation doc.
- **API drift** — every verb/field verified against live docs before coding (the gate above). BB
  pipeline rerun + step-log endpoints are the most quirk-prone.
- **`create_issue` / merge-methods / resolve_thread lack PR context** in the Protocol signatures.
  Resolve by carrying PR context on the client or encoding it in `thread_id`; if truly impossible,
  document + emit the reason code without crashing. Do NOT change the Protocol signatures (consumers
  depend on them).
- **1500-line guardrail** — split client vs parsing aggressively; if the client alone nears 1500,
  extract auth/`_request`/ETag into a third focused module rather than breach it.
- **Secret leakage** — auth headers/tokens must be redaction-wrapped everywhere; explicit test.

### Assumptions
- `RepoRef` (Part 1) already parses `bitbucket.org` and exposes `owner`/`name` correctly — reuse, no
  changes (confirmed by reading `github_client.py`).
- `base_behind_count` is computed by the caller (local git), passed in — same contract as GitHub.
- No API schema (`api/schemas.py`) changes → **OpenAPI drift gate not triggered** (confirm; run the
  `--check` only if a schema actually changes).
- Construction sites (`service/worker.py`, `control/executor/monitor_handoff.py`) keep calling
  `make_forge_client(forge, runner)`; the factory builds the BB client from env internally.

### Non-goals (defer / out of scope)
- BitBucket **Server / Data Center**; the forge-neutral **open-PR resolver**; **bare-slug** BB repos.
- Replacing `gh` for GitHub; git clone/push transport changes (git is provider-neutral).
- Refactoring consumers or the merge_loop beyond **flagging** the #352 seam (no silent rewrite).
