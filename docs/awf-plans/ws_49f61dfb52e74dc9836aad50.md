# Plan: Normalize List Pagination Envelopes

## Objective

Implement a narrow P1 API contract slice so AWF list APIs expose a consistent
pagination envelope while avoiding response churn in item payloads and preserving
legacy clients where the current contract cannot be changed in place safely.

The normalized envelope should be:

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false,
  "limit": 50,
  "cursor": null
}
```

`items`, `next_cursor`, and `has_more` remain the backward-compatible fields for
endpoints that already return envelopes. `limit` and `cursor` are additive
metadata fields. Endpoint-specific item fields must not be renamed or removed.

## Current API Context

List endpoints identified in the current code:

- `GET /v1/workspaces`: legacy bare JSON list from
  `src/awf/api/routes/workspaces.py`; changing the default top-level shape would
  break existing clients and tests.
- `GET /v1/workspaces/overview`: envelope exists but cursor is accepted and
  ignored.
- `GET /v1/events` and `GET /v1/workspaces/{workspace_id}/events`: envelope
  exists, no `limit` / `cursor` echo fields.
- `GET /v1/tasks` and `GET /v1/tasks/{task_ref}/attempts`: envelope exists, no
  `limit` / `cursor` echo fields.
- `GET /v1/merge-queue`: cursor-backed envelope already exists.
- `GET /v1/locks`: cursor-backed envelope already exists via
  `awf.service.locks`.
- `GET /v1/workspaces/{workspace_id}/stale-reasons`: items-only envelope.
- `GET /v1/workspaces/{workspace_id}/logs`: envelope exists, no limit query.
- `GET /v1/workspaces/{workspace_id}/artifacts`: local route schema with
  envelope fields, no limit query.
- `GET /v1/workspaces/{workspace_id}/validation`: envelope exists, no limit
  query.
- `GET /v1/operations` and
  `GET /v1/workspaces/{workspace_id}/operations`: envelope exists, no
  `limit` / `cursor` echo fields.

## Implementation Steps

1. Add the tests above and verify the focused contract tests fail because
   current envelopes omit `limit` / `cursor`, stale reasons omit pagination
   fields, and workspace list has only legacy bare-list behavior.

2. Add the shared schema/helper only after the failing tests describe the exact
   response shape. Keep it small: this slice should not introduce a general
   repository pagination framework.

3. Update existing response schema classes to include `limit` and `cursor` with
   safe defaults. Prefer additive schema changes so existing `items`,
   `next_cursor`, and `has_more` assertions continue to pass.

4. Update route returns to pass `limit` and `cursor` explicitly. For endpoints
   without cursor mechanics, return `cursor=None`, `next_cursor=None`, and
   `has_more=False` unless the route can already fetch `limit + 1` safely.

5. Preserve current real cursor behavior on `/v1/merge-queue` and `/v1/locks`;
   only add metadata echo fields there.

6. Handle `GET /v1/workspaces` as the compatibility exception:
   - Default legacy bare list remains unchanged in this slice, because JSON
     cannot be both an array and an envelope object.
   - If product requires an envelope immediately, add an explicit opt-in query
     such as `envelope=true` and test both shapes.
   - Do not silently flip the default response shape without an explicit
     migration decision.

7. Re-run focused tests after implementation, then the broader API test subset,
   then ruff and mypy.

## Risks

- `GET /v1/workspaces` is the only current list endpoint where the legacy shape
  is a bare array. Returning an object by default would break existing clients,
  CLI output expectations, and tests that index `response.json()` as a list.
- Adding actual cursor pagination to every endpoint could expand the slice into
  repository ordering and cursor validation work. Keep this task focused on the
  envelope contract unless an endpoint already has cursor mechanics.
- Moving the artifact list schema from the route to `schemas.py` could cause
  import churn; do it only if the shared pattern materially reduces duplication.
- Some clients may treat unknown top-level envelope fields strictly. Adding
  `limit` and `cursor` is intended to be additive, but API consumers with
  closed-world decoders may need a compatibility note.

## Assumptions

- The P1 requirement is to normalize the response envelope shape first, not to
  implement full cursor pagination semantics for every list endpoint.
- `limit` should echo the effective bounded query limit when a route has a
  `limit` parameter. Routes without a limit parameter may use a documented
  default metadata value unless a small local limit can be added safely.
- `cursor` should echo the request cursor only on routes that accept one; routes
  without cursor input should return `null`.
- Existing item projections are part of the compatibility contract and should
  not change as part of this work.

## Explicit Non-Goals

- Do not implement a new database-wide pagination abstraction.
- Do not change ordering semantics for existing list endpoints.
- Do not remove, rename, or restructure item fields.
- Do not change MCP tool contracts unless needed to preserve existing behavior.
- Do not update console UI code in this slice.
- Do not change mutating endpoint responses, log byte-range read responses, or
  non-list metrics/health/runtime endpoints.
