# Plan: P0 Workspace Rebase Operation API

## Objective

Add a token-protected, idempotent `POST /v1/workspaces/{workspace_id}/rebase`
operation endpoint that complements the existing `refresh` and `validate`
controls. The endpoint should accept `Idempotency-Key` and optional
`If-Match`, return the existing `OperationResponse` shape with `202 Accepted`,
record an `operations.type == "rebase"` row, and enqueue the existing AWF
rebase recovery path without doing git merge, push, or arbitrary branch mutation
inside the HTTP request.

## Intended Files And Modules To Touch

- `src/awf/api/routes/controls.py`
  - Add `POST /rebase` route using the existing auth dependency,
    `_require_idempotency_key`, `_parse_if_match`, `_http_error`, and
    `OperationResponse` response shape.
  - Extend `_http_error` mapping for new rebase-specific state/conflict errors.

- `src/awf/service/controls.py`
  - Add `WorkspaceControlService.request_rebase_workspace(...)`.
  - Add rebase reason constants and rebase-specific errors:
    missing PR URL, missing open merge candidate, ineligible workspace state,
    active destructive operation conflict, and active incompatible rebase conflict.
  - Reuse `_prepare_operation` for idempotency key locking, replay, payload
    comparison, and `If-Match` version checking.
  - Use `MergeCandidateRepository.get_open_for_workspace_with_merge_inputs` to
    require an open candidate and populate candidate context.
  - Create a pending `OperationType.rebase` row with an operator audit payload
    including `owner`, `source`, `reason`, `reason_code`, `requested_action`,
    `recovery_mode="rebase_only"`, PR/candidate/head/base context, and
    `expected_version` when present.
  - Emit a `workspace.rebase_requested` event and transition
    `monitoring_pr -> ready` so the worker can run the existing executor
    recovery path. Replays should not create another event or transition.

- `src/awf/control/executor.py`
  - Extend recovery discovery so an active pending/running `rebase` operation
    with `recovery_mode="rebase_only"` is treated as a recovery request in the
    same path currently used for PR-monitor rebase recovery.
  - Start and finish the existing operator-created `rebase` operation rather
    than creating a duplicate monitor-owned rebase row.
  - Preserve the current `validate` recovery behavior for PR-monitor and
    operator validate requests.

- `src/awf/db/repositories.py`
  - Add only small query helpers if needed, for example listing active
    destructive operations or active rebase operations for a workspace. Prefer
    existing `list_for_workspace`/`find_active_matching_payload` if sufficient.

- Tests:
  - `tests/unit/api/test_workspace_controls_idempotency.py`
  - `tests/unit/api/test_controls.py`
  - `tests/unit/service/test_controls_lifecycle.py`
  - `tests/unit/control/test_executor_monitor_recovery.py` only if executor
    behavior must be adjusted to reuse the operator-created rebase operation.

## Tests To Write First

1. API auth and request contract:
   - `POST /v1/workspaces/{id}/rebase` without bearer token returns `401`.
   - Missing or blank `Idempotency-Key` returns the existing `400 INVALID_REQUEST`.
   - Invalid `If-Match` parsing stays covered by existing helper tests.

2. API missing resources:
   - Missing workspace returns `404 NOT_FOUND`.
   - Workspace with no PR URL returns a structured bad request
     `WORKSPACE_PR_URL_REQUIRED`.
   - Workspace with PR URL but no open merge candidate returns a structured
     missing-candidate error and creates no operation.

3. API idempotency:
   - Same key and same payload replays the original rebase operation with no
     duplicate operation/event rows.
   - Same key with different reason or different `If-Match` returns
     `409 IDEMPOTENCY_CONFLICT`.
   - Fresh key with stale `If-Match` returns `409 VERSION_CONFLICT` before
     coalescing with any active rebase operation.

4. API conflict handling:
   - Active `cancel`, `stop`, or `destroy` operation on the same workspace
     rejects rebase with a clear `409` response and detail containing the
     conflicting operation id/type/status.
   - Active rebase with the same operator payload coalesces; active rebase with
     an incompatible payload rejects rather than creating a second concurrent
     rebase.

5. API successful operation record:
   - Happy path returns `202 OperationResponse`.
   - Operation row is `type="rebase"`, `status="pending"`, idempotency key is
     recorded, payload has operator audit fields and `recovery_mode="rebase_only"`,
     and event `workspace.rebase_requested` includes the reason, operation id,
     and expected version.

6. Service lifecycle tests:
   - `request_rebase_workspace` performs the same replay/conflict/version
     behavior as refresh/validate.
   - Missing PR/candidate/state/destructive conflict failures do not create
     operation rows.
   - Successful request transitions a monitoring PR workspace to `ready` for
     worker pickup while preserving PR/candidate context.

7. Failed rebase result:
   - If executor changes are required, add a focused regression in
     `tests/unit/control/test_executor_monitor_recovery.py` proving an
     operator-created `rebase` operation is started, reused, and finished
     `failed` with `error_code="MONITOR_RECOVERY_REBASE_FAILED"` and a structured
     result when the existing rebase recovery path fails.

Expected first step after planning: add these tests and run the narrow pytest
target to confirm the new tests fail for missing route/service behavior before
implementation.

## Implementation Sequence

1. Add failing API tests for `/rebase` alongside existing refresh/validate
   idempotency tests.
2. Add failing service tests for `request_rebase_workspace`.
3. Add failing executor reuse/failure test if the pending `rebase` row is not
   consumed by the existing recovery path.
4. Implement service errors and `request_rebase_workspace` with idempotency,
   version, PR/candidate, active-operation, payload, operation, event, and
   workspace transition behavior.
5. Add the FastAPI route and HTTP error mappings.
6. Adjust executor recovery detection/rebase operation reuse if needed so the
   accepted rebase request is actually executable by the existing worker path.
7. Run narrow validation, fix failures, then run the broader unit surface.

## Risks And Assumptions

- Existing executor recovery is currently keyed around pending/running
  `validate` operations with `recovery_mode`; adding a public `rebase` operation
  must not break existing PR-monitor validate-only or rebase-only recovery.
- The public endpoint should record `OperationType.rebase`, while the worker
  must still use the existing `_run_monitor_rebase_recovery` implementation for
  the actual git rebase and force-with-lease push.
- Open merge candidate data is required to make the request PR-candidate scoped;
  tests may need helper seeding for task, attempt, workspace, and candidate rows.
- Response shape should remain `OperationResponse`, not a new bespoke envelope.
- `If-Match` compares the workspace version at request acceptance time; replay
  by the same idempotency key returns the original operation even after later
  version changes, matching existing control behavior.

## Explicit Non-Goals

- Do not perform git rebase, merge, push, or PR mutation directly in the API
  handler or service request method.
- Do not add arbitrary branch selection or target SHA mutation beyond the
  current workspace/candidate base context.
- Do not silently merge a PR or bypass monitor/validation gates.
- Do not lower coverage, lint, mypy, or quality thresholds.
- Do not add migrations unless the implementation proves a schema change is
  unavoidable; `OperationType.rebase` already exists.
- Do not change branch management, push behavior, or AWF PR monitor ownership
  outside the focused rebase operation slice.
