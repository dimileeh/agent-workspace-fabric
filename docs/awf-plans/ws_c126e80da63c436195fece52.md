# Plan: Harden `verify_awf` PATH fallback for issues #331 and #340

## Scope

Resolve the duplicated installer defect reported in GitHub issues #331 and #340: the default-install fallback in `packaging/install.sh` must not accept an arbitrary `awf` already reachable on `PATH` when the current install did not place a binary in the predicted/resolved bin directory.

The fix will preserve the legitimate recovery path where the current install placed the new `awf` somewhere reachable on `PATH`, but the installer's bin-dir prediction missed it.

## Intended Files and Modules to Touch

- `packaging/install.sh`
  - Update `verify_awf()` only, focused on the default-install `command -v awf` fallback branch.
  - Keep the existing resolved-bin-dir identity check unchanged.
  - Keep the explicit `INSTALL_DIR` missing-binary behavior unchanged.
  - Keep the existing runnability check via `$resolved --help` and existing PATH-advice messaging semantics intact.

- `tests/unit/installer/` installer tests
  - Add or update focused subprocess/pexpect-style regression tests following the existing installer test harness patterns.
  - Expected likely test file will be whichever existing installer test module already covers `verify_awf()`, default install PATH advice, or reachable-success cases.

- Plan/validation artifacts required by repository workflow during implementation phase
  - `plans/ISSUE_331_340_PLAN.md`
  - `plans/ISSUE_331_340_VALIDATION.md`

## Implementation Approach

1. Inspect existing installer version plumbing in `packaging/install.sh`.
   - Find where the target install version/release/channel is resolved.
   - Identify what value is available at `verify_awf()` time and whether it represents the concrete version just installed.

2. Write failing regression tests first.
   - Test stale/unrelated `awf` on `PATH` with no binary in the resolved bin dir during a default install.
   - Test current/new `awf` reachable on `PATH` with a matching installed version when no binary exists at the predicted resolved bin dir.
   - Confirm the stale case currently fails by reporting success, or otherwise confirm the new assertion captures the intended bug.

3. Update the default-install fallback branch in `verify_awf()`.
   - When `${bindir}/awf` is missing and no explicit `INSTALL_DIR` was supplied, resolve `command -v awf` as today.
   - Before accepting that path, execute the reachable candidate's version command, likely `awf --version`, using the resolved path.
   - Compare its reported version to the concrete version this installer run resolved/installed.
   - Accept the fallback only when the version identity matches.
   - If the version mismatches, is empty, or cannot be checked reliably, treat the install as not reachable: emit the existing honest PATH guidance and `fail AWF_NOT_REACHABLE`.

4. Preserve existing behavior outside the bug branch.
   - Do not alter the already-correct `${bindir}/awf` identity check.
   - Do not add PATH fallback for explicit `--install-dir` installs.
   - Do not remove the default fallback entirely, because valid uv/pipx placement misses must still verify successfully.

5. Update or add small helper logic only if it matches existing shell style.
   - Prefer simple shell functions or inline checks already used in `install.sh`.
   - Avoid broad refactors or changing installer output unrelated to the defect.

## Tests to Write First

1. `default install rejects stale PATH awf when resolved bin dir is empty`
   - Arrange a fake/default install scenario where the predicted `${bindir}/awf` does not exist.
   - Put a stale/unrelated fake `awf` earlier or otherwise reachable on `PATH`.
   - Make that fake binary report a mismatching version with `--version`.
   - Assert installer verification fails with `AWF_NOT_REACHABLE`.
   - Assert it does not print/report successful verification.
   - Assert expected PATH advice remains honest and present according to existing messaging patterns.

2. `default install accepts reachable PATH awf when version matches installed build`
   - Arrange a missing predicted `${bindir}/awf`.
   - Put a fake newly installed `awf` reachable on `PATH` that reports the same version the installer resolved for this run.
   - Assert installer verification succeeds.
   - Assert no spurious PATH advice is printed.
   - Preserve the semantics covered by `test_no_path_advice_when_awf_already_on_path` and existing default-install reachable-success tests.

3. Existing regression surface to protect
   - Existing tests around default-install reachable success.
   - `test_no_path_advice_when_awf_already_on_path`.
   - Any existing explicit `--install-dir` missing binary / `AWF_NOT_REACHABLE` tests.

## Risks

- The installer may not currently retain a concrete installed version at `verify_awf()` time. If so, the implementation must identify the strongest existing identity signal without accepting blind PATH presence.
- `awf --version` output may include prefixes or formatting that require careful parsing. The comparison should align with existing release/version strings and avoid brittle assumptions where the test harness can expose expected formatting.
- Fake installer binaries in tests must model the real command behavior closely enough to catch stale-path masking without making the test depend on irrelevant output details.
- Changing PATH advice conditions could regress existing UX tests. Keep messaging changes minimal and reuse current advice paths.
- Shell portability matters; follow the existing `install.sh` style and avoid non-portable shell features if the script is intended for POSIX shell.

## Assumptions

- `packaging/install.sh` already resolves a target version/channel before installation and that value can be made available to `verify_awf()` without broad restructuring.
- The installed `awf` binary supports `--version`, or the script has an equivalent supported version command already used elsewhere.
- Installer unit tests under `tests/unit/installer/` include utilities for fake PATH entries, fake install locations, and asserting installer exit codes/output.
- Issues #331 and #340 are duplicate reports of this one default-install fallback defect, so one scoped code fix and two focused regression scenarios should close both.
