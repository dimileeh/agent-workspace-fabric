# T09 MCP Setup/Start/Init/Client Tools Plan

## Problem Statement

Implement T09 from `TODO/awf-full-installer-first-run-setup-backlog.md`: expose first-run setup/start/init/client capabilities through AWF's local MCP server without duplicating the existing CLI/service behavior and without moving credential material through MCP.

This is an MCP parity slice. REST remains unchanged, and broad AWF/GitHub validation remains owned by AWF after the agent completes.

## Scope And Requirements Checklist

- Add MCP tools:
  - `awf_get_setup_status`
  - `awf_start_local_service`
  - `awf_initialize_project_profile`
  - `awf_get_client_integration_instructions`
- Reuse existing setup/start/init/client implementation seams instead of reimplementing behavior:
  - setup readiness/status via `awf.cli.setup_commands` and `awf.host_setup.system_checks`/config helpers;
  - local service start via `awf.service.bootstrap.run_service_bootstrap` and `awf.cli.start_commands` payload/source-checkout helpers;
  - project profile initialization via `awf.profiles.onboarding.preview_project_onboarding` and `write_workspace_profile`, matching CLI writer behavior;
  - client integration instructions via `awf.host_setup.clients` descriptors/plans and the existing client env-file resolver.
- Keep raw credential capture out of MCP inputs and responses.
- `awf_get_setup_status` returns only status and safe references/metadata, never raw credential values or env file contents.
- `awf_start_local_service` is repeatable/idempotent and maps bootstrap/source-checkout failures to structured first-run failure payloads.
- `awf_initialize_project_profile` uses the same onboarding writer as CLI when writing `.awf/workspace.yml`.
- `awf_get_client_integration_instructions` contains no secret values and does not read env-file contents.
- Update MCP parity docs/tests where this repository tracks MCP parity.

## Intended Files And Modules To Touch

- `src/awf/mcp/setup_tools.py` (new): register and implement the four setup/start/init/client MCP tools plus small pure payload helpers for testability.
- `src/awf/mcp/server.py`: import/register `register_setup_tools(...)` inside `build_mcp_server` and route results through the existing `_safe_result` redaction path.
- `tests/unit/mcp/test_setup_tools.py` (new): focused tests for tool registration, behavior, idempotence, writer reuse, structured failures, and secret redaction.
- `docs/MCP_REFERENCE.md`: add the new tool names and concise usage/contract notes.
- `docs/MCP_CLIENT_PARITY.md`: mark the first-run setup/start/init/client MCP surface as implemented and document security boundaries.
- `tests/unit/mcp/test_mcp_client_parity_docs.py` and/or `tests/unit/mcp/test_mcp_parity_matrix_crossref.py`: update parity expectations if the existing docs guards need explicit coverage for the new rows/tools.

Prefer not to touch CLI modules. If direct reuse proves impossible because a needed CLI helper only renders/exits, extract the smallest pure helper in the existing CLI module and keep the CLI call path unchanged; this is a fallback, not the default plan.

## Tests To Write First

1. `tests/unit/mcp/test_setup_tools.py::test_setup_tools_are_registered`
   - Build an MCP server in-process and assert the four new tool names are present.
   - Assert the exposed input schemas do not contain token/password/secret credential-value parameters.

2. `test_get_setup_status_returns_only_status_and_safe_refs`
   - Use temp host setup config/provider config with safe `env://` or `keyring://` refs and monkeypatched readiness/setup seams.
   - Assert the response includes setup/provider status and safe ref metadata only.
   - Assert raw token-shaped values placed in environment/settings do not appear anywhere in `structuredContent` or text content.

3. `test_start_local_service_reuses_bootstrap_and_is_idempotent`
   - Inject/monkeypatch a fake bootstrap runner returning `ServiceBootstrapResult` twice.
   - Assert repeated calls return successful structured payloads and do not require an idempotency key because Docker Compose startup is inherently repeatable.
   - Assert start options (`rebuild`, `skip_agent_runtime_build`, `timeout_seconds`, `source_checkout`) are passed into the existing start/bootstrap seams.

4. `test_start_local_service_reports_structured_failure`
   - Inject/monkeypatch `ServiceBootstrapError` cases for timeout, migration failure, port conflict, and/or missing assets.
   - Assert MCP returns `CallToolResult.isError` with the existing first-run reason code and redacted bootstrap diagnostics.

5. `test_initialize_project_profile_uses_onboarding_writer`
   - Monkeypatch `preview_project_onboarding` and `write_workspace_profile`.
   - Assert preview-only mode never writes.
   - Assert write mode calls `write_workspace_profile(preview, force=...)` and returns `written_path` in the structured payload.
   - Assert file-exists and invalid-path errors become structured MCP errors instead of tracebacks.

6. `test_client_integration_instructions_are_secret_free`
   - Use `build_client_config_plan`/client descriptors with temp Claude/Codex homes.
   - Assert instructions include client, config path, desired command/args, and manual/apply guidance but no env-file contents or raw token-shaped values.
   - Assert unknown client selectors return the existing `SETUP_CLIENT_UNKNOWN` reason code.

7. Docs/parity tests
   - Add/update assertions that `MCP_REFERENCE.md` lists all four tools.
   - Add/update the parity matrix row(s) so real MCP tool discovery, CLI command cross-reference, and status vocabulary tests pass.

## Implementation Steps

1. Add failing focused MCP tests first, keeping all external process, Docker, filesystem, and provider behavior mocked or temp-scoped.
2. Create `src/awf/mcp/setup_tools.py` with:
   - a `SafeResult` protocol matching existing MCP modules;
   - payload helpers that call existing setup/start/init/client seams and return dict payloads;
   - a `register_setup_tools(mcp, safe_result, settings_value, ...)` function registering the four tools with bounded schemas and no credential-value inputs.
3. Implement `awf_get_setup_status`:
   - normalize optional provider/client selectors with existing helpers;
   - read host setup config through existing config APIs;
   - run/read setup status through existing dry-run/status helpers where needed;
   - return only status, selected providers, source-checkout metadata, provider backend/status/safe refs, reason codes, and next-step refs;
   - pass final output through `_safe_result`.
4. Implement `awf_start_local_service`:
   - validate mutually exclusive `rebuild` and `skip_agent_runtime_build` like CLI;
   - reuse start source-checkout and bootstrap-input resolution;
   - call `run_service_bootstrap` with `ServiceBootstrapOptions`;
   - return `_start_success_payload(...)` or `_start_failure_payload(...)` rendered to redacted JSON;
   - mark failure results as MCP errors while preserving structured payload details.
5. Implement `awf_initialize_project_profile`:
   - support non-interactive preview and explicit write modes only;
   - validate path existence/directory exactly as CLI does;
   - build preview via `preview_project_onboarding(...)`;
   - write through `write_workspace_profile(preview, force=force)` when requested;
   - reuse `_init_project_onboarding_payload(...)` for response shape where practical.
6. Implement `awf_get_client_integration_instructions`:
   - normalize clients with `normalize_clients`;
   - resolve the same MCP env-file path used by `awf setup --client` in dry-run/instruction mode;
   - build client plans with `build_client_config_plan` and descriptors;
   - return sanitized manual instructions/config snippets from plan data, not env-file contents.
7. Wire `register_setup_tools(...)` into `build_mcp_server` after existing workspace/metrics/control registrations.
8. Update `docs/MCP_REFERENCE.md` and `docs/MCP_CLIENT_PARITY.md` with the new tools, schemas/error-code notes, and explicit no-secret/no-shell boundaries.
9. Run the focused validation commands below and record evidence in the later validation artifact during implementation.

## Risks And Mitigations

- Private CLI helper coupling: setup/start/init CLI modules currently contain useful pure helpers alongside rendering/exit behavior. Prefer existing pure helpers; if extraction is required, keep it minimal and preserve CLI behavior with regression tests.
- Secret leakage through diagnostics: bootstrap stderr/stdout, env-file paths, client diffs, and provider config can contain sensitive-looking text. Mitigate with `render_first_run_json`, existing MCP `_safe_result`, and explicit secret-redaction tests for every new tool.
- Start side effects: `awf_start_local_service` intentionally starts local Core. Unit tests must inject fake bootstrap runners and avoid Docker; production behavior delegates to the existing idempotent bootstrap engine.
- Project init writes files: MCP write mode must be explicit and non-interactive. Tests use temp repos and monkeypatch the writer so no real project profile is touched.
- Parity matrix constraints: implemented rows are cross-checked against real MCP tool names and CLI commands. Update docs and tests together so the matrix remains mechanically verified.

## Assumptions

- T04/T05/T08 are merged, so setup readiness, start bootstrap wrapper, and client config plan helpers exist and are reusable.
- Safe credential refs such as `env://...`, `keyring://...`, and `plain-file://...` are metadata, not raw secret values; raw credential values remain out of MCP inputs/responses.
- MCP can expose bounded local-service controls and project-profile writes because these are explicit AWF controls, not arbitrary shell or Docker exec.
- This planning artifact is the configured AWF plan location for this workspace, even though the general protocol names `plans/<TOPIC>_PLAN.md`.

## Explicit Non-Goals

- No MCP credential entry, prompting, token capture, or provider secret storage.
- No new REST endpoints or OpenAPI schema changes.
- No changes to existing CLI command grammar or user-facing CLI behavior except a tiny helper extraction if strictly necessary.
- No remote/hosted MCP service.
- No arbitrary shell, Docker exec, filesystem browsing, or env-file content reading through MCP.
- No broad docs rewrite beyond MCP reference/parity updates.
