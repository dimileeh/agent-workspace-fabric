# Plan: Fix #456 — guide control eligible for `failed` workspaces with a PR

## Problem

`guide_workspace` (issue #447) scopes `_GUIDE_ELIGIBLE_STATUSES` to `monitoring_pr` only
(`controls_errors.py:16`). A `failed` workspace that still has a PR raises
`WORKSPACE_STATE_NOT_GUIDABLE`, even though `remonitor_workspace` already supports re-engaging
a failed monitor via `_reset_failed_workspace_for_remonitor`. Operators cannot use the cleaner
directive/audit split provided by `guide` and must fall back to overloading `remonitor --reason`.

## Fix overview

1. **`controls_errors.py`** — add `WorkspaceStatus.failed` to `_GUIDE_ELIGIBLE_STATUSES`; update
   the comment.
2. **`controls_guide.py`** — after creating the operation and persisting the hint, call
   `_reset_failed_workspace_for_remonitor(self._session, workspace)` unconditionally (it no-ops
   for `monitoring_pr` and returns `None`); conditionally skip `advance_workspace_version` when
   state_reset is not None (since `_reset_failed_workspace_for_remonitor` advances internally);
   include `state_reset` in the event payload and result dict; use `add_event_with_states` instead
   of `add_event` when a state transition occurred.

## Risks and assumptions

- `_reset_failed_workspace_for_remonitor` calls `advance_workspace_version` internally; the
  existing test `test_remonitor_failed_workspace_reserves_state_reset_event_order` (part_004)
  verifies `workspace.version == 2` after one remonitor — the same invariant must hold for
  guide on a failed workspace. Our plan skips the outer `advance_workspace_version` exactly
  when state_reset is not None to preserve this.
- The order of operations (hint persisted, claims reset, state reset, event) ensures the hint
  is in `monitor_threads_addressed` before the version-advancing event is persisted — the
  monitor will see a consistent view on claim.
- The `failed` workspace PR URL check (`WorkspaceGuideMissingPrUrlError`) still fires before
  `operations.create(...)`, so no orphan operations are created on that error path (same guard
  order as the existing `monitoring_pr` path).
- Past-settle warning logic is NOT added to guide-on-failed; that's remonitor's concern. The
  task spec does not ask for it.
- The tuple order in `_GUIDE_ELIGIBLE_STATUSES` is `(monitoring_pr, failed)`, which matches the
  order in the error detail's `eligible_statuses` list. The updated assertion in the existing
  test must reflect this order.
- `cast(str, state_reset["from"])` mirrors the existing pattern in `remonitor_workspace` at
  `controls.py:569-570` for type correctness; no runtime cost.

## Non-goals

- No changes to `remonitor_workspace` or any other control.
- No past-settle warning on guide-failed path.
- No changes to the MCP/REST schemas; `guide` already accepts all workspace statuses at the
  schema level (state validation is service-side).
- No migration needed (no DB schema change).
