## Problem Confirmation (verified, not re-derived)

1. A companion healthcheck that fails to go green within `compose_up_timeout_seconds` makes
   `docker compose up -d --wait` exit non-zero. `ComposeManager.up()` raises
   `ComposeOperationError(reason_code="COMPOSE_COMMAND_FAILED")`
   (`src/awf/node/compose_manager.py:330` and `:543`).
2. `ComposeStackLauncher.launch` re-raises that error unchanged for the non-`DOCKER_UNAVAILABLE`
   case (`src/awf/node/stack_launcher.py:182-196`).
3. `Provisioner._provision_claimed_workspace` catches it in the `except ComposeOperationError`
   block (`src/awf/node/provisioner.py:266-297`) and calls `_mark_failed(..., failure_reason=
   FailureReason.service_startup_failure, ...)`.
4. `_mark_failed` (`:451-507`) calls `repo.transition(ws, to=failed, reason_code=
   failure_reason.value.upper())` **without a `payload`**. `WorkspaceRepository.transition`
   (`:787-840`) therefore writes a `workspace.state_changed` event with
   `reason_code="SERVICE_STARTUP_FAILURE"` and `payload=None`. That null payload is the bug.
5. Teardown (`docker compose down --remove-orphans -v`) is **not** synchronous in this handler.
   The except block only logs, records the egress audit, marks failed, and re-raises; the
   compose `down` happens later via GC / `WorkspaceCleaner`. So the failed companion container
   and its logs still exist at the moment we catch `ComposeOperationError` — that is the capture
   window.

Note on "failure_details": the data model has **no** `failure_details` column
(`src/awf/db/models.py` only has `failure_reason: String(64)` and `failure_message: String(2048)`).
The canonical, operator-visible persisted location for the diagnostics is the
`WorkspaceEvent.payload` (what `awf workspace events <id>` surfaces). `failure_message` stays the
short human summary; the rich diagnostics go into the event payload.

## Design Decision

**Capture diagnostics from the provisioner's `except ComposeOperationError` handler, before
`_mark_failed`, via an injected best-effort capturer; gather the raw data inside `ComposeManager`
(reusing its existing `_docker_capture`).**

Why an injected capturer rather than extending the `WorkspaceStackLauncher` Protocol: the
provisioner only holds the `WorkspaceStackLauncher` Protocol, and adding a method to that Protocol
would force a mypy/structural update to every fake launcher in the provisioner test suite (most
fakes implement only `launch`). Instead we add an **optional** `service_diagnostics` dependency
to `Provisioner` that defaults to `None`:

- Production wiring passes the already-constructed `ComposeManager` (`worker.py:78`) as the
  capturer — `ComposeManager` structurally satisfies the small capturer Protocol.
- All existing provisioner tests pass no capturer → `None` → current behavior preserved
  (event payload stays `None`), so no existing test needs editing.
- The capture call originates in the provisioner handler (faithful to the issue's stated seam),
  strictly before `_mark_failed` and before any later `down`.

This also satisfies "reuse existing docker-exec helpers, don't introduce a new abstraction":
the gathering reuses `ComposeManager._docker_resource_ids` / `_docker_capture`.

    - Enumerate project containers:
      `_docker_resource_ids(["ps", "-aq", "--filter", f"label=com.docker.compose.project={project_name}"], operation="ps")`.
    - `docker inspect` all ids in one call: `_docker_capture(["inspect", *ids], operation="inspect")`,
      parse JSON.

      exited non-zero (no healthcheck but `.State.Status == "exited"` and `ExitCode != 0`):

        **list of lines** (so per-line redaction/length-capping applies cleanly).
      - Per-container `docker logs` wrapped in `try/except ComposeOperationError` → on failure set
        `companion_logs_capture_error[service]` and continue (container may be gone — race-safe).
    - Top-level `ComposeOperationError` / `json.JSONDecodeError` from the `ps`/`inspect` steps →
      set top-level `companion_logs_capture_error` and return a partial payload.
    - Always include `schema`, `compose_project`, `compose_file`
      (`self._projects_dir / workspace_id / "compose.yml"`), `tail_lines`, `containers_inspected`.
    - **Redaction:** build the raw dict, then `return redact_audit_value(payload)` so every persisted
      string passes through the audit redactor. Any `_log.*` line that includes captured content uses
      `redact_secrets(...)`.

## Risks, Assumptions, Non-Goals

### Risks & mitigations
- **Secret leakage (highest risk).** All persisted strings pass through `redact_audit_value`; all
  captured-content log lines through `redact_secrets`. Storing logs as a list of lines keeps per-line
  redaction and the 1000-char cap effective. Dedicated redaction regression tests for URL creds,
  `KEY=value` assignments, `Bearer`/`Authorization`, and provider-token prefixes.
- **Bare unstructured secrets.** The existing pattern-based redactor catches the forms the issue
  names (DB URLs, connection strings, tokens, assignments) but cannot catch a high-entropy secret
  printed with no recognizable structure. This matches AWF's current contract for `failure_message`
  / compose stderr; documented as a known limitation rather than newly introduced.
- **Capture masking the real failure.** Capture is best-effort at two layers (capturer never raises;
  provisioner helper also guards) and the original `ComposeOperationError` is always re-raised with its
  `reason_code`. Explicitly tested.
- **Docker race / container already gone.** Per-container `docker logs` failures are caught
  (`ComposeOperationError`, a specific exception — never bare `Exception`) and recorded as markers.
- **Payload size.** Bounded by `tail_lines` (default 200, configurable), per-line 1000-char cap, and
  capturing only unhealthy containers (healthy `postgres` excluded).
- **Coverage gate (99%).** New best-effort/error branches are explicitly exercised by tests c/d/e.

### Assumptions
- `docker compose up -d --wait` leaves the failed companion container present (not auto-removed) on
  healthcheck timeout, so `logs`/`inspect` succeed in the except block.
- Teardown for a failed provision runs later via GC / `WorkspaceCleaner`, not synchronously in the
  provisioner except block (verified — no `down` call there).
- `awf workspace events <id>` surfaces `WorkspaceEvent.payload`; the `SERVICE_STARTUP_FAILURE` event
  is the `workspace.state_changed` row with `reason_code="SERVICE_STARTUP_FAILURE"`.
- The rendered compose file is at `<work_dir>/compose/<workspace_id>/compose.yml`.
- `ComposeManager` structurally satisfies the new capturer Protocol, so production can pass the
  existing `compose` instance directly.

### Non-goals
- No change to the deterministic teardown/cleanup contract — capture is purely additive and the
  compose `down` still runs.
- No new `FailureReason`/reason codes; reuse `COMPOSE_COMMAND_FAILED` and `SERVICE_STARTUP_FAILURE`.
- No diagnostics capture on the `DOCKER_UNAVAILABLE` path (docker is down; nothing to read, and the
  launcher converts it to `WorkspaceServiceExecutionError` anyway).
- No hard-coded project-specific service names — generic over compose-project containers; nothing
  profile-specific lands in `src/awf` core.
- No new docker-exec abstraction — reuse `ComposeManager._docker_capture` / `_docker_resource_ids`.
- No new DB column (`failure_details`); persist into the existing `WorkspaceEvent.payload`.
- No API/OpenAPI, CLI, or migration changes.
