# Base URL Unification Implementation Plan

## Goal

Introduce `AWF_BASE_URL` as the single operator-facing host CLI knob for the AWF API while preserving the distinct `AWF_API_BASE_URL` service self-reference URL used inside the API/container context. The first-run friction to fix is: when a local operator sets `AWF_API_HOST_PORT=8800` and no host CLI URL, `awf` should target `http://localhost:8800` automatically instead of the old static `http://localhost:8000` default.

## Current Findings

- `src/awf/cli/common.py` currently resolves host CLI URLs as `--base-url` or `AWF_CLI_BASE_URL` or `_DEFAULT_BASE_URL`, with `_DEFAULT_BASE_URL = "http://localhost:8000"`.
- `src/awf/cli/__init__.py` still documents `AWF_CLI_BASE_URL` as the CLI env override.
- `src/awf/service/config.py` owns `Settings.api_base_url` / `AWF_API_BASE_URL` resolution. This must remain the server/service self-reference behavior and must not start reading `AWF_BASE_URL`.
- Existing service config tests already cover a lot of `AWF_API_BASE_URL` and `AWF_API_HOST_PORT` behavior. The new regression should explicitly prove `AWF_BASE_URL` is ignored by service settings and that an in-cluster `AWF_API_BASE_URL` such as `http://api:8000` still wins in service resolution.
- `.env.example` exists at repo root. No `docker/compose/.env.example` exists in this checkout, so there is no compose-specific env example to update unless it appears before implementation.
- Several docs currently tell operators to use `AWF_API_BASE_URL` or `AWF_CLI_BASE_URL` for host CLI/API diagnostics; these need to move to `AWF_BASE_URL` and reserve `AWF_API_BASE_URL` wording for service self-reference.

## Risks And Mitigations

- `AWF_API_BASE_URL` has historically been described as host-side in some code comments/docs. Mitigate by changing wording only, not service behavior, and covering the unchanged service behavior with tests.
- The deprecated `AWF_CLI_BASE_URL` warning could spam every CLI call if implemented in the low-level resolver. Mitigate with a module-level process-local flag and a direct one-time regression.
- Tests that invoke the Typer runner may capture stderr differently than direct `_base_url` tests. Mitigate with direct resolver tests for warning semantics and one end-to-end request test for host URL selection.
- Base URLs can contain credentials in reverse-proxy setups. Do not add new logging of raw base URLs; rely on existing request-context sanitization and keep the deprecation message generic.
- Existing docs include manual `curl` examples. Mitigate by using `AWF_BASE_URL` only for host/operator examples and explicitly avoiding `AWF_API_BASE_URL` in those contexts.
- There is no `docker/compose/.env.example` now. Avoid creating one unless implementation discovers it is required by a local pattern; otherwise document that it was absent.

## Assumptions

- `AWF_BASE_URL` is host/operator-facing only; server-side settings do not read it.
- `AWF_CLI_BASE_URL` remains fully functional for compatibility but is deprecated when `AWF_BASE_URL` is absent.
- The final fallback remains `http://localhost:8000` via `AWF_API_HOST_PORT` shell-default semantics.
- MCP remains in-process and requires no base URL change unless code inspection later reveals a host-facing HTTP client path.
- URL path normalization continues to be handled by existing `normalize_api_url` call sites; this change only selects the base URL string.
- The eventual PR description should use a clear title such as “Unify host CLI base URL configuration” and reference the first-run friction from `docs/market-analysis/AWF_MARKET_OPINION_2026-05-31.md` rather than a GitHub issue number.

## Explicit Non-Goals

- Do not collapse `AWF_API_BASE_URL` into `AWF_BASE_URL`.
- Do not make the API/server read `AWF_BASE_URL`.
- Do not add an MCP base URL or route in-process MCP through HTTP.
- Do not change Docker Compose `AWF_API_BASE_URL: http://api:8000` service environment behavior.
- Do not change OpenAPI schemas or regenerate `openapi.json` unless implementation unexpectedly changes API schema surface.
- Do not run full-repository coverage, frontend builds, pushes, rebases, branch switches, or commits in this AWF agent phase.
