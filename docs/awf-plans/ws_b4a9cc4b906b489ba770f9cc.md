# Plan: Profile Runtime Health-Check Wait Semantics

## Goal

Implement the narrow P1 profile-runtime slice where validation waits for
profile-declared service health checks before any post-agent or validation
command starts. The behavior must be profile-driven, backward-compatible for
profiles without health checks, observable through validation logs/events, and
safe from browser-triggered arbitrary execution.

## Current Anchors

- `src/awf/profiles/models.py` defines `ProfileHealthCheck` as a required
  `name`, `command`, and `timeout_seconds`.
- `src/awf/runtime/validation.py` currently prepends health checks to the
  command list when `run_healthchecks=True`, but it treats each check as a
  one-shot command.
- `src/awf/control/executor.py` calls `run_profile_phases(...,
  run_healthchecks=True)` before finishing validation, persists validation-run
  command records, maps `phase == "healthcheck"` to
  `FailureReason.health_check_failure`, and builds validation failure messages.
- Durable command logs already flow through `LogStore` with stream IDs like
  `validation.01_healthcheck.stdout`.
- Workspace events are appended through `WorkspaceRepository.add_event()`;
  failures currently transition with coarse `FailureReason` values.

## Tests To Write First

1. Runtime wait loop in `tests/unit/runtime/test_validation.py`:
   - Profile has `validation.healthchecks` and `phases.validate`.
   - Fake runner returns two failed health-check attempts, then success, then a
     successful validation command.
   - Assert validation command is not invoked until the health check succeeds.
   - Assert the result records one health-check command result with
     `phase == "healthcheck"`, `reason_code == "HEALTHCHECK_OK"`, attempt
     count metadata, and then the validation command.

2. Runtime timeout in `tests/unit/runtime/test_validation.py`:
   - Health check has a very small total wait budget and keeps failing.
   - Assert no post-agent or validate command is invoked.
   - Assert `result.all_passed` is false, `first_failure.phase` is
     `healthcheck`, and the reason code is `HEALTHCHECK_TIMEOUT` rather than a
     generic `COMMAND_FAILED`.
   - Assert stdout/stderr artifacts contain the latest actionable output and a
     timeout diagnostic.

3. Runtime command failure without waiting forever:
   - Health check command returns a deterministic non-zero result until the
     deadline.
   - Assert the final result preserves the command output, service/check name,
     attempt count, and reason code.

4. Runtime HTTP-style health check:
   - Add a profile health check such as `{name: "api", url:
     "http://app:8080/healthz", expected_status: 200}`.
   - Assert the runner invokes a fixed AWF-generated Python/urllib command
     inside the agent container through the existing compose exec path.
   - Assert no browser-facing API or arbitrary browser-triggered exec path is
     introduced.

5. No-health-check compatibility:
   - Existing profile with only `phases.validate` and
     `run_healthchecks=True` should make exactly the old validation command
     calls and artifact names.
   - Existing legacy `ValidationRunner.run(...)` should remain unchanged.

6. Profile schema compatibility in `tests/unit/profiles/test_profiles.py`:
   - Existing `{name, command, timeout_seconds}` health checks parse with the
     same defaults and values.
   - HTTP-style checks parse with `url` and default wait/interval fields.
   - Invalid checks fail when neither `command` nor `url` is supplied, when a
     URL is not `http` or `https`, or when unsafe status/interval values are
     supplied.

7. Executor observability in control tests:
   - A validation health-check timeout finishes the validation run with
     `reason_code == "HEALTHCHECK_TIMEOUT"`.
   - Workspace ends in `failed` with
     `failure_reason == "health_check_failure"`.
   - Failure message includes the health-check name, target command or URL,
     timeout, and log stream/artifact hint.
   - Workspace events include a `workspace.health_check_failed` event with
     structured payload fields: `healthcheck_name`, `healthcheck_kind`,
     `reason_code`, `attempts`, `timeout_seconds`, and stream IDs.

8. Validation provenance helpers:
   - `_validation_run_command_records()` includes health-check names/kinds or a
     stable display command for HTTP checks.
   - `environment_identity_digest()` changes when health-check URL, command,
     expected status, interval, or timeout changes.

## Implementation Sequence

1. Add the failing tests above, starting with `tests/unit/runtime/test_validation.py`
   because the wait semantics belong in the runtime runner.
2. Extend `ProfileHealthCheck` conservatively:
   - Keep existing `name`, `command`, and `timeout_seconds` accepted.
   - Add optional `kind`/`type` defaulting to command when `command` is present
     and HTTP when `url` is present.
   - Add `url`, `method` defaulting to `GET`, `expected_status` defaulting to
     `200`, `interval_seconds` defaulting to a small positive value, and
     optional `attempt_timeout_seconds`.
   - Validate that exactly one executable mode is configured: command or HTTP.
   - Treat `timeout_seconds` as the total wait deadline for the check; use
     `attempt_timeout_seconds` for a single command/HTTP attempt when provided.
3. Add small helper functions in `src/awf/runtime/validation.py`:
   - Build a display label for each health check using its name.
   - Convert command checks to the existing `sh -lc` compose exec path.
   - Convert HTTP checks to a fixed AWF-owned Python stdlib command using
     `urllib.request`, with shell quoting handled centrally and no caller
     shell fragments beyond the declared URL/status/method fields.
   - Run attempts until success or deadline, sleeping `interval_seconds`
     between attempts.
4. Replace `ordered = [*healthchecks, *commands]` execution for health checks
   with a pre-validation wait stage:
   - Run every declared health check to success before any post-agent,
     validate, or coverage command.
   - Stop on the first timed-out or failed health check.
   - Return a `ValidationResult(commands=[health_result])` so existing
     `first_failure`, validation-run finish, and failure-reason paths still
     work.
5. Preserve artifact/log behavior:
   - Continue using labels like `01_healthcheck`.
   - For repeated attempts, append output to the same stdout/stderr artifacts
     with attempt delimiters that identify attempt number and elapsed time.
   - Ensure `LogStore` streams receive the same output written to artifacts.
6. Add result metadata without disrupting old callers:
   - Extend `ValidationCommandResult` with `metadata: dict[str, object]`.
   - Populate health-check metadata for name, kind, target, attempts,
     timeout, interval, and final failure details.
   - Keep existing fields and `ok` semantics unchanged for normal validation
     commands.
7. Update executor helpers:
   - Make `_validation_run_reason_code()` return health-specific reason codes.
   - Make `_validation_failure_message()` produce actionable health-check text
     instead of `validation failed: <command>`.
   - Pass the validation reason code into `_mark_failed()` for terminal
     validation failures.
   - Add a focused helper to record `workspace.health_check_failed` events
     when the first failure phase is `healthcheck`.
8. Update provenance/display helpers:
   - Update `_validation_run_command_records()` and API command lookup for HTTP
     checks.
   - Update `validation_identity` health-check identity serialization for the
     new fields and secret-safe target display.
9. Run focused tests, then the repo quality gates listed below.

## Reason Codes And Event Shape

Use stable, actionable reason codes:

- `HEALTHCHECK_OK` for successful wait completion.
- `HEALTHCHECK_TIMEOUT` when the total health-check deadline expires.
- `HEALTHCHECK_COMMAND_FAILED` when a command-style check exits non-zero at
  the deadline.
- `HEALTHCHECK_HTTP_STATUS_MISMATCH` when an HTTP-style check reaches the URL
  but does not return an expected status before the deadline.
- `HEALTHCHECK_INVALID_CONFIGURATION` only for defensive runtime failures that
  should normally be caught by profile validation.

Proposed event:

```json
{
  "event_type": "workspace.health_check_failed",
  "reason_code": "HEALTHCHECK_TIMEOUT",
  "payload": {
    "healthcheck_name": "api",
    "healthcheck_kind": "http",
    "target": "http://app:8080/healthz",
    "attempts": 6,
    "timeout_seconds": 30,
    "stream_ids": {
      "stdout": "validation.01_healthcheck.stdout",
      "stderr": "validation.01_healthcheck.stderr"
    }
  }
}
```

## Risks And Assumptions

- Assumption: Health checks should run only when validation explicitly passes
  `run_healthchecks=True`; setup/pre-agent phase runs should not suddenly wait
  on validation health checks.
- Assumption: Existing `timeout_seconds` on a health check can become the total
  wait deadline. If single-attempt timeout control is needed, use the new
  optional `attempt_timeout_seconds`.
- Assumption: The agent runtime has Python available, so HTTP-style checks can
  use Python stdlib instead of adding `curl`, `wget`, `requests`, or browser
  dependencies.
- Risk: Repeated health-check attempts can create noisy logs. Mitigate by
  appending concise attempt headers and preserving only command stdout/stderr
  plus final diagnostic text.
- Risk: Existing tests may assume exactly one fake-runner call for a failing
  health check. Update only health-check-specific expectations; profiles
  without health checks must keep the old call count.
- Risk: Sleeping in unit tests can slow the suite. Use tiny intervals/deadlines
  and monkeypatch or inject a sleeper/clock if needed so wait-loop tests remain
  deterministic.
- Risk: HTTP-style checks may include URLs with credentials. Validate schemes,
  redact target display through existing redaction helpers where logs/events
  include URLs, and avoid exposing raw secret-like header values in identity or
  events.

## Explicit Non-Goals

- Do not add a browser or console endpoint that executes arbitrary health-check
  commands.
- Do not implement Playwright/browser readiness orchestration in this slice.
- Do not replace Docker Compose service-level `healthcheck_cmd`; this slice
  waits on profile validation health checks before validation commands.
- Do not add migrations or change validation-run table shape.
- Do not change branch management, push behavior, PR creation, or monitor
  merge policy.
- Do not lower coverage thresholds, retry quality gates, or hide health-check
  failures behind generic retries.
- Do not change implementation files, tests, config, migrations, lockfiles, or
  docs other than this plan during the planning phase.
