# Implementation Plan — PR Monitor Recovery Must Not Re-enter Full Agent Path

## Objective
Implement and harden the guarantee that a workspace already in `monitoring_pr` with an existing PR/candidate can be redispatched for validate-only or rebase-only recovery without ever running planning, the main agent CLI, PR creation, or push again.

## Background
The AWF executor already has a recovery branch (triggered by `source="pr_monitor"` in an active `Operation` row) that skips planning and the agent CLI run. However, it currently falls through to the full post-agent commit and push/PR-creation steps. For validate-only recovery, the PR already exists and the branch is already pushed; re-pushing is unnecessary and violates the "never re-enter the full agent execution path" contract. For rebase-only, the actual rebase is owned by the monitor's `SyncBase` action, but the executor should still skip push.

## Files to Touch

| File | What to change |
|------|----------------|
| `src/awf/control/executor.py` | Skip push/PR creation in the recovery branch; transition directly to `monitoring_pr` (or `completed` if no monitor is wired). Ensure the recovery operation is closed with `validation_run_id`. |
| `tests/unit/control/test_executor_monitor_recovery.py` | Add regression tests proving skip-push, stale-callback guards, and correct operation finalization. |
| `tests/unit/runtime/test_pr_monitor_recovery_grace.py` | Extend coverage for rebase-only dispatch semantics. |
| `tests/unit/runtime/test_pr_monitor_runner_coverage_edges.py` | Add coverage for monitor-side idempotency guards. |

## Tests to Write First (strict TDD)

1. **Recovery skips push when PR already exists**
   - Seed a workspace in `ready` with a pending `pr_monitor` recovery operation, `pr_url`, and `pr_number` populated.
   - Run `executor.execute` with a clean validation pass.
   - Assert: no `git push` or `gh pr create` subprocess calls are issued.
   - Assert: workspace ends in `monitoring_pr` (if a monitor is wired) or `completed`.

2. **Validate-only recovery does not invoke the adapter at all on a clean pass**
   - Existing test `test_executor_skips_planning_and_agent_run_when_recovery_dispatched` already proves no planning prompts; extend with stricter assertion that **zero** `docker compose exec … codex` adapter calls occur.

3. **Recovery operation is closed with `validation_run_id` on success**
   - Already partially covered by existing tests; add explicit assertion for the `result["validation_run_id"]` key on the finished operation row.

4. **Recovery operation is closed `failed` when validation fails**
   - Already covered; add explicit assertion that the finished row carries the failed validation's `reason_code`.

5. **Stale callbacks cannot move cancelled/destroyed workspaces forward**
   - Seed a workspace in `ready` with recovery op; transition it to `cancelled` after the executor claims it (`ready→running`).
   - Assert: executor's `_recheck_status` returns `False`, workspace stays `cancelled`, and the recovery operation is **not** silently marked `succeeded`.
   - Repeat for `destroyed` status.

6. **Rebase-only recovery skips push just like validate-only**
   - Seed workspace with `recovery_mode="rebase_only"` payload.
   - Assert: after validation passes, no push is issued and workspace returns to `monitoring_pr`.

## Implementation Steps

### Step 1 — Executor recovery branch
In `executor.py`, after the validation loop concludes successfully (same block where `_finish_pending_validate_operations` is called), branch on whether the workspace is in recovery mode **and** already has a PR URL:

```python
if recovery is not None and ws.pr_url:
    # Skip push — the PR already exists and the branch is already on origin.
    # Transition directly back to monitoring_pr so the monitor resumes.
    if monitor is not None:
        await repo.transition(persisted, to=WorkspaceStatus.monitoring_pr,
                              reason_code="RECOVERY_VALIDATION_OK")
    else:
        await repo.transition(persisted, to=WorkspaceStatus.completed,
                              reason_code="RECOVERY_COMPLETED")
    await session.commit()
    return  # Do NOT re-enter the push/PR-creation path below
```

*Where to insert:* immediately after the validation loop block (`for pass_number in range(max_fix_passes + 1):`) and before the Step-3 `pushing` transition.

### Step 2 — Ensure recovery operation gets `validation_run_id`
The operation is type `validate`, so it is already finished by `_finish_pending_validate_operations` (which embeds `validation_run_id`). No code change needed here, but the new regression tests make this contract explicit.

### Step 3 — Stale-callback guard
The existing `_recheck_status` check at the top of `execute` and before each major step already respects `cancelled`/`destroyed`. No new production code is required, but add targeted unit tests to prove the guard holds for the recovery-specific entry points (`_start_pending_monitor_recovery_operations`, post-validation finalize).

### Step 4 — Worker-level guard (if gap found)
If `worker.py` stale-execution recovery or monitor-resume paths lack a `cancelled`/`destroyed` check, add a `_recheck_status` equivalent inside `resume_pr_monitor` or the worker dispatch. Re-examine after tests are written.

## Risks & Assumptions

- **Assumption:** The `pr_url` field is populated for every workspace that reaches `monitoring_pr` and then re-enters `ready` through recovery dispatch. This is already enforced by the monitor runner and resume logic.
- **Risk:** Fix-cycle commits produced during recovery would be left unpushed if we unconditionally skip push. For the current scope this is acceptable because the task explicitly says "without … push again". A future slice can decide whether a recovery fix-cycle should be pushed (it would require a conditional push, not a full PR creation).
- **Risk:** Skipping push means `pr.head_sha` is not refreshed in the executor's local variable. The validation_run target_head_sha update that happens after PR creation would be skipped. This is expected for recovery because the PR head hasn't changed (validate-only does not alter branch state).
- **Assumption:** Rebase-only recovery is currently handled as validate-only by the executor (the monitor dispatches via a `validate` operation row). The production fix does not implement a true rebase path inside the executor — that belongs to a future slice.

## Explicit Non-Goals

- Do NOT implement a first-class `rebase` operation type inside the executor.
- Do NOT add new UI/API endpoints for recovery; keep the workspace concept primary.
- Do NOT change the monitor's grace, review, or merge logic.
- Do NOT lower coverage thresholds or profile requirements.
