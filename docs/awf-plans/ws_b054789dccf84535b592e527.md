# Plan: P0 Operation Truth Idempotency Slice

## Objective

Complete the operator-control idempotency contract for `cancel`, `stop`,
`delete`/`destroy`, `remonitor`, `refresh`, `validate`, and `rebase`.

The implementation should make every duplicate `Idempotency-Key` replay return
the original durable operation identity and operation status, including after
the original operation has reached a terminal status. Replays must not create
new operation/event rows, rerun cleanup/stack-stop side effects, or reject only
because the workspace later moved to an ineligible state. A reused key with a
different payload must keep returning `IDEMPOTENCY_CONFLICT`.

## Tests To Write First

1. Exact replay after terminal operation status:
   - For `refresh`, `validate`, and `rebase`, create the operation through the
     API, manually mark the original operation `succeeded` or `failed`, move the
     workspace to a state that would reject a fresh request, then repeat the same
     `Idempotency-Key` and same payload.
   - Expected: response is still `202`, response id matches the original
     operation id, response status matches the stored terminal operation status,
     and operation/event row counts do not change.
   - This should fail first for `validate` if exact replay is still treated the
     same as active coalescing and rejected by current workspace-state checks.

2. Sync control operation status:
   - Extend `cancel`, `stop`, `delete`/`destroy`, and `remonitor` replay tests to
     assert the response includes the durable operation status, normally
     `succeeded`.
   - Repeat the same key after the operation is already terminal and assert the
     response keeps the same `operation_id`/`operation_status`, row counts do not
     change, and stack-stop/cleanup fakes are not called again.

3. Conflicting payload with the same key:
   - Keep and extend existing conflict cases for all seven controls:
     different body fields (`reason`, `stop_stack`, `remove_*`,
     `requested_tier`) and different `If-Match` must return
     `409 IDEMPOTENCY_CONFLICT`.
   - Assert no extra rows and no extra side effects after the conflict.

4. Fresh request versus active coalesce:
   - Keep the current `refresh`, `validate`, and `rebase` behavior where a fresh
     key with the same active payload coalesces to the existing pending/running
     operation.
   - Add a service-level test proving exact replay is allowed after terminal
     workspace movement, while a fresh key with the same payload still receives
     the appropriate state/version conflict instead of silently replaying.

5. Rebase regression from PR #115:
   - Re-run and preserve the existing rebase API tests around operation payload,
     candidate context, active rebase coalescing, destructive conflicts, missing
     PR/candidate handling, and stale `If-Match` ordering.
   - Add only terminal exact-replay assertions; do not change the accepted
     rebase endpoint behavior or payload identity semantics.

## Implementation Sequence

1. Add the failing tests above in the narrow files covered by the requested
   validation command.
2. Add an internal replay/coalesce marker in `WorkspaceControlService`, for
   example a small enum or dataclass returned by `_prepare_operation`.
3. Update `request_validate_workspace` so exact idempotency-key replay returns
   the stored operation regardless of the current workspace state, but active
   coalescing still checks `_VALIDATE_REPLAY_STATUSES`.
4. Apply the same replay/coalesce distinction to `refresh` and `rebase` only
   where needed, preserving their existing fresh-key coalescing and conflict
   ordering.
5. Extend `WorkspaceControlResponse` and `_control_response` to include the
   operation status for `cancel`, `stop`, `destroy`, and `remonitor`; update
   direct return paths that currently instantiate the response manually.
6. Confirm the rebase endpoint behavior from PR #115 is unchanged by keeping the
   existing assertions green before broadening validation.

## Risks And Assumptions

- Assumption: `delete` maps to the existing `destroy_workspace` service method
  and `OperationType.destroy`; no separate delete operation type is needed.
- Assumption: exact idempotency-key replay must return the stored operation even
  if the workspace has since advanced to `completed`, `cancelled`,
  `destroying`, or `destroyed`.
- Assumption: active-operation coalescing is not the same as exact replay. It may
  remain constrained by current workspace state and optimistic `If-Match`
  checks.
- Risk: `_prepare_operation` is shared across all controls. Changing its return
  contract should be mechanical and covered by the targeted tests so sync
  controls do not accidentally skip side effects on first execution.
- Risk: adding `operation_status` to `WorkspaceControlResponse` changes JSON
  output additively. Existing clients should remain compatible, but tests with
  exact response bodies may need explicit updates.
- Risk: rebase idempotency intentionally compares a stable operator identity
  instead of full candidate-expanded payload. Changing that would break PR #115
  behavior, so this slice should leave it intact.
- Risk: operation idempotency relies on the existing Postgres advisory lock for
  same-key serialization. This plan does not introduce a schema migration unless
  a concrete failing test proves the current lock/index arrangement is
  insufficient for the accepted concurrency model.

## Explicit Non-Goals

- Do not implement new operation types, migrations, or retention policies.
- Do not change the public request bodies or remove existing response fields.
- Do not change PR monitor recovery semantics, executor rebase execution, git
  push/rebase behavior, or merge policy.
- Do not broaden optimistic conflict handling beyond the exact replay versus
  active coalesce distinction needed for this slice.
- Do not lower coverage thresholds, quality gates, lint rules, or mypy strictness.
- Do not switch branches, push, rebase, force-push, create a PR, merge a PR, or
  commit during this planning phase.
