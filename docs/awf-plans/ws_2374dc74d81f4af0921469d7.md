# Plan: Target Branch Reconciliation Refreshes Open Merge Candidates

**Task**: After a post-merge target branch reconciliation runs for
repo_url/base_branch, AWF refreshes staleness for open merge candidates
on that same repo/base branch.

**Priority**: P0 (from TODO/pre-gke-industrial-readiness.md: "Make target
branch monitor detect every merged PR that can stale open candidates.")

## Current State

- `TargetBranchReconcileMonitor.reconcile()` checks out a target branch,
  runs resolvers (Alembic), commits/pushes repairs, and returns a
  `TargetBranchMonitorResult` with `resolver_results`, `commit_sha`,
  `status`, `pushed`.
- `StalenessRefreshService.refresh_candidate(candidate_id)` takes one
  candidate, evaluates staleness against the latest target branch state,
  and persists `StaleReason` rows + flips the `MergeCandidate.stale`
  boolean.
- `MergeCandidateRepository.list_queue(repo_url=, base_branch=)` already
  queries open candidates filtered by repo/base_branch (joins Workspace
  to exclude destroying/destroyed).
- `PostMergeTargetReconciler` Protocol currently has signature
  `async def __call__(self, *, repo_url: str, branch: str) -> object`.
- The PR monitor (`_reconcile_target_branch_after_merge`) calls the
  reconciler, logs the result, and emits a workspace event — but does
  NOT refresh other open candidates' staleness.

## Design

### Core Change

Add a **post-reconciliation staleness refresh step** that runs after a
successful target branch reconciliation. The step:

1. Queries all open merge candidates for the same `repo_url` /
   `base_branch` (excluding the just-merged workspace).
2. For each open candidate, calls
   `StalenessRefreshService.refresh_candidate()`.
3. Collects per-candidate results and any failures.
4. Returns structured result data that includes both the reconciliation
   outcome and the staleness refresh outcome.

### Where to Put It

Two options were considered:

**Option A**: Add the refresh loop to
`TargetBranchReconcileMonitor.reconcile()` directly.
- Pros: Single entry point; less wiring.
- Cons: The monitor currently has no DB session and no knowledge of
  `StalenessRefreshService`. Adding both would couple a git-level
  operation to the persistence layer.

**Option B**: Add an async wrapper function
`reconcile_and_refresh_stale_candidates()` in a new module
`src/awf/service/target_branch_reconcile_service.py` (or add to
`target_branch_monitor.py`) that composes the existing
`TargetBranchReconcileMonitor.reconcile()` with a staleness refresh
pass. The wrapper receives a DB session factory and a
`TargetBranchStateProvider`.
- Pros: Preserves separation of concerns. The git-level monitor stays
  pure. The service wrapper owns the DB session lifecycle and
  staleness refresh.
- Cons: Slightly more wiring at the call site.

**Chosen: Option B.** We add a `reconcile_and_refresh_stale_candidates()`
function to `src/awf/service/target_branch_monitor.py` (keeps the
module cohesive since it already defines `TargetBranchReconcileMonitor`).

### Structured Result

```python
@dataclass(frozen=True)
class CandidateRefreshSummary:
    candidate_id: str
    workspace_id: str
    stale: bool
    findings_count: int
    error: str | None = None

@dataclass(frozen=True)
class ReconcileAndRefreshResult:
    reconcile: TargetBranchMonitorResult
    candidate_refreshes: tuple[CandidateRefreshSummary, ...]
```

`TargetBranchMonitorResult` already has `to_dict()`. We add
`to_dict()` to the new types. The PR monitor's
`_target_reconcile_payload()` already calls `result.to_dict()` if
available; it will naturally pick up the nested data.

### Error Isolation

- If the reconciliation itself fails, we do NOT attempt candidate
  refreshes (the target branch state is uncertain).
- If reconciliation succeeds but one candidate refresh fails (e.g.
  missing row, provider error), we record the failure in the
  `CandidateRefreshSummary.error` field for that candidate and continue
  with remaining candidates. Reconciliation results are not hidden.
- The existing `_reconcile_target_branch_after_merge` in
  `pr_monitor_runner.py` already catches exceptions from the reconciler.
  Our wrapper will NOT raise for individual candidate failures; it
  returns them as structured data.

### Owned-Path Overlap Remains Advisory

No change to admission control. The task explicitly says overlap must
NOT become a launch blocker. The staleness refresh uses the existing
`evaluate_staleness()` which already treats overlap as a stale-risk
signal (STALE_OVERLAP finding), not an admission gate.

### Wiring in Worker

`worker.py` already constructs `TargetBranchReconcileMonitor` and passes
`target_branch_reconciler.reconcile` as the
`post_merge_target_reconciler` callback.

We need to change the callback from `monitor.reconcile` to
`reconcile_and_refresh_stale_candidates`. This requires:
- The worker passes a `session_factory` and a
  `TargetBranchStateProvider` (or a way to build one from the git
  checkout) to the new wrapper.
- The `PostMergeTargetReconciler` Protocol signature stays the same
  (`async def __call__(self, *, repo_url: str, branch: str) -> object`)
  so the PR monitor caller doesn't change at all.

We will add a `GitCheckoutTargetBranchStateProvider` that implements
`TargetBranchStateProvider` by running git commands on the checkout
directory (which `TargetBranchReconcileMonitor` already has). This
provider lives in `src/awf/service/target_branch_monitor.py` (or
alongside the staleness module) and uses the
`AsyncCommandRunner` + checkout path to compute `head_sha`,
`changed_paths`, and `advanced_commits`.

Actually, to keep the TDD increments small and avoid requiring live
git subprocesses in the staleness refresh path, we should build the
`TargetBranchState` from the git checkout that the reconciler already
has. After `reconcile()` returns, we know the checkout path and the
latest `HEAD` SHA. The wrapper can construct a
`TargetBranchState` by:
1. `git rev-parse HEAD` → `head_sha`
2. For each candidate's `base_sha`: `git rev-list --count <base_sha>..HEAD`
   and `git diff --name-only <base_sha>..HEAD` → changed_paths and
   advanced_commits.

But this means we'd need a git runner for the provider too. A simpler
approach: after reconciliation, the checkout is at the latest target
HEAD. We can build one `TargetBranchState` per unique `base_sha` among
the open candidates (usually 1-2 distinct base SHAs), then pass the
appropriate `TargetBranchState` to each `refresh_candidate()` call via
its `target=` parameter.

For the initial implementation, we'll add a
`GitCheckoutTargetBranchStateProvider` that uses the
`AsyncCommandRunner` and the checkout path from the reconcile result.
It will be testable with `FakeCommandRunner` in unit tests.

### Step 2: Green Implementation

1. Add `CandidateRefreshSummary` and `ReconcileAndRefreshResult`
   dataclasses to `target_branch_monitor.py`.
2. Add `GitCheckoutTargetBranchStateProvider` class that implements
   `TargetBranchStateProvider` and uses `AsyncCommandRunner` + checkout
   path.
3. Add `reconcile_and_refresh_stale_candidates()` async function:
   - Accepts `runner`, `work_dir`, `repo_url`, `branch`,
     `session_factory`, `dry_run=False`, optional `exclude_workspace_ids`.
   - Calls `TargetBranchReconcileMonitor.reconcile()`.
   - If reconcile fails, propagates the error (no refreshes).
   - If reconcile succeeds and `status != clean` or pushed, opens a DB
     session, queries `MergeCandidateRepository.list_queue()` for the
     same `repo_url`/`base_branch`, filtering out destroyed/merged.
   - Excludes the workspace that triggered the reconcile (passed via
     caller context — the PR monitor knows the `workspace_id`).
   - Groups candidates by `base_sha`, builds `TargetBranchState` via
     `GitCheckoutTargetBranchStateProvider` for each unique `base_sha`.
   - Calls `StalenessRefreshService.refresh_candidate()` for each open
     candidate.
   - Catches per-candidate exceptions, records them.
   - Returns `ReconcileAndRefreshResult`.
4. Update `worker.py` to wire the new function as
   `post_merge_target_reconciler`.
5. Ensure `PostMergeTargetReconciler` Protocol is satisfied (signature
   is `async def __call__(self, *, repo_url: str, branch: str) -> object`
   — our function needs to be partially applied or wrapped to match).

**Protocol adaptation**: The PR monitor calls
`reconciler(repo_url=repo_url, branch=base_branch)`. Our new function
needs `session_factory` and `runner` in addition. We'll create a
closure or functools.partial in `worker.py`:

```python
async def _post_merge_reconciler(
    *, repo_url: str, branch: str
) -> object:
    return await reconcile_and_refresh_stale_candidates(
        runner=runner, work_dir=work_dir,
        repo_url=repo_url, branch=branch,
        session_factory=session_factory,
    )
```

## Risks

1. **Session lifecycle in the wrapper**: The reconcile step doesn't need
   a DB session, but the refresh step does. Using a fresh session per
   call via `session_factory` is safe but means we need to handle
   transaction boundaries carefully. We'll open one session for the
   entire refresh pass, commit at the end, and rollback on unexpected
   errors.

2. **GitCheckoutTargetBranchStateProvider requires the checkout to
   exist**: After `reconcile()`, the checkout is guaranteed to be at
   the latest target HEAD. But if the checkout was cleaned up between
   reconcile and refresh (unlikely in the same function call), the
   provider would fail. We'll pass the `checkout_path` from the
   reconcile result directly.

3. **Performance with many open candidates**: If there are N open
   candidates with M distinct base SHAs, we make M git calls to build
   `TargetBranchState` objects. For typical AWF usage (N < 20), this is
   fine. For very large N, we could batch, but that's a non-goal.

4. **Circular dependency risk**: `target_branch_monitor.py` importing
   from `staleness.py` is fine (no cycle). The staleness module doesn't
   import target_branch_monitor.

## Assumptions

- The `PostMergeTargetReconciler` Protocol's return type is `object`,
  so returning a `ReconcileAndRefreshResult` is safe — the PR monitor
  only calls `to_dict()` or `str()` on it.
- The PR monitor already emits a `target_branch.reconciled` event. The
  enhanced result will be richer. The event type stays the same.
- `MergeCandidateRepository.list_queue()` filters out
  destroying/destroyed workspaces, which is correct for our use case.
- The `TargetBranchReconcileMonitor.reconcile()` result includes
  `checkout_path`, which we'll reuse for git commands in the provider.

## Explicit Non-Goals

- Changing the `PostMergeTargetReconciler` Protocol signature (it stays
  `async def __call__(self, *, repo_url: str, branch: str) -> object`).
- Making owned-path overlap a launch blocker (remains advisory per PRD).
- Building a scheduler-level overlap graph (that's a P1 scheduler task).
- Adding API endpoints for manual staleness refresh (P0 operations task,
  separate).
- Changing the Alembic resolver or adding new resolver types.
- Adding integration tests for two parallel PRs (P0 test coverage task
  listed separately — our unit tests cover the logic).
