# Plan: P0 Validation Provenance Identity

## Goal

Implement the focused P0 validation-provenance slice so every persisted
validation run can explain what command set ran, which target/base/workspace
SHAs it covered, and which profile/environment identity produced it. The API
must expose this without requiring console clients to scrape logs, while old
validation rows continue to serialize with safe fallback values.

## Current Anchors

- Durable validation rows already live in `ValidationRun` in
  `src/awf/db/models.py`, with repository helpers in
  `src/awf/db/repositories.py`.
- Initial validation provenance API exposure is in
  `src/awf/api/routes/validation.py` and `src/awf/api/validation_runs.py`.
- Merge queue latest validation exposure is in
  `src/awf/api/routes/merge_queue.py`.
- Public response models are in `src/awf/api/schemas.py`.
- Validation runs are started and finished by
  `src/awf/control/executor.py`, using command records derived from
  `WorkspaceProfile`.
- Profile shape and runtime/toolchain inputs are in
  `src/awf/profiles/models.py`; stack launch consumes runtime/docker/services
  through `src/awf/node/stack_launcher.py` and `src/awf/profiles/compose.py`.
- Migration style for validation runs is established in
  `migrations/versions/e6f7a8b9c0d1_validation_runs.py` and
  `migrations/versions/ec041f62c7fc_add_retry_count_to_validation_runs.py`.

## Tests To Write First

1. Identity hashing stability in `tests/unit/runtime/test_validation.py`:
   - Two profiles with the same runtime/docker/service inputs in different
     dict/list construction order produce identical environment identity
     digests.
   - Changing `runtime.toolchain_image`, `runtime.agent_image`, docker mode, a
     service image, or a validation healthcheck changes the environment digest.
   - Changing profile description, monitor grace, planning paths, or other
     non-validation metadata does not change the environment digest.
   - The resolved profile digest changes when any resolved profile field
     changes and is stable across key ordering.
   - Sanitized identity inputs never expose raw secret values and either list
     environment keys or stable value hashes.

2. Repository persistence in `tests/unit/db/test_repository_coverage.py`:
   - Starting a validation run with full provenance persists
     `base_sha`, `workspace_head_sha`, profile metadata, resolved profile
     digest, environment digest, and environment identity inputs.
   - Starting a validation run without the new fields still succeeds, proving
     old call sites and rows are compatible during migration.

3. Migration coverage in `tests/unit/db/test_migration_graph.py`:
   - Alembic single head is the new revision.
   - `alembic upgrade head` creates all new `validation_runs` columns in
     SQLite.

4. API response shape in `tests/unit/api/test_validation_provenance.py`:
   - A persisted validation run returns the new fields for every command item.
   - `target_head_sha`, `current_target_head_sha`, and `fresh_for_target`
     continue to behave as today.
   - `base_commit` remains for compatibility while `base_sha` is populated.

5. Legacy fallback in `tests/unit/api/test_validation_provenance.py`:
   - A manually inserted old-style row with null new fields returns
     `base_sha` from `base_commit`, `workspace_head_sha` from
     `target_head_sha` when available, null identity fields, and an explicit
     fallback marker if adopted.
   - A workspace with only legacy validation log streams still returns the
     existing stream-derived shape.

6. Summary helper tests in `tests/unit/api/test_validation_run_helpers.py`:
   - `validation_run_summary()` includes identity fields and fallback values.
   - Malformed JSON identity inputs normalize to `{}` rather than failing
     response serialization.

7. Merge queue exposure in `tests/unit/api/test_merge_queue.py`:
   - `latest_validation` includes profile/environment identity fields.
   - Required validation tier, latest satisfied tier, and freshness fields are
     still present and unchanged.
   - A legacy validation row appears in merge queue with fallback values rather
     than omitting `latest_validation`.

8. Executor persistence in `tests/unit/control/test_executor.py`:
   - A normal successful execution creates a validation run with command hash,
     target branch, base SHA, workspace head SHA, profile metadata, resolved
     profile digest, and environment identity digest.

## Implementation Sequence

1. Add the failing tests above, starting with identity hashing and repository
   persistence.
2. Implement canonical identity helpers with deterministic JSON serialization
   (`sort_keys=True`, compact separators, explicit schema version).
3. Add nullable ORM columns and Alembic migration, then update migration graph
   tests.
4. Extend `ValidationRunRepository.start()` and existing call sites with the
   new provenance fields.
5. Capture local workspace `HEAD` SHA in the executor before validation starts.
   If the git command fails, store `None` and continue validation rather than
   turning provenance collection into a validation blocker.
6. Populate profile metadata and digests from the resolved `WorkspaceProfile`
   already used to build command records.
7. Extend API schemas and shared response helpers with persisted values plus
   legacy fallbacks.
8. Update merge queue serialization so the expanded
   `ValidationRunSummaryResponse` is visible through `latest_validation`.
9. Run focused validation, then the full requested unit/lint/typecheck surface.

## Risks

- Digest scope can be too broad or too narrow. The environment identity digest
  should include runtime/toolchain/service/validation-environment inputs, while
  command contents stay represented by `command_set_hash` and full profile
  drift stays represented by `resolved_profile_digest`.
- Environment variables may contain secrets. The digest can use raw values
  internally, but API-exposed identity inputs must be sanitized to avoid
  logging or returning token values.
- `base_commit` already exists and may be used by clients. Add `base_sha`
  without removing or renaming `base_commit`.
- Local workspace `HEAD` capture may fail in unusual git states. Provenance
  collection must not hide or replace the real validation result.
- Old rows cannot truly reconstruct profile/environment identity. Fallbacks
  should be explicit and conservative rather than pretending old provenance is
  complete.
- Merge queue expected-response tests use exact dictionaries; expanding
  `latest_validation` will require careful test updates.

## Assumptions

- `target_head_sha` remains the canonical persisted target/PR head field; API
  clients can treat it as the task's requested `target_sha`.
- `current_target_head_sha` can continue to be computed from the latest merge
  candidate head or `workspace.monitor_last_commit_sha`.
- For new rows, `base_sha` initially matches the executor's `base_commit`
  value, including rebase-recovery updates.
- For legacy rows, `workspace_head_sha` can only be best-effort, falling back
  to `target_head_sha` when present.
- A nullable-column migration is sufficient for backward compatibility; no
  batch backfill is required in this slice.

## Explicit Non-Goals

- Do not implement merge policy enforcement changes beyond exposing the
  provenance inputs merge policy needs.
- Do not change validation tier rules or PR monitor recovery behavior.
- Do not alter command execution semantics, retries, coverage parsing, or log
  stream layout except to expose identity metadata.
- Do not expose raw secrets, tokens, or full unredacted environment values in
  API responses.
- Do not remove or rename existing validation API fields.
- Do not modify console code in this slice.
- Do not push, rebase, switch branches, or commit during this planning phase.
