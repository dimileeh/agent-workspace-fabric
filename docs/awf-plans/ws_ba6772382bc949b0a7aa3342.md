# Plan — Fix #477: BitBucket PR never auto-merges (abbreviated head SHA blocks pre-merge validation gate)

## Problem & root cause (verified on a real BitBucket PR)

A BitBucket PR with `merge_state CLEAN` and no blockers has the monitor decide
`action=Merge` every cycle, but the pre-merge **validation-provenance gate**
silently blocks forever.

Root cause chain:

- `bitbucket_client.py:1078` `_pr_head_sha()` returns `source.commit.hash`
  **verbatim**, which BitBucket Cloud's PR GET serves in the **abbreviated
  12-char** form (e.g. `a59f411ce4c4`).
- `fetch_pr_status` (`bitbucket_client.py:297,350`) puts that abbreviated value
  into `PRStatus.head_sha`.
- AWF's pre-merge gate compares `PRStatus.head_sha` against the **full 40-char**
  `ValidationRun.target_head_sha` (e.g.
  `a59f411ce4c403fe6185df79df05f9b51743c084`) by **exact equality** → never
  matches → `validation_missing_for_current_head` → merge blocked every cycle
  even though validation succeeded.
- GitHub is unaffected: the GitHub API returns full 40-char SHAs.

The gate is correct (it legitimately assumes full SHAs everywhere). The bug is
that the **BitBucket forge adapter lets an abbreviated SHA escape**. Fix the
adapter so an abbreviated hash NEVER leaves the BitBucket client.

## Fix strategy

Resolve the **full 40-char** head SHA inside `BitBucketClient` before it is
stored on `PRStatus` (and before any per-commit endpoint is called with it).

Mechanism (Preferred per task): BitBucket's commit endpoint resolves an
abbreviated hash to the full one —
`GET /2.0/repositories/{ws}/{repo}/commit/{abbrev-or-full}` returns
`hash` = full 40-char SHA. Resolve **only when abbreviated** (one extra cached
GET); a hash already ≥ 40 chars is left untouched (no extra call).

The `links.self.href` alternative is rejected: BitBucket's PR `source.commit`
links also carry the abbreviated form, so the commit endpoint is the reliable
source. (Stated as the explicit decision; commit endpoint chosen.)

Failure handling: if the commit-resolve GET fails or returns an unusable
payload, surface a **reason-coded `BitBucketClientError`** — do NOT silently
fall back to the abbreviated hash (that would re-introduce the merge block).
Genuine HTTP/transport failures already propagate from `_request_json` with
their existing transient codes (`BITBUCKET_TRANSPORT_ERROR`,
`BITBUCKET_RATE_LIMITED`, `BITBUCKET_API_ERROR`) so the monitor's retry path
still works for blips; only a malformed/short resolved payload gets the new
deterministic code.

  - Add a new reason code constant `BITBUCKET_COMMIT_RESOLVE_FAILED` with a

  - Import/re-export the new constant alongside the other
    `bitbucket_client_errors` symbols (lines 43–60 block).
  - Add an async helper, e.g.:
    `async def _resolve_full_commit_sha(self, repo: RepoRef, sha: str) -> str:`
    - If `len(sha) >= 40`: return `sha` unchanged (no HTTP call).
    - Else: `GET {self._repo_path(repo)}/commit/{quote(sha, safe='')}` via
      `self._request_json(..., operation="bitbucket resolve_commit_sha",
      cache=True)`.
    - Extract `hash` via `_clean_optional_str(_as_dict(data).get("hash"))`.
      If missing or `len < 40`, raise
      `BitBucketClientError(operation="bitbucket resolve_commit_sha",
      status=None, body=..., reason_code=BITBUCKET_COMMIT_RESOLVE_FAILED)`.
    - Return the resolved full hash.
  - In `fetch_pr_status` (lines ~296–308): after computing the raw head and the
    `None` guard, resolve to the full SHA **before** the commit-statuses fetch
    and **before** `_remember_pr`, so:
    - `PRStatus.head_sha` is full,
    - the `commit/{head_sha}/statuses` fetch uses the full hash (endpoint
      accepts both — safe),
    - the remembered `_PRContext.source_sha` is the full hash (so
      `rerun_failed_workflow_jobs` reconstructs the pipeline target with the
      full hash, keeping consistency; endpoint accepts both).
  - Update `_remember_pr` to accept the resolved full head SHA (e.g. a
    `head_sha: str` param) and store it as `source_sha`, instead of re-reading
    the abbreviated `source.commit.hash`. Reorder so `_remember_pr` is called
    after resolution. Keep `dest_sha` as-is (the destination commit hash is not
    used for head matching / validation provenance; out of scope).
  - `fetch_failing_check_logs` needs **no change**: its `head_sha` parameter is
    supplied by the monitor runner from `PRStatus.head_sha`, which is now full.
    (Note this explicitly in code review — the abbreviated value can no longer
    reach it.)

## Risks & mitigations

- **Extra HTTP call per poll**: mitigated by resolving ONLY when abbreviated and
  caching the GET (`cache=True`, ETag conditional). Full hashes (incl. all
  GitHub) incur zero extra calls. Real BitBucket PR GETs always abbreviate, so
  ~1 cached GET per head change.
- **Endpoints fed the full hash**: `commit/{sha}/statuses` and the rerun
  pipeline target accept both abbreviated and full hashes, so widening to full
  is safe (and is what GitHub already does end-to-end).
- **Reason-catalog drift**: the catalog is generated from `_REASON_TEXT`
  (`awf.service.doctor.reasons`), not from scanning constants, so adding the new
  constant does NOT require `docs/REASON_CATALOG.md` regeneration. Verify no
  drift gate trips; if a future doc gate references it, add a `_REASON_TEXT`
  entry (out of scope unless the gate demands it).
- **Coverage**: every new branch (early-return for full hash, resolve success,
  malformed-hash raise) is covered by the tests above; the propagation of an
  HTTP error reuses existing `_request_json` paths.
- **File size**: `bitbucket_client.py` is ~1458 lines; the addition is ~15
  lines. No automated file-size gate exists (errors were already extracted to
  `bitbucket_client_errors.py` by convention). Acceptable.

## Assumptions

- BitBucket SHA-1 full length is 40 chars; the `>= 40` threshold both detects
  "already full" and tolerates a future longer hash without forcing a resolve
  of something already full. (If BitBucket ever serves an abbreviated hash ≥ 40
  chars this would skip resolution, but that contradicts git SHA semantics.)
- The commit endpoint returns the full `hash` reliably (verified in the issue).
- `ValidationRun.target_head_sha` is the full 40-char SHA produced from local
  git at validation time (full SHAs everywhere AWF assumes them).

## Non-goals (explicitly out of scope)

- The validation gate's exact-equality comparison — it correctly assumes full
  SHAs; fix the forge adapter, not the gate.
- GitHub client behavior (already returns full SHAs).
- #475 (PR-number display) — separate workspace.
- BitBucket `resolve_thread` / merge strategy / async-merge poll semantics —
  unchanged.
- `_PRContext.dest_sha` resolution — destination hash is not used for head
  matching or validation provenance.
