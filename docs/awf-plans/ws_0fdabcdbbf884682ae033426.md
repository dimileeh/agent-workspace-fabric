# Plan: P1 DB-Backed Profile Hooks

## Objective

Add a narrow profile-driven database hook slice for DB-backed workspaces. Profiles
should be able to declare workspace-local project database commands that AWF runs
inside the existing per-workspace compose stack:

- generated database setup hooks during the setup/pre-agent path;
- pre-validation database refresh hooks during the validation path;
- durable stdout/stderr artifacts and log streams for those hooks;
- structured hook-specific timeout/failure reason codes.

This slice must keep project databases as profile-declared workspace services.
It must not reuse or expose AWF's control-plane Postgres as a project database.

## Current Code Context

- `src/awf/profiles/models.py`
  - `WorkspaceProfile` is a strict Pydantic model with `runtime`, `docker`,
    `services`, `phases`, and `validation`. Unknown top-level fields are
    currently rejected, so a new `database` profile section needs explicit
    modeling.
  - `ProfileCommand` already provides the command shape and timeout field that
    DB hooks can reuse.

- `src/awf/runtime/validation.py`
  - `ValidationRunner.run_profile_phases()` is the existing runtime path for
    setup, pre-agent, post-agent, validate, health checks, coverage, artifacts,
    command timeouts, and durable log streams.
  - `_exec()` already writes per-workspace artifacts and log streams with
    `validation.<label>.stdout/stderr`, and maps subprocess timeouts to
    `PHASE_TIMEOUT`.

- `src/awf/control/executor.py`
  - Setup currently calls `run_profile_phases(..., phase_names=("setup",
    "pre_agent"))`.
  - Validation currently records validation provenance with
    `_validation_run_command_records()` and then calls
    `run_profile_phases(..., phase_names=("post_agent", "validate"),
    run_healthchecks=True)`.
  - `_failure_reason_for_phase()` maps setup/pre-agent failures to
    `service_startup_failure`, health checks to `health_check_failure`, and
    timeouts to `phase_timeout`.

- `tests/fixtures/workspace_services/python_postgres_app/.awf/workspace.yml`
  - Already proves profile-declared Postgres/app services are project-local and
    distinct from AWF control-plane Postgres.

## Intended Files And Modules To Touch

Production modules:

- `src/awf/profiles/models.py`
  - Add a small `ProfileDatabase` model on `WorkspaceProfile`.
  - Proposed YAML shape:
    ```yaml
    database:
      generated_setup:
        - command: ./scripts/db-generated-setup.sh
          timeout_seconds: 120
      pre_validation_refresh:
        - command: ./scripts/db-refresh.sh
          timeout_seconds: 120
    ```
  - Reuse `ProfileCommand` coercion so strings and command objects work the
    same way as existing phases.

- `src/awf/runtime/validation.py`
  - Build an ordered execution plan instead of passing only raw phase commands.
  - Insert `database.generated_setup` after `setup` commands and before
    `pre_agent` commands when the selected phase set includes setup/pre-agent.
  - Insert `database.pre_validation_refresh` after `post_agent` commands and
    before health checks/validate commands when the selected phase set includes
    `validate`.
  - Label synthetic phases as `db_generated_setup` and `db_refresh`.
  - Preserve existing behavior for profiles with no database hooks.
  - Map hook failures to hook-specific reason codes:
    - `DATABASE_GENERATED_SETUP_FAILED`
    - `DATABASE_GENERATED_SETUP_TIMEOUT`
    - `DATABASE_REFRESH_FAILED`
    - `DATABASE_REFRESH_TIMEOUT`
  - Include hook metadata on `ValidationCommandResult.metadata`, such as
    `database_hook`, `hook_kind`, and `timeout_seconds`.

- `src/awf/control/executor.py`
  - Update `_validation_run_command_records()` so validation provenance and
    operation log stream refs include pre-validation DB refresh hooks in the
    same order the runner executes them.
  - Update `_validation_command_count()` for refresh hooks and coverage counts.
  - Update `_failure_reason_for_phase()` only as needed:
    - DB timeout reason codes should map to `FailureReason.phase_timeout`;
    - non-timeout generated setup failures should remain setup/service startup
      failures;
    - non-timeout refresh failures should remain validation failures.

- `src/awf/runtime/validation_identity.py`
  - Include the new `profile.database` hook commands in validation environment
    identity inputs, because changing refresh/setup commands changes what was
    proven.

- `src/awf/profiles/registry.py`
  - Touch only if the Aira compatibility profile should move existing
    DB-oriented setup commands into `database.generated_setup`. Keep this
    conservative; preserving current behavior is acceptable if no test requires
    registry changes.

## Risks And Assumptions

- Assumption: DB hooks are shell commands run in the agent container through the
  existing compose exec path, using profile-declared workspace services and
  profile runtime environment.
- Assumption: `database.generated_setup` belongs in the setup/pre-agent path
  after ordinary setup commands, so dependency installation can happen first.
- Assumption: `database.pre_validation_refresh` belongs after post-agent hooks
  and before health checks/validate, so validation observes the final branch
  state and a freshly prepared project DB.
- Risk: Moving health checks after DB refresh for DB-backed validation profiles
  changes ordering for those profiles. The red test should pin the intended
  order and existing no-hook profiles should keep their current order.
- Risk: Hook-specific reason code mapping adds another translation layer on top
  of `_exec()`'s generic `COMMAND_FAILED`/`PHASE_TIMEOUT`. Keep it small and
  covered by unit tests.
- Risk: A fixture hook that mutates the DB can make integration tests order
  dependent. Use idempotent fixture commands and workspace-local volumes only.
- Risk: Adding database hooks to validation identity can change existing digest
  snapshots. Update only tests that intentionally assert the new identity
  surface.

## Explicit Non-Goals

- Do not add migrations, database tables, or new control-plane DB columns.
- Do not make AWF's control-plane Postgres available as a project database.
- Do not implement cloud secret brokers, profile-level database provisioning
  beyond profile-declared services, or cross-workspace shared DBs.
- Do not add implicit Alembic behavior back into `ValidationRunner.run()`.
- Do not broaden stale detection, schema lineage locks, merge policy, or PR
  monitor behavior in this slice.
- Do not lower coverage thresholds, quality gates, lint, typecheck, or
  validation requirements.
- Do not switch branches, push, rebase, force-push, or commit during this
  planning phase.
