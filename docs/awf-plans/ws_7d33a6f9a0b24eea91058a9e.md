# Plan: P1 Operator Doctor Diagnostics

## Scope

Add a narrow operator-facing diagnostic command under the established local
service CLI surface: `awf service doctor`.

The existing `awf service status` command is already the structured dependency
status surface for API, DB, Docker, agent runtime image, disk pressure, provider
readiness, orphan resources, stranded workspace containers, and cleanup
readiness. The doctor slice should reuse that collector, keep `service status`
behavior unchanged, and add a terminal-readable diagnostic layer with stable
reason codes and a structured JSON shape suitable for later console/MCP parity.

The new command should default to readable terminal output, support JSON output,
exit non-zero on failing diagnostics, and never print secrets.

## Intended Files And Modules To Touch

Production code:

- `src/awf/cli/main.py`
  - Add `awf service doctor`.
  - Accept `--format pretty|json`, defaulting to `pretty` for operator use.
  - Accept repeated `--provider` using the same provider validation as
    `service status`.
  - Catch provider/config errors cleanly without tracebacks.
  - Leave `awf service status` behavior and output untouched.
- `src/awf/service/doctor.py` (new)
  - Define small dataclasses or typed helpers for `DoctorReport` and
    `DoctorDiagnostic`.
  - Reuse `collect_service_status()` for existing structured checks.
  - Add supplemental read-only diagnostics for local worker reachability,
    required host ports, and local env/config issues.
  - Map stable reason codes to plain-language messages and actions while
    preserving the original source check metadata.
  - Expose dependency injection points for tests: service-status collector,
    subprocess runner, socket connector, environment mapping, and filesystem
    predicates.
- `src/awf/service/status.py`
  - Touch only if a tiny helper must be exported to avoid duplicating existing
    check/result normalization. Do not change `collect_service_status()` output
    unless tests prove a small additive field is required.
- `src/awf/service/config.py`
  - Touch only if doctor needs a reusable redacted config summary helper beyond
    existing `service_config_payload()`.

Tests:

- `tests/unit/service/test_doctor.py` (new)
  - Primary TDD coverage for diagnostic normalization, redaction, worker/port
    probes, and plain-language output data.
- `tests/unit/cli/test_service_cli.py`
  - CLI wiring tests for `awf service doctor`, output formats, exit codes,
    provider validation, and no regression to `awf service status`.

Docs, after implementation:

- `README.md`
  - Add a short local troubleshooting example for `awf service doctor`, only if
    CLI help is not sufficient for discoverability.

## Diagnostic Shape

Structured report shape:

```json
{
  "service": "awf",
  "status": "ok|warn|fail",
  "summary": {
    "ok": 0,
    "warn": 0,
    "fail": 0
  },
  "diagnostics": [
    {
      "id": "docker",
      "label": "Docker",
      "status": "ok|warn|fail|skipped",
      "reason": "DOCKER_DAEMON_UNREACHABLE",
      "message": "Docker is installed but the daemon is not reachable.",
      "action": "Start Docker Desktop or verify DOCKER_HOST.",
      "source": "checks.docker",
      "detail": "redacted bounded detail",
      "metadata": {}
    }
  ]
}
```

Pretty output should be concise, one diagnostic per line or small block, for
example:

```text
AWF doctor: fail
[ok] Docker: Docker daemon is reachable.
[fail] API: AWF API is not reachable at http://localhost:8000/healthz.
       action: Run awf service bootstrap or inspect api logs.
```

## Risks

- `service status` already performs many checks. The doctor command must avoid
  duplicating probe logic and drifting from the authoritative status payload.
- Worker reachability does not currently have a DB heartbeat or API endpoint.
  For this local packaging slice, use the local Compose worker service as the
  signal and make that assumption explicit in the diagnostic metadata.
- Port checks can produce false negatives in non-host or non-local Docker
  layouts. Keep them short, report host/port only, and preserve the underlying
  API/DB checks as the stronger readiness signal.
- Docker being unavailable can cascade into worker/container diagnostics. Keep
  dependent diagnostics readable and reason-coded instead of hiding the root
  Docker failure.
- Redaction is critical because doctor output is likely to be pasted into issue
  trackers. Use existing redaction patterns and add explicit regression tests.

## Assumptions

- The established local operator namespace is `awf service ...`, so
  `awf service doctor` is preferable to changing `awf service status`.
- `collect_service_status()` remains the source of truth for API health,
  Docker, disk pressure, provider readiness, orphan resources, and stranded
  workspace checks.
- Local service packaging uses `docker/compose/local-service.yml`, where the
  API maps to host port `8000`, Postgres maps to host port `5433`, and the
  worker runs as the `worker` Compose service.
- Provider strictness should match existing `service status --provider`
  semantics.
- JSON output should prioritize stable reason codes and source paths over a
  finalized console/MCP schema.

## Explicit Non-Goals

- Do not add a package publisher, installer, daemon manager, or service repair
  workflow.
- Do not mutate Docker resources, clean containers, open ports, write config,
  or run migrations from doctor.
- Do not change existing `awf service status` output, exit behavior, or default
  format.
- Do not add DB migrations, API endpoints, PR monitor behavior, scheduler
  behavior, merge policy changes, or cleanup execution.
- Do not print raw secrets, tokens, unredacted database URLs, or full
  environment dumps.
- Do not lower coverage targets, fail-under settings, workspace coverage
  requirements, or PRD quality gates.
- Do not use `# pragma: no cover` except for truly unreachable defensive
  protocol/declaration branches with a short comment.
