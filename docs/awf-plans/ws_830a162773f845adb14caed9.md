# Plan: P1 Local Docker Egress Policy Enforcement

## Scope

Implement a narrow local-mode security slice for profile-declared egress policy.
AWF already models `security.egress` on `WorkspaceProfile`; this work will make
the local Docker Compose launch path honor that policy at the compose
network/profile boundary.

The minimum safe behavior is:

- `open` remains backward compatible: same public Docker network behavior and
  `host.docker.internal` access as today.
- `offline` gets deterministic local enforcement by rendering the workspace
  Compose network as `internal: true` and omitting the host-gateway mapping.
- `mirrored` uses the same offline network enforcement only when it does not
  require external named destinations; this allows profile-declared in-stack
  mirror sidecars without public egress.
- `allowlist`, and any restricted mode that requires external destination
  filtering the local backend cannot enforce generically, is rejected before
  `docker compose up` with a structured policy reason code.

Do not implement cloud `NetworkPolicy`, host firewall rules, iptables mutation,
transparent proxies, DNS filtering, or package-registry mirror management in
this slice.

## Intended Files And Modules

- `src/awf/node/egress_policy.py` (new)
  - Add a small local-only policy decision helper, for example
    `local_egress_plan(profile.security.egress)`.
  - Return a typed decision with:
    - `mode`;
    - `network_internal`;
    - `host_gateway_enabled`;
    - deterministic `reason_code`;
    - sanitized policy details suitable for logs/events.
  - Raise a typed `LocalEgressPolicyError` for unsupported local modes, carrying
    `reason_code`, `mode`, and a bounded message.

- `src/awf/node/compose_manager.py`
  - Extend `WorkspaceComposeSpec` with network policy fields such as
    `network_internal: bool = False` and `host_gateway_enabled: bool = True`.
  - Pass those fields into the Jinja template.
  - Keep defaults equivalent to today's open behavior.

- `docker/compose/workspace.base.yml.j2`
  - Render `networks.awf_net.internal: true` only when requested by the spec.
  - Render the agent `extra_hosts` host-gateway entry only when requested.
  - Do not add service-level custom commands or firewall sidecars.

- `src/awf/node/stack_launcher.py`
  - Evaluate the profile egress policy before resolving services and before
    `compose.up(...)`.
  - Pass the resulting network flags into `WorkspaceComposeSpec`.
  - Let `LocalEgressPolicyError` abort launch before any Docker resources are
    created.

- `src/awf/node/provisioner.py`
  - Catch `LocalEgressPolicyError`.
  - Mark the workspace failed as `policy_failure`.
  - Preserve the specific policy reason code on the terminal transition event
    instead of collapsing it to only `POLICY_FAILURE`.
  - Keep existing `ComposeOperationError` behavior unchanged except where a
    tiny helper change is needed to pass custom transition reason codes.

- `src/awf/db/enums.py`
  - No new enum is expected. Reuse existing coarse `FailureReason.policy_failure`.

- `src/awf/profiles/models.py`
  - No model rename is expected. Keep current modes
    `open`, `allowlist`, `offline`, and `mirrored`.
  - Touch only if tests expose a needed validation clarification for mirrored
    mode. Avoid schema churn.

- `README.md`
  - Add a concise "Local egress policy" note documenting current local behavior,
    reason-code expectations, and the explicit cloud/proxy non-goal.

No migrations, lockfiles, frontend files, scheduler code, runtime validation
identity code, or cloud backend code should be touched. The existing validation
identity helper already includes profile egress inputs.

   network rendering.
2. Add the failing stack-launcher tests for translating `ProfileEgress` into
   local compose flags or deterministic launch rejection.
3. Add the failing provisioner test that proves policy launch rejection becomes
   `policy_failure` with the specific egress reason code in workspace events.

   - `open` -> `network_internal=False`, `host_gateway_enabled=True`,

   add an optional `reason_code` parameter to `_mark_failed(...)` with the

8. Add README documentation for the local-only behavior and reason codes.
9. Run the focused tests, then broader Python validation.

## Risks And Mitigations

- Docker Compose cannot enforce domain allowlists by itself. Mitigate by
  rejecting unsupported restricted modes before launch with explicit reason
  codes instead of pretending a partial allowlist is enforced.
- `internal: true` blocks public egress but still allows communication inside
  the workspace network. Mitigate by documenting that offline/mirrored local
  mode is intended for in-stack services and mirrors only.
- `host.docker.internal` can provide an unintended path to host-local services.
  Mitigate by omitting the host-gateway mapping when egress mode is enforced as
  offline/mirrored.
- Existing AWF self-development workflows may rely on open egress for package
  installs and GitHub access. Mitigate by leaving the default as `open` and
  preserving current compose output for profiles without an egress policy.
- Provisioner failures currently collapse many terminal events to coarse
  failure reason codes. Mitigate with a small optional reason-code parameter
  rather than a broad failure-taxonomy refactor.
- Tests should not require Docker. Keep enforcement unit tests at render,
  launcher, and provisioner levels with fakes/mocked subprocesses.

## Assumptions

- Local Docker Compose is the only backend in scope for this slice.
- Existing profile mode names remain stable: `open`, `allowlist`, `offline`,
  and `mirrored`.
- `offline` can be enforced locally with an internal Compose network plus no
  host-gateway mapping.
- `allowlist` requires a future proxy/firewall/backend implementation and must
  fail closed locally.
- `mirrored` without external allowlist entries can be represented as an
  offline internal workspace network for local mode.
- Coarse terminal failure taxonomy remains `policy_failure`; specific causality
  is carried by workspace event `reason_code` and failure message.

## Explicit Non-Goals

- No Kubernetes, GCP, cloud `NetworkPolicy`, service mesh, or egress gateway.
- No host firewall, iptables, nftables, Docker daemon config, or DNS resolver
  mutation.
- No implementation of destination/domain allowlisting in local mode.
- No secret broker, package mirror, artifact store, or credential-scope work.
- No database schema changes, migrations, queue policy changes, PR monitor
  changes, validation provenance changes, or scheduler changes.
- No destructive Docker cleanup or changes to AWF branch/push behavior.
- No coverage or quality-gate relaxation.
