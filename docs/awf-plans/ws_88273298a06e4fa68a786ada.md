# Plan: PR monitor terminally fails on transient DNS base-fetch error (Issue #336)

## Problem

`_is_transient_base_fetch_error` in `helpers.py` classifies DNS-resolution failures
(e.g., `Could not resolve host: github.com`) as non-transient because
`_TRANSIENT_GITHUB_ERROR_MARKERS` in `constants.py` contains no DNS markers.
This causes terminal `GIT_FETCH_BASE_FAILED` instead of retried fetch.

The `_NON_TRANSIENT_GITHUB_ERROR_MARKERS` already includes
`could not resolve to a repository` and `could not resolve to a node`
(GitHub "repo/node not found" — genuinely non-transient), checked FIRST.
The DNS markers (e.g., `could not resolve host`) are distinct strings and
will not collide.

## Files to touch

1. **`src/awf/runtime/pr_monitor_runner/constants.py`** — Add DNS-resolution
   failure markers to `_TRANSIENT_GITHUB_ERROR_MARKERS`:
   - `"could not resolve host"`
   - `"temporary failure in name resolution"`
   - `"name or service not known"`
   - `"could not resolve proxy"`

2. **`tests/unit/runtime/test_pr_monitor_runner_coverage_edges_parts/test_pr_monitor_runner_coverage_edges_part_001.py`**
   — Add regression tests in `test_transient_base_fetch_classifier_and_corrupt_retry_count_recovery`:
   - DNS variants (`Could not resolve host: github.com`, etc.) → assert True
   - Non-regression: `could not resolve to a repository` / `could not resolve to a node` → assert False

## Tests to write first (TDD)

Extend the existing `test_transient_base_fetch_classifier_and_corrupt_retry_count_recovery`:

```python
# DNS-transient → True
assert _is_transient_base_fetch_error(
    BaseFetchError("fatal: unable to access 'https://github.com/org/repo': Could not resolve host: github.com")
)
assert _is_transient_base_fetch_error(
    BaseFetchError("fatal: unable to access 'https://github.com/org/repo': Temporary failure in name resolution")
)
assert _is_transient_base_fetch_error(
    BaseFetchError("fatal: unable to access 'https://github.com/org/repo': Name or service not known")
)
assert _is_transient_base_fetch_error(
    BaseFetchError("fatal: unable to access 'https://proxy.example.com': Could not resolve proxy: proxy.example.com")
)

# Non-regression: GitHub "resolve to a repository/node" → still False
assert not _is_transient_base_fetch_error(
    BaseFetchError("could not resolve to a repository")
)
assert not _is_transient_base_fetch_error(
    BaseFetchError("could not resolve to a node")
)
```

## Risks & assumptions

- **No collision risk**: The new DNS markers (`could not resolve host`,
  `temporary failure in name resolution`, `name or service not known`,
  `could not resolve proxy`) do not contain the non-transient substrings
  (`could not resolve to a repository`, `could not resolve to a node`).
  Case-insensitive matching is already applied (`text.lower()`), and the
  strings are token-distinct.
- **No retry-budget change**: Existing `_increment_base_fetch_retry_count` /
  `_base_fetch_retry_wait_seconds` / `_wait_after_transient_base_fetch_error`
  path handles these once the classifier returns True. No new retry path needed.
- **Markers are git/libcurl standard**: These four phrases are standard
  libcurl/c-strings for DNS failures across Linux and macOS.
