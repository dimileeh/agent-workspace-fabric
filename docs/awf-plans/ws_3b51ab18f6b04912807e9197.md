# Plan: P0 Restart-Safe PR Monitor Recovery

## Objective

Make active PR workspaces recoverable after the AWF API/worker process restarts.
A workspace already persisted in `monitoring_pr` with an open `pr_url` must be
claimed by the fresh worker and handed back to the PR monitor without re-running
the feature agent, re-validating from the beginning, pushing/opening a second PR,
or resetting persisted monitor state. Recovery must leave durable operation and
event breadcrumbs so the console can explain why the monitor was reattached.

## Current Code Context

- `src/awf/control/worker.py`
  - `run_once()` already lists `monitoring_pr` workspaces, claims them through
    `WorkspaceRepository.claim_monitoring_pr()`, and dispatches
    `executor.resume_pr_monitor()`.
  - Stale runtime scanning already classifies stopped/missing runtime for
    `monitoring_pr` with a PR URL as recoverable and can clear stale claims, but
    automatic worker resume currently has no explicit recovery operation row.

- `src/awf/control/executor.py`
  - `resume_pr_monitor()` is the intended restart path and skips setup,
    feature-agent execution, validation, push, and PR creation.
  - It currently requires persisted metadata, tries to restart Compose, then
    builds the monitor and calls `monitor.run()`.
  - A Compose restart failure currently marks the workspace failed, which is too
    aggressive for an already-open PR.

- `src/awf/runtime/pr_monitor_runner.py`
  - `_load_state()` reconstructs `MonitorState` from persisted
    `monitor_iter_count`, `monitor_threads_addressed`, `monitor_last_commit_sha`,
    and `monitor_started_at`.

- `src/awf/service/controls.py`
  - Manual `remonitor` already creates `OperationType.remonitor` and
    `workspace.remonitor_requested` events. The automatic restart path should
    use the same observability model without changing public API responses.

## Intended Files And Modules To Touch

### Production

- `src/awf/control/worker.py`
  - Add worker-owned monitor recovery operation/event creation around automatic
    `monitoring_pr` resume dispatch.
  - Record enough payload context for the console: `source`, `owner`,
    `requested_action`, reason code, `pr_url`, `pr_number`, previous claim

## Implementation Steps

1. Add the tests above and run the focused subset to confirm the current red
   failures are the intended gaps.
2. In `ControlWorker`, add a small automatic recovery context around claimed
   monitor resumes:
   - create a running `OperationType.remonitor` row after a claim succeeds;
   - append a `workspace.monitor_recovery_started` event with operation id and
     prior claim/runtime context;
   - pass the operation id into the resume task;
   - finish the operation as `succeeded` when the monitor handoff exits normally
     and `failed` if an unexpected exception escapes the handoff path.
3. Keep monitor claim semantics unchanged: active unexpired leases still block
   duplicate workers, and the claim heartbeat/release path still owns
   concurrency.
4. In `WorkspaceExecutor.resume_pr_monitor()`, change only the Compose failure
   branch:
   - log and append a durable event such as
     `workspace.monitor_runtime_restart_failed`;
   - keep the workspace in `monitoring_pr`;
   - continue building/running the PR monitor with the persisted compose
     project/file values.
5. If the unavailable-runtime test is red because runtime health inspection
   returns `decision="none"`, adjust the worker-side recovery decision for
   `monitoring_pr` plus `pr_url` rather than broadening failure behavior for
   active pre-PR workspaces.
6. Re-run focused tests, then the requested validation commands.

## Risks And Assumptions

- Assumption: `monitoring_pr` plus non-empty `pr_url`/`pr_number` is the
  authoritative signal that PR creation already happened and must not be
  repeated.
- Assumption: Existing monitor state columns are sufficient; no migration is
  needed.
- Risk: A long-running recovered monitor may keep its `remonitor` operation in
  `running` until the PR reaches a terminal state. This is acceptable if the
  operation represents monitor ownership, but the payload and event names should
  make that clear.
- Risk: Continuing after Compose restart failure means a later monitor action
  that needs the agent container may fail inside the monitor loop. That is still
  better than losing PR monitoring entirely, and the runtime warning event gives
  the console an explanation.
- Risk: Operation duplication after repeated worker crashes. The monitor claim
  prevents live duplicates; historical duplicate recovery attempts are useful
  audit data as long as each operation payload identifies the worker/reason.

## Explicit Non-Goals

- Do not change public API response schemas or remove existing fields.
- Do not add migrations or new database tables.
- Do not recreate PRs, rerun the original feature-agent task, or manually merge
  PRs.
- Do not lower coverage thresholds, workspace quality gates, or validation
  requirements.
- Do not change branch management, push behavior, or AWF PR ownership rules.
- Do not implement a full distributed scheduler or external queue; this slice
  is the local service restart-safety path for already-open PRs.
