# Plan: P1 MCP And Project Onboarding Client Parity – Make the Parity Matrix a Testable Implementation Driver

## Goal

Convert `docs/MCP_CLIENT_PARITY.md` from a documentation-only gap inventory into an
implementation driver where every row includes REST endpoint, CLI command, MCP tool
name, schema/error-code contract, security boundary, status, and a concrete backlog
slice reference for missing or partial coverage. Then add a `docs/status` consistency
regression test that fails if an implemented row lacks evidence, or if a missing/partial
row lacks a concrete follow-up slice reference.

This slice is docs/test focused. It does **not** implement all missing MCP tools.

## Current Observations

1. The existing `docs/MCP_CLIENT_PARITY.md` has 22 rows with columns:
   `Capability | Canonical REST surface | CLI surface | MCP surface | Status | Notes and backlog`.
   Missing columns: **schema/error-code contract**, **security boundary**, **backlog slice reference**.

2. Six rows are `MCP partial` and three are `MCP missing/backlog`. None have a concrete
   backlog/slice reference pointing to an implementation issue or TODO item.

3. Two rows are `Out of scope` (WebSocket stream, secret lease status). These are valid
   but should still state their exclusion rationale in the new `Security boundary` column.

4. `tests/unit/mcp/test_mcp_client_parity_docs.py` (32 lines) only checks that the
   parity doc exists, contains role-contract language, lists missing surfaces, and has
   the security boundary prose. It does **not** verify that the matrix rows are
   structurally complete or that statuses are consistent with real code.

5. There is no test anywhere that cross-references parity doc rows against the actual
   REST routes, CLI commands, MCP tool names, and error codes in the codebase. The
   TODO explicitly calls for this: "entries marked implemented must correspond to real
   REST routes, CLI commands, MCP tools, and contract-test coverage; partial or missing
   entries must remain visible as unchecked backlog work."

6. The control-plane error codes are centralized in `src/awf/service/controls.py`
   (`NOT_FOUND`, `WORKSPACE_ACTIVE`, `IDEMPOTENCY_CONFLICT`, `VERSION_CONFLICT`,
   `STACK_STOP_FAILED`, `WORKSPACE_PR_URL_REQUIRED`, `WORKSPACE_STATE_NOT_REMONITORABLE`,
   `WORKSPACE_STATE_NOT_REFRESHABLE`, `WORKSPACE_STATE_NOT_VALIDATABLE`,
   `WORKSPACE_STATE_NOT_REBASEABLE`, `MERGE_CANDIDATE_NOT_FOUND`,
   `WORKSPACE_REBASE_CONFLICT`, `WORKSPACE_OPERATION_CONFLICT`).

7. The REST api schemas are centralized in `src/awf/api/schemas.py`. Response envelope
   names are `WorkspaceResponse`, `WorkspaceControlResponse`, `OperationResponse`,
   `ErrorResponse`, etc.

8. The MCP server registers 32 tools in `src/awf/mcp/server.py`. The REST api exposes
   ~40 endpoints across 16 route modules. The CLI exposes 21 commands on 4 groups.

## Parity Matrix Schema

Each row must contain:

| Column | Content | Example |
| --- | --- | --- |
| Capability | Human-readable surface name | Workspace create, list, and get |
| Canonical REST surface | HTTP method and path | `POST /v1/workspaces`, `POST /v2/workspaces` |
| CLI surface | Full command path or `CLI absent` | `awf workspace create` |
| MCP tool name | `awf_*` tool name or `No <tool>` | `awf_create_workspace`, `awf_create_workspace_v2` |
| Schema / Error-Code Contract | Response schema or error-code set | `WorkspaceAcceptedResponse`; controls: `NOT_FOUND`, `VERSION_CONFLICT`, `IDEMPOTENCY_CONFLICT` |
| Security Boundary | Auth, scope, or safety constraint | `require_api_token`; MCP: no shell, no exec |
| Status | One of: `MCP implemented`, `MCP partial`, `MCP missing/backlog`, `CLI absent`, `Out of scope` | `MCP implemented` |
| Backlog Slice | Concrete issue or TODO line reference, or `—` for complete rows | `TODO§P1-refresh` or `—` |

### Status vocabulary (unchanged)

- `MCP implemented`: full parity with REST.
- `MCP partial`: useful subset, named gap documented.
- `MCP missing/backlog`: REST or CLI exposes the surface, MCP has no equivalent.
- `CLI absent`: no CLI command, use REST or MCP.
- `Out of scope`: excluded for safety or transport reasons, rationale in Security Boundary.

### Backlog slice references for missing/partial rows

| Row | Status | Slice reference |
| --- | --- | --- |
| Artifact content/download | MCP missing/backlog | `TODO§P1-artifact-download` |
| Refresh workspace | MCP missing/backlog | `TODO§P1-mcp-refresh` |
| Rebase workspace | MCP missing/backlog | `TODO§P1-mcp-rebase` |
| Retry workspace | MCP missing/backlog | `TODO§P1-mcp-retry` |
| Optimistic concurrency (If-Match) | MCP partial | `TODO§P1-if-match-parity` |
| Workspace events (global) | MCP partial | `TODO§P1-mcp-global-events` |
| Cancel workspace (If-Match) | MCP partial | `TODO§P1-if-match-parity` |
| Stop workspace (If-Match) | MCP partial | `TODO§P1-if-match-parity` |
| Destroy workspace (If-Match) | MCP partial | `TODO§P1-if-match-parity` |
| Remonitor workspace (If-Match) | MCP partial | `TODO§P1-if-match-parity` |
| Request validation (If-Match) | MCP partial | `TODO§P1-if-match-parity` |

The `TODO§P1-*` references will use an anchor-style notation pointing into
`TODO/pre-gke-industrial-readiness.md` P1 section items.

## Tests To Write First

### 1. Structural consistency test (in `test_mcp_client_parity_docs.py`)

Expand the existing test module. New tests:

- `test_parity_matrix_has_required_columns`: Parse the markdown table header row; assert it contains `Canonical REST surface`, `CLI surface`, `MCP tool name`, `Schema / Error-Code Contract`, `Security Boundary`, `Status`, `Backlog Slice`.
- `test_parity_matrix_status_values_are_from_vocabulary`: Every status cell is one of `MCP implemented`, `MCP partial`, `MCP missing/backlog`, `CLI absent`, `Out of scope`.
- `test_implemented_rows_have_rest_endpoint_and_mcp_tool`: For every row where status starts with `MCP implemented`, the REST column is non-empty and the MCP column starts with `awf_`.
- `test_partial_or_missing_rows_have_backlog_slice`: For every row where status contains `partial` or `missing`, the Backlog Slice column is non-empty and starts with `TODO§`.
- `test_security_boundary_column_non_empty`: Every row has a non-empty security boundary.
- `test_schema_contract_column_non_empty_for_control_rows`: Rows whose REST surface includes `POST` or `DELETE` must name at least one response schema or error code.

### 2. Cross-reference regression test (in new `test_mcp_parity_matrix_crossref.py`)

- `test_parity_matrix_rest_endpoints_exist_in_api_routes`: Every REST endpoint cell parses to `METHOD /path`; the path must appear in the FastAPI route collection. (Import and inspect `app.routes` from `awf.api.app` or parse route module source for the path prefixes and method decorators.)
- `test_parity_matrix_mcp_tools_exist_in_server`: Every MCP tool name cell that starts with `awf_` must appear in the list returned by `build_mcp_server(...)._list_tools()` or by parsing `@mcp.tool()` registrations from `src/awf/mcp/server.py`.
- `test_parity_matrix_cli_commands_or_absent`: Every CLI cell that is not `CLI absent` must start with `awf ` and the command subpath must be discoverable in the Typer app registered commands from `src/awf/cli/main.py`.
- `test_parity_matrix_error_codes_mentioned_exist_in_controls`: Error codes named in Schema/Contract cells (comma-separated) that match `[A-Z_]+` pattern must exist in the error constant set from `src/awf/service/controls.py`.
- `test_parity_matrix_schema_names_exist_in_schemas_module`: Schema names named in contract cells must exist as class names in `src/awf/api/schemas.py`.

### Test implementation approach

All tests will be `@pytest.mark.unit` and will:

- Read `docs/MCP_CLIENT_PARITY.md` from disk (like the existing test).
- Use a small helper to parse the markdown table into structured rows (split on `|`, trim whitespace).
- Import route/app/tool definitions at test time to avoid duplicating the canonical lists.
- Be tolerant of minor formatting differences (extra spaces, line breaks within cells).

No database, Docker, network, or external service is needed.

## Implementation Steps

1. **Red phase**: Write the structural tests in `test_mcp_client_parity_docs.py` and the
   cross-reference tests in `test_mcp_parity_matrix_crossref.py`. Run them and confirm
   they fail because the current parity doc lacks the new columns.

2. **Update the parity matrix**: Rewrite `docs/MCP_CLIENT_PARITY.md` preserving all
   existing content in the Role Contract, Status Vocabulary, and MCP Security Boundary
   sections. Restructure the Parity Matrix table to add the three new columns. Fill
   every cell:

   - **Schema / Error-Code Contract**: For read rows list the REST response schema name
     (e.g., `WorkspaceOverviewListResponse`). For control rows list the response schema
     plus the relevant error codes from `controls.py` (e.g., `WorkspaceControlResponse;
     NOT_FOUND, VERSION_CONFLICT, IDEMPOTENCY_CONFLICT`). For `Out of scope` rows use
     `N/A (out of scope)`.

   - **Security Boundary**: `require_api_token` for all rows (matching the FastAPI
     dependency). For MCP control rows add `MCP: no shell, no exec, no credential dump`.
     For `Out of scope` rows state why (e.g., `WebSocket excluded: MCP prefers bounded
     snapshots over streaming transport`).

   - **Backlog Slice**: `—` for `MCP implemented` rows. Concrete `TODO§P1-*` references
     for missing/partial rows as outlined above.

3. **Green phase**: Run the parity doc tests. They should pass once the matrix is updated.

4. **Verify**: Run the full narrow test suite for MCP parity and doc tests, then the
   broader unit suite.

## Risks

- **Table parsing fragility**: Markdown tables are easy to break with alignment. The
  test helper must be forgiving of whitespace but strict about column presence. Risk is
  low since tests will fail visibly on formatting drift.

- **Codebase drift**: REST routes, MCP tools, or CLI commands may be added or renamed
  between when the matrix is updated and when tests run. This is intentional: the
  cross-reference test should fail noisily to force the matrix to stay current.

- **Circular import risk**: Importing FastAPI `app` or Typer `app` in unit tests may
  trigger side effects (DB connections, settings). Mitigation: parse tool names and
  route paths from source or use lightweight inspection (e.g., `app.routes` without
  starting the server). If needed, extract static registration lists as module-level
  constants.

- **Incremental adoption**: If this slice lands before backlog items are filed, the
  `TODO§P1-*` references will point to anchors in the existing TODO file. That is
  acceptable; the references are forward pointers to P1 items that already exist or
  will be created.

## Assumptions

- The parity matrix is the single source of truth for client surface status. Adding
  columns does not change the semantic meaning of existing statuses.

- The `TODO§P1-*` anchor notation is sufficient as a "concrete backlog slice reference."
  It points to items already tracked in `TODO/pre-gke-industrial-readiness.md`. If
  GitHub issues replace that file later, the references should be updated to issue URLs.

- Cross-referencing REST routes by parsing `@router.get/post/delete` decorators from
  source files is acceptable for unit tests. An alternative is to import the FastAPI
  app and read `app.routes`, but this risks side effects in test environments.

- Schema names and error codes referenced in the matrix are module-level identifiers
  importable from `awf.api.schemas` and `awf.service.controls`. This avoids fragile
  string matching.

- This slice does not implement any missing MCP tools. That is an explicit non-goal.
  The backlog slice references document what is missing and where it should be tracked.
