# Plan: Node/Next Browser Profile Fixture

## Scope

Implement a narrow P1 realistic-profile slice proving that AWF can model a
frontend project end to end: a tiny Node/Next-style app, an explicit browser
validation fixture, profile setup/health/validate phases, Docker smoke coverage
that skips deterministically when Docker is unavailable, and docs showing how a
real project declares the profile.

Keep the slice generic. The fixture should use profile-declared services in
AWF's existing per-workspace Compose stack, service-name URLs on `awf_net`, and
AWF-owned `docker compose down -v` cleanup. It must not add Aira-specific
assumptions or build a dashboard.

## Intended Files And Modules To Touch

Primary fixture files:

- `tests/fixtures/workspace_services/node_next_browser_app/.awf/workspace.yml`
  - New repo-local profile named `node-next-browser-app`.
  - Use `docker.mode: none`; the app and browser validator are AWF profile
    services in the outer workspace stack.
  - Declare runtime env such as `APP_BASE_URL=http://app:3000` and
    `BROWSER_VALIDATE_URL=http://browser:9323/validate`.
  - Declare an `app` service built from the fixture Dockerfile, with a Node
    healthcheck, no required host port, and a deterministic start command.
  - Declare a `browser` service built from a Playwright-based fixture
    Dockerfile, depending on healthy `app`, with `/healthz` and `/validate`
    endpoints.
  - Declare `phases.setup` to initialize the app, `validation.healthchecks` for
    app and browser readiness, and `phases.validate` to trigger browser
    validation through the browser validator service.
  - Declare `ports` entries documenting service-name endpoints.
- `tests/fixtures/workspace_services/node_next_browser_app/Dockerfile`
  - Tiny Node app image, preferably `node:22-alpine` or equivalent.
  - No production AWF dependency changes.
- `tests/fixtures/workspace_services/node_next_browser_app/Dockerfile.playwright`
  - Browser validator image based on a pinned Playwright image.
  - If the base image does not include the needed Node package, install a pinned
    fixture-local Playwright dependency inside this image only.
- `tests/fixtures/workspace_services/node_next_browser_app/package.json`
  - Minimal scripts for app start and optional local checks.
  - Add a fixture-only lockfile only if needed for deterministic `npm ci`; do
    not touch `apps/console/package-lock.json` or repo-level lockfiles.
- `tests/fixtures/workspace_services/node_next_browser_app/server.mjs`
  - Small Node HTTP server with `/`, `/api/status`, `/setup`, and `/healthz`.
  - The root page should expose a stable DOM marker that browser validation can
    assert, such as a heading and `data-awf-ready` attribute.
- `tests/fixtures/workspace_services/node_next_browser_app/scripts/*.mjs`
  - Agent-side setup, healthcheck, and validation request scripts using Node 22
    built-in `fetch`.
  - Container-side app healthcheck script if the app image lacks curl/wget.
- `tests/fixtures/workspace_services/node_next_browser_app/browser/validator-server.mjs`
  - HTTP server that launches Chromium via Playwright, visits `APP_BASE_URL`,
    asserts the page and API contract, closes the browser, and returns a stable
    success body such as `browser validated awf-node-profile-fixture\n`.

Primary tests:

- `tests/unit/profiles/test_workspace_services_profile.py`
  - Add fixture contract tests for repo-local profile resolution, runtime env,
    ports, service schemas, phase commands, and validation healthchecks.
  - Assert `profile_services(profile, base_path=fixture)` resolves
    worktree-relative Dockerfile/build paths and preserves dependencies,
    healthchecks, commands, and environment.
- `tests/unit/runtime/test_workspace_services_compose.py`
  - Add launcher/rendering coverage for the Node/browser fixture.
  - Assert rendered services are `agent`, `app`, and `browser`; app and browser
    run on `awf_net`; browser depends on healthy app; agent depends on both
    healthchecked services; no host ports or named volumes are required.
- `tests/unit/runtime/test_node_next_browser_profile_validation.py`
  - New no-Docker validation-runner contract using `FakeCommandRunner`.
  - Assert setup runs as `setup`, healthchecks precede validate only when
    `run_healthchecks=True`, validate triggers the browser endpoint, and
    artifact labels are stable.
- `tests/integration/test_node_next_browser_profile_compose.py`
  - New Docker smoke test using the existing skip style:
    `Docker daemon or Compose plugin not available; set AWF_SKIP_DOCKER_TESTS=1 to force-skip.`
  - Use `agent_runtime_image="node:22-bookworm-slim"` or another public Node 22
    image so the test does not depend on a locally built AWF runtime image.
  - Launch the stack with `manager.up(spec, wait=True)`, run setup, then run
    validation with healthchecks enabled through `ValidationRunner`.
  - Tear down in `finally` with `manager.down(spec)` and assert no
    `awf-<workspace_id>-*` containers or volumes remain.

Docs:

- `README.md`
  - Add a concise generic Node/Next plus browser validation profile example
    near the existing "Working With Dockerized Projects" examples.
  - Show a real `.awf/workspace.yml` with app and browser services,
    setup/health/validate phases, service-name URLs, and no host port
    requirement.
  - Note that this is profile-driven project validation, separate from the AWF
    console/dashboard.

Production modules, only if tests expose a real gap:

- `src/awf/profiles/compose.py`
  - Touch only for narrow profile-service path or field-preservation bugs.
- `src/awf/node/compose_manager.py`
  - Touch only if service rendering, health dependencies, named resources, or
    cleanup semantics fail the fixture contract.
- `src/awf/node/stack_launcher.py`
  - Touch only if launch-time environment or path propagation is missing.
- `src/awf/runtime/validation.py`
  - Touch only if existing phase/healthcheck execution cannot run the fixture's
    declared setup, health, and validate commands.
- `src/awf/node/cleanup.py`
  - Not expected. Touch only if deterministic Compose cleanup cannot be proven
    through the current `down -v` path.

No migrations should be needed.

   Expected red after the directory exists but before details are complete:
   missing app/browser services, missing phase commands, or missing

3. Add launcher/rendering unit tests.
   Expected red if existing code mishandles worktree-relative build paths,
   healthchecked dependencies, agent env propagation, or service rendering.

4. Add the validation-runner unit test with `FakeCommandRunner`.
   Expected red if the profile commands are not shaped for AWF's existing phase
   runner or healthcheck ordering.

5. Add the Docker integration smoke test last.
   Expected red before implementation: fixture/profile/app is missing.
   Expected behavior without Docker: skipped with the exact existing
   unavailable reason above.

6. Implement the smallest green change.
   Prefer fixture, test, and docs changes if existing AWF machinery already
   supports the scenario. Keep production code changes limited to gaps exposed
   by the tests.

## Implementation Sequence

1. Write the failing profile, rendering, validation-runner, and Docker smoke
   tests.
2. Add the Node fixture app:
   - Small HTTP server using Node stdlib.
   - Stable setup and health endpoints.
   - Stable DOM and API contract for browser assertions.
3. Add the Playwright/browser validator service:
   - Pinned base image.
   - `/healthz` confirms the validator process is ready.
   - `/validate` runs Chromium against the app service URL and returns a stable
     success body.
4. Add the repo-local AWF profile:
   - Outer stack services for `app` and `browser`.
   - Runtime env consumed by the agent-side scripts.
   - Setup, healthcheck, and validate phases with bounded timeouts.
5. Run the narrow unit tests and update production code only for genuine
   profile/compose/validation gaps.
6. Add README documentation after the executable contract is green.
7. Run focused profile/node/integration validation and, if any `src/awf` files
   changed, run ruff and mypy.

## Risks

- Playwright images are large and can be architecture-sensitive. Docker or
  Compose unavailability must skip deterministically; image pull or browser
  runtime failures should remain real integration failures.
- The pinned Playwright image may not include the exact Node package entrypoint
  needed by the validator script. If so, keep the dependency fixture-local and
  pinned rather than changing AWF dependencies or repo-level lockfiles.
- Current AWF profile services are launched with the workspace stack, not
  started on demand only for validation. This slice can model the browser
  validator as a profile service and document that full test-burst lifecycle is
  a later feature.
- `ValidationRunner` executes phase commands in the agent container, not inside
  the browser service. The plan uses an HTTP validator endpoint so the browser
  work stays in the Playwright service while AWF still executes declared
  profile phases.
- Host port mappings can collide under parallel workspaces. The fixture should
  avoid host ports unless a test explicitly needs them.
- Cleanup safety depends on `ComposeManager.down(..., remove_volumes=True)`.
  The integration test must assert containers and volumes with the workspace
  prefix are gone after teardown.
- Node 22 built-in `fetch` is assumed for agent-side scripts; use a Node 22
  agent image in the integration test.

## Assumptions

- Profile-declared services are the correct generic mechanism for frontend app
  and browser validation sidecars in this slice.
- Service DNS names plus container ports are the canonical communication path
  inside `awf_net`.
- Existing profile schema, healthchecks, `ComposeStackLauncher`, and
  `ValidationRunner` are expected to be sufficient for this fixture.
- A realistic end-to-end proof can be limited to stack launch, profile setup,
  readiness healthchecks, browser validation, and deterministic teardown.
- No database migrations, API shape changes, scheduler changes, PR monitor
  changes, or cloud backend changes are required.

## Explicit Non-Goals

- Do not build or modify the AWF console dashboard.
- Do not implement a full Next.js application or marketing UI; the fixture is a
  tiny Node/Next-style app contract.
- Do not implement on-demand compose profiles or test-burst service lifecycle
  in this slice.
- Do not introduce Aira-specific service names, database assumptions, pgvector,
  or Alembic behavior.
- Do not require Docker for unit tests.
- Do not depend on a locally built `awf-agent-runtime:latest` image in the new
  integration test.
- Do not push, rebase, switch branches, or commit as part of this planning
  phase.
- Do not lower coverage thresholds, quality gates, requested validation tiers,
  lint strictness, or test-quality guardrails.
