## Objective

Replace the reserved `awf start` placeholder with a real, friendly wrapper that
**delegates to the existing `run_service_bootstrap` engine** to start local AWF
Core, then renders a first-run-contract success panel or a reason-coded failure.
T05 owns only the start CLI delegation, the source/package asset-selection hooks
that start needs, and tests. It does not reimplement service startup, rework
`awf setup` (T04), implement package-data inclusion (T13), or add the no-token
smoke proof (T10).

## Design / Approach

### Command shape (`src/awf/cli/start_commands.py`)

Replace `start_command` with a real implementation exposing exactly the public
interface from the source plan:

```text
awf start [--rebuild] [--skip-agent-runtime-build] [--timeout-seconds N]
          [--source-checkout PATH] [--format json|pretty]
```

Options and their mapping onto existing bootstrap internals:

- `--format json|pretty` — `OutputFormat`, default `pretty` (consistent with the
  current placeholder and other first-run commands).
- `--timeout-seconds N` — `float`, `min=0.0`, default `180.0`; maps to
  `ServiceBootstrapOptions.timeout_seconds`.
- `--skip-agent-runtime-build` — `bool`; maps to
  `ServiceBootstrapOptions.skip_agent_runtime_build=True` for a faster restart.
- `--rebuild` — `bool`; forces a from-scratch rebuild of the agent-runtime image
  by bypassing the Docker layer cache. Maps to a new, scoped
  `ServiceBootstrapOptions.force_rebuild` flag (see "Bootstrap hooks" below).
  **Mutually exclusive** with `--skip-agent-runtime-build`; passing both exits
  with code 2 and a `--rebuild`/`--skip-agent-runtime-build` conflict message
  (no Core start attempted). (Decision/assumption — see Risks.)
- `--source-checkout PATH` — optional path selecting verified source-checkout
  assets explicitly (see "Asset selection" below).

The command keeps the same control-flow skeleton as `service_bootstrap`: resolve
settings + compose/env paths via the existing
`_resolve_service_compose_paths()` / `_resolve_service_runtime_env_files()` /
`local_service_environ()` / `resolve_service_settings()` helpers, build
`ServiceBootstrapOptions`, call `run_service_bootstrap(...)`, and translate the
structured result/exception into first-run output. No strict-provider flag is
exposed for start (not in the public interface); start passes no strict
providers.

### Asset selection (package vs. verified source checkout)

Precedence, evaluated before any Core start:

1. **Explicit `--source-checkout PATH`** — call
   `validate_source_checkout(path)`. On `SourceCheckoutError`, render a
   reason-coded first-run failure (`SOURCE_CHECKOUT_INVALID` or
   `SOURCE_CHECKOUT_ASSETS_STALE`) carrying `missing_markers` / details, and exit
   without attempting Core start. On success, pin bootstrap to the verified
   checkout (root + compose file + agent-runtime dockerfile + compose env file).
2. **Stored config metadata** — when no `--source-checkout` is given, attempt
   `read_host_setup_config()`; if `config.source_checkout` metadata is present,
   revalidate it via `verified_source_from_metadata(...)`. A stale/moved checkout
   raises `SOURCE_CHECKOUT_ASSETS_STALE` and fails loudly — it does **not**
   silently fall back to package assets (acceptance criterion). A missing
   config, a config with no source-checkout metadata, or an unreadable/corrupt
   config when source assets were not requested falls through to (3).
3. **Default discovery (package or in-repo source)** — no explicit selection;
   `run_service_bootstrap` discovers assets exactly as today via
   `get_bootstrap_asset_root()` (package wheel `bootstrap_assets/` root or a
   verified in-repo checkout). T13 owns package-asset *inclusion*; T05 only
   *consumes* whatever bootstrap already resolves.

When (1) or (2) yields a `VerifiedSourceCheckout`, start passes
`compose_file=verified.compose_file` **and** the new `asset_root=verified.root`
hook so the agent-runtime build, compose, and env-file resolution all use the
selected checkout — never a discovered package root. This is the "explicit"
selection the acceptance criteria require.

### Bootstrap hooks (`src/awf/service/bootstrap.py`)

Two minimal, backward-compatible additions ("existing service bootstrap adapters
only for delegation if needed"):

- `asset_root: Path | None = None` on `run_service_bootstrap(...)`, threaded into
  `_resolve_bootstrap_assets(compose_file, *, require_agent_runtime,
  asset_root=None)`. When provided, asset resolution is **pinned** to that root
  (compose, agent-runtime Dockerfile, and compose env file derived from it)
  instead of running `_resolve_bootstrap_asset_root()` discovery. An
  `asset_root` that is not a valid bootstrap asset root raises the existing
  `_bootstrap_assets_not_found_error(...)` (`SERVICE_BOOTSTRAP_ASSETS_NOT_FOUND`)
  — start maps this to `START_COMPOSE_ASSETS_MISSING`. Default `None` preserves
  today's behavior and the existing `service_bootstrap` command path unchanged.
- `force_rebuild: bool = False` on `ServiceBootstrapOptions`. When `True`, the
  `agent_runtime_build` stage command gains `--no-cache`
  (`docker build --no-cache -t ... -f ... <root>`). Only affects the agent
  runtime image build stage; no effect when `skip_agent_runtime_build=True`
  (start forbids that combination at the CLI layer anyway). Default `False`
  preserves current stage output.

Both changes are guarded by focused bootstrap tests (see Tests).

### Failure translation (preserve structured bootstrap failures)

Add a pure, unit-testable helper
`_start_failure_payload(exc: ServiceBootstrapError) -> FirstRunPayload` that
classifies the structured bootstrap error into a START_* reason code while
**embedding the full `exc.to_dict()` diagnostic** (stage, command, returncode,
stdout, stderr, last_status) under issue `details["bootstrap"]` so existing
diagnostics are retained and redacted by the first-run renderer:

- `SERVICE_BOOTSTRAP_ASSETS_NOT_FOUND` → `START_COMPOSE_ASSETS_MISSING`.
- `SERVICE_BOOTSTRAP_TIMEOUT` → `START_HEALTH_TIMEOUT` (carries `last_status`).
- `SERVICE_BOOTSTRAP_STAGE_FAILED` with `stage == "migrate"` →
  `START_MIGRATION_FAILED` (preserves the Alembic/migrate stderr summary).
- `SERVICE_BOOTSTRAP_STAGE_FAILED` whose stdout/stderr matches a known Docker
  port-bind signature (e.g. "port is already allocated", "address already in
  use", "bind: address already in use", "failed to bind host port") →
  `START_PORT_CONFLICT`.
- Any other `SERVICE_BOOTSTRAP_STAGE_FAILED` → a first-run failure built
  manually (not via the catalog helper) that echoes the original
  `exc.reason_code` as the payload `reason_code` and derives
  problem/cause/fix/docs from the bootstrap message + stage, still embedding the
  full diagnostic. This guarantees no bootstrap failure is dropped or
  mislabeled.

Classified codes use `first_run_failure_payload(reason_code=START_*, summary=...,
details={"bootstrap": exc.to_dict(), ...})`; the port-conflict path adds the
detected port/stage to details. Failure output: JSON → stdout via `_emit`;
pretty → stderr via `render_first_run_pretty`; exit code 1 (matching the
placeholder/`service_bootstrap` convention). `KeyboardInterrupt` keeps exit 130.

### Success rendering (operator success panel)

Add a pure helper
`_start_success_payload(settings, result: ServiceBootstrapResult) ->
FirstRunPayload` building `first_run_success_payload(command="awf start", ...)`
with details:

- `api_url` — from `settings.api_base_url`, host normalized to `127.0.0.1` for
  first-run display (source-plan P2 note).
- `console_url` — `settings.console_url` when set, else
  `smoke.DEFAULT_LOCAL_CONSOLE_URL`, host normalized to `127.0.0.1`.
- `docker` — summarized from `result.service_status["checks"]["docker"]`
  (ok/version/reason).
- `providers` — summarized from `result.service_status["agent_readiness"]`
  (overall status + per-provider status); the first-run renderer redacts any
  provider refs/tokens so no secret leaks.
- `health` — overall `result.service_status["status"]`.

`next_steps` (provider-free primary action): `awf init <path>` to onboard a
repository, plus `awf service status` / the console URL for inspection. (T10 owns
the dedicated no-token smoke proof; start only points to onboarding here.)
Success output: pretty and JSON both to stdout; exit code 0.

### Registration / cleanup (`src/awf/cli/main.py`)

Update the `app.command("start", help=...)` help text to describe the real
command (start local AWF Core; mention it wraps existing bootstrap and that
`awf service bootstrap/status/doctor` remain expert commands). Remove the now-
dead `_start_placeholder_payload` / `START_PLACEHOLDER_REASON` from
`start_commands.py`. **Keep** the `AWF_START_PLACEHOLDER` reason code in
`rendering.py` / `reasons.py` / `FIRST_RUN_START_REASON_CODES` (still referenced
by the reason catalog and public-docs tests owned by T15/T18 — out of scope to
remove here).

`tests/unit/cli/test_start_commands.py`:

1. **Parser / help / dispatch**
   - `awf start --help` exits 0, advertises `--rebuild`,
     `--skip-agent-runtime-build`, `--timeout-seconds`, `--source-checkout`,
     `--format`, mentions local AWF Core, and has no traceback.
   - `--rebuild` together with `--skip-agent-runtime-build` exits 2 with the
     conflict message and never calls bootstrap.
2. **Bootstrap delegation (fake bootstrap runner)**
   - Monkeypatch the bootstrap entrypoint the command calls with a fake that
     records the `ServiceBootstrapOptions` (and `asset_root`/`compose_file`) and
     returns a canned `ServiceBootstrapResult`. Assert flags map correctly:
     `--timeout-seconds` → `timeout_seconds`; `--skip-agent-runtime-build` →
     `skip_agent_runtime_build=True`, `force_rebuild=False`; `--rebuild` →
     `force_rebuild=True`, `skip_agent_runtime_build=False`; defaults →
     both `False`.
   - Success path: JSON output has `status="success"`, `command="awf start"`,
     and details containing `api_url`, `console_url` (both `127.0.0.1`),
     `docker`, `providers`, `health`; exit 0. Pretty success goes to stdout with
     a readable panel and next commands.
3. **Source asset selection**
   - `awf start --source-checkout <valid tmp checkout>` (built from a fixture
     that satisfies `SOURCE_CHECKOUT_MARKERS`) passes `asset_root=<root>` and
     `compose_file=<root>/docker/compose/local-service.yml` into the fake
     bootstrap.
   - `--source-checkout <missing markers>` → exit 1, `SOURCE_CHECKOUT_INVALID`,
     `missing_markers` present, **bootstrap never called** (no silent fallback).
   - Stored-config-metadata path: with a fake `read_host_setup_config` returning
     stale `source_checkout` metadata and no `--source-checkout`, start exits 1
     with `SOURCE_CHECKOUT_ASSETS_STALE` and does not call bootstrap; with no
     metadata it falls through to default discovery (bootstrap called with
     `asset_root=None`).
4. **Structured bootstrap failure preservation**
   - Fake bootstrap raising `ServiceBootstrapError(SERVICE_BOOTSTRAP_STAGE_FAILED,
     stage="migrate", returncode=1, stderr="alembic ...")` → output
     `START_MIGRATION_FAILED`, exit 1, details preserve stage/returncode/stderr.
   - Port-conflict stderr ("port is already allocated") on a stage failure →
     `START_PORT_CONFLICT`, diagnostics preserved.
   - `SERVICE_BOOTSTRAP_TIMEOUT` → `START_HEALTH_TIMEOUT` with `last_status`
     preserved; `SERVICE_BOOTSTRAP_ASSETS_NOT_FOUND` →
     `START_COMPOSE_ASSETS_MISSING`; an unclassified stage failure echoes the
     bootstrap reason code and keeps the diagnostic.
   - Redaction: a token-shaped/provider-ref value injected into the bootstrap
     error stderr or provider summary is redacted in both JSON and pretty output.
5. **Pure helper unit tests** for `_start_success_payload` and
   `_start_failure_payload` (no CLI) covering the classification table and URL

## Risks, Assumptions, And Non-Goals

Assumptions (flagged for reviewer confirmation):

- **`--rebuild` semantics.** Interpreted as "rebuild the agent-runtime image from
  scratch, bypassing the Docker layer cache" via a scoped
  `ServiceBootstrapOptions.force_rebuild` flag, and made mutually exclusive with
  `--skip-agent-runtime-build`. Fallback if review prefers zero bootstrap
  change: `--rebuild` simply *ensures* the agent-runtime build stage runs
  (`skip_agent_runtime_build=False`), making it the explicit inverse of the skip
  flag with no `--no-cache`. The plan picks the `--no-cache` interpretation
  because a flag that merely restates the default would be a poor CLI surface.
- **Console URL.** `settings.console_url` is optional; when unset, start uses
  `smoke.DEFAULT_LOCAL_CONSOLE_URL` (`http://localhost:3000`) and displays the
  host as `127.0.0.1`. Start does not introduce a new console default constant.
- **Stored-config consumption.** Start honors `HostSetupConfig.source_checkout`
  metadata when `--source-checkout` is absent (failing loudly on staleness).
  Start never *writes* config (setup owns writes per T02/T04); a corrupt/missing
  config is tolerated as "no source selection" only when source assets were not
  explicitly requested.

Risks / mitigations:

- *Bootstrap behavior regression.* New `asset_root`/`force_rebuild` are
  defaulted off and covered by dedicated tests; the existing `service_bootstrap`
  command path is unchanged. Mitigation: assert current stage output is
  byte-identical when both default.
- *Asset-root pinning mismatch with compose env-file resolution.* The hook must
  derive the compose env file from the pinned root (mirroring
  `_resolve_compose_env_file`) rather than from discovery. Covered by a pinned
  bootstrap test.
- *Coverage gate (99%).* Every new branch (each classification arm, each
  precedence arm, the conflict guard) gets an explicit test; the pure helpers
  are tested without the CLI to keep branches reachable.
- *Output-stream/exit-code drift.* Failure pretty→stderr / JSON→stdout / exit 1
  and success→stdout / exit 0 conventions are asserted to match the established
  first-run command behavior.

Non-goals (owned elsewhere; explicitly out of scope for T05):

- Reworking `awf setup` or its dry-run system checks — **T04**.
- Package/wheel bootstrap-asset *inclusion* and packaging metadata — **T13**.
- No-token local smoke proof / mocked smoke path — **T10**.
- New setup/start/init MCP tools — **T09**.
- README/quickstart/upgrade/uninstall docs and docs-drift grammar tests —
  **T15/T18** (including removal of `AWF_START_PLACEHOLDER` doc language).
- Provider credential capture/orchestration — **T06/T07**.
- Any broad AWF/GitHub validation run during the agent phase (AWF owns it).
