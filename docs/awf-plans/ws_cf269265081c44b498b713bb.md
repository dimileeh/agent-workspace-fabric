# Plan: Alembic Target-Branch Resolver Integration Slice

## Goal

Implement a focused P0 integration test slice proving that AWF detects the
post-merge Alembic multi-head state created by independently merged workspace
PRs, generates a deterministic and safe merge revision when configured to do so,
and reports enough structured information for operators through resolver
results, monitor results, logs, and workspace events.

Use strict TDD: add the failing tests first, confirm the red state when
practical, then make the smallest production changes needed to pass without
lowering quality or coverage thresholds.

## Current Anchors

- Alembic graph inspection and merge-revision rendering live in
  `src/awf/service/alembic_resolver.py`.
- Target-branch checkout, resolver execution, staging, commit, and push logic
  live in `src/awf/service/target_branch_monitor.py`.
- Post-merge monitor event/log plumbing lives in
  `src/awf/runtime/pr_monitor_runner.py`, especially
  `_reconcile_target_branch_after_merge()` and `_target_reconcile_payload()`.
- Existing resolver unit tests live in
  `tests/unit/service/test_alembic_resolver.py`.
- Existing target-branch monitor unit tests live in
  `tests/unit/service/test_target_branch_monitor.py`.
- Existing runtime event tests live in
  `tests/unit/runtime/test_pr_monitor_runner_coverage_edges.py`.
- The new end-to-end slice should use temporary git repositories and Alembic
  files under `tmp_path`; it should not call real GitHub.

## Tests To Write First

1. Integration no-op test in
   `tests/integration/test_alembic_target_branch_resolver.py`:
   - Build a temporary git origin with `alembic.ini`, one migrations directory,
     and a linear migration chain.
   - Run `TargetBranchReconcileMonitor.reconcile()` on the target branch.
   - Assert status is `clean`, resolver result is `ALEMBIC_SINGLE_HEAD`, no
     generated merge revision exists, no follow-up commit is added, and no push
     occurs beyond the monitor's checkout/fetch behavior.

2. Integration multi-head repair test:
   - Create two independent branch histories from the same base migration,
     each adding a different Alembic revision with the same `down_revision`.
   - Merge both into the temporary target branch so Alembic has two heads but
     git has no content conflict.
   - Run reconciliation with commit policy enabled.
   - Assert the generated merge revision is deterministic for the sorted heads,
     its `down_revision` tuple contains both head revision IDs in stable order,
     Alembic now reports a single head, the generated file is staged and
     committed, the pushed target branch contains the follow-up commit, and the
     commit message matches the existing conventional migration format.

3. Unit malformed/unsafe graph refusal tests in
   `tests/unit/service/test_alembic_resolver.py`:
   - Invalid Python in a revision file returns a structured refusal/unsupported
     result with a stable reason code and does not write a merge revision.
   - A revision that references a missing `down_revision`, duplicates a
     revision ID, or otherwise makes Alembic's graph unsafe returns a structured
     reason and does not mutate files.
   - The result serializes status, reason code, message/details, and the absence
     of generated revision/path.

4. Unit commit-policy tests in
   `tests/unit/service/test_target_branch_monitor.py`:
   - When policy permits commits, a changed resolver result causes only the
     generated relative path to be added, then committed and pushed.
   - When policy forbids commits, the resolver may report what it would generate
     but the monitor does not stage, commit, or push; result status remains a
     dry-run/policy-blocked outcome with structured reason.
   - `dry_run=True` continues to avoid git write operations even when policy
     would otherwise permit a commit.

5. Operator visibility tests:
   - `TargetBranchMonitorResult.to_dict()` includes nested resolver details:
     status, reason code, heads, generated revision, generated path, and
     operator-readable message.
   - `_reconcile_target_branch_after_merge()` appends
     `target_branch.reconciled` events whose payload preserves the above
     details plus commit SHA, pushed flag, target branch, and repo URL.
   - Failure/refusal payloads preserve stable reason codes without relying on
     unstructured exception text.

## Implementation Sequence

1. Add temporary Alembic/git helper functions in the new integration test file:
   write `alembic.ini`, write revision files, run git commands with
   `subprocess.run(check=True)`, create a bare origin, and create/merge
   independent migration branches into a target branch.
2. Add the no-op integration test and confirm it passes or identifies any
   missing result assertions. This locks down the single-head behavior before
   touching production code.
3. Add the multi-head integration test with deterministic revision ID
   expectations. Confirm it fails on any missing determinism, commit-policy, or
   result payload behavior.
4. Add malformed/unsafe graph unit tests. Confirm they fail where the resolver
   currently treats unsafe graphs as generic unreadable output or mutates files.
5. Add target-branch commit-policy and operator-payload unit tests. Confirm the
   red state for policy and event/log visibility gaps.
6. Update `AlembicMergeResolver` minimally:
   - sort heads once and pass the sorted tuple through result/rendering;
   - validate the loaded Alembic graph before writing;
   - return stable reason codes for malformed/unsafe graphs;
   - keep generated revision IDs sanitized and deterministic for identical head
     sets in tests.
7. Update `TargetBranchReconcileMonitor` minimally:
   - introduce or wire an explicit commit permission/policy if one does not
     already exist;
   - ensure generated files are added by relative path only when commits are
     permitted;
   - preserve existing `dry_run` behavior;
   - include sufficient structured data in `to_dict()`.
8. Update runtime event/log payload handling only if nested reconciliation data
   is dropped or flattened too aggressively.
9. Run focused validation, then the requested full validation commands.
10. Commit locally after implementation in the later implementation phase using
    conventional commits. Do not push, rebase, or switch branches.

## Risks

- Alembic's own exceptions can vary by malformed graph type. Tests should assert
  AWF's stable reason codes and only minimal message content.
- Temporary git integration tests can become flaky if branch names, user config,
  or default-branch assumptions leak from the host. Set local git config inside
  each temp repo and create branches explicitly without touching AWF's branch.
- The current resolver writes files as soon as it detects multiple heads. Unsafe
  graph tests must verify no mutation occurs before any production refactor.
- Deterministic revision IDs must still avoid collisions and remain valid
  Alembic revision identifiers.
- Adding a commit policy surface could break CLI/worker callers if defaults are
  not backward-compatible.
- Operator payloads can become too noisy. Include enough resolver details for
  diagnosis while keeping existing event field names stable.

## Assumptions

- "Independent PRs merge" can be represented by local temporary git branches
  merged into a temporary target branch; no real GitHub API is needed.
- The existing `dry_run=True` path is part of "policy forbids commit", but the
  implementation may need a more explicit policy flag/default to satisfy the
  requirement that generated revisions are committed only when configured.
- `ALEMBIC_SINGLE_HEAD`, `ALEMBIC_HEADS_MERGED`, and
  `ALEMBIC_GRAPH_UNREADABLE` are existing stable reason-code anchors; new
  reason codes should be additive if malformed/unsafe graphs need finer
  distinction.
- It is acceptable for integration tests to shell out to local `git` and use
  generated Alembic files, but not to depend on Docker, Postgres, or networked
  remotes.
- Production code should remain generic AWF behavior and must not introduce
  Aira-specific migration paths or branch names.

## Explicit Non-Goals

- Do not implement a full GitHub PR lifecycle, real PR merges, or GitHub status
  checks for this slice.
- Do not add Docker, Postgres, or service-stack dependencies to the new
  integration tests.
- Do not redesign the entire target-branch monitor or stale-candidate refresh
  flow.
- Do not change Alembic migration files for AWF's own database schema.
- Do not lower coverage, ruff, mypy, or pytest quality thresholds.
- Do not push, rebase, switch branches, or commit during the planning phase.
