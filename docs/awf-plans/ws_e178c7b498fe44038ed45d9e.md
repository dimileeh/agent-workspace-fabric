# Plan — Wire agent-container BitBucket git-over-HTTPS auth (closes #465 + #466)

Workspace: `ws_e178c7b498fe44038ed45d9e`
Closes **#465** and **#466** (duplicate reports — Cursor + Codex flagged the same
gap on PR #464) with **one** fix.

## Problem / root cause

The **worker** git path can already clone/fetch/push private `bitbucket.org`
repos over HTTPS (#461/#464; sentinel username fixed in #467) via a host-scoped
credential helper rendered into the worker's git env
(`apply_bitbucket_git_auth` in `common/git_auth.py`, called from
`service/worker.py:415`).

The **agent** container cannot. `node/secret_mounts.py`
`_resolve_bitbucket_secret` (~line 280) injects only the env-var pair
`("BITBUCKET_API_TOKEN", "${BITBUCKET_API_TOKEN}")` into the agent env (the
resolve loop, ~lines 178–190). Plain git over HTTPS does **not** consult that
env var by itself, so an agent doing `git clone/fetch/push` against
`bitbucket.org` hangs on a credential prompt or fails. GitHub works agent-side
only because `gh`/`git` pick up `GH_TOKEN` natively; BitBucket has no native
pickup.

## Mechanism (engineering-reviewed): askpass file + URL username rewrite

The agent env crosses four layers (Jinja2 template → YAML →
docker-compose `${VAR}` interpolation → container shell). Rendering a
token-referencing **shell credential helper** through that stack (the worker's
mechanism) is fragile here and risks leaking the token into the rendered
`compose.yml`. Instead the agent path uses a design that is **leak-proof by
construction**:

1. **Static askpass script** materialized per workspace, mounted read-only +
   executable into the agent. Content (no token, only an env-var *name*):

   ```sh
   #!/bin/sh
   printf '%s' "$BITBUCKET_API_TOKEN"
   ```

   It reads the token from the **container runtime env** at git call time. The
   agent env sets `GIT_ASKPASS=/run/awf/secrets/bb-askpass.sh`.

2. **Username via URL rewrite (`insteadOf`)** — rewrite any `bitbucket.org`
   remote (HTTPS form **and both** SSH-form shapes) to
   `https://x-bitbucket-api-token-auth@bitbucket.org/...`. The sentinel username
   is **not secret**, so embedding it in the URL is safe; git then asks
   `GIT_ASKPASS` only for the password (the token). The sentinel matches the
   worker fix in #467.

3. **Agent env additions**: `GIT_ASKPASS=<path>`, `GIT_TERMINAL_PROMPT=0`, and
   the `insteadOf` `GIT_CONFIG_KEY_n/VALUE_n/COUNT` entries (plain URLs — no
   token, no shell syntax), **accumulated** onto any existing `GIT_CONFIG_COUNT`
   via the existing `add_git_config_entries`.

The token VALUE never appears in any rendered string (compose YAML, git-config,
askpass script) — only at runtime in the container env, supplied by the existing
`${BITBUCKET_API_TOKEN}` lease pair.

**Divergence is intentional:** the worker path keeps its existing
credential-helper (no compose layer; already works) and is left **byte-for-byte
unchanged**. Document the two-mechanism split in both modules.

## Intended files/modules to touch

### `src/awf/common/git_auth.py` (agent helpers; worker entries unchanged)
Add a small, self-contained agent-side API alongside the existing worker API:

- Constant `_BITBUCKET_GIT_USERNAME` is reused (already
  `x-bitbucket-api-token-auth`). Add the sentinel-prefixed base URL constant
  `https://x-bitbucket-api-token-auth@bitbucket.org/`.
- `bitbucket_askpass_script(token_env_var: str) -> str` — returns the **static**
  `#!/bin/sh` + `printf '%s' "$<token_env_var>"` content. Contains no token
  value; references exactly the env-var **name** passed in (the agent-side
  injected key, not an alias).
- `bitbucket_agent_git_config_entries() -> tuple[tuple[str, str], ...]` — the
  three `insteadOf` rewrites onto key
  `url.https://x-bitbucket-api-token-auth@bitbucket.org/.insteadOf` with values
  `https://bitbucket.org/`, `git@bitbucket.org:`, `ssh://git@bitbucket.org/`
  (HTTPS + both SSH-form shapes; `insteadOf` is multi-valued). No credential
  helper, no token, no shell syntax. (Rewrite target carries the sentinel
  username prefix so git does not re-apply the rule — no loop.)
- `apply_bitbucket_agent_git_auth(env, *, askpass_path, token_env_var) -> None`
  — sets `env["GIT_ASKPASS"]=askpass_path`, `env["GIT_TERMINAL_PROMPT"]="0"`,
  and calls `add_git_config_entries(env, bitbucket_agent_git_config_entries())`
  (accumulating onto existing `GIT_CONFIG_COUNT`). The token name only flows into
  the askpass *script content* (produced separately), never into `env`.
- Module docstring: note the worker (credential-helper) vs agent (askpass +
  insteadOf) divergence and why.

### `src/awf/node/secret_mounts.py` (materialize + mount + emit, only when token injected)
- New module constants: `_BITBUCKET_GIT_TOKEN_TARGET = "BITBUCKET_API_TOKEN"`,
  `_BITBUCKET_ASKPASS_TARGET = "/run/awf/secrets/bb-askpass.sh"` (already under a
  `_SAFE_SECRET_MOUNT_PREFIXES` prefix), and a per-workspace subdir name
  (e.g. `secret-leases`).
- In `resolve()` bitbucket branch (~178–190): after appending the token
  placeholder pair, when the **injected** target is the token target
  (`pair[0] == _BITBUCKET_GIT_TOKEN_TARGET`), call a new private helper
  `_materialize_bitbucket_agent_askpass(env, mounts, workspace_id, token_env_var=pair[0])`
  that:
  1. writes the static askpass script to
     `self.work_dir / "secret-leases" / workspace_id / "bb-askpass.sh"`
     (`mkdir(parents=True, exist_ok=True)`; idempotent re-write), then
     `os.chmod(path, 0o555)` (world read+execute; bind-mount preserves host mode
     so the agent — uid 1000 — can execute it; no chown needed for a
     non-secret, world-readable script);
  2. appends `AuthMount(source=str(path), target=_BITBUCKET_ASKPASS_TARGET,
     mode="ro")` to `mounts`;
  3. calls `apply_bitbucket_agent_git_auth(env,
     askpass_path=_BITBUCKET_ASKPASS_TARGET, token_env_var=pair[0])`.
- Gate strictly on the **token** target being injected (independent of
  `BITBUCKET_EMAIL`): the agent askpass needs only the token; the sentinel
  username replaces the email for git. Email lease (REST basic auth) is
  unaffected.
- Mount source path uses `work_dir` directly, matching the existing
  `auth_mounts_claude` convention where the worker `work_dir` is host-equal for
  bind-mount sources (the rendered compose binds these source paths verbatim;
  see `compose_manager.render` `auth_mounts` and the template line
  `"{{ m.source }}:{{ m.target }}:{{ m.mode }}"`).
- The resolver runs under `asyncio.to_thread` (`stack_launcher.launch`), so the
  filesystem writes are safe off the event loop.

## Risks / assumptions / non-goals

**Assumptions**
- `LocalSecretLeaseMountResolver.work_dir` is host-equal for bind-mount sources
  (verified: `auth_mounts_claude` builds `AuthMount.source` from `work_dir`
  directly with no host-path translation). If a host-path translation is in fact
  required, mirror whatever `auth_mounts` does — but no evidence one exists.
- A `0o555` host file bind-mounted `ro` is executable by the agent (uid 1000):
  bind mounts preserve host inode permissions; world-x covers any owner.
- `git ls-remote --get-url` applies `insteadOf` offline (documented git
  behavior) — the test asserts the rewrite without network.

**Risks**
- `insteadOf` rewrite-loop: avoided because the rewrite target carries the
  sentinel-username prefix and so never matches the bare `https://bitbucket.org/`
  source rule again. Covered by the `--get-url` test.
- askpass returning the token as a *username*: avoided because the sentinel
  username is in the URL (so git only prompts for the password). Documented.
- Leftover per-workspace `secret-leases/<id>/bb-askpass.sh` dir after teardown:
  the script holds **no** secret, so a leftover is not a leak; cleanup can ride
  existing `work_dir` GC. Note as a possible follow-up; **not** expanded here to
  keep the diff scoped.
- Existing exact-tuple test breaks for the bitbucket case — expected and updated;
  it is a semantic, intended change, not a regression.

**Non-goals (explicitly out of scope)**
- The worker git path (left byte-for-byte unchanged).
- Backfilling already-running workspaces.
- `x-token-auth` Access Tokens (only Atlassian API tokens via the sentinel
  `x-bitbucket-api-token-auth` username).
- Any console/docs/profile changes beyond the in-module docstring divergence
  note.

**Never log/leak the token.** All new strings reference env-var *names* only;
the leak-proof boundary test enforces this at the rendered/launched edge.
