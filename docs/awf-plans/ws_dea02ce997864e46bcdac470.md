# Issue #300: --companion-env-from and --companion-env-exclude flags

## Summary

Add two repeatable CLI flags to `awf workspace create` that read a companion's local `.env` file and merge it into that companion's `environment` block — removing the need to hand-copy every env var into the dispatch JSON.

## Current State (verified)

- `awf workspace create` accepts `--companion-json <json>` (repeatable) in `src/awf/cli/workspace_commands.py`. Each JSON is parsed by `_parse_json_option()` in `src/awf/cli/common.py` and sent as the `companions` list in the POST body.
- Companion env validation rules exist in `src/awf/api/schemas_companions.py`:
  - Keys must match `^[A-Za-z_][A-Za-z0-9_]*$` (the `EnvironmentKey` annotated type).
  - Values must NOT contain Docker Compose interpolation (`$VAR` or `${VAR}`).
  - `environment` and `environment_secrets` keys must not overlap.
- Node-layer validation in `src/awf/node/companion_services.py` (`_resolve_environment_sections()`) enforces the same rules at runtime.
- `python-dotenv>=1.0.0` is already a dependency; `src/awf/service/environment.py` uses `dotenv_values()` for compose `.env` parsing.
- Redaction helpers exist in `src/awf/common/redaction.py` (`redact_secrets()`).

## New Flags

1. **`--companion-env-from <name>=<path>`** (repeatable): Reads the `.env` file at `<path>` and merges its key-value pairs into the companion whose `name` matches `<name>`. Explicit values already in `--companion-json` WIN over file values (file fills gaps; it never clobbers).
2. **`--companion-env-exclude <name>=<KEY1,KEY2,...>`** (repeatable): Drops the named keys for that companion after reading the file.

## New Module: `src/awf/cli/companion_env.py`

A client-side helper module (NOT in the API/server layer). Contains:

### `parse_env_file(path: Path) -> dict[str, str]`

- Expands `~` and `$ENV_VAR` in `path` using `os.path.expanduser` and `os.path.expandvars`.
- Uses `dotenv_values(str(path))` from python-dotenv for parsing (reuses the existing dependency).
- Strips a leading `export ` prefix from lines (dotenv handles this natively).
- Returns a `dict[str, str]` of parsed key-value pairs, excluding entries with `None` values (unset dotenv lines).
- Raises `CompanionEnvError` (a custom exception) with a clear message on file-not-found or permission errors.

### `parse_companion_env_arg(raw: str, flag_name: str) -> tuple[str, str]`

- Validates and splits `<name>=<value>` format.
- Raises `CompanionEnvError` with an actionable message on malformed input (missing `=`, empty name).

### `parse_companion_env_exclude_arg(raw: str) -> tuple[str, list[str]]`

- Validates and splits `<name>=<KEY1,KEY2,...>` format.
- Raises `CompanionEnvError` on malformed input.

### `validate_env_keys(keys: Iterable[str], source_desc: str) -> list[tuple[str, str]]`

- Checks each key against `EnvironmentKey` regex (`^[A-Za-z_][A-Za-z0-9_]*$`), importing the pattern from `schemas_companions` to maintain single source of truth.
- Checks each value for Docker Compose interpolation (`$VAR` or `${VAR}`), reusing `_value_has_compose_interpolation()` logic from `schemas_companions`.
- Returns a list of `(key, reason)` tuples for keys/values that would be rejected.
- Does NOT print/log values — only key names and rejection reasons.

### `merge_companion_env(companions: list[dict], env_from: list[str], env_exclude: list[str]) -> list[dict]`

- The main merge function called from `workspace_create`.
- For each `--companion-env-from`, parse the arg, find the matching companion by name, parse the env file, validate keys, warn on invalid keys (to stderr, key names only, never values), merge (payload wins over file), then apply `--companion-env-exclude` exclusions.
- Raises `CompanionEnvError` (→ exit 2) when: companion name not found in any `--companion-json`; file path does not exist or is unreadable; malformed argument.
- Returns the modified companions list.

## Changes to Existing Files

### `src/awf/cli/workspace_commands.py`

- Add two new `typer.Option` parameters to `workspace_create`:
  - `companion_env_from: list[str] | None` with `--companion-env-from`
  - `companion_env_exclude: list[str] | None` with `--companion-env-exclude`
- After building `body["companions"]` from `--companion-json`, call `merge_companion_env()` to apply env-from and env-exclude.
- Wrap in try/except for `CompanionEnvError` → `typer.echo(err, err=True); raise typer.Exit(2)`.
- Add help text documenting the flags and merge precedence.

### `src/awf/api/schemas_companions.py`

- **Export** the `EnvironmentKey` regex pattern and `_value_has_compose_interpolation` function so the CLI can reuse them for client-side validation. Currently they are module-level; we add `__all__` or explicit re-exports. No behavioral change.

### No changes to:
- `src/awf/node/companion_services.py` (server-side validation stays unchanged)
- `src/awf/api/` (the API never sees `.env` paths; this is client-side only)
- `openapi.json` (no schema changes)

## Risks & Assumptions

- **Risk:** python-dotenv's `dotenv_values()` may interpret `.env` files differently than expected (e.g., multiline values). Mitigation: test edge cases; document exactly what syntax is supported.
- **Risk:** Path expansion on Windows may behave differently. Mitigation: `os.path.expanduser` and `os.path.expandvars` are cross-platform; document that only Unix-style `~` expansion is tested.
- **Assumption:** The `EnvironmentKey` regex and `_value_has_compose_interpolation` from `schemas_companions.py` are the canonical validation rules. Reusing them via import keeps a single source of truth.
- **Assumption:** `dotenv_values()` handles `export`, comments, blank lines, and quoted values correctly (it does — this is what python-dotenv is designed for).
- **Assumption:** The CLI is the only place this feature is needed; no need to add it to the API or workspace YAML profile.

## Explicit Non-Goals

- Reading AWF's own service `.env` — explicitly out of scope per the issue.
- Secret storage or management — the flag is read-only.
- Server-side `.env` reading — the API cannot access the operator's filesystem.
- Changing the `environment_secrets` contract — this feature only populates the `environment` dict, not `environment_secrets`.
- Adding `.env` file support to `workspace.yml` profiles — that's a separate concern.
