# Plan: Stop Terminal Runtime Resources Without Destroying Salvage Evidence

## Goal

Fix the P0 regression where a workspace reaches terminal state but keeps live runtime containers/networks, blocking `/readyz` and orphan-resource checks. Terminal failed, cancelled, completed, and destroyed workspaces must release scheduler reservations and stop/remove live runtime containers/networks while preserving salvage evidence: logs, artifacts, worktree/branch metadata, failure diagnostics, validation/conformance evidence, and operator recovery metadata.

## Current Context

- `WorkspaceRepository.transition()` and `transition_if_current()` already release active `ResourceReservation` rows for `completed`, `failed`, `cancelled`, and `destroyed` via `_releases_resource_reservation()`.
- Runtime cleanup is not consistently tied to terminal transitions:
  - `WorkspaceControlService.destroy_workspace()` performs explicit destructive cleanup.
  - `WorkspaceControlService.cancel_workspace()` can stop containers only when `stop_stack=true`, and uses `docker stop` rather than compose teardown/network release.
  - `ControlWorker._cleanup_and_fail_stale_active_execution()` cleans before marking stale active workspaces failed, but currently removes volumes and does not represent the general terminal cleanup contract.
  - `PullRequestMonitorRunner._terminate_completed()` tears down compose only on completed PR monitor paths, and explicitly avoids failed teardown.
  - `WorkspaceExecutor._mark_failed()` records failed state without a terminal runtime release step.
- Readiness/status scanners treat recent terminal resources as retained too broadly; retained terminal worktrees are valid salvage evidence, but terminal containers/networks are leaked live runtime resources.

## Tests To Write First

1. Terminal runtime release service tests

- Add a focused fake cleaner test proving a terminal failed workspace calls cleanup with:
  - `remove_worktree=False`
  - `remove_volumes=False`
  - persisted `compose_project_name` and `compose_file_path`
- Assert existing `failure_reason`, `failure_message`, branch metadata, PR metadata, logs/artifacts paths, and worktree path are not removed or overwritten.
- Assert cleanup success records a `workspace.terminal_runtime_released` event with structured cleanup evidence.
- Assert cleanup failure records `workspace.terminal_runtime_release_failed` and does not overwrite the original failure diagnostics with `cleanup_failure`.

2. Conformance failure regression

- Extend the existing conformance-stall/failure executor test path so after the workspace transitions to `failed`, a fake terminal runtime releaser is called once.
- Assert the failure event still includes conformance details/salvage payload and the workspace failure reason remains the primary conformance/agent failure.
- Assert the preserved worktree path remains present in salvage metadata.

3. Validation failure regression

- Add an executor validation failure test that drives `validating -> failed` and asserts terminal runtime release is invoked with preserve-evidence cleanup.
- Assert validation run/evidence artifacts remain recorded and failure diagnostics are unchanged by runtime release.

4. Stale-active failure regression

- Update/add `ControlWorker._cleanup_and_fail_stale_active_execution()` coverage so stale active cleanup uses `remove_worktree=False` and `remove_volumes=False`.
- Assert successful cleanup is followed by `failed` transition and reservation release remains handled through repository transition.
- Add/extend cleanup failure coverage proving failed cleanup keeps the row active, emits cleanup-failed evidence, and does not create a terminal failed row with unreleased runtime.

5. Cleanup failure regression

- Add a terminal runtime release failure test where compose cleanup returns partial/fails.
- Assert the workspace remains in its primary terminal state, original failure cause is preserved, a cleanup-failure event is present, and readiness/orphan checks would still classify the remaining terminal container/network as a leaked live resource.

6. Preserved-worktree salvage path

- Add scanner and `/readyz` tests where a recent terminal workspace has only a managed worktree (and, if policy allows, retained volume) and readiness stays green with retained-evidence counts/reasons.
- Add the inverse test where a recent terminal workspace has a container and/or network; readiness fails even within retention, with a reason like `TERMINAL_LIVE_RUNTIME_RESOURCE` instead of treating it as retained evidence.
- Add GC dry-run assertions that preserved failed worktrees/logs/artifacts are reported as retained salvage evidence and are not deletion candidates merely to make readiness green.

## Implementation Approach

1. Introduce a small terminal runtime release coordinator

- Add `awf.service.terminal_runtime` with a narrow async function/class that accepts a session factory, workspace id, cleaner factory, and expected terminal status/reason.
- It should load current workspace metadata, no-op if the workspace is missing or no longer terminal, and call the existing `WorkspaceCleaner.cleanup()` with `remove_worktree=False` and `remove_volumes=False`.
- It should preserve volumes initially as runtime/salvage data; later filesystem/volume reclamation remains the GC/retention job.
- It should record structured success/failure events without changing the primary terminal failure reason/message.
- It should be idempotent enough for retry: if no compose project/resources exist, record skipped/succeeded cleanup evidence rather than raising.

2. Wire terminal release at terminal transition owners

- In `WorkspaceExecutor`, add an optional terminal releaser dependency for tests and production defaulting to the new coordinator. Call it after successful terminal commit from `_mark_failed()` and no-monitor `completed` paths.
- In `PullRequestMonitorRunner`, replace completed-only teardown semantics with terminal release for both `_terminate_completed()` and `_terminate_failed()`. Keep completed filesystem GC only after terminal runtime release succeeds.
- In `ControlWorker`, keep cleanup before stale-active failure, but preserve worktree and volumes. Record the same release evidence shape when cleanup succeeds/fails.
- In `WorkspaceControlService`, make cancel/stop terminal paths use preserve-evidence runtime release semantics rather than only `docker stop`; keep explicit destroy behavior destructive only when the operator requested destroy/removal.

3. Keep reservation release centralized

- Do not duplicate reservation-release logic in every caller unless a test exposes a direct terminal-status assignment bypassing `WorkspaceRepository.transition()`.
- Add/keep repository-level regression tests proving `completed`, `failed`, `cancelled`, and `destroyed` release active reservations.

4. Fix retained-evidence vs leaked-live classification

- Update `orphan_resources.py` and `orphans.py` so terminal worktrees are retained evidence within retention and terminal containers/networks are live leaks regardless of retention.
- Decide volume behavior conservatively: preserve terminal volumes within retention as retained evidence only if the retention policy says they are salvage data; otherwise classify them as cleanup-ready retained runtime. The first implementation should make the distinction explicit in payloads either way.
- Add payload fields such as `retained_evidence_count`, `retained_evidence_counts_by_kind`, and/or `leaked_live_counts_by_kind` while preserving existing fields for compatibility.
- Update `/readyz` and service status response schemas/helpers to expose the new fields.

5. Update GC/dry-run output

- Ensure terminal GC plan output states whether a preserved workspace is preserved for salvage/retention versus blocked by leaked live runtime.
- Keep logs/artifacts/worktrees outside deletion candidates for failed workspaces until policy expiry or explicit destroy; do not delete evidence to clear readiness.

## Risks

- Terminal cleanup side effects can accidentally mask the original failure cause if cleanup failures overwrite `failure_reason` or terminal state details. Tests must assert primary diagnostics survive.
- Existing tests or operator flows may rely on failed workspaces retaining running containers for inspection. This task intentionally changes that: salvage evidence remains, but live containers/networks must be released.
- Docker compose teardown without `--volumes` should remove containers/networks while preserving named volumes; this must be verified in `ComposeManager` behavior and tests.
- Adding new readiness fields can affect OpenAPI snapshots and any console/status consumers. Preserve existing keys and only add fields where possible.
- There are several terminal transition owners. Missing one path could leave another leak class. Tests should cover executor, monitor, worker, and operator-control paths.
- Cleanup failure handling must avoid creating retry loops that hide reason codes; event payloads should include structured cleanup result details.

## Assumptions

- Existing repository transition reservation release is correct and should remain the single source of truth for scheduler reservation release.
- Worktrees, logs, artifacts, branch metadata, PR metadata, validation runs, and conformance payloads are salvage evidence and must not be removed by terminal runtime release.
- Runtime containers and networks are live resources, not salvage evidence, and should not be retained after terminal states.
- Volumes may contain salvage-relevant runtime state; the initial implementation should preserve them within retention unless the existing profile/cleanup policy explicitly marks them reclaimable.
- AWF-managed compose labels/project names are sufficient for cleanup and readiness classification.

## Explicit Non-Goals

- Do not change DB connection retry policy.
- Do not implement broader primary failure-causality preservation beyond ensuring terminal runtime cleanup does not overwrite existing diagnostics.
- Do not remove preserved worktrees, logs, artifacts, branch metadata, validation/conformance evidence, or retained volumes merely to make readiness green.
- Do not redesign the workspace state machine or scheduling model.
- Do not implement cloud secret broker/profile security work outside the terminal cleanup/release path.
- Do not push, rebase, branch-switch, or open the PR manually in this planning phase; AWF owns that workflow after implementation.
