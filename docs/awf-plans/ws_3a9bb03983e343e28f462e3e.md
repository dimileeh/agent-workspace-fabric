# Plan: Contract Tests For REST / CLI / MCP Parity

## Objective

Implement the P1 backlog slice "Add contract tests proving REST API, CLI, and MCP stay aligned" by turning the existing contract capability registry into the executable source of truth for AWF's implemented safe read/control surfaces.

The completed slice should prevent silent drift in REST route metadata, CLI command/flag shape, MCP tool schemas, request field names, response envelope fields, public reason codes, idempotency-key requirements, optimistic concurrency / workspace-version semantics, auth failure shape, and structured terminal errors.

## Current Findings

- `tests/unit/contracts` already exists and includes a registry in `tests/unit/contracts/_capabilities.py`, but it is currently centered on mutating workspace/control capabilities plus create/adoption.
- Read-only REST/MCP parity is covered separately in `tests/unit/mcp/test_mcp_operator_surfaces.py`; that coverage is useful but is not driven by the contract registry.
- `docs/MCP_CLIENT_PARITY.md` is already parsed by tests and documents implemented, partial, missing/backlog, CLI-absent, and out-of-scope surfaces.
- Existing contract tests cover pieces of idempotency, If-Match, auth failures, reason-code alignment, and structured envelopes, but several tests are hard-coded to specific capabilities instead of proving every implemented safe read/control surface.
- Likely drift to validate with tests first: MCP idempotency-key optionality may not match REST-required control semantics on all mutating controls, and CLI coverage/absence needs to be explicitly asserted from the matrix rather than skipped.
- Coordination warning: implementation will likely touch files that overlap active workspaces, especially `src/awf/api/routes/workspaces.py`, `src/awf/mcp/server.py`, `src/awf/cli/main.py`, `tests/unit/api/**`, `tests/unit/mcp/**`, and `tests/unit/cli/**`. Re-check worktree and target-branch state before implementation edits.

## Tests To Write First

1. Registry completeness failure
   - Add/strengthen a test that loads `docs/MCP_CLIENT_PARITY.md` and fails for any safe read/control row marked `MCP implemented` or `MCP partial` that is not represented in `tests/unit/contracts/_capabilities.py`.
   - Assert missing/partial/API-only/CLI-absent rows carry explicit matrix/backlog status.

2. Surface metadata failure
   - Add a failing metadata test that walks the registry and compares real FastAPI routes, Typer command/flag definitions, and MCP tool input schemas.
   - Assert expected request fields, required idempotency fields, optional/required version fields, and response model names.

3. Read-only parity failure
   - Move or mirror the most important read-only REST-vs-MCP parity cases into registry-driven contract tests for overview, merge queue, tasks/attempts, validation, stale reasons, artifacts metadata, metrics, locks, overlap graph, service health/readiness, operations, runtime, logs, and events.
   - Include populated and empty cases where current fixtures already support them.

4. Control success/replay/conflict failure
   - Parameterize success, replay/idempotency, idempotency conflict, and version conflict cases for the registry controls.
   - Start with controls that already have helper coverage, then generalize to validate/refresh/rebase/remonitor/stop/destroy/cancel.

5. Auth and structured error failure
   - Add parameterized REST auth failure checks for protected routes and CLI propagation checks for commands that call those routes.
   - Add MCP no-auth-argument/redaction assertions.
   - Add terminal structured error cases for invalid state and not-found/error-envelope surfaces.

6. CLI explicitness failure
   - Add a test that any matrix row with a CLI surface resolves to a real Typer command and flags.
   - Add a companion assertion that rows without a CLI command must say `CLI absent` or carry an explicit backlog/partial status; no silent absence.

After these tests fail for any real drift, make the smallest compatible production/docs fix. Do not weaken the tests to preserve current drift.

## Implementation Sequence

1. Expand registry data structures and parser helpers while keeping existing tests readable.
2. Add failing registry and metadata tests first.
3. Add failing executable parity tests for success, replay/idempotency, version conflict, auth-like failure, invalid state, and structured errors.
4. Fix real drift in REST/CLI/MCP production code with the narrowest compatible changes.
5. Update `docs/MCP_CLIENT_PARITY.md` only for implementation-backed status/backlog changes.
6. Update `TODO/pre-gke-industrial-readiness.md` with evidence only after validation is green.
7. Commit implementation-phase work locally with a focused message. AWF handles push and PR creation.

## Risks And Mitigations

- Risk: The registry becomes a second, inconsistent matrix.
  - Mitigation: keep `docs/MCP_CLIENT_PARITY.md` cross-validation mandatory and fail on either side drifting.

- Risk: Read-only parity fixtures get duplicated across `tests/unit/mcp` and `tests/unit/contracts`.
  - Mitigation: extract only small reusable helpers or keep assertions registry-driven while reusing existing seed patterns.

- Risk: Contract tests become brittle by asserting volatile fields.
  - Mitigation: compare stable envelope fields and normalize timestamps/ids where the behavior is not about identity generation.

- Risk: CLI surfaces are actively being aligned in another workspace.
  - Mitigation: re-check current branch and target updates before implementation, keep CLI edits minimal, and preserve explicit `CLI absent` / backlog status for intentional gaps.

- Risk: Tightening MCP idempotency/version schemas may affect existing callers.
  - Mitigation: write the failing contract first, then choose the smallest compatible production change; if a difference is intentional, require explicit matrix/backlog status rather than hiding it.

- Risk: Auth expectations differ by route, especially public health/create/list surfaces versus token-protected controls.
  - Mitigation: encode auth policy per capability and test auth failure only where the route declares protection.

## Assumptions

- REST remains the canonical public contract for request/response schemas.
- `docs/MCP_CLIENT_PARITY.md` remains the source of truth for implementation status and backlog status.
- Safe read/control surfaces are the parity-matrix rows that expose bounded AWF operator reads or audited control-plane operations, excluding WebSocket streaming, secret lease material, unrestricted file/artifact content, and explicit out-of-scope rows.
- Tests may use seeded database state and service fakes for external GitHub/provider dependencies, but must not fake away the REST/CLI/MCP contract layer under test.
- Any discovered drift should be fixed in production/docs rather than encoded as an unexplained skip.

## Explicit Non-Goals

- Do not implement new product capabilities such as artifact downloads, global MCP event streaming, secret lease reads, arbitrary shell, Docker exec, host file access, or SDK support.
- Do not broaden console/frontend behavior.
- Do not refactor unrelated API, CLI, MCP, service, or database internals.
- Do not lower coverage/profile gates or add fake tests that bypass the contract.
- Do not resolve other active backlog slices such as PR adoption terminal idempotency or broader CLI command coverage beyond fixes directly required by these contract tests.
