# Implementation Plan: P0 Provider Resilience Executor Fallback End-to-End

## Goal
Close the executor no-work provider-failure gap with strict TDD. When an agent CLI fails before useful work because of provider auth/quota/capacity/usage-limit/timeout/no-work signals, AWF must preserve the structured provider recovery metadata and create or schedule the approved retry/fallback attempt with explicit lineage instead of collapsing into an unproven generic `agent_failure` path.

This slice will build on the existing provider failure classifier in `awf.adapters.provider_failures` and the existing `awf.service.provider_recovery` decision/row-creation service. It will not reimplement classification, coverage parsing, PR-monitor recovery, or console surfacing.

## Current Seams Observed
- `src/awf/adapters/base.py` already classifies provider failures from CLI stdout/stderr and places `provider_recovery` metadata in `AgentRunError.details`.
- `src/awf/control/executor.py` currently catches `AgentRunError`, salvages any work, and in the no-commit path marks the workspace failed before calling `_prepare_provider_recovery()` when an agent reason code exists.
- `src/awf/service/provider_recovery.py` already derives metadata from persisted failure details, decides retry vs fallback vs terminal, records circuit-breaker state, and creates retry/fallback workspace rows plus task-attempt lineage.
- `tests/unit/control/test_executor_error_paths.py` contains a stale TODO-style capacity-exhaustion test that only proves structured failure details are persisted, not that fallback/retry dispatch is created and linked.

## Intended Files and Modules to Touch

### Tests
- `tests/unit/control/test_executor_error_paths.py`
  - Replace the stale TODO capacity-exhaustion test with executable end-to-end assertions for executor no-work provider recovery.
  - Add/extend local seeding helpers only as needed to create a ready workspace with `task_policy.provider_recovery`, `owned_paths`, `profile_ref`, inline/requested profile, resolved profile monitor/validation policy, `auto_merge`, review grace, and validation commands.
  - Add a generic deterministic failure regression proving no provider recovery attempts/events are created for non-provider `AGENT_CLI_FAILED` no-work failures.
- `tests/unit/service/test_provider_recovery.py`
  - Strengthen existing recovery row tests to assert full policy preservation, retry/fallback state, target provider/model, task lineage, and canonical-attempt lineage where available.
  - Add a focused service regression if executor tests expose missing lineage fields that are easier to prove at the service layer with deterministic timestamps.

### Implementation
- `src/awf/control/executor.py`
  - Keep the executor no-work path responsible for persisted source failure plus calling provider recovery preparation.
  - Remove or replace stale fallback TODO comments with the implemented recovery behavior.
  - If tests show generic no-work failures still invoke unnecessary recovery plumbing, add a narrow helper/guard that only prepares provider recovery when existing metadata/classification is present, using `provider_recovery_metadata_from_failure` rather than new string matching.
- `src/awf/service/provider_recovery.py`
  - Preserve any missing retry/fallback lineage in `provider_recovery_state`, event payloads, and operation payloads. Expected additions, if absent, are `source_task_id` and `source_canonical_attempt_id` alongside existing `source_workspace_id` and `source_attempt_id`.
  - Ensure fallback row creation keeps `task_prompt`, `owned_paths`, `profile_ref`, `requested_profile`, `resolved_profile`, validation commands/profile validation policy, `auto_merge`, `initial_review_grace_period_seconds`, task kind, and PR monitor policy snapshots.
  - Ensure fallback decisions reset `retry_attempt_number` to `0` for the selected fallback provider/model and persist `target_provider`/`target_model`.

No migrations are planned; any new lineage data should live in existing JSON payloads/policy state unless tests prove a durable column is already expected by the model.

## Tests to Write First

1. `test_provider_no_work_failure_from_stderr_creates_fallback_workspace_and_lineage`
   - In `tests/unit/control/test_executor_error_paths.py`, monkeypatch a Gemini test adapter that uses the base `AgentAdapter.run()` path, so provider detection comes from a queued CLI stderr result rather than prebuilt details.
   - Queue stderr such as `RESOURCE_EXHAUSTED RetryableQuotaError Retry-After: 90` with no subsequent git changes.
   - Seed a ready source workspace with an approved fallback policy, e.g. Gemini/Google to Codex/OpenAI, and either `max_same_provider_retries=0` or pre-seeded retry state that makes fallback the next decision.
   - Assert the source failure state event has `reason_code == "AGENT_PROVIDER_CAPACITY_EXHAUSTED"` and `details.provider_recovery` includes `failure_type`, `provider`, `model`, `retryable`, `retry_after_seconds`, `cooldown_seconds`, `failure_fingerprint`, `fallback_allowed`, and `recommended_action`.
   - Assert a `workspace.provider_recovery_requested` event exists and the provider recovery payload selects `action == "fallback"`, `decision_reason_code == "PROVIDER_FALLBACK_SELECTED"`, target agent/provider/model, fallback attempt number `1`, and retry attempt number `0`.
   - Assert exactly one new fallback workspace is created/scheduled and preserves prompt, owned paths, test commands, requested/resolved profile snapshots, profile ref, validation policy in the resolved profile, `auto_merge`, review grace, task kind, and PR monitor policy.
   - Assert task-attempt lineage: same task, fallback attempt number increments, `parent_attempt_id` and `redispatch_from_attempt_id` point at the source attempt, and provider recovery state links back to the source workspace/attempt/task/canonical attempt where present.

2. `test_provider_no_work_failure_schedules_same_provider_retry_when_policy_requires_retry_first`
   - Use the executor no-work path with a retryable provider failure and a policy where same-provider retry budget remains.
   - Assert a new retry workspace is created with the same agent/model, `provider_recovery_state.action == "retry"`, `retry_attempt_number == 1`, `fallback_attempt_number == 0`, and a persisted `not_before` cooldown derived from existing service policy/metadata.
   - Avoid exact wall-clock assertions in the executor test; assert the timestamp is parseable and in the future relative to the test window, or move exact timestamp assertions to the service test with explicit `now`.

3. `test_generic_no_work_agent_failure_does_not_create_provider_recovery_attempt`
   - Queue a deterministic non-provider CLI failure with no provider markers and no commits.
   - Assert the source workspace fails with the ordinary agent failure path, but no `workspace.provider_recovery_requested`, `workspace.provider_recovery_created`, `workspace.provider_recovery_cooldown`, or provider retry operation/workspace is created.
   - This proves deterministic non-transient failures do not enter a retry/fallback loop.

4. Strengthen `test_fallback_attempt_inherits_lineage_and_workspace_policy`
   - Add assertions for preserved `requested_profile`, `resolved_profile.monitor.initial_review_grace_period_seconds`, `resolved_profile.validation.requested_tier`, test commands, source/fallback task IDs, source attempt ID, target provider/model, fallback counter, and reset retry counter.
   - If adding explicit canonical lineage, create or mark a canonical attempt in the fixture and assert the provider recovery payload/state preserves its ID without making the new fallback canonical prematurely.

## Implementation Sequence

1. Write the executor regression tests above and run the focused failing subset first.
2. Update `provider_recovery` service only where the tests reveal missing preservation or lineage fields; keep existing decision logic and classifier calls intact.
3. Update executor no-work handling only where needed to prepare provider recovery for classified provider failures and to remove stale TODO comments now covered by executable assertions.
4. Re-run focused provider recovery service tests, then focused executor error-path tests.
5. Run style/type validation after behavior is green.

## Risks

- The executor uses real `datetime.now(UTC)` inside `_prepare_provider_recovery()`, so exact cooldown timestamps should be asserted in service tests with explicit `now`, not in executor tests.
- Source workspaces may still have coarse `failure_reason == agent_failure`; the important invariant is that persisted events/details carry the structured provider reason and recovery metadata. Tests should assert both without requiring a database enum change.
- Event ordering through ORM relationships can be fragile; tests should query/filter explicit event types and operation rows rather than relying on relationship order.
- Adding canonical lineage to JSON payloads must not mark retry/fallback attempts canonical early. Canonical selection remains tied to normal completed PR/merge-candidate lifecycle.
- Provider fingerprints include redacted stderr content; assertions should check required fields and redaction behavior without depending on an entire fingerprint string unless the service test controls all inputs.

## Assumptions

- `task_policy.provider_recovery` is the authorization boundary for provider fallback targets and retry budgets.
- Requested and resolved profile snapshots are the durable carrier for validation policy and PR monitor policy, while `initial_review_grace_period_seconds` remains the workspace-level override.
- Same-provider delayed retries are represented as new requested workspaces with provider recovery `not_before` state; worker scheduling suppression remains in `ControlWorker` and is only regression-tested here if directly affected.
- Existing provider failure classification covers auth/quota/capacity/usage-limit/timeout signals; this task only exercises it from the executor path.

## Explicit Non-Goals

- No PR-monitor recovery changes.
- No console or API surfacing changes.
- No new provider classification vocabulary or duplicate classifier implementation.
- No coverage parsing changes.
- No branch management, pushing, rebasing, or merging.
- No broad scheduler rewrite beyond preserving existing delayed retry behavior.
