# Plan: validation provenance observability

## Objective

Expose merge-policy validation provenance in operator-facing API and console
surfaces so a workspace or merge candidate explains its validation tier,
freshness identity, and blocking reason without requiring raw log inspection.

This is an additive P0 observability slice. Existing response fields and route
semantics must remain compatible.

## Current Code Context

- `validation_runs` already persists tier, command set hash, base/target/head
  identity, profile identity, environment identity, status, reason code, retry
  count, and log stream references.
- `/v1/workspaces/{id}/validation` already exposes per-command validation run
  provenance through `ValidationProvenanceItemResponse`.
- `/v1/merge-queue` already exposes `required_validation_tier`,
  `latest_satisfied_validation_tier`, `latest_validation`, stale reasons, queue
  blockers, and policy findings.
- Workspace detail responses do not yet expose a compact validation freshness
  summary unless the selected workspace is also present in the merge queue
  snapshot.
- The console currently renders validation freshness in workspace detail from
  `selectedMergeQueueItem`; non-queued or legacy workspaces show only that the
  workspace is not in the merge queue snapshot.

## Implementation Approach

1. Add response schemas.
   - Define one compact validation observability response with:
     `required_tier`, `latest_satisfied_tier`, `freshness_status`,
     `reason_code`, `required_reason_code` if useful, `current_target_head_sha`,
     `latest_validation`, and optional source/status fields.
   - Keep `latest_validation` as `ValidationRunSummaryResponse` to avoid a
     second identity shape.
   - Use nulls for unavailable scalar values and explicit string statuses for
     freshness.

2. Centralize computation.
   - Create a service helper that accepts a workspace, validation runs, and the
     current/open merge candidate if present.
   - Compute required tier as the max of task-class floor, profile requested
     tier, and post-rebase tier-2 requirement.
   - Compute latest satisfied tier from successful validation runs, scoped to
     the candidate attempt when there is one, and after the latest successful
     rebase.
   - Compute latest validation as the most recent run, preserving failed/running
     status for observability even when it does not satisfy policy.
   - Compute target freshness from `latest_validation.target_head_sha` and the
     candidate head or monitor last commit SHA.
   - Prefer persisted identity fields; fall back to legacy base/target fields
     through the existing `validation_identity_fields()` behavior.

3. Wire workspace detail.
   - Update the workspace detail route to fetch validation runs with
     `ValidationRunRepository.list_for_workspace()` and open merge candidate
     context, or add a repository method that eager-loads exactly the needed
     relationships.
   - Pass the computed summary into `workspace_response()` through the existing
     `_WorkspaceResponseSource` pattern.
   - Preserve list endpoint compatibility; only add the summary there if it can
     be populated cheaply and consistently.

4. Wire merge queue.
   - Replace private tier/freshness helper duplication with the shared service
     helper where possible.
   - Preserve existing field names and values on `MergeQueueItemResponse`.
   - Add only additive explicit fields if tests show the boolean
     `fresh_for_target` is insufficient for operators.

5. Wire console.
   - Extend types first, then formatter tests.
   - Render workspace detail from `workspace.validation_provenance` so selected
     workspaces outside the current merge queue still show required/satisfied
     tier, freshness, identity, and reason code.
   - Keep merge queue drilldown dense: required tier, latest satisfied tier,
     freshness, base/workspace/target SHAs, command hash, profile/env identity,
     reason code, stale reasons, queue blockers, and policy findings.

## Risks And Mitigations

- Required-tier logic already appears in multiple places. Mitigate by moving the
  logic into one helper and having merge queue and workspace detail share it.
- `Workspace.validation_runs` is `lazy="raise"`. Mitigate by loading validation
  runs explicitly through the repository and by adding a regression test that
  workspace detail does not crash on legacy rows.
- Latest validation and latest satisfied validation are different concepts.
  Keep both fields: latest run for observability, latest satisfied tier for
  merge policy.
- Target freshness can be indeterminate when candidate head or validation target
  SHA is missing. Return an explicit `unknown`/`unavailable` status rather than
  coercing to fresh or stale.
- Console labels can become too wide in dense panels. Use existing `QueueChip`
  and `QueueDatum` truncation/tooltip patterns, compact IDs, and short labels.
- Refactoring merge queue helpers can accidentally change queue semantics. Keep
  existing merge queue tests green and add focused tests around the helper before
  replacing private code.

## Assumptions

- Validation run identity data already persisted by recent migrations is
  sufficient for this slice.
- The current merge candidate head SHA or monitor last commit SHA is the best
  available current target identity for local API/console observability.
- Required validation tier remains task-class floor plus profile requested tier
  plus post-rebase tier-2 freshness requirement.
- Legacy workspaces may have no validation runs, missing attempt ids, missing
  candidate rows, missing profile identity, or partial SHA fields.
- Additive response fields are acceptable compatibility-wise for the REST API
  and console proxy.

## Explicit Non-Goals

- Do not change merge policy or auto-merge eligibility behavior.
- Do not add migrations unless implementation proves existing persisted
  validation data is insufficient.
- Do not change validation execution, retry behavior, stale detection, PR
  monitoring, or GitHub merge flow.
- Do not lower coverage thresholds or quality gates.
- Do not redesign the console layout or introduce a new page; this is a compact
  detail/drilldown observability slice.
- Do not push, rebase, switch branches, manually merge PRs, or commit during
  this planning phase.
