# Plan: P0 PR Recovery Must Not Re-Enter Full Agent Execution

## Goal

Close the merge-safety regression where a workspace with an already-open PR can
move backward from `monitoring_pr` into `ready`/`running` and accidentally run
the full feature-agent path again.

The regression slice must prove:

1. PR monitor recovery dispatch creates an explicit recovery operation before
   any backward state transition.
2. Recovery execution uses validation/rebase-only handling and never invokes
   the original feature task prompt, planning prompts, post-agent commit path,
   PR creation, or a fresh full agent run.
3. Remonitor paths resume the PR monitor directly from `monitoring_pr` or
   failed-workspace monitor reset state, without entering `ready`.
4. Stale/rebase recovery rebases or refreshes the existing PR branch, then runs
   validation at the required tier without invoking a new feature-agent run.
5. Any intentional backward step is observable through a reason code/event.
   Any open-PR `ready` row without an active recovery discriminator is blocked
   rather than treated as a normal feature execution.

## Current Code Context

- `src/awf/runtime/pr_monitor_runner.py`
  - `_handle_merge_gate_blocker()` creates monitor-owned validate operations
    with `recovery_mode="validate_only"` or `"rebase_only"`, then transitions
    `monitoring_pr -> ready` with reason `RECOVERY_DISPATCH`.
  - The monitor itself does not call the feature task agent when dispatching
    recovery.
- `src/awf/control/executor.py`
  - `execute()` claims `ready -> running`.
  - `_get_active_recovery_payload()` is the durable discriminator that makes
    `execute()` skip planning, the feature prompt, branch-drift/post-agent
    commit work, and PR creation.
  - `rebase_only` recovery runs `_run_monitor_rebase_recovery()`, then Tier 2
    validation, then returns to `monitoring_pr` when a monitor is wired or
    `completed` in no-monitor test/legacy paths.
  - Current likely gap: a workspace already associated with a PR can be in
    `ready` with no active recovery operation. Today that shape can be claimed
    and executed as a normal feature run.
- `src/awf/control/worker.py`
  - Polls `monitoring_pr` rows first and calls `resume_pr_monitor()`.
  - Polls `ready` rows afterward and calls `execute()`.
  - The worker does not inspect operation payloads; the executor owns the final
    re-execution guard.
- `src/awf/service/controls.py`
  - Operator validate/rebase transitions `monitoring_pr -> ready` only after
    creating an operation with `source="operator_api"` and a recovery mode.
  - Remonitor leaves or resets the workspace in `monitoring_pr`; it should not
    dispatch full execution.
- `src/awf/db/repositories.py`
  - `WorkspaceRepository.transition()` records `workspace.state_changed`
    events with the transition reason code.
  - `monitor_started_at` is set when a workspace enters `monitoring_pr`, which
    can distinguish a post-PR workspace from first execution.

## Tests To Write First

### 1. Executor guard: open PR without recovery op cannot run feature agent

File: `tests/unit/control/test_executor_monitor_recovery.py`

Test name:
`test_open_pr_ready_without_recovery_operation_is_blocked_before_feature_agent`

Arrange:

- Seed a workspace through
  `requested -> provisioning -> ready -> running -> validating -> pushing -> monitoring_pr`.
- Set `pr_url`, `pr_number`, `remote_push_branch`, `monitor_last_commit_sha`,
  and `monitor_started_at` by using the normal transition to `monitoring_pr`.
- Move it back to `ready` with a bogus/legacy reason but do not create any
  pending/running validate or rebase operation with `recovery_mode`.
- Queue no feature-agent command responses.

Assert first, before production changes:

- `WorkspaceExecutor.execute()` must not call the Codex/Claude/Gemini adapter.
- It must not run branch-drift/post-agent commit commands.
- It must not call `git push` or `gh pr create`.
- The workspace must not continue as a normal completed feature run.
- A structured event/reason is recorded, expected as
  `workspace.pr_reexecution_blocked` or a `workspace.state_changed` failure with
  reason `PR_REEXECUTION_GUARD`.

Expected current failure:

- The existing executor likely treats this as normal `ready` work and attempts
  full feature execution because `_get_active_recovery_payload()` returns
  `None`.

### 2. Validate-only recovery round-trip returns to monitor/completed without agent

File: `tests/unit/control/test_executor_monitor_recovery.py`

Test names:

- `test_validate_only_recovery_with_monitor_factory_returns_to_monitoring_pr_without_agent`
- `test_validate_only_recovery_without_monitor_factory_completes_without_agent`

Arrange:

- Use `_seed_ready_workspace_with_recovery()` with `source="pr_monitor"`,
  `recovery_mode="validate_only"`, and an existing `pr_url`.
- Use the fake validation runner command queue only: `rev-parse HEAD`, then a
  passing validation command.
- Variant A wires a monitor factory stub that records `run()` calls.
- Variant B does not wire a monitor.

Assert:

- No adapter invocations and no feature task/planning prompt text.
- No post-agent commit commands and no PR creation commands.
- Recovery validate operation transitions `pending -> running -> succeeded`.
- Variant A transitions back to `monitoring_pr` and calls the monitor once.
- Variant B transitions to `completed`.
- State/event reasons include `RECOVERY_DISPATCH` and
  `RECOVERY_VALIDATION_OK`.

### 3. Rebase-only stale recovery validates at Tier 2 without feature agent

File: `tests/unit/control/test_executor_monitor_recovery.py`

Test name:
`test_rebase_only_recovery_rebases_then_tier2_validates_without_feature_agent`

Arrange:

- Seed a PR-monitor recovery operation with `recovery_mode="rebase_only"`.
- Queue fake git results for fetch, switch, rebase or already-synced branch,
  head/base SHA capture, and force-with-lease push where applicable.
- Queue only the validation command after rebase.

Assert:

- No feature-agent adapter calls.
- No `gh pr create`.
- A rebase operation row is created or reused and ends succeeded with
  `reason_code="REBASE_OK"`.
- Validation run tier is at least 2.
- The validate operation ends succeeded and references the validation run.
- Existing PR branch metadata (`base_commit`, `monitor_last_commit_sha`, and
  validation `target_head_sha`) is updated.
- Final state is `monitoring_pr` when a monitor is wired, otherwise
  `completed`.

### 4. Monitor dispatch creates recovery operation before stepping back

File: `tests/unit/runtime/test_pr_monitor_runner.py`

Test names:

- `test_monitor_validation_recovery_dispatch_is_operation_first_and_terminal`
- `test_monitor_stale_rebase_recovery_dispatch_is_operation_first_and_terminal`

Arrange:

- Seed a `monitoring_pr` workspace with PR metadata and an open merge
  candidate.
- For validation recovery, make merge eligibility fail with
  `VALIDATION_INSUFFICIENT_TIER`.
- For stale/rebase recovery, attach an active stale reason such as
  `STALE_TARGET_ADVANCED`.
- Call `_execute(action=Merge(), ...)` with a green PR status.

Assert:

- No `gh pr merge` call.
- Exactly one pending operation exists before the state step-back:
  - validate recovery: `type == "validate"`,
    `payload["recovery_mode"] == "validate_only"`.
  - stale recovery: `type == "validate"` for monitor dispatch,
    `payload["recovery_mode"] == "rebase_only"`,
    `payload["requested_action"] == "rebase"`.
- Workspace status is `ready`, reason/event is `RECOVERY_DISPATCH`, and event
  payload includes `recovery_mode`, PR number, head SHA, stale reason or
  validation reason.
- `_execute()` returns terminal `True` so the monitor loop stops until the
  worker/executor recovery pass owns the next step.
- The fake adapter has no calls.

### 5. Remonitor never enters ready execution

Files:

- `tests/unit/service/test_controls_lifecycle.py`
- `tests/unit/control/test_worker.py`

Test names:

- `test_remonitor_keeps_workspace_monitoring_pr_and_creates_remonitor_operation`
- `test_worker_routes_monitoring_pr_to_resume_not_execute_after_remonitor`

Arrange:

- Seed a `monitoring_pr` workspace with an existing PR, stale monitor claim,
  and runtime stranding/remonitor reason.
- Call `WorkspaceControlService.remonitor_workspace()` or run the worker with a
  recording executor.

Assert:

- Remonitor creates a `remonitor` operation and event with reset claim snapshot.
- Workspace status remains or resets to `monitoring_pr`; it does not become
  `ready`.
- Worker calls `resume_pr_monitor(workspace_id)` and never calls
  `execute(workspace_id)` for that workspace.

## Risks

- A broad ban on `ready` workspaces with `pr_url` could break legitimate
  attach/sync workflows. The guard must be scoped to workspaces that previously
  reached `monitoring_pr` and lack an active recovery operation.
- Failing a bad `ready` row is safer than looping, but it changes recovery
  handling for corrupted legacy rows. The reason code and event must make the
  operator path explicit: remonitor from failed state.
- Recovery validation fix-cycles may legitimately invoke the agent with a
  validation-fix prompt after a failed validation pass. Tests must distinguish
  that from the forbidden original feature task prompt/full execution path.
- Operation idempotency is important. The fix must not create duplicate
  validate/rebase operations or bypass existing idempotency keys.
- State-machine changes are high blast radius. Prefer executor/service guards
  over changing allowed transitions unless tests prove the transition map
  itself is the problem.

## Assumptions

- `monitor_started_at is not None` is a reliable local signal that the workspace
  already entered PR monitoring at least once.
- `recovery_mode` on a pending/running operation is the durable discriminator
  for intentional `monitoring_pr -> ready` recovery execution.
- Remonitor is not a validate/rebase recovery dispatch; it should keep the
  workspace in `monitoring_pr` and let the worker call `resume_pr_monitor()`.
- Public API response shapes remain unchanged; new observability is through
  events, reason codes, failure reason/message, and operation payload/result.

## Explicit Non-Goals

- No branch switching, rebasing the agent workspace branch outside existing
  recovery code, pushing, or PR merging.
- No schema migrations.
- No changes to coverage targets, quality gates, or workspace profile
  validation requirements.
- No refactor of the full workspace state machine or merge queue.
- No new retry loops that hide root causes or collapse reason codes.
- No manual PR monitor intervention outside AWF-owned monitor/recovery paths.
