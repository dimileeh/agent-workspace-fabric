# Implementation Plan: Observability-Truth Hardening for Workspace Logs

## 1. Intended Files/Modules to Touch

### `src/awf/db/repositories.py`
- Modify `WorkspaceLogStreamRepository.append_metadata` to handle appending to closed streams.
  - If `stream.closed_at` is not `None`, set it back to `None` (reopening the stream).
  - Update `byte_count` and `line_count` accurately.

### `src/awf/runtime/logs.py`
- Review `WorkspaceLogSink.write` and `WorkspaceLogSink.close` to ensure they handle reopen semantics correctly.
- Update `LogBroadcaster.publish` (or related message structures) if needed, so that WebSocket consumers receive a clear signal when a stream is appended to after closing (e.g. they should resume streaming if they stopped).

### `src/awf/control/executor.py` & `src/awf/runtime/pr_monitor_runner.py`
- Ensure monitor and recovery operations write their logs to durable `WorkspaceLogStream` instances using the `LogStore`.
- Update the instantiation of log sinks for these operations to use `source="monitor"` and `source="recovery"` instead of defaulting to `agent` or `system`.

### `src/awf/api/schemas.py` & `src/awf/db/models.py`
- Ensure any literal types or validations for `WorkspaceLogStream.source` accept `monitor` and `recovery` (if constrained).
- Preserve existing log list, read, and WebSocket API compatibility by ensuring these new sources are serialized exactly as existing ones are.

## 4. Risks, Assumptions, and Explicit Non-Goals

### Risks
- **Client Disconnects:** Console UI clients might disconnect their WebSocket or stop polling if they see `closed_at` is set. If the stream reopens, they might miss subsequent logs unless the console is refreshed. This is an accepted risk for now; the server must maintain correct state, and clients can be updated independently to handle reopen events.
- **Race Conditions:** High-frequency logging during stream close could cause concurrent updates. The lock in `WorkspaceLogSink` mitigates this locally, but we must ensure `append_metadata` safely handles concurrent writes.

### Assumptions
- A stream is considered "reopened" simply by clearing its `closed_at` timestamp.
- The existing API contracts for `/logs` and `/logs/{stream_id}/read` are purely metadata/byte-range based and do not need schema changes to support `monitor` and `recovery` sources (the `source` field is just a string).

### Explicit Non-Goals
- **UI Modifications:** We are not updating the console React code to handle these new states. We are purely hardening the backend observability truth.
- **Log Rotation:** We are not implementing log rotation or archival for large streams in this task.
- **Changing Agent Logging:** We are not altering how the main agent runs or logs, only how its streams (and others) manage lifecycle metadata.
