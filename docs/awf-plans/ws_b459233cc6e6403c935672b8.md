## Problem Statement

T03 should provide the shared first-run error contract used later by setup, start, credentials, installer, and client/MCP slices. The result should make every known first-run failure render as both:

- concise operator-facing pretty output with problem, cause, fix, docs, reason code, and safe details;
- JSON-safe structured output with stable `reason_code` and structured remediation fields.

The slice must not implement T04 dry-run checks, T05 real start behavior, T06 credential storage, T11/T12 installer behavior, or later orchestration. It should only create the reusable contract, catalog entries, redaction, and placeholder CLI integration needed to prove the contract.

## Reason-Code Catalog Baseline

T03 should catalog the existing first-run reason codes introduced by T01/T02 and add stable catalog entries for known downstream first-run failures from the source plan/backlog. The implementation should prefer existing equivalent codes if one is already present, but should not silently omit any category below.

Existing codes to cover:

- `AWF_SETUP_PLACEHOLDER`
- `AWF_START_PLACEHOLDER`
- `HOST_SETUP_CONFIG_CORRUPT`
- `HOST_SETUP_CONFIG_SECRET_VALUE`
- `HOST_SETUP_CONFIG_WRITE_FAILED`
- `SOURCE_CHECKOUT_INVALID`
- `SOURCE_CHECKOUT_ASSETS_STALE`

New catalog-only first-run codes to introduce for later slices:

- `SETUP_READINESS_FAILED` for setup preflight blockers such as Docker/offline prerequisites.
- `SETUP_PROVIDER_UNKNOWN` for unsupported `awf setup --provider` names.
- `INTERACTIVE_INPUT_REQUIRED` for non-interactive setup paths that need secret/input collection.
- `CREDENTIAL_BACKEND_UNAVAILABLE` for keychain/backend unavailability.
- `CREDENTIAL_PLAIN_FILE_CONSENT_REQUIRED` for plain-file fallback without explicit consent.
- `CREDENTIAL_REF_INVALID` for malformed provider credential references.
- `PROVIDER_SETUP_AUTH_INVALID` for provider authentication failures that should mark one provider unavailable.
- `CLIENT_CONFIG_CONFLICT` for Claude/Codex MCP config conflicts.
- `CLIENT_CONFIG_WRITE_FAILED` for failed client config writes.
- `INSTALLER_UNSUPPORTED_PLATFORM` for unsupported installer OS/arch.
- `INSTALLER_DEPENDENCY_MISSING` for missing installer prerequisites such as curl/tar/sh tooling.
- `INSTALLER_CHECKSUM_MISMATCH` for manifest/artifact checksum mismatch.
- `INSTALLER_METHOD_FAILED` for failed uv/pipx/manual install method execution.
- `INSTALLER_PATH_NOT_REACHABLE` for installed `awf` not reachable on PATH without an exact shell fix.
- `START_COMPOSE_ASSETS_MISSING` for package/source Compose asset selection failures.
- `START_PORT_CONFLICT` for local Core port conflicts.
- `START_MIGRATION_FAILED` for local Core migration failure summaries.
- `START_HEALTH_TIMEOUT` for API/worker/postgres health timeout after start.

Each catalog entry should include non-empty problem/message, likely cause, operator fix, related command when useful, and docs link. Success/OK statuses can remain undocumented in public catalog, matching current catalog conventions.

## Rendering Contract

Design target for `src/awf/host_setup/rendering.py`:

- Pydantic models with strict/frozen JSON-safe fields, likely:
  - `FirstRunRemediation` with `problem`, `cause`, `fix`, `docs_link`, `related_command`, and `next_steps`.
  - `FirstRunIssue` or equivalent with `reason_code`, `severity`, remediation, and redacted `details`.
  - `FirstRunPayload` with `status` (`success`, `warning`, `blocked`, `failed`), `command`, `summary`, optional top-level `reason_code`, issues, details, and next steps.
- A helper to build an issue from a reason code by reading the reason catalog text, with explicit overrides for context-specific messages/details.
- `render_first_run_json(payload)` returning a dict/string suitable for CLI JSON output using `model_dump(mode="json")` after redaction.
- `render_first_run_pretty(payload)` returning concise plain text suitable for `typer.echo`, with stable labels: `Reason`, `Problem`, `Cause`, `Fix`, `Docs`, `Next`.
- Helper constructors for success, warning, and failure payloads so later T04/T05/T06 callers do not hand-roll dictionaries.

Pretty output should stay terminal-friendly and not depend on a rich-only rendering path. If a Rich panel is used, tests should assert unstyled text so output remains stable.

## Redaction Contract

T03 must redact both token-shaped values and provider refs in pretty and JSON outputs.

Representative values to test:

- GitHub tokens: `ghp_...`, `github_pat_...`.
- OpenAI/Codex tokens: `sk-proj-...`, `sk-...`.
- Anthropic/Claude tokens: `sk-ant-...`.
- Gemini keys: `AIza...`.
- Slack-style tokens already handled by common audit patterns: `xoxb-...`.
- Authorization/bearer assignments and URL credentials.
- Provider refs: `keyring://awf/github/token`, `env://OPENAI_API_KEY`, `plain-file:///home/user/.awf/secrets/openai`.
- Nested details, lists, tuples, and mappings whose keys are `credential_ref`, `provider_ref`, `token`, `api_key`, or related sensitive names.

Implementation should reuse existing common redaction where possible (`awf.common.audit` and/or `awf.common.redaction`) and add the missing provider-ref handling in the first-run rendering boundary. JSON redaction should operate before returning the payload, not only on final text.

## Risks And Mitigations

- Risk: Duplicating reason text between rendering helpers and doctor catalog creates drift. Mitigation: keep canonical problem/cause/fix/docs text in `src/awf/service/doctor/reasons.py`; rendering helpers should consume it or a small public adapter rather than copy it.
- Risk: Existing common redaction does not hide provider refs because refs are not always raw secrets. Mitigation: add first-run output redaction for provider-ref schemes and sensitive field names at the rendering boundary, with nested JSON tests.
- Risk: Over-scoping into actual setup/start/credential/installer behavior. Mitigation: only wire placeholders to the helper and only add catalog entries/models; leave real orchestration to downstream tasks.
- Risk: Public CLI JSON placeholder shape changes. Mitigation: update focused CLI tests and keep the shape stable from T03 onward, including `reason_code` and structured remediation.
- Risk: Catalog sync tests are strict. Mitigation: update `docs/REASON_CATALOG.md` in the same generated format expected by existing tests.
