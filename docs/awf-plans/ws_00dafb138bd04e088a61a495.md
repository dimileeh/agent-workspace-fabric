# Worker Heartbeat Readiness Plan

Planning artifact for AWF workspace `ws_00dafb138bd04e088a61a495`.

## Goal

Address issue #368 by replacing the token-free smoke proof's worker signal with a real worker heartbeat. The worker process will write a durable heartbeat record, `/readyz` will expose it as `checks.worker`, and `awf smoke run --mocked-local` will consult that worker sub-check instead of inferring worker health from `checks.db.ok`.

The fix must stay token-free, preserve stable reason codes end-to-end, and cover healthy worker, stale heartbeat, and smoke evidence/reason-code behavior.

## Current Context

- Issue #368 was deferred from PR #366 because `src/awf/service/smoke.py` mapped `/readyz` `checks.db.ok` to `worker_db_substrate="ok"`, allowing smoke to pass when API and DB were healthy but the worker process was stopped.
- `src/awf/api/routes/health.py` currently emits `/readyz` checks for DB, Docker, agent runtime image, orphan resources, and egress audit, but no worker liveness check.
- `src/awf/service/worker.py` builds a standalone `ControlWorker`; the API app does not own the worker lifecycle. Heartbeats must therefore be written by the worker runtime, not by API startup.
- Existing smoke tests in `tests/unit/service/test_smoke.py` explicitly encode the old DB-substrate behavior and need to be rewritten to require `checks.worker`.

## Data and Reason-Code Design

Proposed heartbeat table `worker_heartbeats`:

- `worker_id` string primary key, using the existing `ControlWorker._worker_id` value.
- `node_id` string, using `effective_worker_config_node_id(self._config)`.
- `started_at` timestamptz, first heartbeat for this worker process.
- `last_heartbeat_at` timestamptz, updated periodically.
- `poll_interval_seconds` float, stored so readiness can compute a conservative freshness window from the worker's configured polling cadence.
- `created_at` and `updated_at` timestamps.
- Indexes on `node_id`, `last_heartbeat_at`, and `(node_id, last_heartbeat_at)` for latest-heartbeat reads.

Freshness policy:

- `/readyz` should check the latest heartbeat for the service node id, not stale rows from unrelated workers.
- A heartbeat is healthy when `now - last_heartbeat_at <= stale_after_seconds`.
- `stale_after_seconds` should be derived conservatively, for example `max(15.0, poll_interval_seconds * 3.0)`, unless existing settings indicate a better local convention.
- Missing heartbeat is unhealthy; stale heartbeat is unhealthy; DB/query failures are structured unhealthy worker checks, not unhandled 500s.

Proposed `/readyz` worker reason codes:

- `WORKER_HEARTBEAT_FRESH` for a healthy recent heartbeat.
- `WORKER_HEARTBEAT_MISSING` when no heartbeat exists for the node.
- `WORKER_HEARTBEAT_STALE` when the latest heartbeat is older than the freshness window.
- `WORKER_HEARTBEAT_UNAVAILABLE` or `WORKER_HEARTBEAT_QUERY_FAILED` when the heartbeat lookup cannot be completed; map specific DB/factory/timeout exceptions into this family without logging secrets.

Smoke phase behavior:

- `_default_service_collector()` still calls `/healthz` first to prove API liveness.
- It then calls `/readyz` and reads `checks.worker.ok` and `checks.worker.reason` from the JSON body regardless of `/readyz` HTTP status, preserving provider-free behavior when provider checks make `/readyz` return 503.
- If the worker check is fresh, return `{"status": "ok", "api": "ok", "worker": "ok", "worker_reason": "WORKER_HEARTBEAT_FRESH"}`.
- If the worker check is stale, missing, malformed, or unreachable, return a degraded service result and make `_phase_service_readiness()` fail with `SMOKE_WORKER_UNAVAILABLE` and evidence containing `worker`, `worker_reason`, and any non-secret detail from `/readyz`.
- Backward-compatible injected collectors that only return `{"status": "ok"}` can remain accepted, but they must report worker evidence as `unknown` rather than claiming worker readiness.

## Tests to Write First

1. `/readyz` healthy worker contract:
   - Seed a recent `worker_heartbeats` row for the effective service node.
   - Call `/readyz` with existing fake Docker/provider setup.
   - Assert status 200, `checks.worker.ok is True`, `checks.worker.reason == "WORKER_HEARTBEAT_FRESH"`, and the worker check is included in the stable checks map.

2. `/readyz` stale worker contract:
   - Seed an old heartbeat beyond the freshness window.
   - Assert `/readyz` returns 503, top-level status `fail`, `checks.worker.ok is False`, and reason `WORKER_HEARTBEAT_STALE`.

3. `/readyz` missing worker contract:
   - Do not seed a heartbeat.
   - Assert `/readyz` returns 503 with `WORKER_HEARTBEAT_MISSING` so an API+DB-only stack does not look worker-ready.

4. Worker write/upsert contract:
   - Run a focused `ControlWorker` tick or short `run_forever()` loop against the test DB.
   - Assert a heartbeat row exists with the worker id, node id, poll interval, and recent `last_heartbeat_at`.
   - If testing `run_forever()`, assert the timestamp advances across idle cycles and stop handling still completes promptly.

5. Smoke collector contract:
   - Rewrite the old `/readyz checks.db.ok` tests so a body with `checks.worker.ok=true` succeeds even if `/readyz` itself is 503 due provider readiness.
   - Add a regression where `checks.db.ok=true` but `checks.worker.ok=false` returns degraded worker status and the smoke phase fails with `SMOKE_WORKER_UNAVAILABLE`.
   - Add a malformed/missing `checks.worker` response path that fails closed without crashing.

6. CLI smoke evidence contract:
   - Update `tests/unit/cli/test_smoke.py` so emitted JSON/pretty output includes the worker heartbeat evidence/reason and no longer names `worker_db_substrate` as the liveness proof.

7. Migration graph/schema contract:
   - Update the single-head migration test to the new revision.
   - Add focused schema assertions for `worker_heartbeats` if the existing migration graph test is the right place.

## Implementation Steps

1. Add the failing tests above first and run only the focused failing commands for those tests.
2. Add the heartbeat ORM model and Alembic migration.
3. Add repository helpers for heartbeat upsert and latest heartbeat lookup, using SQLAlchemy structured queries instead of ad hoc SQL strings unless an upsert needs PostgreSQL dialect support.
4. Add worker heartbeat writes in `ControlWorker`, ensuring failures are logged with reason codes and do not kill the worker loop. Use specific exception handling around DB writes and avoid logging database URLs or secrets.
5. Add the `/readyz` worker sub-check. Keep it concurrent with the other readiness tasks and bounded by the existing readiness timeout pattern.
6. Update smoke collection and service phase evidence to read `checks.worker` instead of `checks.db`.
7. Update docs and generated OpenAPI if the public schema changes.
8. Re-run the focused validation commands, then document any validation gaps in the implementation validation artifact when the implementation phase allows it.

## Risks and Assumptions

- Assumption: adding a small Postgres-backed heartbeat table is within "worker heartbeat infra" even though the task's named files focus on health, smoke, tests, and docs.
- Assumption: `/readyz` remains token-free, and reading the JSON body on 503 remains acceptable because provider readiness can fail independently of worker liveness.
- Assumption: local worker readiness should use the effective service node id (`local` by default) so unrelated stale worker rows do not fail the wrong service node.
- Risk: a stale threshold that is too short could fail readiness during DB latency or worker event-loop stalls; deriving it from poll interval with a minimum window reduces false negatives.
- Risk: if `run_once()` can spend a long time inside provisioning, heartbeat writes tied only to poll-loop entry could become stale while the worker is alive. Prefer a lightweight periodic heartbeat loop in `run_forever()` plus an initial/tick write for `run_once()` coverage.
- Risk: migration head conflicts can occur if another agent adds a migration; resolve by rebasing the migration revision only within the current branch constraints and without switching branches.
- Risk: adding structured fields to `CheckResult` will cause OpenAPI drift and may require updating `openapi.json`.
- Risk: old tests and docs use `worker_db_substrate`; all user-facing claims must be updated so the no-token proof no longer presents DB health as worker liveness.

## Explicit Non-Goals

- Do not touch GC, overlay, or workspace cleanup behavior.
- Do not add Docker/container-health probing for worker readiness; the locked design is a DB-backed worker heartbeat.
- Do not add token requirements to `/readyz` or smoke.
- Do not change PR monitor, merge policy, scheduler admission, or provider readiness semantics beyond including `checks.worker` in readiness.
- Do not implement multi-worker quorum or cluster scheduling policy; this task only needs a latest heartbeat for the relevant node.
- Do not log secrets, database URLs, tokens, or provider credentials in heartbeat errors or smoke evidence.
