## #444 — shared `ForgeClientError` base

### Files
- `src/awf/common/github_client.py` — `GitHubClientError` extends new base; add normalized accessors.
- `src/awf/common/bitbucket_client.py` — `BitBucketClientError` extends new base; add normalized
  accessors. (Base class itself lives in a neutral module — see decision below.)
- `src/awf/runtime/pr_monitor_runner/helpers.py` — classification (`_is_transient_*`).
- `src/awf/runtime/pr_monitor_runner/transient_ops.py` — wait helpers.
- `src/awf/runtime/pr_monitor_runner/{runner,merge_loop,fix_cycle,loop}.py` — catch sites.

### Where the base lives (decision)
Create `ForgeClientError` in a **new tiny neutral module** `src/awf/common/forge_errors.py` to
avoid a github↔bitbucket import cycle (bitbucket_client already imports from github_client for
`RepoRef`; adding the base there is acceptable too, but a dedicated module keeps it forge-neutral
and import-safe). Both client modules import the base from there. *(Assumption: a new file under
`common/` counts as a "client file" — it is part of the forge-client contract. If the reviewer
prefers no new file, fall back to defining the base in `github_client.py`.)*

### Base contract — FULLY normalize every field catch sites read
`ForgeClientError(Exception)` exposes (concrete, not abstract, so each subclass sets backing
fields in `__init__`):
- `operation: str` — already common.
- `reason_code: str` — **stable**. GitHub today has none; add a derived `reason_code` on
  `GitHubClientError` (map from returncode/stderr markers to a stable code, defaulting e.g.
  `GITHUB_API_ERROR`) OR expose a base property that returns a GH default. BB already has it.
- `is_transient: bool` property — normalized transient flag (see classification below). This is
  the single source the wait helpers consult.
- `redacted_detail() -> str` — normalized redacted human detail: BB returns `self.body`, GH
  returns `self.stderr` (both already redacted at construction).
- `merge_method_stderr() -> str` — **GH-stderr-equivalent** for the merge-method-mismatch parser:
  GH returns `self.stderr`; BB returns `""` (BB carries no per-method rejection signal). This lets
  `_merge_method_rejection_method` consume the base without an isinstance.
- `http_status: int | None` property — GH returns `None` (no HTTP status; it shells `gh`), BB
  returns `self.status`. Used only by classification, never by GH-specific parse paths.

GitHub keeps `returncode`/`stderr`; BitBucket keeps `status`/`reason_code`/`body`. The base only
adds normalized accessors over those — **no field renames**, so existing `exc.stderr`/`exc.body`
/`exc.status`/`exc.returncode` reads keep working unchanged.

### Classification = reason_code FIRST, status second (locked)
- BB classifier (`_is_transient_bitbucket_client_error`) is already correct (reason_code-first;
  `status=None` deterministic for pagination/SSRF/parse/missing-context; 409-in-progress &
  task-timeout transient; 429-after-retry transient; 5xx transient). Keep it; route it through the
  base `is_transient`.
- GH classifier stays marker-based but is exposed via the same `is_transient` property.
- Map `404/422/400` deterministically (not generic noise → no terminate-as-noise). Confirm BB
  `_error_for` already gives 401/403→AUTH_FAILED, 429→RATE_LIMITED, else→API_ERROR; 404/422/400
  fall into API_ERROR with `status` set ⇒ classifier returns deterministic (status not in transient
  set) ⇒ surfaces a stable reason-coded blocker. Add explicit tests for each.
- 429-after-internal-retry → transient (don't spin forever — bounded by client retries then
  `BITBUCKET_RATE_LIMITED` transient wait at monitor level; document the two-layer bound).

### Catch-site consolidation (behavior-preserving)
- Sites where the GH and BB arms run **identical** transient-wait-then-fail logic (status fetch,
  pre-merge recheck, fix_cycle settle/CI/resolve, loop best-effort notify, post-human-notify):
  replace the dual arms with **one** `except ForgeClientError as exc:` calling a unified
  `_wait_after_transient_forge_error(exc, ...)` (new in `transient_ops.py`, consuming
  `exc.is_transient` + `exc.reason_code` + `exc.redacted_detail()`; emits a forge-neutral event,
  or branches log/event names on `isinstance` only for the audit string). Keep `runner.py:243`
  /`354` reason-code propagation (`reason_code=exc.reason_code`) — now available on the base.
- **GH-specific parse sites — keep provably unchanged (top regression risk):**
  - `merge_loop.py:315` `_attempt_merge_method` GH arm: keeps `except GitHubClientError`
    explicitly (it parses `exc.stderr` via `_merge_method_rejection_method` for the
    squash→merge→rebase retry + MERGE_METHOD_MISMATCH recording). The BB arm at 371 stays a
    separate explicit `except BitBucketClientError` (its in-flight/cancel logic is BB-only).
    **Do not merge these two arms.**
  - `merge_loop.py:141` `_merge_method_rejection_method(exc)`: signature can widen to accept the
    base and read `exc.merge_method_stderr()`, but since it's only ever called from the GH arm,
    leave the GH typing to keep the contract obvious. (Decision: minimal change — keep
    `GitHubClientError` typing; revisit only if mypy demands.)
  - `merge_loop.py:987` GH preflight, `merge_loop.py:1322` `isinstance(merge_blocker, …)` dispatch:
    leave the explicit subclass dispatch — it already routes GH→stderr path, BB→reason path.
- `release_pr_sync.py:252` — **untouched** (GH-only duplicate-PR returncode/stderr inspection).

### Tests first
- `tests/unit/common/test_github_client_parts/…` + `test_bitbucket_client_parts/…`:
  `isinstance(GitHubClientError(...), ForgeClientError)` and same for BB; each normalized accessor
  (`is_transient`, `reason_code`, `redacted_detail()`, `merge_method_stderr()`, `http_status`)
  returns the right value for both subclasses.
- BB classification matrix (extend existing): 429/5xx/transport/409-in-progress/task-timeout →
  transient; 401/403/404/422/400/409-conflict/JSON-parse/pagination-cap/SSRF → deterministic.
- **GH regression (critical):** the merge-method-mismatch stderr parser still classifies
  "squash merges are not allowed" → retry next method → MERGE_METHOD_MISMATCH recording, byte-for-
  byte the same through the base. Reuse existing merge-method tests; add an explicit assertion that
  the GH path is unchanged.
- BB monitor-level: 429/5xx/transport → wait-and-retry (not monitor-terminating); 409-conflict/
  auth/422 → stable reason-coded blocker / NotifyHuman (terminates or notifies, never silent).

## #445 — BitBucket PR-tasks gating (auto-resolve + safety)

### Files

  task-resolve rollback needs a distinct dispatch from comment-thread resolve. Keep within the
  monitor/client boundary.

### Fetch + map (locked: full auto-resolve like comments)
- In `fetch_pr_status`, add a paginated GET
  `/2.0/repositories/{ws}/{repo}/pullrequests/{id}/tasks` (mirror the comments `_paginate`,
  `cache=True`).
- Build unresolved-task feedback in parsing: a task has `state` (`UNRESOLVED`/`RESOLVED`),
  `content.raw`, `id`, optional `comment` link (inline anchor). Map **UNRESOLVED** tasks to
  review-feedback so `decide()` blocks `Merge` and routes to `AddressComments`:
  - **Decision:** surface as `ReviewComment` with `source_kind="task"`, `comment_id` encoded with a
    **task discriminator** (e.g. `bbtask:<task_id>`), so the resolve dispatch can tell tasks from
    comments. (Inline tasks may additionally carry path/line if needed, but `ReviewComment` is the
    simplest path that the address-comments gate already treats as merge-blocking pending work.)
  - Resolved tasks are dropped (don't block) — mirror `_comment_is_resolved` filtering.
- Wire the new tuple into `PRStatus.unresolved_review_comments` (extend, don't replace the comment
  feed). Verify `decide()` treats `source_kind="task"` items as actionable (they default to needing
  attention; confirm no bot/issue exemption applies — tasks are reviewer-authored).

### Auto-resolve with REQUIRED safety design
- Add BB client method (mirrors `resolve_thread`): `PUT
  .../pullrequests/{id}/tasks/{task_id}` with `{"state": "RESOLVED"}`. Recover repo/PR/task from a
  neutral task-id encoding (`bbtask:<owner>/<name>#<pr>:<task_id>` via new
  `encode_task_id`/`decode_task_id`). Route the forge-neutral resolve call (the same surface the
  fix cycle uses for inline threads) to this PUT when the id carries the task discriminator;
  otherwise fall back to the existing comment-resolve POST.
- **Resolution queue + rollback:** the agent must address task content first; only after the PUT
  **succeeds** is the task's addressed-state cleared/committed. A FAILED PUT must leave the task
  still blocking (do not mark `fix_committed`/clear addressed state until the resolve returns 2xx) —
  mirror the existing `_clear_addressed_state_by_id` rollback the fix cycle already does for
  threads. Net: a failed resolve ⇒ task re-surfaces next poll ⇒ merge stays blocked.
- **403 (insufficient task scope)** → stable human blocker, reason-coded (new
  `BITBUCKET_TASK_RESOLVE_FORBIDDEN`), **not** a retry storm: classifier maps 403→AUTH_FAILED
  (deterministic) already; ensure the resolve path surfaces it as NotifyHuman, not a transient loop.
- **UNADDRESSABLE criteria → NotifyHuman (explicit):** `needs_human` verdict / repeated
  `agent_failed` / no-diff after N attempts / protected-scope block / resolve-permission failure.
  **Never** let no-diff agent output mark a task `fix_committed` (no closing reviewer tasks without
  evidence) — reuse the existing review-comment verdict gating (`agent_failed`/`needs_human` are
  already excluded from the publish/rollback set in fix_cycle.py:312).

### Forge-aware feedback state (`feedback_state.py`)
- Replace hardcoded `n="github"` (lines 54, 110) and the `https://github.com/...` URL (line 57)
  with values derived from the workspace's forge kind (thread the `ForgeKind`/provider + a
  forge-aware PR-URL builder through `_record_pr_feedback_resolution` /
  `_apply_pr_feedback_resolution_state`). BB → `scm_provider="bitbucket"` and a bitbucket.org PR
  URL (reuse `_pr_page_url` shape). This stops BB tasks/comments from poisoning GitHub provenance/
  replay rows. *(Assumption: forge kind is available on the runner via the workspace row /
  `resolved_profile`; confirm the accessor and pass it down rather than re-resolving.)*

### Tests first
- BB `fetch_pr_status`: PR with open tasks + **no comments** → non-empty
  `unresolved_review_comments` → `decide()` ≠ `Merge` (this is the headline bug). Tasks **paginate**
  (two pages via MockTransport `next`). Resolved tasks don't block.
- Routing: an open task → `AddressComments`; after agent addresses → PUT-resolve marks RESOLVED
  (assert PUT body `{"state":"RESOLVED"}` + correct URL). **PUT-resolve FAILS** → task stays
  blocking, no merge, addressed-state rolled back. 403 → stable human blocker (no retry storm).
  Unaddressable (needs_human / repeated agent_failed / no-diff) → NotifyHuman, task not resolved.
- Provenance: BB feedback resolution records `scm_provider="bitbucket"` + bitbucket URL;

## Risks
- **#1 GitHub merge-method regression (#444).** The squash→merge→rebase retry + MERGE_METHOD_MISMATCH
  stderr parser must be byte-for-byte unchanged. Mitigation: keep the GH `_attempt_merge_method` arm
  explicitly typed `GitHubClientError`; do not merge it with the BB arm; lock it with a dedicated
  regression test that asserts identical behavior through the base.
- **GH `reason_code` addition.** Giving `GitHubClientError` a `reason_code` must not change any
  existing GH log/event/DB field that currently relies on its absence. Default to a stable
  `GITHUB_API_ERROR` and verify no GH test asserts on a *missing* reason_code.
- **Import cycle.** Base in a new `common/forge_errors.py` avoids github↔bitbucket cycles.
- **`decide()` semantics for `source_kind="task"`.** Must confirm task-kind review comments are
  treated as actionable merge blockers and not silently exempted (e.g. bot/issue carve-outs).
- **New reason codes → REASON_CATALOG drift.** New BB task codes
  (`BITBUCKET_TASK_RESOLVE_FORBIDDEN`, etc.) feed the generated `docs/REASON_CATALOG.md` via
  `scripts/generate_reason_catalog.py`. The catalog is a **generated artifact**; if a drift gate
  exists, regenerate it. Flagged because it may sit outside "monitor/client files" — keep new codes
  defined in `bitbucket_client.py` (a client file) and note catalog regen as generated output.
- **1500-line guardrail.** `bitbucket_client.py` is ~1498 lines; adding `/tasks` fetch + resolve +
  reason codes will exceed it. **Plan: split BitBucket HTTP-core or merge/task internals into a
  `bitbucket_client_*` sibling (`_parts` pattern)** before the file crosses the cap, mirroring the
  existing fine-grained split. `merge_loop.py` is ~1404 lines; #448 adds ~1 line (safe), #444
  consolidation should net-reduce it.
- **Coverage of new branches.** Each new arm (PUT-resolve failure rollback, 403 blocker,
  unaddressable→NotifyHuman, task pagination) needs a focused test so the 99% gate holds.
