# Plan: Workspace Recovery Observability Slice

## Scope

Implement a focused observability/API/console slice that explains intentional
workspace workflow reversals. The primary case is a workspace that reached
`monitoring_pr`, then AWF intentionally moved it back to `ready` and resumed
execution/validation for stale recovery, rebase-only recovery, validate-only
recovery, comment recovery, or another PR-monitor-owned repair.

The change should preserve the workspace-centric model: operators should not
need to inspect raw events or operation payloads to understand that AWF stepped
back on purpose, why it did so, and what it is doing now.

## Intended Files And Modules

- `src/awf/service/workspace_observability.py`
  - Add a derived recovery/reversal summary helper, likely named
    `workspace_recovery_summary` plus payload/dataclass types.
  - Reuse existing workspace events and operations; do not add database columns.
  - Detect reverse lifecycle transitions using the existing ordered lifecycle
    stage vocabulary, especially `workspace.state_changed` events where
    `old_state == "monitoring_pr"` and `new_state == "ready"`.
  - Pair the latest reverse transition with the nearest relevant recovery
    event/operation payload:
    - `monitor.recovery_dispatched` event payloads;
    - pending/running or latest completed operation payloads with
      `source == "pr_monitor"` or `owner == "pr_monitor"`;
    - operator validate-only payloads only as a fallback when they caused the
      same explicit reverse transition.
  - Derive fields such as `from_state`, `to_state`, `reason_code`, `action`,
    `recovery_mode`, `started_at`, `current_operation`, `summary`, and a bounded
    raw `payload`.

- `src/awf/api/schemas.py`
  - Add `WorkspaceRecoverySummaryResponse` and, if useful, a small nested
    current-operation response shape.
  - Add `recovery: WorkspaceRecoverySummaryResponse | None = None` to
    `WorkspaceResponse` and `WorkspaceOverviewResponse`.
  - Keep the field additive and nullable so old clients remain compatible.
    Existing schema style includes nullable optional fields in JSON responses,
    so the planned no-recovery shape is `recovery: null`.

- `src/awf/service/workspaces.py`
  - Ensure `workspace_response()` includes the new observability payload through
    the existing `_WorkspaceResponseSource` path.

- `src/awf/api/routes/workspaces.py`
  - Include `recovery` in `/v1/workspaces/overview` rows using the same ordered
    events already computed for lifecycle and latest-event projection.
  - Detail responses should inherit the field from `workspace_response()`.

- `apps/console/lib/types.ts`
  - Add a `WorkspaceRecoverySummary` interface.
  - Add optional/nullable `recovery` fields to `WorkspaceOverview` and
    `Workspace`.

- `apps/console/lib/recovery-format.ts` (new)
  - Add pure formatting helpers for testable console text:
    - compact list badge label, for example `Recovery: STALE_OVERLAP`;
    - detail callout title/body, for example
      `Reverted from monitoring_pr to ready`;
    - action/recovery-mode labels such as `rebase + revalidate` and
      `validate-only recovery`;
    - reverse timeline detection for `workspace.state_changed` events.

- `apps/console/lib/recovery-format.test.mjs` (new)
  - Add Node test coverage for the formatting helpers before the UI change.

- `apps/console/components/console-dashboard.tsx`
  - In `WorkspaceList`, show a compact recovery/revalidating badge when
    `item.recovery` is present.
  - In the selected workspace detail area, add a compact recovery callout near
    the workspace summary/lifecycle rail. It should explain the reverse
    transition, reason code, action/recovery mode, current operation, and
    current status without adding any control buttons.
  - In `EventsPanel`, visually distinguish reverse `workspace.state_changed`
    timeline rows from normal forward transitions.
  - Keep the layout compact on mobile and wide screens using existing panel,
    badge, truncation, and tone conventions.

   - Failing test: a workspace with no reverse transition or recovery event has
     `workspace_recovery_summary(...) is None`.
   - Failing test: a `monitoring_pr -> ready` state change plus a
     `monitor.recovery_dispatched` event produces a summary with:
     `from_state == "monitoring_pr"`, `to_state == "ready"`,
     stale/recovery `reason_code`, requested action, recovery mode,
     `started_at`, raw payload, and a human-readable summary.
   - Failing test: a pending/running PR-monitor operation is surfaced as
     `current_operation` and influences the summary text for a workspace now in
     `ready`, `running`, or `validating`.
   - Failing test: when multiple recoveries exist, the latest reverse/recovery
     pair wins and older payloads do not leak into the active/latest summary.

2. `tests/unit/service/test_workspace_response.py`
   - Failing test: `workspace_response()` includes the derived recovery summary

3. `tests/unit/api/test_workspaces.py` or
   `tests/unit/api/test_observability_api.py`
   - Failing test: `/v1/workspaces/{workspace_id}` includes `recovery` for a
     reversed monitor recovery workspace.
   - Failing test: `/v1/workspaces/overview` includes the same recovery summary
     shape and still exposes `last_event` and `active_operation`.
   - Failing test: ordinary workspaces return `recovery: null`.

Console tests:

4. `apps/console/lib/recovery-format.test.mjs`
   - Failing test: badge formatting prefers `reason_code` and remains compact.
   - Failing test: detail callout formatting renders
     `Reverted from monitoring_pr to ready`, formats `STALE_OVERLAP`, and maps
     rebase/validate payloads to `rebase + revalidate` or `validate-only`.
   - Failing test: missing optional fields have stable fallbacks and do not
     produce `undefined` text.

Use helper tests plus `lint`, `typecheck`, and `build` for the UI integration.
Do not introduce a React test framework for this narrow slice unless another
concurrent change has already added one.

## Implementation Steps

1. Add the backend service/API tests above and run focused pytest commands to
   confirm they fail for the expected missing summary/schema behavior.
2. Add the console formatting tests and run
   `npm --prefix apps/console run test` to confirm the helper module is missing
   or incomplete.
3. Implement the backend derivation in `workspace_observability.py`:
   - sort events with `workspace_events_by_occurrence`;
   - detect reverse state transitions by lifecycle stage index;
   - prefer PR-monitor operation payload fields over generic state-change reason
     codes when deriving the operator reason;
   - include only JSON-safe raw payload data that already exists in event or
     operation records.
4. Project the derived payload through `workspace_response()` and
   `/v1/workspaces/overview`.
5. Implement console types and formatting helpers.
6. Update `ConsoleDashboard`:
   - list badge for recovery/revalidating status;
   - detail callout near lifecycle/workspace summary;
   - reverse timeline row styling.
7. Run focused backend and console tests, then the full requested validation
   commands.
8. Inspect the final diff to confirm there are no migrations, lockfile changes,
   unrelated docs, or new control actions.

## Risks And Mitigations

- Event and operation ordering can be subtle because the monitor creates an
  operation, transitions state, then appends `monitor.recovery_dispatched`.
  Mitigate by deriving from ordered events and pairing the latest reverse event
  with the nearest relevant recovery event and PR-monitor operation payload.
- Some historical rows may have the reverse state event without the monitor
  recovery event, or vice versa. Mitigate with tolerant fallbacks and return
  `recovery: null` only when there is not enough evidence of an intentional
  reversal.
- `reason_code` can appear in several places (`RECOVERY_DISPATCH` on the state
  event versus `STALE_OVERLAP` in operation payloads). Mitigate by preferring
  domain reason codes from recovery/operation payloads, falling back to the
  state event reason only when no better reason exists.
- Raw payload exposure must not reveal secrets. Mitigate by exposing only the
  existing structured event/operation payloads, keeping the payload bounded, and
  not adding any new secret-bearing fields.
- The lifecycle helper currently summarizes the first start/end per stage.
  Mitigate by adding recovery context separately instead of broadly refactoring
  lifecycle duration semantics in this slice.
- Console density can become noisy. Mitigate with compact badges in the list,
  one callout in detail, and full raw event visibility only in the existing
  timeline/operations areas.

## Assumptions

- PR-monitor recovery operations continue to carry `source` or `owner` values
  that identify `pr_monitor`.
- Existing `monitor.recovery_dispatched` payloads carry enough detail to map
  `req_action`/`requested_action`, `recovery_mode`, and stale reason codes.
- `monitoring_pr -> ready` is the primary intentional reversal currently
  supported by the state machine; the detector can still be generic across the
  known lifecycle order.
- Additive nullable API fields are acceptable for old clients.
- Existing console helper tests are the right level for formatting coverage in
  this repository today.

## Explicit Non-Goals

- No new mutating API endpoints or console control buttons.
- No changes to PR monitor recovery behavior, merge policy, stale detection, or
  validation execution.
- No database schema changes, migrations, or persisted recovery-summary columns.
- No broad lifecycle-duration refactor beyond the visual reverse-transition
  highlight needed for this slice.
- No changes to branch management, pushing, rebasing, or AWF-owned PR monitor
  operations.
