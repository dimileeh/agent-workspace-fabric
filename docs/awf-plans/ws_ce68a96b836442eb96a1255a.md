# Implementation Plan: Live workspace activity signals

## Intended files/modules to touch

### Backend (Python)
- `src/awf/db/models.py`:
  - Add `last_activity_at: Mapped[datetime | None]`, `last_log_at: Mapped[datetime | None]`, and `subphase: Mapped[str | None]` to the `Workspace` model.
- `src/awf/db/repositories.py`:
  - Update `WorkspaceLogStreamRepository.append_metadata` to update the `last_log_at` and `last_activity_at` fields on the `Workspace` record. Use a direct `update()` query to avoid unnecessary ORM fetching and lock contention.
  - Add a helper method in `WorkspaceRepository` to explicitly set `subphase` and `last_activity_at` (e.g. `update_activity`).
- `src/awf/control/executor.py`:
  - Inject calls to `workspace_repo.update_activity(subphase="...")` at the boundaries of the `planning`, `agent`, `conformance`, and `validation` subphases inside the `execute` method.
- `src/awf/api/schemas.py`:
  - Add `last_activity_at`, `last_log_at`, `subphase` (str), and `is_stale_running` (bool) to `WorkspaceResponse` and `WorkspaceOverviewResponse`.
- `src/awf/service/workspaces.py`:
  - Compute `is_stale_running` in `_WorkspaceResponseSource` mapping. A workspace is `is_stale_running = True` if its `status == WorkspaceStatus.running` and `last_activity_at` is older than a defined threshold (e.g., 5-10 minutes).
- `alembic` migrations:
  - Generate a new migration script using `alembic revision --autogenerate` for the new fields on the `workspaces` table.

  - Add a prominent warning indicator if `is_stale_running` is true, guiding operators to check logs or recover.
- `apps/console/components/console-dashboard.tsx`:
  - Incorporate the `is_stale_running` state into the dashboard list/grid, perhaps as a warning badge on the workspace card/row.
- `apps/console/lib/api.ts` (or equivalent types):
  - Update the TypeScript interfaces (`WorkspaceResponse`, `WorkspaceOverviewResponse`) to match the new API fields.

## Risks, assumptions, and explicit non-goals

- **Risk:** Rapid log streaming causing excessive DB lock contention due to updating `workspaces` on every log chunk.
  - **Mitigation:** Execute a simple non-blocking `UPDATE` without fetching the `Workspace` entity. If performance becomes an issue during testing, throttle the `last_log_at` DB write to once every few seconds.
- **Assumption:** The `is_stale_running` threshold is purely an observability signal for operators and does not automatically terminate or restart the agent run (AWF handles provider failure retries separately via circuit breakers). We assume a threshold of 10 minutes is appropriate for the UI warning.
- **Non-goal:** Modifying the PR Monitor loop to report `is_stale_running`. The monitor loop has its own detailed logging and active state. The "stale running" warning is targeted specifically at the `running` status (the agent implementation phase).
- **Non-goal:** Creating generic "agent failure" auto-recovery solely based on this stale signal. This slice provides the *signal*; recovery actions remain operator-driven or handled by existing timeout mechanisms.
