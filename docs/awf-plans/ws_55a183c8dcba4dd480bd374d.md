# Plan: Quiet Successful OpenCode/Ollama Fallback Readiness

## Goal

Fix OpenCode/Ollama readiness so an expected host-side fallback from `host.docker.internal` to `localhost` does not emit `provider_readiness.ollama_probe_exception` stack traces when the fallback succeeds. Earlier failed candidate endpoints should remain available as redacted structured/debug evidence, while true all-candidate failures should still return/report `OLLAMA_HOST_UNREACHABLE` with redacted failure detail.

## Intended Files / Modules To Touch

- `tests/unit/service/test_provider_readiness.py`
  - Add regression coverage for successful fallback after an initial `host.docker.internal` transport exception.
  - Add/adjust coverage for all-candidate failure to prove redacted details remain present.
  - Update any existing probe logging expectations if the desired behavior changes direct `_probe_ollama` semantics for multi-candidate success only.
- `src/awf/service/provider_readiness.py`
  - Narrowly update `_probe_ollama` so exception logging is deferred until it knows every candidate failed.
  - Preserve existing URL candidate ordering and redaction helpers.
  - Return failed earlier candidate attempts as structured redacted evidence/debug detail when a later candidate succeeds, without changing provider readiness status to fail.
  - Ensure `_check_opencode` continues to surface `OLLAMA_HOST_UNREACHABLE` detail only when `_probe_ollama` reports failure.
- `docs/REASON_CATALOG.md`
  - Touch only if implementation changes the operator-facing reason text for `OLLAMA_HOST_UNREACHABLE` or related OpenCode/Ollama readiness reasons. Current expectation is no catalog change.

## Tests To Write First

1. In `tests/unit/service/test_provider_readiness.py`, add or strengthen a `collect_agent_readiness` regression test for default OpenCode/Ollama URL fallback:
   - create host-side OpenCode auth signal under `tmp_path / "home" / ".config" / "opencode"`;
   - call `collect_agent_readiness(_settings(tmp_path), environ={}, run_subprocess=_unexpected_subprocess, http_get=_http_get)`;
   - fake `http_get` raises on `http://host.docker.internal:11434/api/version` and returns HTTP 200 for `http://localhost:11434/api/version`;
   - set `caplog` to `logging.ERROR` for `provider_readiness.__name__`;
   - assert provider `opencode` is OK / `OPENCODE_FILE_AUTH_PRESENT`;
   - assert attempted URLs are exactly host gateway then localhost;
   - assert `caplog.text` does not contain `provider_readiness.ollama_probe_exception`, `Traceback`, or the raised exception message;
   - assert serialized payload does not expose secrets and, if structured evidence is exposed in the result, that the failed candidate detail is redacted.

2. Add or strengthen an all-candidates-fail regression test:
   - use a host gateway default/custom URL that yields multiple candidates;
   - make each candidate fail, including at least one exception containing a token-like secret and/or an HTTP body containing a token-like secret;
   - call strict OpenCode readiness so failure blocks;
   - assert `status == "fail"` and `reason == "OLLAMA_HOST_UNREACHABLE"`;
   - assert `detail` includes candidate-level context and `<redacted>` but not the raw secret;
   - assert `provider_readiness.ollama_probe_exception` is still logged only for the terminal all-candidates-failed case, with redacted traceback content and no raw secret.

3. Preserve existing focused unit coverage around `_probe_ollama` single-candidate failure:
   - if the new design still logs direct single-candidate exceptions immediately at terminal failure, keep the existing expectation that the log event and traceback are redacted;
   - if the implementation centralizes terminal logging after the loop, adjust only the assertion shape needed to match equivalent terminal-failure behavior.

## Implementation Approach After Tests Fail

1. Run the new targeted pytest case(s) first and confirm the successful-fallback/no-error-log test fails against current behavior because `_probe_ollama` logs before trying localhost.
2. In `_probe_ollama`, replace immediate exception logging with collection of structured failure records, for example candidate URL plus redacted error text and optional sanitized traceback.
3. On candidate success:
   - return `{"ok": True}` plus a small optional redacted `debug`/`attempts` field only if existing payload conventions can safely carry it;
   - do not call `_log_redacted_exception` for earlier failed attempts;
   - keep final `_check_opencode` result OK.
4. On all candidates failing:
   - build the existing redacted semicolon-joined `detail` from collected failures;
   - emit `provider_readiness.ollama_probe_exception` for exception failures at terminal failure time, preserving redaction and traceback truncation;
   - return `{"ok": False, "detail": ...}` so `_check_opencode` still maps to `OLLAMA_HOST_UNREACHABLE`.
5. Keep the change scoped to the version readiness probe. Do not alter `_probe_ollama_model` unless a test reveals the same logging problem affects selected OpenCode model preflight and the requested behavior clearly requires parity.

## Risks And Assumptions

- Assumption: the noisy operator-visible event is specifically the version readiness path `_probe_ollama`, not model availability `_probe_ollama_model` used by selected launch preflight.
- Assumption: retaining failed candidate evidence in returned probe/provider structures is acceptable if redacted; if provider result schema should stay stable, keep evidence internal on success and only expose failure details on terminal failure.
- Risk: changing `_probe_ollama` logging semantics could break tests that currently assert per-candidate exception logs. Mitigation is to preserve terminal all-candidates-failed logging and only suppress logs for recovered fallback failures.
- Risk: adding structured evidence to successful provider payloads may affect clients that assume exact fields. Prefer either an existing debug/detail convention or omit success evidence from public payload if no stable field exists.
- Risk: redaction must cover URL credentials, known token patterns, explicit secret values, exception strings, response bodies, and traceback text.

## Explicit Non-Goals

- Do not change Ollama URL normalization or fallback ordering.
- Do not change OpenCode auth detection semantics or credential-source reporting.
- Do not change Docker/container lifecycle behavior.
- Do not broaden provider readiness reason taxonomy unless existing reason text is demonstrably inaccurate.
- Do not run full coverage locally; PR monitor/CI will handle the authoritative GitHub full coverage gate.
