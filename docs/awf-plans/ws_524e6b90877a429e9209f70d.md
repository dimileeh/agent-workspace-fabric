# Implementation Plan: MCP safe operator action tools (refresh, rebase, retry, cancel, stop, destroy, remonitor, validate)

## Background

The P1 backlog item from `TODO/pre-gke-industrial-readiness.md` line 583 requires:

> Add MCP tools for safe operator actions already present in the API: remonitor, refresh, validate, rebase, retry, cancel, stop, and destroy, with the same idempotency/concurrency/version/error semantics as REST.

Current state:
- REST endpoints exist for all 8 actions (`src/awf/api/routes/controls.py`, `src/awf/api/routes/workspaces.py`).
- `WorkspaceControlService` implements all 8 (`src/awf/service/controls.py`).
- MCP already has tools for **cancel, stop, destroy, remonitor, validate, retry** (`src/awf/mcp/server.py`).
- MCP is **missing** tools for **refresh** and **rebase**.
- MCP control tools currently lack the `expected_version` (optimistic concurrency / `If-Match`) parameter that the REST endpoints and underlying `WorkspaceControlService` accept.
- Parity matrix (`docs/MCP_CLIENT_PARITY.md`) lists refresh/rebase as `MCP missing/backlog` and marks `TODO§P1-mcp-refresh`, `TODO§P1-mcp-rebase`, and `TODO§P1-if-match-parity`.

## Files / Modules to Touch

| File | Change |
|------|--------|
| `src/awf/service/workspaces.py` | Add `request_refresh_workspace` and `request_rebase_workspace` facade methods on `WorkspaceService` so MCP can call them the same way it calls `request_validate_workspace`. |
| `src/awf/mcp/server.py` | Add `awf_refresh_workspace` and `awf_rebase_workspace` tools. Add optional `expected_version: int \| None = None` to all 8 control-tool schemas and pass it through to the service. |
| `docs/MCP_CLIENT_PARITY.md` | Update matrix rows for Refresh, Rebase, Cancel, Stop, Destroy, Remonitor, Validate, Retry to reflect `MCP implemented` (or `MCP partial` for if-match parity where appropriate) and remove backlog slice references. |
| `TODO/pre-gke-industrial-readiness.md` | Check the item and add implementation-backed evidence note. |
| `tests/unit/mcp/test_mcp_server.py` (or new `test_mcp_control_contracts.py`) | TDD contract tests for success, replay/idempotency, conflict, auth-like failure mapping, and invalid-state errors. |

## Tests to Write First (strict TDD)

1. **Tool registration & schema contract**
   - Assert `awf_refresh_workspace` and `awf_rebase_workspace` are registered.
   - Assert all 8 control tools have `expected_version` in input schema with correct type/range.

2. **Success / happy path**
   - Parametrized harness: for each tool, mock the service method and assert the MCP tool calls it with the exact arguments (including `expected_version`) and returns the `WorkspaceControlResponse` / `OperationResponse` payload.
   - Real DB path: create a workspace in `monitoring_pr` state and call refresh/validate/rebase via MCP, assert an `Operation` row is created with correct type.

3. **Replay / idempotency**
   - Same `idempotency_key` + same payload (including `expected_version`) returns the same operation / response without creating a duplicate.
   - Same key + different payload returns an MCP error with `IDEMPOTENCY_CONFLICT`.

4. **Conflict / version mismatch**
   - Pass `expected_version` that does not match the DB workspace version; assert MCP error payload contains `VERSION_CONFLICT` and detail with `expected_version` / `actual_version`.

5. **Invalid-state errors**
   - For refresh/rebase/validate/remonitor: target workspace in a non-eligible state; assert MCP error contains the correct error code (`WORKSPACE_STATE_NOT_REFRESHABLE`, `WORKSPACE_STATE_NOT_REBASEABLE`, etc.) and `isError=True`.

6. **Auth-like failure mapping**
   - When the service raises any `WorkspaceControlError` subclass, the tool must return an MCP `CallToolResult` with `isError=True` and `structuredContent` carrying `error_code`, `message`, and optional `detail`. No raw exception should leak.

7. **Parity doc cross-check**
   - `test_mcp_client_parity_docs.py` currently asserts `awf_refresh_workspace` and `awf_rebase_workspace` are listed in the doc. After we change the doc, the existing tests should still pass (the tools will also exist in `server.py`).
   - `test_mcp_parity_matrix_crossref.py` asserts every matrix-declared MCP tool is registered. After we change the doc and register the tools, this should pass without modification.

## Risks

| Risk | Mitigation |
|------|------------|
| **Owned-path overlap** with active workspaces (`tests/unit/api/**`, `tests/unit/mcp/**`, `src/awf/api/routes/controls.py`). | Keep changes minimal and additive. Do not rewrite existing control logic; only add facade methods and MCP tool closures. Add new test files if necessary rather than heavily editing overlapping ones. |
| **Coverage regression** from broad schema additions. | Write failing tests first to cover every new parameter and branch. Parametrize tests across tools to keep line count low while keeping branch coverage high. |
| **Schema backward compatibility** after adding `expected_version` to existing tools. | Use `default=None` and do not add to `required`. Existing callers that omit the field continue to work identically. |
| **Parity doc / crossref tests fail** because status wording changes. | Update `MCP_CLIENT_PARITY.md` and `test_mcp_client_parity_docs.py` assertions in lockstep within the same PR. |

## Assumptions

- `WorkspaceControlService.request_refresh_workspace` and `request_rebase_workspace` are correct and fully tested by `tests/unit/service/test_controls_lifecycle.py`.
- `WorkspaceService` is the canonical MCP facade; adding two thin pass-through methods there is the right seam.
- MCP tools are allowed to expose `expected_version` as an explicit integer parameter rather than an HTTP header; this is the only practical mapping for `If-Match` in a tool-call transport.
