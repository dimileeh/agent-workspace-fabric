# PR Monitor Adoption Model/Effort Parity Plan

## Scope

Implement the narrow AWF parity slice for PR monitor adoption model/effort selection across REST, CLI, and MCP. The implementation phase will not change workspace creation, scheduling, provider recovery, PR monitor execution, merge/comment repair logic, or coverage policy.

## Intended Files/Modules To Touch

Exact module paths will be confirmed before implementation, but the expected touch set is:

- REST request/schema surface defining `PullRequestMonitorAdoptionRequest`, likely under `src/awf/api/`.
- REST route/handler for `POST /v1/workspaces/adopt-pr`, likely under `src/awf/api/routes/`.
- PR monitor adoption service/storage logic, likely under `src/awf/service/` or `src/awf/services/`.
- Existing default model/effort policy helper, only as a caller unless a small extension is required to reuse it correctly.
- CLI `awf workspace adopt-pr` command definition and request payload construction, likely under `src/awf/cli*`.
- MCP server/tool definition and handler for PR adoption if such a tool exists, likely under `src/awf/mcp*`.
- Tests:
  - `tests/unit/api/test_pr_monitor_adoption.py`
  - `tests/unit/service/test_pr_monitor_adoption.py`
  - `tests/unit/cli/test_cli.py`
  - `tests/unit/mcp/test_mcp_server.py` if MCP adoption exists

No migrations are expected if `task_policy` is already a structured/JSON policy container that can store `agent_model` and `agent_effort`.

## Tests To Write First

1. REST/API schema tests:
   - Assert `PullRequestMonitorAdoptionRequest` accepts optional `model` and optional `effort`.
   - Assert OpenAPI/schema output for `/v1/workspaces/adopt-pr` exposes both fields.

2. Service persistence tests:
   - Adoption with explicit `model` and explicit `effort` persists `task_policy.agent_model` and `task_policy.agent_effort`.
   - Adoption with `model` only persists `agent_model` and resolves `agent_effort` through existing default model/effort policy; for Codex models this should be `xhigh`.
   - Adoption with explicit `effort` only persists `agent_effort` and does not fabricate `agent_model` unless existing policy code already requires one.
   - Adoption with neither `model` nor `effort` preserves current behavior and does not add policy keys unnecessarily.

3. Idempotency/conflict tests:
   - Repeating an adoption request with the same PR identity and same resolved policy returns/attaches to the existing live adoption as idempotent.
   - Repeating with a different requested `model` produces a policy conflict.
   - Repeating with a different requested or resolved `effort` produces a policy conflict.
   - Include the model-only default-effort case so conflict comparison uses resolved policy, not just raw request fields.

4. CLI tests:
   - `awf workspace adopt-pr --model <model> --effort <effort>` includes both fields in the JSON payload sent to `/v1/workspaces/adopt-pr`.
   - `--model` without `--effort` sends only `model` so the server remains the source of default effort resolution.
   - CLI help for `awf workspace adopt-pr --help` includes both flags.

5. MCP tests, only if an MCP PR adoption tool exists:
   - Tool input schema exposes optional `model` and `effort` fields.
   - Handler forwards both values into the same adoption service/request path used by REST.
   - Model-only MCP calls get the same default effort behavior as REST.

Each test group should be run first in a failing state before the related implementation change.

## Implementation Plan

1. Locate the current PR monitor adoption surfaces:
   - Find `PullRequestMonitorAdoptionRequest`.
   - Find the REST route and service function that creates or attaches to a PR monitor workspace.
   - Find the live-adoption conflict/idempotency comparison.
   - Find CLI `workspace adopt-pr` command and MCP adoption tool, if present.

2. Extend the REST request model:
   - Add optional `model: str | None` and optional `effort: str | None` fields.
   - Keep defaults as `None` to preserve existing request compatibility.
   - Avoid validation or enum expansion unless existing model/effort request fields elsewhere already use a shared type.

3. Normalize adoption policy in the service layer:
   - Build a small policy fragment from request fields.
   - If `model` is provided, set `agent_model` to that value.
   - If `effort` is provided, set `agent_effort` exactly to that value.
   - If `model` is provided and `effort` is omitted, call the existing AWF default model/effort policy helper to resolve the highest supported/default effort for the selected model; Codex models should resolve to `xhigh`.
   - If neither field is provided, leave `task_policy` unchanged relative to current adoption behavior.

4. Persist policy into adopted workspace/task data:
   - Merge the normalized policy fragment into the adopted workspace `task_policy` at creation time.
   - Preserve unrelated existing task policy values.
   - Do not add a local DB patch or one-off post-adoption mutation path.

5. Update idempotency/conflict comparison:
   - Include the normalized requested `agent_model`/`agent_effort` values in the live adoption policy comparison.
   - Treat identical resolved policy as idempotent.
   - Treat mismatched model or effort as an adoption policy conflict with the existing conflict error style/status.
   - Ensure missing keys remain compatible with old/no-policy adoption requests.

6. Add CLI parity:
   - Add `--model` and `--effort` flags to `awf workspace adopt-pr`.
   - Include fields in the request JSON only when the operator provides them.
   - Leave server-side default effort resolution authoritative.

7. Add MCP parity if applicable:
   - If a PR adoption tool exists, add optional input fields and pass them through to the same service/request path.
   - If no MCP adoption tool exists, document that in validation and do not create a new MCP surface unless the existing architecture clearly expects one.

8. Observability check:
   - Verify `workspace show` or task observability already surfaces task-policy-derived `agent_model`/`agent_effort` once persisted.
   - Only adjust display mapping if existing observability omits these persisted values despite already having a generic task policy display path.

9. Update validation document after implementation in the required validation phase:
   - Save validation findings to the corresponding required validation artifact for the implementation plan workflow.
   - If gaps remain, iterate on the highest-impact gap before finalizing.

## Risks And Assumptions

- Assumption: `task_policy` can already store `agent_model` and `agent_effort` without a schema migration.
- Assumption: AWF already has a reusable default model/effort policy helper; the implementation should call it rather than duplicating a Codex-specific mapping.
- Assumption: Conflict/idempotency checks currently compare enough adoption identity and policy context to extend narrowly.
- Risk: Existing default-effort helper may be oriented around workspace creation rather than PR adoption; if so, a small shared helper may be needed, with tests proving no behavior change for workspace creation.
- Risk: CLI tests may mock HTTP payload construction at a different layer than the command parser; use the existing CLI testing style to avoid brittle assertions.
- Risk: MCP adoption may not exist. The implementation should verify presence before changing MCP and should not invent a new tool outside the requested parity scope.
- Risk: OpenAPI snapshots or generated spec files may need updating if they are checked in; only update generated API artifacts if existing repo workflow requires it.

## Explicit Non-Goals

- Do not rewrite `awf workspace create`.
- Do not change scheduler behavior, provider fallback, circuit breakers, or model execution.
- Do not reimplement PR monitor execution, merge conflict repair, comment handling, CI repair, or auto-merge logic.
- Do not add hardcoded database patching or manual post-adoption mutations.
- Do not change coverage policy or broad validation defaults.
- Do not switch branches, push, rebase, or force-push; AWF owns branch and PR lifecycle.
