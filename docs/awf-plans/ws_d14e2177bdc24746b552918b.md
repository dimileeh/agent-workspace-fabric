# Plan: Profile Secret/Auth Mount Lint Slice

## Goal

Implement the narrow P1 security slice for workspace profile validation: safe declared secret mounts remain valid, unsafe secret targets fail with structured reason codes, and broad host-home auth mounts are rejected or warned according to profile policy while preserving documented local-development compatibility. Do not log secret values.

## Intended Files And Modules To Touch

- `src/awf/profiles/models.py`
  - Extend profile/security models with a small lint policy surface, likely under `security`:
    - default severity for broad host-home auth mounts;
    - explicit local-development compatibility allowance for known narrow credential paths;
    - structured lint finding models/reason-code constants if they belong with schema.
  - Tighten `ProfileSecret` target validation for unsafe mount/env targets and return stable codes through the lint layer rather than relying only on free-text `ValueError` messages.
- `src/awf/profiles/resolver.py`
  - Run profile lint after schema validation for inline, repo-local, registry, detected, and fallback profiles.
  - Raise `ProfileResolutionError` with structured reason codes/findings for blocking profile lint failures.
  - Keep error messages redacted: include secret names, kinds, targets, provider/ref identifiers only when they are references, never raw values.
- `src/awf/profiles/compose.py`
  - Validate profile-declared service volumes before conversion to `ComposeService`.
  - Detect host-home bind sources such as `~`, `$HOME`, `${HOME}`, `${AWF_HOST_HOME}`, `/home/<user>`, or `/Users/<user>` when targeting agent/service auth locations.
  - Permit existing local-service compatibility only for the current known narrow credential paths documented in `README.md`, and only when policy says warn rather than block.
- `src/awf/api/routes/workspaces.py`
  - If `ProfileResolutionError` grows structured codes/findings, include the primary code in the existing `INVALID_PROFILE` 422 payload path without exposing secrets.
- `README.md`
  - Document the compatibility rule: local service mode may mount only listed credential paths; profiles should prefer declared `secrets`; broad host-home mounts are not accepted in strict policy.
- Tests:
  - `tests/unit/profiles/test_security_policy.py`
  - `tests/unit/profiles/test_profiles.py`
  - `tests/unit/profiles/test_profile_lint.py` if a separate lint module is clearer.
  - `tests/unit/node/test_stack_launcher.py` or `tests/unit/profiles/test_profile_compose.py` for service-volume conversion failures/warnings.
  - `tests/unit/api/test_workspaces.py` only if the API error payload is extended.

## Tests To Write First

1. Safe declarations:
   - Profile with `secrets: [{name, kind: "mount", target: "/run/awf/secrets/github-token", provider, ref}]` validates cleanly and produces no lint findings.
   - Profile with `kind: "env"` for a non-reserved env target such as `GITHUB_TOKEN` validates cleanly.
   - Existing local-service known auth paths remain documented and, if represented through lint helpers, produce non-blocking compatibility findings rather than failures under warn policy.

2. Unsafe secret targets:
   - Mount targets `/`, `/home`, `/home/agent`, `/home/agent/.ssh`, `/root`, `/etc`, `/tmp`, `/var`, `/proc`, `/sys`, and path-traversal variants fail.
   - Env targets `PATH`, `HOME`, `USER`, empty strings, and invalid env-var identifiers fail.
   - Raw-looking secret values in `ref` are rejected without the raw value appearing in `str(exc)`.
   - Assertions check stable reason codes such as `SECRET_TARGET_TOO_BROAD`, `SECRET_ENV_TARGET_RESERVED`, and `SECRET_REF_LOOKS_RAW`.

3. Broad host-home auth mounts:
   - Profile-declared service volume from `${HOME}` or `${AWF_HOST_HOME}` to `/home/agent`, `/root`, or broad auth directories blocks by default with a code such as `HOST_HOME_AUTH_MOUNT_TOO_BROAD`.
   - Narrow known credential mounts, such as `${AWF_HOST_HOME}/.config/gh` to `/home/agent/.config/gh:ro`, are accepted or warned according to policy.
   - Writable known auth mounts are rejected unless explicitly seeded into the per-workspace auth directory.

4. Resolver/API propagation:
   - Invalid inline profile fails resolution with a primary structured reason code and redacted detail.
   - `/v2/workspaces` continues returning `422 INVALID_PROFILE`, with structured profile lint details if the response schema is extended.

## Implementation Sequence

1. Add failing profile-lint tests first, starting with `tests/unit/profiles/test_security_policy.py` or a new `test_profile_lint.py`.
2. Add the smallest lint data model:
   - `ProfileLintSeverity` enum: `warning`, `error`;
   - `ProfileLintFinding` with `reason_code`, `message`, `path`, `severity`;
   - `lint_workspace_profile(profile) -> tuple[ProfileLintFinding, ...]`;
   - `profile_lint_errors(profile)` helper for blocking findings.
3. Wire lint into profile resolution so blocking findings become `ProfileResolutionError` with a primary code and findings.
4. Add/adjust schema validators for clearly unsafe secret declarations where Pydantic validation is the right boundary, keeping lint codes available for API/console consumers.
5. Add volume-source inspection in profile compose conversion for profile-declared service volumes. Keep source-path normalization string-based enough to handle `${HOME}` placeholders without expanding host secrets.
6. Update README compatibility docs for known local-service auth mounts and declared secret preference.
7. Run focused tests after each small step, then full requested validation.

## Risks And Mitigations

- Risk: breaking local dogfood service auth by treating existing narrow credential mounts as broad host-home mounts.
  - Mitigation: keep local-service mounts documented and covered by tests; reject only broad home/root/auth-directory mounts or writable host auth mounts.
- Risk: leaking raw secret values through validation errors.
  - Mitigation: assertions check that raw-looking `ref` contents are absent from exception strings and API responses.
- Risk: overfitting path checks to one OS.
  - Mitigation: cover Linux `/home/...`, macOS `/Users/...`, `~`, `$HOME`, `${HOME}`, and `${AWF_HOST_HOME}` forms.
- Risk: conflating profile schema validation with future runtime secret leasing.
  - Mitigation: this slice only validates declarations and structured findings; no secret broker or lease issuance is implemented.
- Risk: Pydantic `ValidationError` cannot easily carry structured reason codes.
  - Mitigation: keep stable codes in a lint finding layer and use schema validators only for hard structural invalidity.

## Assumptions

- Existing local service mode remains compatible with narrow read-only host credential mounts listed in `README.md`.
- Declared `secrets` are the preferred future-facing profile contract, even though full cloud secret lease/broker enforcement is not part of this slice.
- Profile-declared service volumes are the relevant place to catch broad host-home auth mounts in profile/schema/service validation scope.
- The API can keep `error_code="INVALID_PROFILE"` while carrying more detailed profile-lint reason codes inside message/detail fields for future console use.

## Explicit Non-Goals

- No implementation of a cloud secret broker, lease issuance, revocation, or secret material injection.
- No changes to Docker lifecycle ownership, branch handling, merge policy, PR monitor behavior, or workspace cleanup.
- No broad refactor of profile models, compose rendering, or API error schemas beyond what the lint slice requires.
- No changes to actual local-service compose mounts unless tests reveal an existing broad host-home mount.
- No logging of secret values or filesystem reads of secret contents.
