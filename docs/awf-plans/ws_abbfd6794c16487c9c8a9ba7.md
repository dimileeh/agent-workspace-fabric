# Plan: Release Terminal Workspace Runtime Without Destroying Salvage Evidence

## Goal

When a workspace reaches a terminal state (`failed`, `cancelled`, `completed`,
`destroyed`) AWF must stop and remove the live runtime — Docker containers and
networks — that workspace was using, but must preserve everything operators
need for postmortem and salvage: the worktree, Docker volumes, logs, artifacts,
branch/PR metadata, validation/conformance evidence, the original failure
reason/message, and audit events. Today, runtime teardown happens only inside
the explicit `destroy` path
(`src/awf/service/controls.py:862` `WorkspaceControlService.destroy_workspace`)
and inside the stale active-execution recovery
(`src/awf/control/worker.py:1343` `_cleanup_and_fail_stale_active_execution`).
Workspaces that transition directly to `failed/cancelled/completed` keep their
containers/networks alive, and `/readyz` then incorrectly classifies them as
"expected within retention" because
`src/awf/service/orphan_resources.py:_classify` (line 830) does not distinguish
live runtime from salvage evidence.

This plan introduces the smallest safe change that closes that gap and keeps
the implementation materially narrower than the closed PR #226 (which touched
71 files and added ~21.6k lines).

## Implementation Shape

Two narrow changes, both extending existing modules:

1. **Worker-driven terminal runtime release sweep**
   (`src/awf/control/worker.py`). A new periodic helper iterates workspaces
   that are in a non-`destroyed` terminal state and still have a
   `compose_project_name`, calls the already-present `runtime_cleaner` with
   `remove_volumes=False, remove_worktree=False`, and records a success or
   failure event. Idempotency is enforced by a single new event type
   (`workspace.terminal_runtime_released`) — workspaces that already carry it
   are skipped. DB row locks are never held during Docker/Compose IO.

2. **Salvage-vs-leak classification fix**
   (`src/awf/service/orphan_resources.py`). Inside `_classify`, a terminal
   workspace's `container` and `network` resources are always classified as
   `terminal` orphans (leaked live runtime), even within the retention window.
   `volume` and `worktree` resources remain `expected` while within retention
   — they ARE the salvage evidence. The existing public dataclasses
   (`ClassifiedResource`, `OrphanResourceSummary`,
   `legacy_orphan_workspaces_payload`) keep their shape; only the per-kind
   classification rule changes.

No new module, no schema migration, no changes to the state machine,
scheduler, profile parsing, planning, PR monitor, repository scoring, or
adapter surfaces.

## Intended Files / Modules To Touch

### Source

- `src/awf/control/worker.py`
  - New private method `_release_terminal_runtime_resources()` plus its
    listing helper and event-recording helper. Reuses the existing
    `self._runtime_cleaner` (already declared as
    `RuntimeCleanerProtocol`, line 201–212).
  - New per-batch entry point `_maybe_release_terminal_runtime()` modelled on
    `_maybe_recover_stale_active_executions()` (line 748): swallow transient
    DB-connection errors, schedule next run via a monotonic deadline, never
    raise from `run_once`.
  - One call site added inside `run_once()` (line 245) immediately after
    `_maybe_expire_due_secret_leases()` so the sweep runs on the same cadence
    as existing background scans without altering dispatch ordering.
  - New `WorkerConfig` field
    `terminal_runtime_release_scan_interval_seconds` (default identical to
    `stale_active_execution_scan_interval_seconds`, i.e. 300s; configurable so
    tests can drive it to 0).
  - Reason-code and event-type constants
    (`_TERMINAL_RUNTIME_RELEASE_REASON_CODE`,
    `_TERMINAL_RUNTIME_RELEASE_EVENT_TYPE`,
    `_TERMINAL_RUNTIME_RELEASE_FAILED_REASON_CODE`,
    `_TERMINAL_RUNTIME_RELEASE_FAILED_EVENT_TYPE`).
  - Listing query: filter `Workspace.status.in_({failed, cancelled,
    completed})`, `Workspace.compose_project_name.is_not(None)`,
    `Workspace.node_id == self._config.node_id`, and an `~exists(...)`
    sub-clause for `WorkspaceEvent.event_type ==
    workspace.terminal_runtime_released` (or equivalent left-join).
    `destroying`/`destroyed` workspaces are excluded — `destroy_workspace`
    already runs the full cleaner and owns those rows.
  - The helper materialises a small dataclass (e.g. `_TerminalRuntimeCandidate`
    holding `workspace_id`, `status`, `compose_project_name`,
    `compose_file_path`, `repo_url`), commits the listing transaction, then
    invokes `self._runtime_cleaner.cleanup(...)` outside any DB transaction.
  - After IO returns, a short separate transaction:
    - re-fetches the workspace,
    - re-checks status is still terminal and no success event has appeared
      meanwhile,
    - on success: adds `workspace.terminal_runtime_released` event with
      cleanup payload,
    - on failure: adds `workspace.terminal_runtime_release_failed` event with
      cleanup payload and short error message. The workspace's
      `failure_reason` / `failure_message` are **never** touched here so the
      original failure cause is preserved.
  - The sweep never transitions workspace status. It does not touch
    `execution_claimed_by` / `monitor_claimed_by`; for terminal rows those are
    already cleared by upstream paths or are inert.

- `src/awf/service/orphan_resources.py`
  - `_classify(resource, workspace_view)` (line 830) gets a tiny branch:
    when `resource.workspace_id` is in `workspace_view.terminal_ids`,
    classify based on `resource.kind`:
      - `container` and `network`: always
        `classification="terminal"`, `reason="WORKSPACE_TERMINAL_LIVE_RUNTIME"`
        (new reason code) — even if also in `retained_ids`.
      - `volume` and `worktree`: keep the current behaviour — `expected` with
        `WORKSPACE_TERMINAL_WITHIN_RETENTION` when in `retained_ids`,
        `terminal` with `WORKSPACE_TERMINAL` when past retention.
  - No changes to scanning code, no changes to public dataclass schemas. The
    `to_dict()` payloads are unchanged because the `classification` and
    `reason` fields are already strings, and the new `reason` value flows
    through naturally.

## Implementation Approach After Tests Fail

1. Add the new reason codes, event types, and `WorkerConfig` field.
2. Implement `_release_terminal_runtime_resources` plus
   `_maybe_release_terminal_runtime`. Call the latter from `run_once`.
3. Modify `_classify` in `orphan_resources.py` with the kind-aware branch.
4. Update the new tests under TDD; iterate until all pass.
5. Run the focused validation command (see below) and resolve any regression.
6. Tidy imports, type hints, and event payload shapes; ensure
   `WorkspaceCleanupResult.to_dict()` output is what gets stored in event
   payloads (consistent with `_cleanup_and_fail_stale_active_execution`).

### DB-safety pattern (mirrors existing worker patterns)

- Read transaction: list candidates → snapshot fields → commit and close.
- Docker IO: `await self._runtime_cleaner.cleanup(...)` runs with no open DB
  session.
- Write transaction: open a new session via `self._session_factory()`,
  `repo.get(workspace_id)`, re-check `status in TERMINAL`, re-check absence
  of the success event, then `repo.add_event(...)` and `await
  session.commit()`. This is the same shape used by
  `_record_stale_active_execution_detected` (worker.py:1019).

### Idempotency

- Success path writes `workspace.terminal_runtime_released`. The listing query
  excludes workspaces that already carry this event. The post-IO recheck
  guards against the narrow race where two sweeps grab the same workspace
  before either commits. Because Docker compose down on an absent project is
  a no-op (`compose_manager.py:340`), at most one extra harmless duplicate
  IO is possible; no state can diverge.
- Failure path writes `workspace.terminal_runtime_release_failed`. We do
  **not** suppress duplicate failure events; each sweep that retries records
  one event, and the operator can see the retry history. This keeps the diff
  small. If event noise becomes a problem, a later patch can add a per-sweep
  cooldown — explicitly out of scope here.

### Cancellation

- Cancellation raises `CancelledError` either before, during, or after the
  Docker IO. In all three cases the success event simply does not get
  written, the next sweep retries, and Docker compose down's idempotency
  guarantees no state divergence. The sweep does not acquire any new claim
  columns, so there is no claim to release on cancellation.

### Preserving original failure diagnostics

- The sweep writes only events. It never assigns to `Workspace.status`,
  `failure_reason`, or `failure_message`. The original failure cause —
  whether it came from agent failure, validation failure, infrastructure
  failure, conformance, etc. — is preserved as-is on the row. Failure to
  write the success event because of a transient DB error similarly does
  not destroy salvage evidence: the worktree, volumes, logs, artifacts, and
  PR metadata are untouched.

## Risks And Assumptions

- **Assumption:** the sweep frequency (default 300s) is acceptable for the
  P0 outcome. /readyz still surfaces leaked live runtime immediately via the
  classification fix, so an operator detects the leak even before the next
  sweep stops it. If a faster cadence is wanted, the field is configurable.
- **Assumption:** the existing `runtime_cleaner` already enforces the
  preservation contract when called with `remove_volumes=False,
  remove_worktree=False` — verified at
  `src/awf/node/cleanup.py:149-254` and
  `src/awf/node/compose_manager.py:321-389`.
- **Assumption:** `node_id` filtering is sufficient to scope the sweep to
  the worker's own node, matching the existing stale-active-execution scan
  (worker.py:899).
- **Risk:** if a workspace transitions to `destroying` between listing and
  IO, the destroy operation in `controls.py` will also call compose down at
  about the same time. Both calls are idempotent and operate on the same
  compose project; the worst case is two sequential `docker compose down`
  calls on an absent project, which is a logged no-op. The post-IO recheck
  refuses to write the success event if status is no longer terminal,
  preventing event divergence.
- **Risk:** the new classification rule changes
  `legacy_orphan_workspaces_payload` output shape only by widening the set of
  workspaces flagged as orphans within retention. Existing health tests that
  use a `>200h` `updated_at` (e.g.
  `test_readyz_orphan_resources_present_returns_503`,
  test_health.py:1414) remain unaffected because the workspace is past
  retention. Tests that rely on retained terminal worktrees passing through
  as `expected` (e.g.
  `test_retained_terminal_workspace_resources_are_not_orphans`,
  test_orphan_resources.py:191) are still correct because they only touch
  worktrees.
- **Risk:** introducing a sweep into `run_once` adds one short DB read each
  poll batch. The query is index-friendly (status + node_id + a NOT-EXISTS
  on workspace_events.event_type) and gated by a monotonic deadline so the
  full sweep only runs every
  `terminal_runtime_release_scan_interval_seconds`. Hot-path overhead is
  bounded by a single deadline check.
- **Risk of scope creep:** PR #226 hit 71 files because it tried to also
  rework `readyz` semantics, expand cleanup-step taxonomy, and surface
  retained-evidence aggregates in many payloads. This plan keeps payload
  shapes stable, reuses the existing cleaner protocol, and avoids any new
  orchestration module. If review surfaces a need for richer evidence
  totals or per-kind breakdowns those are explicit follow-ups.

## Explicit Non-Goals

- Do not introduce a new orchestration module, controller, service class, or
  background process. The work is a new method on the existing
  `ControlWorker` and a tiny edit to `orphan_resources._classify`.
- Do not change the workspace state machine, the `transition` semantics,
  resource reservation release, or the destroy path's strong-cleanup
  contract.
- Do not change DB schema, add migrations, or add new repository methods.
- Do not change scheduler scoring, profile parsing, planning, PR monitor,
  validation pipeline, conformance/salvage capture, repository scoring,
  agent prompt transport, or any unrelated API surface.
- Do not modify `WorkspaceCleanupResult` or its `to_dict()` shape. Event
  payloads carry whatever the cleaner returns today.
- Do not remove worktrees, volumes, branches, PR metadata, audit events,
  failure diagnostics, or conformance-salvage evidence as part of the sweep.
- Do not change `/readyz` request handling, scoreboard structure, retention
  thresholds, or the `release-readiness` scorecard.
- Do not import code, tests, or design patterns from the closed PR #226
  branch (`awf/ws_de86ae75f42943d1830f1b0c`). Start from
  `codex/awf-post-merge-fixes` and build the minimal slice described here.
- Do not add a new failure taxonomy entry; cleanup failures from the sweep
  surface as events, not as a new `FailureReason` enum value.
- Do not add per-failure-event suppression or backoff in this PR. If event
  noise becomes a real problem, that is a follow-up.
