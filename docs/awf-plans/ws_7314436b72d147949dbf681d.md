# Plan: Merge Queue Operator Context Slice

## Scope

Implement the narrow P0 console slice from `TODO/pre-gke-industrial-readiness.md`: make the operator console Merge Queue panel clearly show candidate blockers, active stale reasons, required next action, and canonical-attempt/readiness context while keeping PR row details collapsed by default.

This is planned as a console-only change. The existing `/v1/merge-queue` API already exposes the needed fields: `merge_blocker_reason`, `required_next_action`, `readiness`, `canonical`, `queue_blockers`, `latest_validation`, and `stale_reasons`. Backend work is not planned unless implementation uncovers a tiny schema or mapping mismatch between the documented API response and actual payload.

## Intended Files And Modules

- `apps/console/lib/types.ts`
  - Align frontend merge queue types with the API schema:
    - add `waiting_for_older_candidate` and `policy_blocked` to `MergeBlockerReason`;
    - add `stale_reason` to `MergeCandidateReadiness`;
    - add `required_next_action` to `MergeQueueItem`;
    - add `queue_blockers` to `MergeQueueItem`;
    - add a `MergeQueueBlocker` type;
    - add validation summary fields already returned by the API if the display uses them, such as retry and coverage metadata.

- `apps/console/lib/merge-queue-format.ts` (new)
  - Add focused, testable formatting helpers used by the panel, likely including:
    - `activeStaleReasons(item)` to filter stale reasons to `status === "active"`;
    - `formatRequiredNextAction(action, blockerReason)` for dense operator labels such as `rebase`, `validate`, `resolve policy`, `wait for queue`, or `none`;
    - `formatMergeBlockerReason(reason)` for human-readable blocker labels without hiding raw codes where useful;
    - `summarizeQueueBlockers(item)` for count plus first blocker title/PR/status;
    - `summarizeStaleReasons(item)` for active stale reason codes, trigger refs, and overflow count;
    - `summarizeReadiness(item)` for candidate/readiness state including legacy/null readiness fallback;
    - `summarizeValidation(item)` for tier, status, freshness, target/current head, and coverage status when present.
  - Move or mirror the current local `readinessSummary` and `mergeQueueMergedAt` behavior here if that keeps row rendering simpler and testable.

- `apps/console/lib/merge-queue-format.test.mjs` (new)
  - Add Node test coverage for the data formatting helpers before implementation.

- `apps/console/components/console-dashboard.tsx`
  - Import the new helpers.
  - Keep `expandedRows` initialized to an empty `Set`, preserving collapsed PR details by default.
  - Update the collapsed row to show dense operational context:
    - blocker reason and required next action;
    - canonical/superseded and candidate/attempt identifiers;
    - readiness summary and latest validation freshness/tier;
    - active stale reason summary;
    - queue blocker summary for older candidate or monitor-owned recovery blockers.
  - Keep the expanded details as a secondary drill-down for full stale reason and queue blocker rows, PR links, timestamps, validation hashes, and raw codes where useful.
  - Reuse the existing restrained visual language: compact badges, small grid rows, muted text, existing tone classes, no decorative cards or marketing layout.

## Tests To Write First

The console currently has `node --test` helper tests but no React component test setup or DOM testing dependency, so the first tests will target the new formatting helper module.

1. `apps/console/lib/merge-queue-format.test.mjs`
   - Failing test: a stale candidate with multiple stale reasons returns only active reasons in the stale summary, includes reason codes/trigger refs, and maps `required_next_action: "rebase"` to a clear action label.
   - Failing test: a candidate blocked by an older queue candidate returns a queue blocker summary with blocker count, first blocker title, PR number, blocker state, and `wait_for_queue` action.
   - Failing test: canonical/readiness formatting distinguishes `canonical` from `superseded`, handles `readiness.stale_reason`, and preserves a legacy/null readiness fallback.
   - Failing test: validation formatting shows tier, status, freshness, and target/current head context for fresh and stale validation runs.

2. Existing tests remain in place:
   - `apps/console/lib/format.test.mjs`
   - `apps/console/lib/agent-format.test.mjs`

If a lightweight component test setup is already added by another concurrent change before implementation, add one focused render test for collapsed merge queue rows. Otherwise, do not introduce a React test framework just for this narrow slice.

## Implementation Steps

4. Refactor `MergeQueueRow` in `apps/console/components/console-dashboard.tsx` to use the helpers:

   - expanded details include full blocker/stale/validation context without requiring backend changes.
5. Run focused tests, lint, and typecheck.
6. Inspect the final diff to confirm no backend files, config, lockfiles, migrations, or unrelated docs changed.

## Risks And Mitigations

- API/frontend type drift: the backend schema currently has fields not represented in `apps/console/lib/types.ts`. Mitigate by updating frontend types to match the existing API contract and keeping helpers tolerant of null/legacy payloads.
- Dense row readability: adding blockers, stale reasons, validation, and action context can overcrowd the row. Mitigate with short labels, first-item-plus-count summaries, truncation, and full detail only inside the already collapsed details area.
- Backend behavior ambiguity: `required_next_action` may be null for some blocker states. Mitigate with deterministic fallback labels derived from `merge_blocker_reason` without inventing new API semantics.
- Legacy merge queue items: candidate fields can be null. Mitigate with explicit legacy fallbacks for candidate id, attempt id, readiness, queue blockers, stale reasons, and validation.

## Assumptions

- `/v1/merge-queue` is the source of truth for this slice.
- `stale_reasons` returned by the merge queue endpoint are intended to be active reasons, but the UI helper will still filter by `status === "active"` defensively.
- The operator value is in fast scanning, not a new workflow control surface.
- The existing panel height and polling behavior are acceptable for this narrow slice.

## Explicit Non-Goals

- No new backend merge policy, stale detection, validation provenance, or PR monitor behavior.
- No new mutating console controls for rebase, refresh, remonitor, validate, or make-canonical.
- No changes to migrations, lockfiles, coverage thresholds, Python backend tests, or unrelated docs.
- No branch switching, pushing, PR creation, rebasing, or manual AWF lifecycle work.
