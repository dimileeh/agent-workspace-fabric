# Issue 310 Cursor CLI Agent Runtime Plan

## Scope

Add the Cursor CLI coding agent as a new AWF `AgentRuntime` named `cursor`, backed by the installed `cursor-agent` binary. This is additive: existing `codex`, `claude_code`, `gemini`, and `opencode` behavior must remain unchanged.

The adapter will follow AWF's current runner convention: the wrapped AWF prompt stays on stdin, and `_cli_args()` only returns the CLI argv. Cursor print mode will be invoked as `cursor-agent -p --force ...`, with `--force` always present so non-interactive runs can write inside the workspace container. The adapter docstring will cite the official Cursor CLI overview and headless docs:

- https://cursor.com/docs/cli/overview
- https://cursor.com/docs/cli/headless

## Intended Files and Modules

Core runtime registration:

- `src/awf/db/enums.py`: add `AgentRuntime.cursor = "cursor"` with a docstring describing `cursor-agent -p --force`.
- `src/awf/adapters/cursor.py`: new `CursorAdapter(AgentAdapter)` with `runtime`, `name`, `get_provider() == "cursor"`, `_cli_args()`, and documented effort behavior.
- `src/awf/adapters/registry.py`: import `cursor` so `@register_adapter` populates the registry.
- `src/awf/adapters/__init__.py`: update adapter package wording if it names the complete runtime set.
- `src/awf/adapters/defaults.py`: add cursor defaults. Planned default: `AgentDefaults(model="sonnet-4-thinking", effort="xhigh")`, using Cursor's documented thinking-capable model variant as the portable high-effort mechanism. No undocumented Cursor thinking flags will be introduced.

Adapter behavior:

- `_cli_args(model=...)` should return `cursor-agent`, `-p`, `--force`, optional `-m <model>`, and `--output-format text`.
- The prompt must not be placed in argv.
- Effort handling will be documented as model-selection based/no separate flag: AWF's default chooses a thinking model for `xhigh`; explicit models are respected unchanged; low/medium/high/xhigh do not add undocumented CLI flags.

Provider readiness, auth, and redaction:

- `src/awf/service/provider_readiness.py`: add `cursor` to `ProviderName`, `PROVIDER_NAMES`, `KNOWN_SECRET_ENV_KEYS`, launch-provider mapping, env-key list (`CURSOR_API_KEY`), `_check_provider_readiness`, CLI executable mapping (`cursor-agent`), reason-code prefix, selected preflight behavior, and readiness payloads.
- `src/awf/service/provider_readiness_helpers.py`: update imports/types if needed by the new provider name or known secret set.
- `src/awf/profiles/compose.py`: add `CURSOR_API_KEY` to `AGENT_AUTH_ENV_VARS` so workspace compose files receive `${CURSOR_API_KEY}` placeholders without recording the raw key.
- `docker/compose/local-service.yml`: forward `CURSOR_API_KEY` into the API/worker service environment so local service readiness and workspace launch can see it.
- `src/awf/node/auth_mounts.py`: verify no directory mount is needed for Cursor. Avoid adding a `~/.cursor` mount unless tests reveal an existing provider-suppression path needs an explicit no-mount entry.
- `src/awf/service/doctor/__init__.py` and `src/awf/service/doctor/reasons.py`: add Cursor provider diagnostics and `CURSOR_AUTH_MISSING` reason text.
- `docs/REASON_CATALOG.md`, `docs/GETTING_STARTED.md`, `docs/TROUBLESHOOTING.md`, and live runtime/auth docs that enumerate providers: add Cursor/CURSOR_API_KEY where these are operator-facing. Do not rewrite historical plan docs unless tests require it.

Provider failure and recovery:

- `src/awf/adapters/provider_failures.py`: add Cursor auth markers (`cursor_api_key`, `CURSOR_API_KEY`, `cursor-agent`, Cursor auth wording) and provider inference markers when Cursor appears in output. Ensure redaction uses the common secret redactor and never logs the key.
- `src/awf/service/provider_recovery.py`: map `cursor` to provider `cursor`. Because Cursor is a gateway runtime, special-case `provider_for_agent_model("cursor", model)` to return `cursor` before model-name inference can classify `sonnet-*` as Anthropic or `gpt-*` as OpenAI.

Runtime image and local service surfaces:

- `docker/agent-runtime.Dockerfile`: install Cursor with `curl https://cursor.com/install -fsS | bash`. If the installer exposes a version pin, add `ARG CURSOR_VERSION=...`; otherwise document that this tracks the official installer. Ensure `cursor-agent` is on `PATH` for the non-root `agent` user, likely by symlinking/copying from the installer location into `/usr/local/bin` if the installer writes under root home. Add `cursor-agent --version || true` to the CLI version smoke lines.
- `tests/unit/test_agent_runtime_dockerfile.py`: assert the Cursor installer command, non-npm shape, `cursor-agent` binary, version check, and no npm package install for Cursor.
- `docker/compose/local-service.yml`: covered above for `CURSOR_API_KEY` propagation.

CLI, API, MCP, smoke, usage, and profile wiring:

- `src/awf/cli/workspace_commands.py`: confirm `--agent cursor` and `adopt-pr --agent cursor` work through `AgentRuntime`; update help text if it enumerates runtimes.
- `src/awf/cli/service_commands.py`: update provider help text to include `cursor`.
- `src/awf/mcp/control_tools.py`, `src/awf/mcp/workspace_tools.py`, `src/awf/mcp/metrics_tools.py`: update provider/runtime descriptions where they enumerate provider names.
- `src/awf/api/schemas.py`: no manual enum list is expected, but OpenAPI drift must be checked because `AgentRuntime` is surfaced in request/response schemas.

- `src/awf/service/usage_store.py` and `src/awf/service/usage_collection.py`: add Cursor to provider/source mapping if `ccusage cursor` is supported by the pinned `ccusage`; otherwise keep a reason-coded unsupported path and document the gap. The implementation should not call a real Cursor CLI.
- `src/awf/runtime/pr_monitor.py` and `src/awf/runtime/pr_monitor_runner/runner.py`: inspect any runtime enumerations and update only if Cursor is explicitly omitted.
- `src/awf/profiles/*`: update runtime/provider enumerations and live docs/help text only where Cursor must be user-selectable or visible.
- `src/awf/__init__.py`: update top-level package description if it names the complete supported runtime set.

## Risks and Assumptions

- The Cursor installer may not expose a stable version pin. If so, the Dockerfile must clearly document that it tracks the official installer and the Dockerfile test should assert that documented behavior, not a fake pin.
- The installer may place `cursor-agent` under the installing user's home. The Dockerfile must ensure the binary is available to the final non-root `agent` user on `PATH`.
- Cursor has no documented portable effort flag. The safe mapping is model selection only: default to a thinking-capable model for `xhigh`, respect explicit model overrides, and do not invent flags.
- `ccusage` Cursor support is uncertain. If the pinned `ccusage` supports a `cursor` source, wire it. If it does not, leave Cursor usage reason-coded as unsupported and document the reason in validation.
- Readiness can only validate local signals: `CURSOR_API_KEY` presence and `cursor-agent` binary presence in the agent runtime image. It cannot prove the key is valid without a real Cursor API call, which is out of scope for this sandbox.
- Existing runtime semantics and provider mappings must not regress. Cursor provider classification should remain `cursor` even when the model name looks like Anthropic or OpenAI.

## Explicit Non-goals
