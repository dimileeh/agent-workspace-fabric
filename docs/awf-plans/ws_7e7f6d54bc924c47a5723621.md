## 1. Acceptance Criteria Summary

From the checklist:
> Record outbound egress audit evidence without leaking secrets: workspace id, policy posture, destination host/category, allow/deny decision, timestamp, and reason code for policy-controlled network attempts; expose summary counts in service status, workspace detail, MCP, metrics, and console security panels.

With the local Docker backend, per-destination filtering is deferred (the `local_egress_plan()` produces `network_internal`/`host_gateway_enabled` booleans for the entire compose project). The audit evidence therefore records **egress policy enforcement events** at the workspace level, not per-packet decisions. The "destination host/category" field is set to the category that describes the decision scope: `"policy_decision"` for the initial enforcement, with the mode and allowlist templates captured as metadata.

## 2. Implementation Approach

### 2.1 Data Model: `EgressAuditRecord`

A new SQLAlchemy model and DB migration to persist egress audit evidence per workspace:

| Column | Type | Description |
| ------ | ---- | ----------- |
| `id` | UUID (PK) | Stable identifier |
| `workspace_id` | UUID (FK → workspaces) | The workspace whose egress policy was enforced |
| `attempt_id` | UUID (FK, nullable) | The task attempt during which the enforcement happened |
| `policy_posture` | VARCHAR | `open`, `restricted`, `offline` |
| `decision` | VARCHAR | `allow`, `deny`, `deferred` |
| `destination_category` | VARCHAR | `policy_decision`, `public_internet`, `internal_only` |
| `reason_code` | VARCHAR | `LOCAL_EGRESS_OPEN_UNRESTRICTED`, `LOCAL_EGRESS_OFFLINE_NETWORK`, `LOCAL_EGRESS_RESTRICTED_LOCAL_ONLY` |
| `details` | JSONB | Allowlist templates, network settings, any deferred-enforcement notes |
| `enforced_at` | TIMESTAMPTZ | When the policy was applied |
| `created_at` | TIMESTAMPTZ | Row creation time |

The details JSON is redacted using `redact_audit_value()` before persistence to prevent secrets from leaking.

### 2.2 Audit Recording Point

During workspace provisioning (in `stack_launcher.py` or `provisioner.py`), after computing `local_egress_plan()`, persist an `EgressAuditRecord`. The `decision` field is derived from the mode:
- `open` → `allow` (public internet allowed)
- `offline` → `deny` (all internet denied)
- `restricted` → `deferred` (internal-only with destination filtering deferred)

### 2.3 Summary Counts and Exposure Surfaces

**Service status** (`/readyz`, `collect_service_status`):
- Add `egress_audit` field to `ReadyResponse` with per-posture counts (open/restricted/offline) and deferred-enforcement note.
- Add a new check to `collect_service_status()` returns: `egress_audit` with `active_counts_by_posture`, `recent_enforcement_count`, and `deferred_enforcement_note`.

**Workspace detail** (`GET /v1/workspaces/{id}`):
- Add `egress_audit` field to `WorkspaceResponse` containing the latest `EgressAuditRecord` for that workspace.

**MCP**:
- New read-only MCP tool: `awf_get_egress_audit_evidence` — returns the latest audit record for a workspace, or all records if no workspace_id filter.
- Existing `awf_get_workspace` will automatically include the new `egress_audit` field.

**Metrics** (`GET /v1/metrics/resources/saturation`):
- Add `egress_posture_counts` to `ResourceSaturationSummaryResponse` with `open`, `restricted`, `offline`, `deferred` counts.

**Console security panels**:
- Extend `SecurityEgressPanel` to display the `egress_audit` evidence from the workspace's latest audit record, including enforcement timestamp and reason code.

### 2.4 Secret Redaction

- All audit payloads pass through `redact_audit_value()` before DB persistence.
- API responses for egress audit evidence must use `_console_safe_profile_snapshot()`-equivalent redaction.
- Regression tests explicitly prove that known token patterns (`ghp_*`, `github_pat_*`, `sk-*`, `xox*`, etc.) are never persisted or returned.

## 6. Risks, Assumptions, Non-Goals

### Risks
- **OWNED_PATH_OVERLAP_RISK**: Multiple workspaces are touching overlapping test paths (`tests/unit/**`) and `src/awf/api/**`, `src/awf/mcp/**`. We must keep changes scoped to avoid merge conflicts with the other active workspaces (`ws_72055a2cbe8148b4a7d1468e`, `ws_2f77344b87ba4cf987d62cbe`, `ws_ce68a96b836442eb96a1255a`). Specifically:
  - Avoid modifying existing MCP test files — create new focused test files
  - Add new route endpoints rather than heavily refactoring existing ones
  - Use `append`-style additions to existing schema fields
- Migration ordering — ensure the new migration sorts correctly alongside any in-progress migrations from other workspaces.

### Assumptions
- The local Docker backend's `LocalEgressPlan` is the current truth for what egress policy is enforced. We don't need to implement actual per-request interception yet (that's deferred to a future proxy/firewall backend).
- `destination_category` values are coarse (`policy_decision`, `public_internet`, `internal_only`) for the local backend; finer categories like `github`, `pypi` will come when per-destination filtering is no longer deferred.
- The `decision` value `deferred` is a legitimate audit state reflecting the local backend's posture.

### Explicit Non-Goals
- Per-packet or per-request network interception — that requires a proxy/firewall backend, which is deferred.
- Changing the existing `ProfileEgress` model or `local_egress_plan()` signature.
- Creating a full egress audit dashboard or timeline view in the console — only summary counts and the latest audit record per workspace.
- Adding egress audit to the CLI surface beyond what `awf service status` already shows.
- Modifying existing `WorkspaceEvent` event_type enumeration to add egress events — we use the dedicated `EgressAuditRecord` table instead.
