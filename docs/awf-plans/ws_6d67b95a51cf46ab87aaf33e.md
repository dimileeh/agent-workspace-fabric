# Plan: Console Validation Freshness And Stale Recovery Visibility

## Goal

Make the operator console surface merge-safety signals that currently require
reading API payloads: required validation tier, latest satisfied validation
tier, validation freshness, target/base SHA snippets, stale reasons, blockers,
and the recommended recovery action.

Workspace remains the primary UI concept. The merge queue is treated as the PR
integration view for workspaces, and the selected workspace detail gets a
compact validation/staleness summary without reintroducing task-centric main
pane language.

## Intended Files And Modules To Touch

Primary console files:

| File | Intended changes |
| --- | --- |
| `apps/console/lib/merge-queue-format.ts` | Extend type-safe summarizers for validation tier requirements, latest satisfied tier, freshness, base/target/current SHA snippets, blockers, stale reasons, and recommended action labels. Keep pure formatting logic here so Node tests can cover it. |
| `apps/console/lib/merge-queue-format.test.mjs` | Add regression tests for the new formatting/summarization helpers before component edits. |

Backend compatibility files only if absolutely necessary:

| File | Possible minimal change |
| --- | --- |
| `src/awf/api/schemas.py` | Add optional `required_validation_tier` and/or `latest_satisfied_validation_tier` to `MergeQueueItemResponse` only if the console cannot derive them accurately from existing fields. |

Files not expected to change:

- No migrations, lockfiles, package metadata, or unrelated docs.

- No task-list UI or main-pane task mental model.

## Tests To Write First

Use the existing console test setup: `npm --prefix apps/console test` runs
Node tests for `apps/console/lib/*.test.mjs`. There is no React component test
harness, so keep the render changes small and push behavioral coverage into
pure helpers.

1. Extend `apps/console/lib/merge-queue-format.test.mjs` with
   `test("validation recovery summary shows required tier, satisfied tier, freshness, and heads")`.
   - Arrange a merge queue item with `latest_validation.tier=2`,
     `fresh_for_target=false`, `target_head_sha`, `current_target_head_sha`,
     `base_commit`, and a stale validation action.
   - Assert the helper returns:
     - required tier label, such as `T2 required`;
     - latest satisfied tier label, such as `T2 satisfied` or `none satisfied`;
     - freshness label, such as `stale target`;
     - compact `base`, `validated target`, and `current target` SHA snippets;
     - recommended action `validate` or `rebase`, depending on the stale state.

2. Add `test("recovery summary maps stale reasons and queue blockers into compact details")`.
   - Include multiple active stale reasons, one resolved stale reason, queue
     blockers, and policy findings.
   - Assert active reasons are counted and truncated consistently, blockers
     include the older workspace/candidate context, and resolved reasons are not
     counted as active.

3. Add `test("recovery summary falls back safely for legacy or missing validation data")`.
   - Arrange a legacy merge queue row with no candidate id and no latest
     validation.
   - Assert labels are stable (`unknown`, `none`, or `legacy` as appropriate),
     no helper throws on null fields, and action fallback still comes from
     `merge_blocker_reason`.

4. If backend compatibility fields are needed, add a focused API regression in
   `tests/unit/api/test_merge_queue.py`.
   - Seed a candidate whose task class and post-rebase state require a higher
     tier than the latest run satisfies.
   - Assert `/v1/merge-queue` includes the optional tier fields and preserves
     existing `latest_validation`, stale reasons, blockers, and
     `required_next_action`.

Run the console tests after adding the first failing helper assertions, then
implement the smallest helper changes to make them pass before touching
`console-dashboard.tsx`.

## Implementation Steps

1. Add pure helper coverage.
   - Introduce a small summary shape in `merge-queue-format.ts`, for example
     `summarizeRecovery(item)`, or extend `summarizeValidation(item)` if that
     keeps call sites simpler.
   - Prefer existing helpers (`summarizeStaleReasons`,
     `summarizeQueueBlockers`, `formatRequiredNextAction`,
     `requiredNextActionTone`) over duplicating labels in React.

2. Determine tier source with a compatibility-first approach.
   - Use existing API fields first: `task_class`, `latest_validation.tier`,
     `latest_validation.status`, `fresh_for_target`, stale reason
     `validation_insufficient_tier`, and `required_next_action`.
   - If this cannot produce an accurate required tier or latest satisfied tier,
     add optional response fields in the merge queue API and mirror them in
     `apps/console/lib/types.ts`.
   - Keep new fields additive and nullable/optional for old API snapshots.

3. Update the merge queue row.
   - In the collapsed row, show compact chips for:
     - recommended action;
     - blocker status;
     - required tier and latest satisfied tier;
     - freshness;
     - target/base SHA snippets;
     - stale reason count/summary;
     - queue blockers.
   - Keep the existing row detail toggle collapsed by default and use the
     expanded area for full stale reason, blocker, policy finding, validation,
     branch, and SHA details.
   - Preserve wrapping/truncation through `min-w-0`, `truncate`, and responsive
     grids; avoid tables or fixed min-width content in the merge queue panel.

4. Update selected workspace detail.
   - Find the selected workspace's merge queue item from the loaded queue by
     `workspace_id` and pass it to `WorkspaceSummary`.
   - Add a compact "Validation freshness" / "Recovery" block inside the
     existing Workspace panel, near branch/base/status facts.
   - Show workspace-centric language: workspace id, branch, base, validation,
     freshness, blocker, stale reasons, and action. Do not add task ids or task
     mental-model labels to the main pane.
   - If the selected workspace is not in the merge queue, show a minimal
     non-queued state rather than inventing missing recovery data.

5. Polish responsive behavior.
   - Keep card radius and existing visual language unchanged.
   - Ensure long stale reason codes, SHAs, branch names, and PR titles truncate
     or wrap within their cells.
   - Keep collapsed details by default and verify the merge queue container does
     not introduce horizontal overflow on narrow screens.

6. Commit during the implementation phase after validation passes.
   - Do not push, rebase, or switch branches; AWF owns branch and PR handling.

## Risks And Assumptions

- The current console has no React test harness. Assumption: pure helper tests
  plus lint/typecheck/build are acceptable console-side coverage for this slice.
- Required tier may not be fully derivable from the current merge queue payload
  after a rebase because `task_class` alone does not encode the post-rebase tier
  bump. Risk: a tiny additive API compatibility field may be required.
- Latest satisfied tier is ambiguous if only the latest validation run is
  exposed and that run failed while an earlier successful run exists. Risk:
  accurate display may require API support; otherwise the console should label
  it as "latest run" or "unknown" rather than overclaim.
- Stale reason explanations, branch names, and SHA values can be long. The UI
  must treat every value as untrusted display text and preserve `min-w-0`,
  wrapping, truncation, and mobile grids.
- The merge queue fetch is limited to the first 20 candidates today. Assumption:
  workspace detail can only show queue recovery data for candidates present in
  that snapshot unless a later API slice adds workspace-specific merge queue
  lookup.

## Explicit Non-Goals

- No new recovery action endpoints or buttons. This slice makes recommended
  actions visible; it does not execute refresh/rebase/validate/remonitor/human
  actions from the console.
- No backend scheduling, staleness detection, validation provenance, or PR
  monitor behavior changes.
- No redesign of the console shell, navigation, workspace list, logs, runtime,
  or lifecycle panels.
- No reintroduction of task-centric main-pane views, task tables, or task ids as
  primary labels.
- No horizontal-scroll tables for the new merge queue/workspace recovery
  content.
