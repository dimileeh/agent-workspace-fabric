# Plan: P1 Local Service Bootstrap

## Goal

Make local AWF service startup a repeatable one-command operator path while
preserving the current Docker Compose workflow.

Target operator flow:

```bash
cp .env.example .env
uv run --python 3.12 --extra dev awf service bootstrap
uv run --python 3.12 --extra dev awf service status --format pretty
```

`awf service bootstrap` should:

- ensure the agent runtime image exists, unless explicitly skipped;
- start the local Postgres service;
- run Alembic through the existing Compose `migrate` service;
- start the API and worker services;
- poll service health/readiness through existing AWF status checks;
- be safe to re-run when containers and volumes already exist.

The existing direct Compose path remains supported:

```bash
docker compose -f docker/compose/local-service.yml up --build
```

## Current Code Context

- `docker/compose/local-service.yml`
  - already defines `postgres`, one-shot `migrate`, `api`, and `worker`.
  - `api` and `worker` depend on healthy Postgres and successful `migrate`.

- `src/awf/cli/main.py`
  - owns the Typer CLI.
  - already exposes `awf service status`, `config`, `logs`, `gc`, and
    `reconcile-target`.

- `src/awf/service/logs.py`
  - already centralizes `LOCAL_SERVICE_COMPOSE_FILE`.
  - has testable subprocess injection patterns for Docker Compose wrappers.

- `src/awf/service/status.py`
  - owns `collect_service_status(...)`, which already checks API health,
    DB connectivity, Docker, runtime image, disk, orphan resources, cleanup
    readiness, and provider readiness.
  - has injection seams for unit tests.

- `src/awf/service/config.py`
  - resolves local service settings, including Postgres defaults and agent
    runtime image name.

- `README.md`
  - documents manual Compose startup and manual migration commands, but does
    not yet present a single repeatable bootstrap command as the preferred
    local service path.

## Implementation Steps

1. Add `src/awf/service/bootstrap.py`.
   - Define `ServiceBootstrapOptions`, `ServiceBootstrapResult`, and
     `ServiceBootstrapError`.
   - Keep payloads JSON-serializable.
   - Model each stage with a name and command so error output is actionable.
   - Use `subprocess.run(..., check=False, capture_output=True, text=True)` via
     an injected runner.

2. Build commands conservatively around the existing Compose file.
   - Build the agent runtime image by default because `service status` verifies
     `AWF_AGENT_RUNTIME_IMAGE`.
   - Start Postgres first with `up -d --build postgres`.
   - Run migrations with `up --build --force-recreate migrate` so every
     bootstrap pass runs Alembic even if a previous one-shot migrate container
     already completed.
   - Start API and worker with `up -d --build api worker`.
   - Do not add cleanup, volume removal, or container deletion to bootstrap.

3. Poll readiness through `collect_service_status(...)`.
   - Resolve settings with `resolve_service_settings()`.
   - Treat top-level `status == "ok"` as success.
   - Continue polling until timeout for transient API startup lag.
   - Include the last status payload in timeout errors.
   - Pass strict providers through the same validator used by
     `awf service status`.

4. Add the Typer command in `src/awf/cli/main.py`.
   - Keep CLI glue thin.
   - Reuse `_emit(...)` for JSON/pretty output.
   - Print concise errors to stderr and exit non-zero.

5. Update README.
   - In "Local Service Stack", replace the primary startup snippet with
     `awf service bootstrap`.
   - Keep direct Compose commands immediately below as the lower-level/manual
     equivalent.
   - In "Database Migrations", state that bootstrap runs the Compose `migrate`
     service before API/worker startup; retain manual migration examples.
   - In "Observability", use the bootstrap command for starting the full stack.

6. Run focused tests and iterate.

7. Run required validation.

## Risks And Mitigations

- Docker Compose one-shot service behavior can skip an already-completed
  `migrate` container. Mitigation: make the bootstrap migration stage use
  `--force-recreate migrate`.

- `collect_service_status(...)` checks the agent runtime image, so a pure
  Compose startup can be healthy but status can fail if
  `awf-agent-runtime:latest` is missing. Mitigation: build the configured agent
  runtime image by default, with `--skip-agent-runtime-build` only for operators
  who know it already exists.

- Ports `8000` and `5433` may already be occupied by non-AWF processes.
  Mitigation: surface the failing Compose stage and stderr rather than retrying
  blindly.

- Docker Desktop host-path and SSH socket mounts can differ by platform.
  Mitigation: do not broaden mounts or change Compose defaults in this slice;
  document the current assumptions and rely on existing readiness/status output.

- Strict provider readiness may fail bootstrap for missing credentials.
  Mitigation: keep providers optional by default and only enforce providers
  explicitly passed with `--provider`.

- Running Postgres migrations inside API startup could create multi-process
  races later. Mitigation: this slice chooses clearly documented bootstrap and
  Compose `migrate` orchestration rather than API-lifespan Postgres migrations.

## Assumptions

- The bootstrap command is run from the repository root in a local development
  shell with Docker and the Docker Compose plugin available.
- Local service mode continues to use the existing
  `docker/compose/local-service.yml` stack and host Docker daemon.
- Alembic migrations are idempotent when run at the current head, as expected
  for `alembic upgrade head`.
- `awf service status` remains the authoritative local health verification
  surface.
- Optional provider credentials are not required for generic bootstrap success.
