# Implementation Plan: P0 Reliability/Cleanup/SLO Metrics Slice

**Workspace:** ws_3c3d5b6f539245ec84f36d2e
**Date:** 2026-04-28
**Status:** Planning

## Summary

Expose rolling creation success, cleanup success, stuck-state, recovery success,
and monitor-health/SLO indicators through a new `GET /v1/metrics/slo` endpoint and
the existing metrics service layer. All counts are integer fields (not
percentages) derived from persisted workspace rows, events, and operations.
No console UI changes, no DB migrations, no new config settings.

## Context

- **PRD Section 19** defines EXIT_CRITERION metrics: creation success rate
  (≥98% over 7-day rolling window excluding cancelled), cleanup success rate
  (≥99% eventual), stuck-state rate (<0.5% beyond 2×SLA without reason code),
  actionable reason code coverage (≥95% of failures), and retry success rate.
- **PRD Section 10** defines the `cleanup_failure` failure class with async
  retry handling.
- Previous workspace `ws_15fcdd21401d4d0495747d03` implemented this slice
  fully (commit `90a77ed` on its branch) but was not merged. This plan
  re-specifies the same feature cleanly for the current branch, incorporating
  lessons from that prior work:
  - The `SloMetricsSummary` dataclass must use `create` operation rows for
    creation/cleanup/recovery counts (more reliable than workspace status
    alone), while stuck-state and monitor metrics derive from workspace rows.
  - The prior implementation's field `cleanup_failed_count` is renamed to
    `cleanup_failure_count` for consistency with the existing
    `WorkspaceReliabilitySummary.cleanup_failure_count`.
  - The prior implementation's `active_over_slo_count` was slightly misleading
    (it counted non-terminal workspaces created >2×SLA ago regardless of
    reason). This version splits it into `stuck_running_count` (no failure
    reason, beyond 2×SLA) and `stuck_with_reason_count` (has failure reason
    but still non-terminal beyond 2×SLA — operator intervention needed).
- Existing metrics endpoints (`/workspaces/summary`, `/failures/summary`,
  `/resources/saturation`) must remain backward-compatible. The new SLO
  endpoint is additive.

## Data Model: `SloMetricsSummary`

```python
@dataclass(frozen=True)
class SloMetricsSummary:
    generated_at: datetime
    window_start: datetime
    since_hours: int

    # Creation outcome counts (from workspace rows created in window)
    creation_total: int
    creation_succeeded: int
    creation_failed: int
    creation_cancelled: int

    # Cleanup outcome counts (from destroy operations finished in window)
    cleanup_total: int
    cleanup_succeeded: int
    cleanup_failure_count: int

    # Stuck-state counts (from current workspace rows, not windowed)
    stuck_running_count: int
    stuck_with_reason_count: int

    # Recovery operation counts (from remonitor/rebase/retry operations in window)
    recovery_total: int
    recovery_succeeded: int
    recovery_failed_count: int

    # Monitor health counts (from workspace rows, windowed + current)
    monitor_completed_total: int
    completed_after_monitor_count: int
    monitor_stuck_count: int

    # Failure reason code coverage (from failed/cancelled workspaces in window)
    actionable_failure_count: int
    unactionable_failure_count: int
```

### Field derivation rules

| Field | Source | Logic |
|-------|--------|-------|
| `creation_total` | `Workspace` | Count of workspaces with `created_at` in window |
| `creation_succeeded` | `Workspace` | Count of workspaces created in window with terminal status `completed` |
| `creation_failed` | `Workspace` | Count of workspaces created in window with terminal status `failed` |
| `creation_cancelled` | `Workspace` | Count of workspaces created in window with terminal status `cancelled` |
| `cleanup_total` | `Operation` | Count of `destroy` operations with `finished_at` in window |
| `cleanup_succeeded` | `Operation` | Count of `destroy` operations finished in window with `status == succeeded` |
| `cleanup_failure_count` | `Operation` | Count of `destroy` operations finished in window with `status == failed` |
| `stuck_running_count` | `Workspace` | Count of non-terminal, non-destroying workspaces created >2×SLA ago with `failure_reason IS NULL` |
| `stuck_with_reason_count` | `Workspace` | Count of non-terminal, non-destroying workspaces created >2×SLA ago with `failure_reason IS NOT NULL` |
| `recovery_total` | `Operation` | Count of `remonitor`/`rebase`/`retry` operations created in window |
| `recovery_succeeded` | `Operation` | Count of those with `status == succeeded` |
| `recovery_failed_count` | `Operation` | Count of those with `status == failed` |
| `monitor_completed_total` | `Workspace` | Count of workspaces that reached `monitoring_pr` status in window (transient count from events) |
| `completed_after_monitor_count` | `Workspace` | Count of workspaces with current status `completed` and `updated_at` in window that previously touched `monitoring_pr` (detected via `pr_url IS NOT NULL`) |
| `monitor_stuck_count` | `Workspace` | Count of workspaces currently in `monitoring_pr` status created >2×SLA ago |
| `actionable_failure_count` | `Workspace` | Count of failed/cancelled workspaces updated in window with `failure_reason` in `FailureReason` enum |
| `unactionable_failure_count` | `Workspace` | Count of failed/cancelled workspaces updated in window with `failure_reason` not in enum or NULL |

### Reason codes for stuck-state classification

- `stuck_running_count` → reason code `STUCK_NO_REASON_CODE` (watchdog indicator)
- `stuck_with_reason_count` → reason code `STUCK_WITH_REASON_CODE` (operator intervention needed despite having a reason)

These are not new enum values; they are convention strings in the response
`detail` and log events only.

## Risks

| Risk | Mitigation |
|------|------------|
| Operation rows may not exist for older workspaces created before the Operation table was populated | Creation counts use `Workspace` rows (not Operation) as the primary source. Cleanup/recovery counts from Operation are inherently best-effort; zero-operation windows are valid and return 0 totals. |
| `completed_after_monitor_count` uses `pr_url IS NOT NULL` as a proxy for having touched `monitoring_pr` — a workspace could have a `pr_url` without ever entering monitor phase (edge case from manual PR creation) | Document this as a known approximation. A more precise version would query `WorkspaceEvent` rows for `monitoring_pr` transitions; that is deferred to a future accuracy pass. |
| SQLite test DB may not exercise all query patterns the same as Postgres | Existing tests already handle this (no Postgres-specific SQL). All new queries use standard SQLAlchemy constructs. |
| The `Operation` model has `type` stored as a string; must match `OperationType` enum values exactly | Use `OperationType.value` comparisons, consistent with existing `OperationRepository` patterns. |

## Assumptions

- `Operation` rows for `destroy`, `remonitor`, `rebase`, `retry` types are
  created by the existing control service. If a workspace was destroyed before
  the operation recording was in place, that destroy will not appear in cleanup
  counts. This is acceptable because SLO metrics are forward-looking.
- `since_hours` query parameter matches the existing metrics endpoint
  convention (1–168, default 24).
- The new endpoint does not require API token authentication, consistent with
  existing read-only metrics endpoints.

## Explicit Non-Goals

- No console/UI changes for SLO display.
- No DB migrations or new tables/columns.
- No new `Settings` configuration fields.
- No Prometheus/OpenMetrics format — JSON only, matching existing endpoints.
- No multi-node aggregation — local single-node only.
- No percentage calculations in the response — callers compute rates from raw
  counts.
- No automated alerting or threshold enforcement — this slice exposes the
  counts; acting on them is operator-driven.
- No changes to the GC service or orphan container detection (those are
  separate checklist items).
- No changes to workspace lifecycle, state machine, or control flow.
