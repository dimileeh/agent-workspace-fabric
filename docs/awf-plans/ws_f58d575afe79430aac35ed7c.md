# Plan: P0 Provider Recovery Must Preserve Monitoring PR Ownership

## Problem Statement

Provider recovery currently uses the same full-attempt retry/fallback path for PR-monitor agent failures as it uses for pre-PR execution failures. When a workspace is already in `monitoring_pr` with an open PR and the monitor can continue, provider fallback must not create a duplicate requested feature workspace or detach ownership from the existing PR/branch/candidate.

Regression target: `ws_52d8415a02424c4aa4730fa1` hit `AGENT_IDLE_TIMEOUT` while monitoring PR #169. Recovery created duplicate full feature workspace `ws_46a6c903fc7c42098a63edad` instead of keeping PR monitor ownership on the existing workspace/PR/branch.

## Intended Files And Modules To Touch

- `src/awf/service/provider_recovery.py`
  - Add the monitor-stage distinction inside provider recovery creation/decision handling.
  - Preserve existing full retry/fallback behavior for terminal or pre-PR source workspaces.
  - Add a focused helper for `monitoring_pr` + open PR recovery, if needed, rather than spreading status checks through callers.
  - Keep structured reason codes, circuit-breaker/cooldown events, lineage payloads, and provider recovery state shape compatible with existing observability.

- `src/awf/runtime/pr_monitor_runner.py`
  - Route provider failures raised while addressing comments, fixing CI, or resolving sync-base conflicts through the monitor-safe provider recovery behavior.
  - Treat in-place monitor retry/fallback as a monitor retry/outage, not as `ProviderRecoveryFallbackError` that fails the source workspace.
  - Preserve unresolved comment state when provider recovery defers work.

- `src/awf/control/worker.py`
  - Only if tests show a gap: ensure a `monitoring_pr` workspace with in-place fallback metadata and no active future cooldown can be claimed and resumed as a monitor, never executed as a ready feature workspace.
  - Preserve the existing provider-cooldown suppression for same-provider retry.

- `src/awf/control/executor.py`
  - Only if tests show a gap: ensure `resume_pr_monitor()` builds the monitor with the in-place fallback agent/model stored on the same workspace and still skips setup, feature-agent execution, validation, push, and PR creation.

- Tests:
  - `tests/unit/service/test_provider_recovery.py`
  - `tests/unit/runtime/test_pr_monitor_runner.py`
  - `tests/unit/control/test_worker.py`
  - `tests/unit/control/test_executor_error_paths.py` only if fallback adapter/model handoff needs executor-level coverage.

## Implementation Approach

1. Reproduce the failing behavior with the new service test first.
   - Expected initial failure: `create_provider_recovery_attempt_row()` creates a requested fallback workspace for a `monitoring_pr` source.

2. Add a narrow monitor-stage branch in `src/awf/service/provider_recovery.py` after the recovery decision and lineage payload are computed, before creating a new workspace.
   - Guard on source status `monitoring_pr` plus open PR metadata (`pr_url`, `pr_number`, and branch/push target). This is the active/recoverable monitor case.
   - For decision `retry`: update only the source task policy recovery state, add cooldown/event/circuit metadata, clear stale monitor claim fields if needed, and return a result that the PR monitor can treat as retry/defer.
   - For decision `fallback`: update the source row in place with fallback `agent` and `agent_model`, preserve the existing PR/branch/candidate/attempt, record provider recovery state with action `fallback`, and avoid writing a scheduler-suppressing `not_before` that would block the fallback provider from being used. Keep source-provider cooldown evidence in the event/circuit payload.
   - For decision `terminal`: keep existing terminal event behavior.

3. Keep the existing full retry/fallback branch unchanged for non-monitoring sources and terminal failed sources.
   - Existing tests for failed-workspace fallback inheritance should continue passing.
   - Do not change `repo.create(...)` field inheritance except where necessary for the monitor-specific branch.

4. Update `src/awf/runtime/pr_monitor_runner.py` to distinguish in-place monitor provider recovery from full fallback redispatch.
   - If provider recovery returns an in-place monitor result, return/raise the retry-style control path so `run()` writes `monitor.provider_retry`, persists monitor state, and leaves the workspace in `monitoring_pr`.
   - Do not call `_terminate_failed(... PROVIDER_FALLBACK ...)` for monitor in-place fallback.
   - Preserve current handling for true terminal and deterministic failures.

5. Verify worker/executor behavior against the new state.
   - If `provider_cooldown_not_before()` suppresses in-place fallback incorrectly, adjust the filter narrowly so only same-provider retry remains suppressed while fallback target rows can be resumed.
   - Ensure the monitor resume path uses the updated workspace `agent` and `agent_model` and continues to skip feature execution and PR creation.

## Risks

- In-place fallback changes the source workspace agent/model while keeping the same task attempt and candidate. Tests must prove lineage and candidate ownership remain stable and observability clearly records the fallback decision.
- A generic `not_before` stored on source task policy could suppress the fallback provider as well as the failed source provider. The fallback path must preserve cooldown evidence without preventing immediate monitor resume on the fallback target.
- Provider recovery result typing is currently oriented around `new_workspace_id`. Any result-shape change must remain backward-compatible for executor paths and API/observability consumers.
- The worker already suppresses provider cooldowns for `monitoring_pr`; changing that logic too broadly could resume same-provider retries too early.
- Marking the source failed during monitor fallback closes the open merge candidate. The fix must avoid any `monitoring_pr -> failed` transition for recoverable monitor provider failures.

## Assumptions

- A `monitoring_pr` workspace with `pr_url`, `pr_number`, branch/push target, and compose metadata is recoverable by the existing monitor resume path.
- Terminal failed/cancelled sources remain eligible for the existing full retry/fallback attempt creation behavior.
- The current schema does not appear to have a first-class `abandoned` task-attempt enum. If an explicit abandoned marker exists in task policy or attempt status in the implementation pass, the monitor in-place guard should not apply to it.
- Existing `remonitor` operation/event vocabulary is acceptable for worker restart/monitor-only recovery observability; no migration should be needed.

## Explicit Non-Goals

- Do not redesign provider recovery policy, circuit breaker thresholds, or failure classification.
- Do not add a new workspace lifecycle state.
- Do not change PR monitor merge policy, auto-merge gates, review grace semantics, validation tier policy, or stale recovery behavior.
- Do not alter full feature retry/fallback behavior for pre-PR execution failures or terminal failed workspaces beyond the regression guard.
- Do not manually push, rebase, branch-switch, create PRs, resolve comments, or merge anything.
