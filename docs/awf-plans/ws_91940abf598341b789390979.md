# Plan: P1 Core first-run troubleshooting guide (symptom-first)

## Goal and scope

Add a first-run troubleshooting guide for AWF Core that is organized by operator symptom and enables practical diagnosis of local bootstrap/service readiness failures without reading implementation internals.

Scope:
- Update public documentation only (docs-level changes only).
- Add a symptom-first troubleshooting experience for local first run (install/bootstrap, service status, and workspace lifecycle failure modes).
- Add/adjust docs-focused tests that enforce discoverability and required symptom coverage.
- Keep language generic to AWF Core (no Aira-specific assumptions).

  1. service bootstrap failure

  5. provider auth/preflight failure

- [ ] Include CLI and REST surfaces (readability, not internals).
- [ ] No runtime code changes unless a docs drift test directly fails and requires tiny alignment text updates.

## Documentation content shape (for `docs/TROUBLESHOOTING.md`)

Use this symptom-first order:

1. `## Symptom: service bootstrap command fails`
   - command: `awf init`, `awf service bootstrap`
   - check list: command output, service files, Docker availability, duplicate service stack

2. `## Symptom: Postgres is unavailable, is recovering, or disk is full`
   - `awf service status --format pretty`, `awf service doctor`
   - `docker ps` checks for local postgres service
   - `docker system df` + `docker image prune` guidance with caution
   - mention `INSUFFICIENT_DISK`/`PORT_CLOSED`-style behavior as seen in status outputs

3. `## Symptom: Docker daemon/socket/Compose is unavailable`
   - `docker --version`, `docker info`, `docker compose version`
   - `DOCKER_DAEMON_UNREACHABLE`, `DOCKER_SOCKET_UNREACHABLE`, compose checks
   - permission and rootless/group fixes, then re-run bootstrap/status

4. `## Symptom: Agent runtime image is missing`
   - `docker image inspect awf-agent-runtime:latest`
   - re-run `awf service bootstrap` and rebuild path
   - verify `docker compose` project has pulled image

5. `## Symptom: Provider auth/preflight fails`
   - `awf service status --provider codex --format pretty`
   - provider-specific env/mount checks (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `OLLAMA_API_KEY`, local auth mounts)
   - run local smoke/retry path once fixed

6. `## Symptom: GitHub auth fails`
   - `gh auth status`
   - refresh `AWF_GITHUB_TOKEN` and/or `GH_TOKEN`
   - re-run provider/status checks and `awf service status`

7. `## Symptom: `/readyz` reports warnings or 503`
   - `curl http://localhost:8000/readyz`
   - provider-filtered probes: `curl "http://localhost:8000/readyz?provider=codex"`
   - map each warning to next commands/commands to rerun

8. `## Symptom: Workspace is stuck or repeatedly fails`
   - `awf workspace show <workspace_id> --format pretty`
   - `awf workspace events ws_<id> --limit 50`
   - `awf workspace operations ws_<id>`
   - `awf workspace logs ws_<id>` and `awf workspace log ws_<id> agent.stdout`
   - `awf workspace runtime ws_<id>` for stack view
   - action matrix for `failed`, `stuck`, `stale`, `cancelled`, `completed`

9. `## Where to find logs and evidence`
   - service-level: `awf service logs`, `awf service logs --service api|worker|migrate|postgres`
   - workspace-level: `awf workspace logs`, stream reads, log stream IDs
   - API equivalents in existing docs (`GET /v1/workspaces/{workspace_id}/logs*`, `GET /v1/workspaces/{id}/events`, `GET /v1/workspaces/{id}/operations`, `GET /v1/workspaces/{id}/runtime`)

## Risks, assumptions, and explicit non-goals

Risks:
- Existing `tests/unit/api/test_docs_drift.py` may fail if heading or URL drift introduces API-doc alignment changes; only then should a minimal docs-drift-aligned metadata change be considered.
- Symptom guidance can become stale as readiness reason codes evolve; this is acceptable for docs but should remain pinned to current AWF surfaces.

Assumptions:
- `docs/GETTING_STARTED.md` is the primary getting-started path for this slice.
- Current CLI/API commands are available in current branch behavior.

Non-goals:
- Do not change runtime logic, reason-code maps, or code-path behavior for bootstrap/readiness.
- Do not add tooling, scripts, or non-doc support automation as part of this slice.
- Do not add project-specific (Aira-specific) troubleshooting text.
