# Production Configuration Footgun Guardrails Plan

## Planning Constraints

This is the AWF-configured planning artifact for workspace `ws_084580a1fa544b95bcbcab98`. It supersedes the generic `plans/<TOPIC>_PLAN.md` location for this AWF planning phase. No implementation files are to be modified until a later implementation phase.

## Problem Statement and Scope

AWF is local-first, but `AWF_ENV=prod` must not allow bundled local development defaults to become network-facing production configuration. This slice will add deterministic production-only validation that fails before app/service startup admits work, while preserving local and CI defaults.

The implementation will be intentionally narrow: configuration guardrail helpers, startup/service-resolution call sites, focused tests, and documentation for local-vs-production expectations.

## Requirements Checklist

- Keep local development defaults usable when `AWF_ENV` is `local` or `ci`.
- Treat `AWF_ENV=prod` as production. Do not treat `staging` as production unless implementation-time inspection finds an established project convention that already does so.
- Reject the default local database URL/credentials in production: `postgresql+asyncpg://awf:awf_dev@localhost:5433/awf`.
- Reject production with missing `AWF_API_TOKEN`.
- Reject production with obviously weak/default/placeholder `AWF_API_TOKEN` values.
- Guard callback-enabled production posture using currently available settings. The base config currently exposes `callbacks_enabled` but no HTTPS or callback allowlist policy fields, so the planned minimum guard is to require a strong `AWF_API_TOKEN` when callbacks are enabled and document a deferred TODO tied to the active callback SSRF hardening slice.
- Provide reusable helpers such as `settings_guardrails` and `validate_production_settings` that tests can exercise directly.
- Call production validation during app startup and/or service settings resolution before work can be admitted.
- Emit structured, operator-actionable diagnostics without printing raw tokens, database passwords, or full secret-bearing URLs.
- Update docs to explain local-vs-production expectations and relevant environment variables.

## Intended Files and Modules to Touch During Implementation

- `src/awf/common/config.py`
  - Add structured diagnostic types and a reusable production settings validation helper.
  - Keep validation deterministic and side-effect free.
- `src/awf/service/config.py`
  - Call the validation helper from `resolve_service_settings` after service-mode database URL resolution so prod service commands fail fast with the resolved posture.
  - Reuse existing redaction patterns where possible, without leaking full URLs or secrets.
- `src/awf/api/app.py`
  - Add a narrow startup/lifespan validation call before `make_engine(settings.database_url)` so invalid prod settings fail before opening DB connections or admitting requests.
- `tests/unit/service/test_config.py`
  - Add direct unit tests for guardrail helpers, diagnostics, redaction behavior, and service settings resolution.
- `tests/unit/api/test_app_lifespan.py`
  - Add a lifespan test proving invalid production settings fail before engine construction.
- `docs/GETTING_STARTED.md`
  - Add a concise local-vs-production configuration section covering `AWF_ENV`, `AWF_DATABASE_URL`, `AWF_API_TOKEN`, and callback expectations.
- `README.md` only if it has an existing operator configuration section that should point to the new production expectations.

No broad module decomposition is planned. `tests/unit/test_postgres_only_edges.py` is not expected to need edits, but it will be included in validation because it is part of the requested command set and covers DB URL edge behavior.

4. In `tests/unit/service/test_config.py`, add production token tests proving missing tokens and weak/default placeholders such as `local-dev-token`, `changeme`, `default`, or short token strings are rejected with structured `AWF_API_TOKEN` diagnostics.

## Implementation Steps

1. Add failing tests listed above.
2. Add a small structured diagnostic model in `src/awf/common/config.py`, likely a frozen dataclass with fields such as `code`, `field`, `message`, and `remediation`.
3. Add a `ProductionSettingsError` exception carrying a tuple of diagnostics. Its string representation should summarize diagnostic codes/remediation without raw setting values.
4. Add a side-effect-free helper, for example `settings_guardrails(env, database_url, api_token, callbacks_enabled) -> tuple[ProductionSettingsDiagnostic, ...]`, plus `validate_production_settings(settings, database_url=None) -> None`.
5. Implement production detection as `env == "prod"` unless a stronger existing staging convention is discovered during implementation.
6. Implement default DB detection by parsing or normalized comparison so the known local default is rejected even if routed through service defaults. Diagnostics should reference `AWF_DATABASE_URL` and remediation, not the raw URL.
7. Implement weak token detection for missing/blank tokens, known placeholders/defaults, and clearly too-short values. Diagnostics should reference `AWF_API_TOKEN` only, not the token value.
8. Implement callback guardrail using available settings: when `env="prod"`, `callbacks_enabled=True`, and no strong API token is present, emit a callback-specific diagnostic or attach callback-specific remediation to the token diagnostic. Leave a clear deferred note in docs for future callback HTTPS/allowlist policy validation under the SSRF hardening slice.
9. Call validation from `resolve_service_settings` after local service DB URL resolution and from `_lifespan` before `make_engine`.
10. Update docs with local defaults allowed for `local`/`ci`, production requirements for `prod`, and redaction/security expectations.
11. Run validation commands and address failures with the smallest scoped changes.
12. Create the implementation validation artifact after coding, per the AWF plan-and-validate workflow, documenting requirement-by-requirement status and evidence.

## Risks and Assumptions

- Assumption: `AWF_ENV=prod` is the only production mode for this slice. `RuntimeEnv` includes `staging`, but the planning inspection did not find a clear convention that staging must fail with production guardrails.
- Assumption: callback HTTPS/allowlist policy fields do not currently exist in the base settings. The implementation will not invent those policy fields in this slice.
- Risk: service-mode DB URL resolution can replace an unset DB URL with the local default. Validation must run after that resolution so production cannot bypass the guardrail through defaulting.
- Risk: error text can accidentally include secret-bearing values through exception formatting. Tests will assert both structured diagnostics and exception strings are redacted.
- Risk: app lifespan tests use cached settings. Existing tests clear the settings cache; new tests must preserve that pattern.
- Risk: rejecting short tokens may affect real but weak production deployments. This is intentional for obviously weak postures, but the threshold should remain conservative and documented.

## Explicit Non-Goals

- No request rate limiter.
- No callback delivery rewrite.
- No callback DNS rebinding or broader SSRF delivery hardening.
- No new callback HTTPS/allowlist configuration model unless matching fields already exist in the codebase.
- No auth posture rewrite for workspace endpoints.
- No broad module decomposition or unrelated refactors.
- No full local coverage run; GitHub Actions owns full coverage for this slice.
