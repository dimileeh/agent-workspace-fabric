# Plan: Setup Dependency Network Retry And Classification

## Objective

Make AWF profile setup resilient to transient dependency/index/network failures without spending agent/provider time before setup succeeds. The motivating incident is a `uv sync --extra dev` failure while fetching locked `docker==7.1.0` from `files.pythonhosted.org` due to transient DNS resolution. `docker==7.1.0` itself is not the bug; the bug is that AWF currently treats that transient setup dependency fetch as an opaque setup/service failure with no bounded retry or actionable setup dependency metadata.

## Inspected Context

- `src/awf/control/executor.py` calls `self._validation.run_profile_phases(..., phase_names=("setup", "pre_agent"))` before agent execution.
- On any setup/pre-agent failure, executor calls `_mark_failed(...)` with `_failure_reason_for_phase(first_fail)`. `_failure_reason_for_phase` maps phases `setup`, `pre_agent`, and `db_generated_setup` to coarse `FailureReason.service_startup_failure`, so the terminal event reason defaults to `SERVICE_STARTUP_FAILURE` unless the caller supplies a more specific reason code.
- `src/awf/runtime/validation.py` executes profile phase commands in `_run_commands`. Existing retry handling is limited to flaky timeout/signal exits and uses `profile.validation.retry_budget`; it does not classify dependency fetch output or retry setup dependency network failures.
- `ValidationCommandResult` already has `reason_code`, `retry_count`, and `metadata`, which are suitable for structured setup diagnostics without expanding unbounded logs.
- Existing audit helpers in `src/awf/common/audit.py` provide bounded redaction via `redact_audit_text` and recursive payload redaction via `redact_audit_value`.
- Existing focused regression tests are concentrated in `tests/unit/runtime/test_validation.py` and `tests/unit/control/test_executor_error_paths.py`; the old generic setup failure regression lives near `test_setup_phase_failure_marks_service_startup_failure`.

## Intended Files And Modules To Touch

Production code:

- `src/awf/runtime/validation.py`
  - Add setup dependency/network reason-code constants, classifier helpers, bounded diagnostic extraction, and bounded setup retry logic.
  - Keep retry shape-based rather than uv-only: detect DNS lookup failures, temporary name resolution, connection reset/refused/timeout, TLS handshake/read timeouts, and package-index 5xx/fetch errors.
  - Explicitly avoid retrying deterministic failures such as lockfile conflicts, dependency resolution conflicts, auth failures, incompatible Python, missing local files, syntax errors, and command-not-found exits.
  - Attach concise redacted metadata to `ValidationCommandResult.metadata`: command, package when extractable, host/index when extractable, transient category, retryability, retry count/budget, exhausted flag, and a bounded diagnostic excerpt.
  - Preserve command stdout/stderr evidence across retry attempts by appending retry output to the same artifact paths, with a short attempt prefix when practical.

- `src/awf/control/executor.py`
  - Add small helpers that inspect setup `ValidationResult`/`ValidationCommandResult` metadata and emit durable workspace events for setup dependency retry attempts and final exhaustion.
  - When setup exhausts retries with the new reason code, call `_mark_failed(...)` with `reason_code="SETUP_DEPENDENCY_NETWORK_FAILURE"` and structured `details`, while keeping the coarse terminal `failure_reason` in the existing setup/service family unless implementation tests require a new enum.
  - Ensure agent adapter execution and provider recovery are not reached until setup succeeds.
  - Keep monitor recovery setup failure handling intact, but include the precise setup dependency reason and details when present.

- `src/awf/service/validation_provenance.py` and `src/awf/service/metrics.py` only if a new `FailureReason` enum value becomes necessary during implementation. The preferred narrow design is a specific terminal/event `reason_code` plus payload details, not a broad failure-taxonomy expansion.

Tests:

- `tests/unit/runtime/test_validation.py`
  - Add classifier and retry regressions for observed uv/PyPI DNS output, transient connection/read/TLS/5xx shapes, deterministic non-retry cases, and redaction/truncation.
  - Add a setup retry success test proving a transient first attempt and cache-hit/success second attempt returns `all_passed`, preserves `retry_count`, and keeps metadata.
  - Add a setup retry exhaustion test proving the final `ValidationCommandResult.reason_code` and metadata are precise and bounded.

- `tests/unit/control/test_executor_error_paths.py`
  - Add executor-level regressions proving transient setup retry success proceeds to agent execution/post-agent validation without creating a provider recovery path.
  - Add executor-level exhaustion regression proving terminal state uses the setup dependency/network reason code, durable event payload is redacted/bounded, and the original failure evidence remains discoverable.
  - Update the existing deterministic setup failure regression to assert it is still not retried and remains generic setup/service failure.

- `tests/unit/control/test_executor_validation_fix_cycle.py`
  - Add or adjust one focused assertion only if setup retry changes the call sequence used by existing validation-fix-cycle tests.

## Implementation Sequence

1. Add reason-code constants and a small immutable classifier result in `src/awf/runtime/validation.py`.
   - Candidate constants: `SETUP_DEPENDENCY_NETWORK_FAILURE`, `SETUP_DEPENDENCY_NETWORK_RETRY`, and `SETUP_DEPENDENCY_NETWORK_RETRY_EXHAUSTED` for event/log semantics.
   - Keep classifier public enough for unit tests only if useful; otherwise test through `ValidationRunner` behavior.

2. Implement bounded diagnostic extraction.
   - Combine stdout/stderr from the failed command, redact with `redact_audit_text`, normalize whitespace enough for concise operator diagnostics, and cap to a small limit such as 1000 characters.
   - Extract host/index via URL/hostname patterns and package via common dependency tool output patterns such as `package==version`, `Downloading ...`, `Failed to download ...`, or uv package lines.

3. Implement setup-only retry in `ValidationRunner._run_commands`.
   - Apply only when `step.phase == "setup"`, command is required, result is non-zero, and the classifier says the failure is transient/retryable.
   - Use a bounded default retry budget independent of `profile.validation.retry_budget`, because dependency setup needs reliability even when validation retries are disabled.
   - Add constructor-injected or constant backoff support with tests using zero backoff to avoid slow unit tests.
   - Do not retry deterministic failures, database generated setup, healthchecks, validation commands, post-agent commands, command-not-found exits, or auth/configuration failures.

4. Preserve evidence and metadata.
   - For every transient retry attempt, append retry output to the same artifact path and include structured attempt metadata on the final `ValidationCommandResult`.
   - Preserve original failed attempt fields in metadata even when the retry succeeds, so AWF can explain that setup recovered without losing lineage.

5. Add executor durable events.
   - After setup phases return, inspect command metadata for setup dependency retry attempts and record `workspace.setup_dependency_network_retry` events with reason code `SETUP_DEPENDENCY_NETWORK_RETRY`.
   - If setup ultimately fails with `SETUP_DEPENDENCY_NETWORK_FAILURE`, record `workspace.setup_dependency_network_retry_exhausted` before `_mark_failed(...)`, and pass `reason_code="SETUP_DEPENDENCY_NETWORK_FAILURE"` plus structured details to `_mark_failed(...)`.
   - Keep stale-status checks and monitor-recovery operation completion behavior intact.

6. Update existing setup failure tests.
   - Preserve current behavior for deterministic setup failures: no retry, no agent execution, no provider recovery, generic setup/service failure classification.
   - Add assertions that transient setup dependency/network failures do not enqueue provider recovery and do not spend agent time until setup succeeds.

7. If adding a new `FailureReason.setup_dependency_network_failure` becomes necessary, update `src/awf/db/enums.py`, `src/awf/service/metrics.py`, `src/awf/service/validation_provenance.py`, and any reason-code coverage tests in the same TDD loop. This is a fallback, not the initial narrow path.

8. Create the implementation validation artifact after coding, following repository protocol, in the configured AWF plan area if that remains the active workspace contract for the execution phase.

## Risks And Mitigations

- False positives could retry deterministic setup failures and delay useful feedback. Mitigation: start with explicit transient network/index patterns plus explicit deterministic denylist, and keep command-not-found/auth/resolution conflicts non-retryable.
- False negatives could leave some transient package manager failures generic. Mitigation: cover the observed uv/PyPI DNS failure first, then add shape-based patterns for common connect/read/TLS/5xx failures without trying to enumerate every package manager.
- Retry evidence could be overwritten if implemented as an executor-level rerun of all setup phases. Mitigation: implement retries inside `ValidationRunner._run_commands` so the same command artifact can append attempt evidence.
- Durable workspace events are emitted by the executor, while retry mechanics live in validation. Mitigation: return compact retry metadata on command results and have executor translate it into workspace events after setup phases complete.
- Adding a new terminal `FailureReason` would ripple into metrics/action coverage and possibly API contracts. Mitigation: prefer specific `reason_code` and event/details metadata under the existing setup/service coarse failure family unless tests force enum expansion.
- Backoff could slow unit tests. Mitigation: inject zero backoff or a sleeper/backoff sequence in tests.
- Coordination warning: another active workspace owns `src/awf/runtime/validation.py`, `src/awf/control/executor.py`, and related tests. During implementation, inspect current worktree state before editing and keep changes tightly scoped to reduce stale-overlap risk.

## Assumptions

- Profile setup dependency installs are represented by required commands in the `setup` phase; `pre_agent`, `db_generated_setup`, healthchecks, and validation commands should not receive the new dependency-network retry by default.
- The AWF control-plane database and workspace id stay unchanged during setup retry; retrying a setup command within the same executor attempt preserves task lineage better than creating a new workspace slice.
- `uv sync` may use cached wheels after a transient fetch failure, so a retry success can be treated as the same setup lineage recovering, not as a dependency change.
- Structured events may be persisted immediately after setup returns rather than at the exact sleep boundary, as long as the durable event payload includes attempt numbers and original failure diagnostics.
- Diagnostic payloads must summarize command output rather than storing raw unbounded stdout/stderr in the database.

## Explicit Non-Goals

- Do not change scheduler scoring, provider recovery policy, PR monitor loops, merge queue behavior, or Docker lifecycle ownership.
- Do not skip dependency installation, relax profile setup commands, or remove locked dependencies.
- Do not add package-manager-specific retry wrappers around only `uv`; use output-shape classification while keeping the observed uv/PyPI case covered.
- Do not retry deterministic dependency resolution/configuration/auth failures.
- Do not push, rebase, switch branches, or create extra plan/validation artifacts during the planning phase.
