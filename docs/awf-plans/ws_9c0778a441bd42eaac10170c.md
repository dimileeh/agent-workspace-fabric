# Plan: Close Per-Workspace Docker Volume Teardown Gaps (#373, #377)

## Problem Statement

Follow up on AWF issues #373 and #377 from PR #372 review. The goal is to close two related Docker volume leak windows in one scoped change:

- #373: `ComposeManager.teardown_project` must not return an immediate skipped/no-op result solely because the compose file is missing. If labelled Docker resources still exist, teardown must fall back to label-scoped removal so orphaned per-workspace volumes are reaped. If no labelled resources exist, the fallback remains idempotent and successful.
- #377: post-merge PR monitor filesystem GC must pass a volume-removing `compose_teardown` callback into the GC engine, matching the periodic service GC path, so the post-merge cleanup path gets the same `ComposeManager.teardown_project` label fallback before deleting pressure directories.

The implementation must stay generic to AWF core, must not log secrets, and must preserve idempotent cleanup behavior.

## Intended Files and Modules to Touch

Implementation:

- `src/awf/node/compose_manager.py`
  - Update or verify `down_project`/`teardown_project` behavior so a missing compose file routes to label-scoped cleanup rather than immediate skip.
  - Ensure fallback failure catches `ComposeOperationError` specifically and preserves the fallback reason code/error with redaction.
  - Keep the genuine empty-resource case an idempotent ok result.
- `src/awf/runtime/pr_monitor_runner/lifecycle.py`
  - Wire post-merge `_gc_completed_workspace_filesystem` to pass a `compose_teardown` callback to `run_workspace_filesystem_gc` when the completed monitor run has compose project/file context.
  - Prefer reusing the existing GC callback contract backed by `ComposeManager.teardown_project` rather than changing `gc.py` deletion routing.
  - Consolidate the post-merge compose teardown gate so filesystem GC is skipped on a failed compose teardown result from the GC engine, not by a separate raw `docker compose down` path.

Tests:

- `tests/unit/node/test_compose_manager.py`
  - Add/update focused tests for the missing-compose-file label fallback and true no-op/idempotent case.
  - Deliberately update the prior `test_teardown_project_is_idempotent_when_compose_file_missing` expectation if it still exists, because missing compose file now probes/removes by label rather than returning an immediate skipped no-op.
- `tests/unit/runtime/test_monitor_completion_gc.py`
  - Add a focused post-merge test proving lifecycle passes a non-null volume-removing `compose_teardown` callback to `run_workspace_filesystem_gc`.
  - Cover failure gating: a failed compose teardown result should keep filesystem pressure dirs in place and log/return partial behavior through the existing GC result path.

Files explicitly out of scope:

- `src/awf/service/gc.py`
- `src/awf/node/auth_mounts.py`
- GC deletion routing and auth overlay teardown behavior
- migrations, OpenAPI, frontend, profile/config changes

## Risks and Assumptions

- The current checkout already appears to contain some #373-style fallback code/tests. The implementation phase should verify whether those are complete and avoid rewriting them unnecessarily.
- Monitor unit tests currently fake subprocess execution through `FakeCommandRunner`; `ComposeManager` shells out directly. Lifecycle tests must patch the new compose-teardown factory or manager to avoid real Docker access.
- `run_workspace_filesystem_gc` derives candidate compose project/file metadata from the workspace row. Tests should seed or assert against that persisted metadata, not assume only the `runner.run(...)` arguments are used.
- Passing a callback into filesystem GC may change log events from `monitor.compose_teardown_ok` to GC compose teardown result reporting. Existing tests that assert old raw teardown logs may need targeted expectation updates.
- Label fallback must stay idempotent: no labelled resources is success, not human escalation.
- Docker/compose errors must retain specific reason codes where available and must not leak secrets in logs or result errors.

## Explicit Non-Goals

- Do not change `gc.py` path deletion order, candidate classification, retention policy, or reservation release behavior.
- Do not change `auth_mounts.py` or auth overlay unmount semantics.
- Do not add retries or hide failures behind generic success.
- Do not introduce Aira-specific paths, database assumptions, or profile-specific behavior in AWF core.
- Do not run broad validation, push, rebase, switch branches, or touch files outside this issue's implementation/test surface.
