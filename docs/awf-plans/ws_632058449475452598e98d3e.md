# Plan: P0 PR Monitor Non-Actionable Bot Comment Regression

## Goal

Implement the focused PR monitor regression slice proving that non-actionable
bot boilerplate, especially CodeRabbit disabled-review or skipped-review status
text, is ignored as review feedback while preserving merge safety:

- boilerplate alone must not escalate to a human;
- boilerplate observed during initial review grace must still wait out grace
  instead of auto-merging early;
- later actionable review feedback after ignored boilerplate must still route to
  `AddressComments`;
- ignored boilerplate must not mark the monitor complete by itself.

## Current Anchors

- `src/awf/common/github_client.py`
  - `GitHubClient.fetch_pr_status()` converts GraphQL review threads,
    review-level comments, and top-level PR comments into `PRStatus`.
  - Existing helpers classify known bot authors, AWF status comments,
    merge-blocking issue comments, and non-actionable bot review bodies.
- `src/awf/runtime/pr_monitor.py`
  - `decide()` routes new unresolved comments to `AddressComments`, policy
    blockers to `NotifyHuman`, and clean snapshots to `Merge`.
- `src/awf/runtime/pr_monitor_runner.py`
  - `PullRequestMonitorRunner._execute(Merge)` enforces initial review grace
    before attempting the GitHub merge.
  - `NotifyHuman` is a live wait state, not terminal completion.
- `tests/unit/runtime/_monitor_runner_fixtures.py`
  - Provides `pr_payload()`, `issue_comment_node()`, `review_node()`,
    `thread_node()`, `make_runner()`, and `seed_monitoring_workspace()` for
    runner-level tests that exercise the GitHub payload parser and monitor loop.
- Related tests already exist in:
  - `tests/unit/runtime/test_pr_monitor.py`
  - `tests/unit/runtime/test_pr_monitor_initial_review_grace.py`
  - `tests/unit/runtime/test_monitor_action_logging.py`
  - `tests/unit/runtime/test_pr_monitor_manual_merge.py`

## Tests To Write First

1. `test_only_non_actionable_bot_comment_does_not_notify_human`
   - Seed a monitoring workspace.
   - Queue a PR payload containing only a CodeRabbit disabled-review boilerplate
     comment from `coderabbitai`.
   - Assert the monitor does not call `gh pr comment`, does not dispatch
     `AddressComments`, and does not create a `human_wait` operation.
   - Use a terminal follow-up such as `merged=True` only to finish the test
     loop; assert the boilerplate poll itself was not the completion reason.

2. `test_non_actionable_bot_comment_during_initial_grace_waits_without_merge`
   - Configure `initial_review_grace_period_seconds=900`.
   - Present only the disabled-review boilerplate on the first poll.
   - Assert the action log reaches the green-gate `Merge` arm but no
     `gh pr merge` command is called.
   - Assert `sleep_fn.calls == [60]` for the grace wait, the initial grace state
     key is persisted, and the workspace remains `monitoring_pr` after the first
     non-terminal execution.

3. `test_later_actionable_comment_after_ignored_boilerplate_routes_to_address_comments`
   - Poll 1: only ignored CodeRabbit boilerplate.
   - Poll 2: same boilerplate plus a later actionable review item.
   - Use an inline thread or parametrize with both `thread_node()` and
     `review_node()` if that stays compact.
   - Queue the fake adapter result and settle re-poll.
   - Assert action sequence includes `AddressComments` after the ignored
     boilerplate, the adapter receives the actionable text, and the ignored
     boilerplate is not included in the repair prompt.

4. `test_ignored_boilerplate_does_not_complete_monitor_by_itself`
   - Exercise one non-terminal iteration with ignored boilerplate and initial
     grace, or a runner sequence where completion occurs only after an explicit
     later `merged=True` snapshot.
   - Assert the first boilerplate-only snapshot does not transition the
     workspace to `completed` and does not write a defer signal.

5. Optional parser-focused parametrization if the first tests identify a gap:
   - Cover the same disabled-review text as both a top-level PR comment and a
     review-level body.
   - Cover a near-neighbor actionable blocker with `review skipped` plus
     `trigger review` and no disabled-review wording, proving it still becomes
     `blocks_merge=True` and routes to `NotifyHuman`.

## Implementation Sequence

1. Add the dedicated regression tests using the existing monitor runner fixtures.
2. If the failing tests show disabled-review boilerplate is being surfaced as a
   `ReviewComment`, update `src/awf/common/github_client.py` classification:
   - normalize comment bodies with whitespace folding and lowercase matching;
   - recognize CodeRabbit-style disabled-review/skipped-review status text as
     non-actionable only for known bot authors;
   - apply the filter consistently to review-level bodies and top-level issue
     comments;
   - leave human and unknown-author comments untouched.
3. Preserve or refine `_is_merge_blocking_issue_comment()` so true policy
   blockers still become `blocks_merge=True`.
4. If needed, add a tiny helper with a narrow name such as
   `_is_non_actionable_review_skip_comment()` and keep it private to
   `github_client.py`.
5. Avoid changing monitor completion, merge queue, validation provenance,
   branch-management, or PR merge behavior beyond what the tests require.
6. Run the validation surface below and inspect any coverage movement before
   committing in the implementation phase.

## Risks And Assumptions

- Assumption: CodeRabbit disabled-review boilerplate is non-actionable only when
  authored by a known bot account such as `coderabbitai` or a `[bot]` login.
- Assumption: A comment that tells humans to trigger a required review remains a
  policy blocker unless it is specifically disabled-review boilerplate AWF should
  ignore.
- Risk: Over-broad body matching could hide real review feedback. Tests should
  include a near-neighbor actionable blocker so matching stays conservative.
- Risk: Runner action logs may show `Merge` for a green-gate decision even when
  initial grace prevents the actual merge command. Tests must assert command
  side effects and workspace state, not only action names.
- Risk: Bot boilerplate can arrive as either a review-level body or top-level PR
  comment. The implementation should classify both if tests confirm both shapes
  are used.
- Risk: Existing fixtures queue exact `gh` command results. Runner tests should
  keep command queues short and explicit so failures identify behavior changes
  rather than fixture drift.

## Non-Goals

- Do not change branch management, push behavior, PR creation, or AWF-owned
  monitor lifecycle orchestration.
- Do not manually push, merge, rebase, or resolve PR comments.
- Do not lower coverage thresholds, quality gates, lint rules, or type checks.
- Do not redesign bot reviewer policy, non-check reviewer settle policy, merge
  queue behavior, validation provenance, or stale detection.
- Do not suppress actionable human comments, unknown-author comments, failing
  checks, branch protection blockers, or true trigger-review policy blockers.
- Do not add external service calls or network dependencies to the unit tests.
