# Plan: operation audit truth for controls and recovery

## Objective

Persist and expose richer operation audit truth for refresh, rebase/rebase-only,
validate, remonitor, cancel, stop, destroy/delete, and monitor recovery
operations. Operators should be able to inspect operation start, finish,
owner/source, reason, result, failure code/message, and associated log stream
references through operation list/detail APIs without scraping raw logs.

This slice should use the existing `operations` table. The table already has
`payload`, `result`, `error_code`, `error_message`, `started_at`, and
`finished_at`, so no migration is intended unless implementation proves those
fields cannot preserve a stable contract.

## Current Code Context

- `src/awf/db/models.py`
  - `Operation` already stores `payload`, `result`, `error_code`,
    `error_message`, `created_at`, `started_at`, `finished_at`, and
    `idempotency_key`.
- `src/awf/db/repositories.py`
  - `OperationRepository.create()` sets `started_at` for running operations.
  - `OperationRepository.finish()` records result, failure code/message, and
    `finished_at`, and backfills `started_at` if missing.
- `src/awf/api/schemas.py`
  - `OperationResponse` exposes the raw operation fields but not stable
    top-level audit fields for owner/source/reason/log streams.
- `src/awf/api/routes/operations.py` and `src/awf/service/workspaces.py`
  - Operation list/detail responses are built from `OperationResponse`.
- `src/awf/service/controls.py`
  - Refresh and validate payloads already include `source`, `reason`,
    `reason_code`, and `requested_action`.
  - Cancel, stop, remonitor, and destroy currently record less structured
    payloads.
  - Stop/cancel stack-stop failures can raise before the operation is finished.
- `src/awf/runtime/pr_monitor_runner.py`
  - Monitor-created recovery operations include `source="pr_monitor"` and a
    reason string, but not a stable owner, actionable reason code, requested
    action, or log stream references.
- `src/awf/control/executor.py`
  - Validate-only and rebase-only recovery operations are moved from pending to
    running and later finished with validation result metadata.
  - Finish result payloads currently include validation ids and reason codes but
    not the validation log stream references.

## Implementation Approach

1. Add audit response normalization.
   - In `OperationResponse`, add optional top-level audit fields with safe
     defaults.
   - Derive values from `payload` first, then `result`, then existing failure
     columns where applicable.
   - Normalize `log_stream_refs` to `{}` and extract string stream ids
     recursively into `log_stream_ids`.
   - Do not mutate the underlying `payload` or `result` during serialization.

2. Centralize operation start.
   - Add `OperationRepository.start(operation)`:
     set status `running`, set `started_at` only if missing, flush, return row.
   - Update `_start_pending_recovery_operations()` to use it.

3. Standardize operator control audit payloads.
   - Add or extend a local helper in `service/controls.py` so control payloads
     consistently include:
     `owner`, `source`, `reason`, `reason_code`, `requested_action`, and any
     operation-specific fields such as `stop_stack`, `force`, or
     `remove_volumes`.
   - Preserve current request fields and idempotency comparisons.

4. Record failed stop/cancel operation completion.
   - Wrap project-stopper calls after operation creation.
   - On `WorkspaceStackStopError`, finish the operation as failed with the
     error code/message, commit/flush as existing transaction flow requires,
     then re-raise so API behavior remains a control error.
   - Avoid changing workspace status on failed stop/cancel unless existing code
     already did so before the failure.

5. Enrich monitor-created recovery operations.
   - Build operation payload with `owner/source="pr_monitor"`,
     `requested_action=req_action`, `recovery_mode`, `reason`, and
     `reason_code=stale_reason`.
   - Include `log_stream_refs={"monitor": "monitor.log"}` only when a monitor
     log sink is available.
   - Keep duplicate active recovery detection based on active status and
     `source="pr_monitor"` so idempotency behavior is preserved.

6. Enrich validate/recovery completion results.
   - When finishing pending/running validate operations, load the validation
     run by id and copy its `log_stream_refs` into operation result if present.
   - Keep existing result keys stable.
   - For failures, preserve `error_code` and `error_message` while including
     any available validation log refs.

7. Update exact-payload tests.
   - Existing tests that assert payload dictionaries should be updated to the
     new richer payload shape.
   - Keep assertions that old fields are still present.

## Risks

- Adding fields to `OperationResponse` is backward compatible for tolerant
  clients, but exact JSON-shape tests and generated clients may need updates.
- Operation payloads are free-form JSON. Without normalization helpers, each
  caller can drift; tests should assert the stable response fields rather than
  relying only on raw payload shape.
- Stop/cancel failure handling must not make a failed stack stop look
  successful or transition a workspace after the failure.
- Recovery operations currently use `OperationType.validate` for both
  validate-only and rebase-only executor recovery. The audit payload must make
  rebase intent explicit without breaking the executor discriminator.
- Log stream references may not exist when no `LogStore` is configured. The
  API should return empty refs/ids rather than fabricated links in that case.
- Merging validation run log refs into operation results must not overwrite
  existing result keys such as `coverage`.

## Assumptions

- Existing `operations.payload` and `operations.result` JSON columns are the
  intended compatibility layer for richer audit metadata.
- `owner` can initially be the subsystem owner (`operator_api` or
  `pr_monitor`) because the current auth layer does not expose a distinct human
  principal.
- For monitor recovery, the actionable operation `reason_code` should be the
  stale/validation blocker reason, while the workspace event may continue to use
  `RECOVERY_DISPATCH`.
- `destroy` is the operation type backing the public DELETE workspace control.
- Existing idempotency key behavior should remain authoritative: same key and
  same payload returns the same row; conflicting payload raises an idempotency
  conflict.

## Explicit Non-Goals

- Do not create a new operation audit table.
- Do not add a migration unless implementation proves existing JSON/result
  columns are insufficient.
- Do not implement console controls or frontend UI.
- Do not implement a new rebase worker/endpoint in this slice.
- Do not change merge policy, review grace, stale detection policy, validation
  tier policy, or cleanup retention.
- Do not emit or require new operation event streams unless needed by an
  existing call path.
- Do not lower coverage thresholds, `.awf/workspace.yml` coverage settings,
  `pyproject.toml` `fail_under`, or quality gates.
- Do not switch branches, push, rebase, force-push, or commit during the
  planning phase.
