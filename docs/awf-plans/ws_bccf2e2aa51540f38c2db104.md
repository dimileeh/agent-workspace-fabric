# Plan: P1 DB-Backed Profile Fixture

## Scope

Add a narrow, realistic profile slice proving that AWF can launch a generic
Dockerized Python app with a workspace-local Postgres sidecar, then run the
profile setup, health check, and validation commands from the agent container
against that live stack.

The slice should stay generic. It should use profile-declared workspace
services in the existing per-workspace Compose stack, not Aira-specific
pgvector/Alembic behavior and not cloud/GKE execution. Unit tests should cover
the profile and renderer contract without Docker. One Docker integration smoke
test should exercise the full Compose plus validation path and skip with the
existing Docker-unavailable reason style.

## Intended Files And Modules To Touch

Primary fixture files:

- `tests/fixtures/workspace_services/python_postgres_app/.awf/workspace.yml`
  - New repo-local profile fixture named something like
    `python-postgres-app`.
  - Declare `docker.mode: none`; the app and Postgres are AWF profile services
    in the outer workspace stack, not nested project Compose in DinD.
  - Declare runtime env such as `APP_BASE_URL=http://app:8080` and
    `DATABASE_URL=postgresql://awf:${AWF_POSTGRES_PASSWORD}@postgres:5432/awf`.
  - Declare a `postgres` service using `postgres:16-alpine`, `pg_isready`
    healthcheck, deterministic named volume `postgres_data`, and no host port
    requirement for agent reachability.
  - Declare an `app` service built from the fixture Dockerfile, depending on
    healthy Postgres, with a service-local healthcheck and `DATABASE_URL`.
  - Declare `phases.setup` to initialize/reset fixture schema through the app,
    `validation.healthchecks` to prove the agent can reach app health, and
    `phases.validate` to write/read a deterministic DB-backed record through
    the app.
  - Declare `ports` entries documenting service-name endpoints, not
    host-only URLs.
- `tests/fixtures/workspace_services/python_postgres_app/Dockerfile`
  - Tiny Python image that installs only the app's DB driver dependency.
  - No repo lockfile changes; keep fixture dependencies isolated to the image.
- `tests/fixtures/workspace_services/python_postgres_app/app.py`
  - Small stdlib HTTP server plus `psycopg` usage.
  - Endpoints: `/healthz` checks DB connectivity, `/setup` creates/truncates a
    table, and `/validate` inserts/reads a deterministic value and returns a
    stable success body.

  - Assert repo-local profile resolution, runtime env, `ports`, Postgres

- `tests/unit/runtime/test_validation.py` or

- `tests/integration/test_python_postgres_profile_compose.py`

  - Use the same availability guard shape as the existing Docker tests:

  - Run `ValidationRunner(AsyncioSubprocessRunner, ...)` for

  - Tear down in `finally` with `manager.down(spec)` and assert no

## Risks

- Docker integration tests may pull `python:3.12-alpine`, `postgres:16-alpine`,
  and build the fixture app image. Docker or Compose unavailability should skip;
  image pull/build failures should remain real failures.
- The fixture app needs a Postgres driver in its Docker image. Keeping that
  dependency inside the fixture Dockerfile avoids changing AWF package
  dependencies or lockfiles.
- `ComposeManager` only expands `${AWF_POSTGRES_PASSWORD}` placeholders. The
  profile should use that existing placeholder instead of introducing a new
  secret-substitution mechanism.
- `ValidationRunner` runs commands inside the agent container, not the app
  container. The fixture commands should use Python stdlib HTTP calls against
  `APP_BASE_URL` so the minimal agent image is sufficient.
- Existing executor cleanup does not appear to run profile `phases.cleanup`.
  Deterministic cleanup for this slice should therefore be proven through
  AWF-owned Compose teardown (`down -v`) unless implementation work uncovers an
  already-supported profile cleanup path.

## Assumptions

- Profile-declared services are the correct generic mechanism for workspace
  sidecars in the outer AWF Compose stack.
- Service DNS names plus container ports are the canonical communication path
  from the agent to app/Postgres inside `awf_net`.
- AWF's control-plane Postgres remains separate from project/workspace
  Postgres; the fixture must not reuse or assume the control-plane database.
- A realistic end-to-end proof can be limited to stack launch, profile setup,
  validation healthcheck, validation command, and deterministic compose
  teardown.
- No schema migrations, API shape changes, scheduler changes, PR monitor
  changes, or cloud backend changes are required for this slice.

## Explicit Non-Goals

- Do not add Aira-specific pgvector, Alembic, service names, database names, or
  environment conventions to AWF core.
- Do not expand GKE, cloud execution, secret broker, or egress-policy behavior.
- Do not redesign the profile schema, DinD behavior, or nested project Compose
  support.
- Do not require Docker for unit tests.
- Do not depend on a locally built `awf-agent-runtime:latest` image in the new
  integration test.
- Do not lower coverage thresholds, quality gates, requested validation tiers,
  or test-quality guardrails.
- Do not change lockfiles unless a production dependency change becomes
  unavoidable, which is not expected.
