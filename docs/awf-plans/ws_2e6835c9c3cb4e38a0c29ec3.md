# Plan: P0 Terminal-State Stale-Callback Regression

## Goal

Prevent stale executor and provider-recovery callbacks from moving an authoritative terminal or teardown workspace back into active lifecycle states. The regression target is a destroyed workspace whose removed worktree was later observed by an in-flight callback, causing `destroyed -> validating -> failed`. Stale callbacks must preserve audit evidence and operation provenance, but must not change workspace status.

Authoritative callback-terminal statuses for this task:

- `destroyed`
- `destroying`
- `completed`
- `cancelled`
- `failed`

## Current Context

Relevant existing behavior found during planning:

- `src/awf/control/state_machine.py` already has `WorkspaceStateMachine.is_callback_terminal`, but its set currently omits `destroying`.
- `src/awf/control/executor.py` already checks `_is_callback_terminal_status` in several stale callback paths and records `workspace.stale_callback_ignored` plus cancels active recovery operations.
- `tests/unit/control/test_executor_monitor_recovery.py` already has stale callback tests for `cancelled`, `destroyed`, `completed`, and `failed`; `destroying` is the missing P0 case.
- `src/awf/db/repositories.py` already provides `WorkspaceRepository.record_ignored_stale_callback` with reason code `STALE_CALLBACK_IGNORED`.
- `src/awf/service/provider_recovery.py` can create retry/fallback recovery attempts from a source workspace; it needs an explicit stale-callback guard where provider recovery is invoked after the source has moved into an authoritative terminal/teardown state.

3. Add provider-recovery stale callback regression coverage in `tests/unit/service/test_provider_recovery.py`:
   - Seed a workspace with provider-failure metadata/evidence that would otherwise permit recovery.
   - Force the workspace into `destroyed`, `destroying`, `completed`, and `cancelled`, then call `create_provider_recovery_attempt_row`.
   - Assert no retry/fallback workspace is created, source status is unchanged, and a structured `workspace.stale_callback_ignored` event is recorded with a provider-recovery callback source/action and clear reason code.
   - Add or preserve an explicit assertion that a current, legitimate provider failure in `failed` state still follows the existing provider recovery path, so the guard only blocks stale callbacks and does not remove authorized provider fallback behavior.
   - If implementation must treat some `failed` provider-recovery invocations as stale, add a narrow test for a failed workspace without eligible provider-failure metadata and assert it records the ignored callback instead of silently returning `None`.

## Intended Implementation Files

- `src/awf/control/state_machine.py`
  - Add `WorkspaceStatus.destroying` to `_CALLBACK_TERMINAL`.
  - Keep lifecycle transition rules unchanged: `destroying -> destroyed` and `destroying -> failed` remain valid for the destroy cleanup path.

- `src/awf/control/executor.py`
  - Prefer no broad changes; existing stale callback checks should start covering `destroying` once the state machine set is fixed.
  - If tests expose a missed callback path, add the smallest local status check before any transition/finalizer that can run after an async callback resumes.

- `src/awf/service/provider_recovery.py`
  - Add a status guard near the locked source load in `create_provider_recovery_attempt_row`.
  - For stale terminal/teardown sources, record `WorkspaceRepository.record_ignored_stale_callback(...)`, preserve source status, flush, and return `None`.
  - Avoid changing retry/fallback creation for active, explicitly authorized provider recovery.

- `src/awf/db/repositories.py`
  - No change expected; reuse `record_ignored_stale_callback` unless provider-recovery tests require one additional payload field that cannot be supplied today.

## Risks And Assumptions

- `failed` is already callback-terminal for executor callbacks, but provider recovery currently uses failed provider-failure workspaces as a valid source for retry/fallback attempts. The implementation should distinguish stale provider-recovery callbacks from deliberate provider recovery so existing provider fallback behavior is not accidentally disabled.
- `destroying` must be callback-terminal for stale executor/provider callbacks, but normal destroy cleanup still needs to complete `destroying -> destroyed` or `destroying -> failed`. The guard must not break `WorkspaceControlService.destroy_workspace` cleanup finalization.
- Audit evidence must be structured and redacted through existing repository/audit helpers; no secrets or raw provider output should be logged.
- Existing monitor recovery transitions such as `monitoring_pr -> ready -> running -> validating -> monitoring_pr/completed` must remain valid when the workspace is still active.

## Explicit Non-Goals

- Do not redesign the workspace lifecycle state machine beyond the callback-terminal guard.
- Do not change branch management, PR monitor policy, merge eligibility, or stale-reason semantics outside this regression.
- Do not add retries to mask stale callback failures.
- Do not change database schema or migrations unless tests prove the existing event/operation tables cannot preserve the required evidence.
- Do not touch console code.
