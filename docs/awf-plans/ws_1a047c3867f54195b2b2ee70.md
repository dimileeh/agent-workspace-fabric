# Plan: P0 PR Monitor Recovery Operations

## Goal

Make PR monitor recovery visible as durable `operations` rows, not only monitor logs, workspace events, or state transitions. Preserve existing monitor behavior and workspace transitions while adding enough structured operation payload/result detail for the API and console to explain what happened.

## Intended Files And Modules To Touch

- `src/awf/db/enums.py`
  - Add operation type vocabulary for PR-monitor-only actions that do not fit existing types, likely `sync_base`, `comment_repair`, `ci_repair`, and `human_wait`.
  - Keep existing `validate`, `rebase`, and `remonitor` meanings intact.

- `src/awf/db/repositories.py`
  - Add an idempotent operation helper around `OperationRepository` using the existing `idempotency_key` column and advisory-lock hook.
  - Keep existing `create`, `start`, `finish`, and list behavior compatible.

- `src/awf/runtime/pr_monitor_operations.py` (new focused helper module)
  - Centralize PR monitor operation payload construction, deterministic idempotency keys, recursive payload/result redaction, and create/start/finish helpers.
  - Payload shape should include `owner`, `source`, `action`, `requested_action` where relevant, `reason`, `reason_code`, `workspace_id` via the row, `pr_number`, `pr_url`, `source_head_sha`, `source_base_sha`, `target_branch` or `remote_branch` where useful, `log_stream_refs`, and small action-specific summaries.
  - Result shape should include status/outcome details such as queued, succeeded, skipped/replayed, comment posted, pushed, rebased, base/head SHAs, and validation/rebase result reason codes.

- `src/awf/runtime/pr_monitor_runner.py`
  - Replace the inline stale recovery operation creation in `_handle_merge_gate_blocker` with the shared helper.
  - Record operations for:
    - validation recovery dispatch, still using `type=validate` so the executor closes the same pending operation;
    - rebase-only dispatch, still queueing `type=validate` with `recovery_mode=rebase_only`;
    - `SyncBase` as a synchronous `sync_base` operation;
    - `AddressComments` as a synchronous `comment_repair` operation;
    - `ReportCiFailure` as a synchronous `ci_repair` operation;
    - `NotifyHuman` as a `human_wait` operation that records the manual wait/notification outcome without making the workspace terminal.
  - Preserve current sleeps, comment dedupe, retry behavior, state persistence, and transitions.

- `src/awf/control/executor.py`
  - Enrich monitor rebase recovery operation records.
  - Start the rebase operation before the synchronous git rebase/push work when source/base SHAs are known, finish it on success/failure, and make it idempotent for replay.
  - Preserve the existing pending validate recovery operation and close it through the current validation finisher.

- `src/awf/service/controls.py`
  - Enrich existing remonitor operation payload/result with PR number/URL and current head/base SHA where present.
  - Keep operator remonitor idempotency and state reset semantics unchanged.

- `src/awf/api/schemas.py`
  - Add optional derived fields on `OperationResponse` for `action`, `pr_number`, `pr_url`, `source_head_sha`, and `source_base_sha`.
  - Do not remove or rename existing response fields.

- Tests:
  - `tests/unit/runtime/test_pr_monitor_runner.py`
  - `tests/unit/control/test_executor_monitor_recovery.py`
  - `tests/unit/api/test_operations.py` and/or `tests/unit/api/test_operations_listing.py` with wrapper export updated
  - `tests/unit/service/test_controls_lifecycle.py`

No migration should be needed because `operations.type`, `payload`, `result`, and `idempotency_key` are already string/JSON columns. I will avoid config, lockfile, and unrelated docs changes.

## Implementation Sequence

1. Add failing tests first.
2. Add the monitor operation helper with:
   - stable action constants;
   - deterministic idempotency key generation from workspace id, PR number, action, reason code, head/base SHA, and action-specific IDs such as comment IDs or CI check names;
   - recursive redaction and truncation;
   - idempotent create/start/finish wrappers.
3. Wire stale validation/rebase recovery dispatch through the helper while preserving the existing `monitoring_pr -> ready` transition and active-operation guard.
4. Wrap synchronous runner actions with operation start/finish:
   - `SyncBase`;
   - `AddressComments`;
   - `ReportCiFailure`;
   - `NotifyHuman`.
5. Enrich executor rebase recovery operation recording and preserve pending validate operation closure.
6. Enrich remonitor payload/result in the control service.
7. Add optional operation response fields in API schemas and verify existing list/detail clients still receive the same core shape.
8. Run formatting/type/test validation and make the smallest fixes needed.

## Risks And Assumptions

- The existing `operations.idempotency_key` column and index are sufficient for this slice. I assume no migration is required.
- Idempotency is restart/retry oriented, not a new cross-process distributed lock. Postgres advisory locking already exists for operation idempotency decisions; SQLite unit tests will rely on deterministic lookup.
- Some recovery actions can legitimately repeat on a new head SHA, new base SHA, or new comment/check set. The idempotency identity must include those inputs so real later work is not suppressed.
- Redaction must happen before persistence because the operations API intentionally exposes payload/result.
- Comment bodies, CI log excerpts, prompts, raw stdout/stderr, and auth material should not be stored in operation payloads. Store IDs, counts, paths, check names, conclusions, and bounded redacted messages instead.
- Existing monitor behavior is the compatibility boundary: workspace transitions, PR comments, sleeps, GitHub retry handling, and validation/rebase recovery flow must remain unchanged.

## Explicit Non-Goals

- No console UI changes.
- No new REST endpoint; use existing `/v1/workspaces/{id}/operations` and `/v1/operations`.
- No merge policy changes.
- No change to PR monitor decision policy or reviewer/comment semantics.
- No database migration unless implementation proves the existing operation columns cannot satisfy the requirement.
- No branch switching, pushing, rebasing, or committing in the planning phase.
