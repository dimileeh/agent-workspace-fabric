## Problem Statement

T02 must add the shared host setup configuration contract and source-checkout asset model that later setup/start/provider/client tasks consume. The slice should be limited to schema, safe config IO, source checkout verification, and reason-coded diagnostics. It must not implement the setup/start CLI orchestration, credential backends, installer manifest generation, package asset inclusion changes, or documentation tasks.

The output should make a verified AWF source checkout explicit and passable to later setup/start code without guessing paths or silently falling back to package assets when the caller selected source assets.

## Proposed Schema Contract

Add Pydantic models or dataclasses with explicit validation, using repo dependencies already present (`pydantic>=2.9.0`, `pyyaml>=6.0.0`). Prefer Pydantic for field validation and serialization boundaries.

Suggested config shape:

```yaml
version: 1
install:
  channel: stable
api:
  host_port: 8000
work_dir: ~/.awf/service
providers:
  github:
    credential_ref: keyring://awf/github/token
    source: gh
    status: ready
clients:
  codex:
    status: configured
    updated_at: "2026-05-28T00:00:00Z"
consent:
  plain_file_secrets: false
source_checkout:
  root: /path/to/checkout
  verified_at: "2026-05-28T00:00:00Z"
  markers:
    - pyproject.toml
    - src/awf/__init__.py
    - docker/compose/local-service.yml
  asset_paths:
    compose_file: docker/compose/local-service.yml
    agent_runtime_dockerfile: docker/agent-runtime.Dockerfile
```

Concrete model names may be adjusted to match local style, but the contract should include:

- `HostSetupConfig`
- `InstallConfig`
- `ApiConfig`
- `ProviderConfig` or `ProviderRef`
- `ClientIntegrationConfig`
- `ConsentConfig`
- `SourceCheckoutAssetMetadata`
- `VerifiedSourceCheckout` or equivalent runtime-only handoff object
- `HostSetupConfigError` / `SourceCheckoutError` with `reason_code` and structured details

Secret policy:

- Config stores credential references only, never raw token/API-key values.
- Reject obvious secret-bearing fields and token-shaped values in config construction/load/write paths. Examples to test: raw `sk-...`, `ghp_...`, `github_pat_...`, `Bearer ...`, and config dictionaries containing keys such as `token`, `api_key`, `secret`, or `password` where a credential ref is expected.
- Allow safe refs such as `keyring://...`, `env://OPENAI_API_KEY`, or a future `plain-file://...` ref only as references, not contents.

Config IO:

- Default path resolves to `$HOME/.awf/config.yml` or an injected home/config path in tests.
- Create parent directory with conservative permissions, target `0700` for `~/.awf` where possible.
- Write config atomically and set config file permissions to `0600`.
- Read missing config as a default empty config if that matches later setup ergonomics; otherwise return a reason-coded missing result. The implementation plan should choose one and test it explicitly.
- Corrupt YAML, non-mapping YAML, schema validation failures, unsafe permissions where enforced, or secret-looking content should raise/return reason-coded diagnostics such as `HOST_SETUP_CONFIG_CORRUPT` or `HOST_SETUP_CONFIG_SECRET_VALUE`.

## Source-Checkout Validation Contract

Validation should accept a candidate root path and return a verified object containing resolved paths for later setup/start, rather than making later code rediscover assets.

Required markers from the task/source plan:

- `pyproject.toml`
- `src/awf/` or `src/awf/__init__.py`
- Compose/bootstrap assets:
  - `docker/compose/local-service.yml`
  - `docker/agent-runtime.Dockerfile`
  - `docker/control-plane.Dockerfile`
- Docs/release fixtures:
  - `README.md`
  - `docs/`
  - `RELEASING.md`

The marker list should be centralized in `source_assets.py` and exposed for tests/downstream use. If a marker is missing, validation must fail with:

- `reason_code == "SOURCE_CHECKOUT_INVALID"`
- structured `missing_markers` details naming exact relative marker paths
- the candidate root in a normalized/safe form

Unreadable path behavior:

- Treat missing, non-directory, permission-denied, and unreadable marker paths as invalid source checkouts with `SOURCE_CHECKOUT_INVALID`, including a path/status detail. Tests should avoid platform-fragile assumptions where root can still read chmod `000`; monkeypatching `Path.is_dir`, `Path.exists`, or `Path.stat` may be more reliable for the unreadable case.

Stale asset metadata behavior:

- Config-stored source metadata should be revalidated before use.
- If metadata points to a checkout whose current marker set no longer matches the recorded metadata, fail with a reason-coded stale diagnostic, likely `SOURCE_CHECKOUT_ASSETS_STALE`, and include missing/changed marker details.
- No silent fallback to package assets after an explicit source checkout has been recorded or selected.

Handoff object:

- Return an immutable `VerifiedSourceCheckout` containing at least `root`, `compose_file`, `agent_runtime_dockerfile`, `control_plane_dockerfile`, `docs_dir`, `release_metadata_path`/`releasing_path`, `verified_at`, and `markers`.
- Include a conversion to persisted `SourceCheckoutAssetMetadata` for config storage.
- Include a function to convert fresh/stored metadata back into a verified handoff after revalidation.

## Tests To Write First

Use strict TDD where practical. Create `tests/unit/service/test_host_setup_config.py` first with failing tests before implementation.

Initial failing tests:

1. `test_host_setup_config_round_trips_with_conservative_permissions`
   - Build a config with install channel, API host port, work dir, provider refs, client integration status, consent flags, and source checkout metadata.
   - Write to an injected temp home/config path.
   - Assert parent directory mode is owner-only where supported and config file mode is `0600`.
   - Read it back and assert equality/semantic round-trip.

2. `test_host_setup_config_rejects_secret_values`
   - Assert raw token/API-key-looking values cannot be set as provider refs or serialized into config.
   - Assert secret-looking unexpected keys in loaded YAML fail before returning a config object.

3. `test_corrupt_config_has_reason_code_and_path_details`
   - Write invalid YAML or schema-invalid YAML to config path.
   - Assert the diagnostic/exception reason code is stable and includes the config path and parse/schema details without echoing unsafe values.

4. `test_valid_source_checkout_returns_verified_asset_paths`
   - Build a minimal temp AWF checkout fixture with required marker files/directories.
   - Assert validation returns a verified handoff with resolved root and all asset paths populated.
   - Assert persisted metadata can be attached to `HostSetupConfig`.

5. `test_invalid_source_checkout_reports_missing_marker_details`
   - Omit one or more required markers from the fixture.
   - Assert `SOURCE_CHECKOUT_INVALID` and exact `missing_markers` details.

6. `test_unreadable_source_checkout_reports_source_checkout_invalid`
   - Simulate an unreadable candidate path or marker path.
   - Assert `SOURCE_CHECKOUT_INVALID`, with a detail distinguishing unreadable path from ordinary missing marker where possible.

7. `test_stale_source_checkout_metadata_fails_without_package_fallback`
   - Persist metadata from a valid checkout, then remove a marker or change marker fingerprint data.
   - Assert revalidation fails with stale/invalid source asset diagnostic and does not return a package/default asset root.

Potential additional focused tests if implementation chooses these contracts:

- Missing config returns a default `HostSetupConfig` with version/current defaults.
- Unknown future fields are either rejected or preserved according to selected compatibility policy. Prefer rejecting unknown unsafe keys for v1 unless preserving is needed for future-proofing.
- Config write redacts or refuses unsafe values before touching disk.

## Risks And Mitigations

- Permission checks can be platform-sensitive. Mitigate by asserting POSIX modes only where `stat.S_IMODE` is meaningful and by keeping tests temp-directory scoped.
- Running as root can make chmod-based unreadable-path tests unreliable. Mitigate with monkeypatched filesystem calls or a helper injectable path accessor for the unreadable case.
- Secret detection can overmatch benign refs. Mitigate by validating exact credential ref schemes and rejecting high-risk raw token patterns/secret field names, not every long string.
- Source markers may overlap existing bootstrap asset discovery. Mitigate by keeping source-checkout validation in `awf.host_setup.source_assets` and avoiding changes to bootstrap discovery unless required for a typed handoff.
- Stale metadata can be defined too broadly. Mitigate by recording deterministic marker relative paths and basic fingerprints such as existence/type/mtime or content hash for critical files; choose the smallest contract that catches missing/changed assets without expensive scans.
- Later T03 will add broader first-run rendering. Mitigate by returning/raising structured diagnostics now without building pretty/JSON renderer behavior in T02.
