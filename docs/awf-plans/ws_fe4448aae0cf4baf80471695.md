## 1. Problem (verified) & how GH auth reaches git (traced)

A BitBucket workspace can talk REST (`BitBucketClient` via `BITBUCKET_API_TOKEN`) but
**git** for bitbucket.org is unauthenticated, so a **private** repo fails at:

- **Worker mirror clone** — `node/git_manager.py:172` runs `git clone --mirror <repo_url>`
  with no bitbucket credential.
- **Push of the feature branch** — executor/monitor push (`control/executor/git_methods.py`,
  `runtime/pr_monitor_runner/remote_ops.py:508`) also unauthenticated for bitbucket.org.

**How the GitHub token reaches git (the mechanism we mirror):**

1. `service/worker.py::_service_git_environment(host_home, github_token=...)` builds a git env that,
   when a GH token is present, sets `GH_TOKEN`/`GITHUB_TOKEN` **and** two **host-scoped** git-config
   entries via the `GIT_CONFIG_KEY_n/VALUE_n/COUNT` protocol (`_add_git_config_entries`):
   - `credential.https://github.com.helper = !gh auth git-credential`
   - `url.https://github.com/.insteadOf = git@github.com:`
2. `_apply_service_git_environment(git_env)` does `os.environ.update(git_env)`.
3. The worker's `GitManager` is built with `env=git_env` (so its `git clone/fetch` subprocesses
   carry the helper). The executor/monitor push goes through `AsyncioSubprocessRunner`, which sets
   **no explicit env** → inherits `os.environ` (already updated). **One env source feeds both
   clone and push.**
4. The token value is **never** placed in a URL or in git-config text — git invokes the `gh` helper
   binary on demand, and the helper is **host-scoped** (`credential.https://github.com.helper`), so
   it only fires for github.com URLs.

**Agent container (`node/secret_mounts.py`):** injects only GH token sources
(`AWF_GITHUB_TOKEN/GH_TOKEN/GITHUB_TOKEN` → targets `GH_TOKEN/GITHUB_TOKEN`) as Compose `${VAR}`
placeholders into the agent env. No BitBucket equivalent.

**Atlassian API token git auth scheme (confirmed):** new Atlassian API tokens use HTTPS **basic**
auth `username=<BITBUCKET_EMAIL>`, `password=<BITBUCKET_API_TOKEN>` against bitbucket.org. This
matches `BitBucketAuth` "basic" mode (email + token). We mirror the GH approach: a **host-scoped
git credential helper** that emits `username`/`password` by reading **env var references** (never
the literal token) so the secret stays out of git-config text, logs, and URLs.

## 2. Design (mirror the GH mechanism, scoped to bitbucket.org)

### New module: `src/awf/common/git_auth.py` (forge-neutral git-over-HTTPS auth wiring)
Keeps forge specifics in one place so `node/git_manager.py` (generic) and `service/worker.py` stay
clean. Contents:

- `BITBUCKET_GIT_AUTH_NOT_CONFIGURED = "BITBUCKET_GIT_AUTH_NOT_CONFIGURED"` — new reason code (git
  surface; distinct from REST `BITBUCKET_AUTH_NOT_CONFIGURED`).
- `BITBUCKET_GIT_HOST = "bitbucket.org"`.
- `is_bitbucket_repo(repo_url: str) -> bool` — `RepoRef.from_url(repo_url).forge == "bitbucket"`;
  `ValueError → False` (best-effort, never raises).
- `bitbucket_git_config_entries() -> tuple[tuple[str, str], ...]` — host-scoped credential-helper
  entries:
  - `("credential.https://bitbucket.org.helper", "")` — clear inherited helpers (defensive).
  - `("credential.https://bitbucket.org.helper", "!f() { test \"$1\" = get && printf 'username=%s\\npassword=%s\\n' \"$BITBUCKET_EMAIL\" \"$BITBUCKET_API_TOKEN\"; }; f")`
  - `("credential.https://bitbucket.org.useHttpPath", "true")` (scope correctness).
  The helper references **env var names only** — the token value lives solely in the env var
  (exactly like `GH_TOKEN`).
- `bitbucket_git_auth_env(source_env: Mapping[str, str]) -> dict[str, str] | None` — when both
  `BITBUCKET_API_TOKEN` and `BITBUCKET_EMAIL` are present, return a dict that:
  - passes `BITBUCKET_API_TOKEN`, `BITBUCKET_EMAIL` through,
  - sets `GIT_TERMINAL_PROMPT=0` (fail fast instead of hanging on a TTY prompt),
  - appends the config entries via the existing `GIT_CONFIG_KEY_n/VALUE_n/COUNT` accumulation
    (a shared `add_git_config_entries(env, entries)` helper — extract/reuse the one in `worker.py`
    so both sites share one implementation; or import worker's if cleaner without a cycle).
  Returns `None` when not configured (caller leaves git env untouched).
- `verify_bitbucket_git_auth(repo_url: str, env: Mapping[str, str]) -> None` — if
  `is_bitbucket_repo(repo_url)` and (`BITBUCKET_API_TOKEN` missing or `BITBUCKET_EMAIL` missing),
  raise `GitOperationError(operation="mirror.clone", returncode=128, stdout="", stderr=<no-token
  message>, reason_code=BITBUCKET_GIT_AUTH_NOT_CONFIGURED)`. The message names the missing env var
  only — never any value. (Import `GitOperationError` from `node.git_manager`; if that risks an
  import cycle, define a small `GitAuthNotConfiguredError` in `git_auth.py` and have `git_manager`
  translate/raise — prefer reusing `GitOperationError` to keep reason-code flow uniform.)

### Worker side — `src/awf/service/worker.py::_service_git_environment`
After the existing GitHub block, add a BitBucket block:
```python
bb_env = bitbucket_git_auth_env(os.environ)   # read live process env (worker already has BB vars)
if bb_env is not None:
    env.update(bb_env)            # passes BITBUCKET_*, GIT_TERMINAL_PROMPT=0, + GIT_CONFIG_* entries
```
This is **host-scoped** (helper only fires for bitbucket.org), so the GitHub path is **byte-for-byte
unchanged**. Because the result is applied to `os.environ` and to `GitManager(env=...)`, it covers
clone (GitManager) and push (executor/monitor via inherited `os.environ`).

### Worker mirror preflight — `src/awf/node/git_manager.py::ensure_mirror`
At the top of `ensure_mirror` (before clone **and** before the existing-mirror `remote update`),
call `verify_bitbucket_git_auth(repo_url, self._env or os.environ)`. This converts the otherwise
opaque `GIT_COMMAND_FAILED` (or a hang) into a clear `BITBUCKET_GIT_AUTH_NOT_CONFIGURED` for a
bitbucket repo with no configured credential. GitHub repos: `is_bitbucket_repo` is `False` → no-op.
No token ever enters the clone URL (`repo_url` stays plain; auth is via the helper in `self._env`).

### Agent side — `src/awf/node/secret_mounts.py`
Add BitBucket provider support parallel to `_GITHUB_PROVIDERS`, so a profile that declares a
`provider: bitbucket` secret injects the agent-container env (Compose `${VAR}` placeholders):
- `_BITBUCKET_PROVIDERS = frozenset(("bitbucket",))`; add to `_SUPPORTED_PROVIDERS`.
- `_BITBUCKET_TOKEN_SOURCE_NAMES = ("BITBUCKET_API_TOKEN",)` → target `BITBUCKET_API_TOKEN`;
  `_BITBUCKET_EMAIL_SOURCE_NAMES = ("BITBUCKET_EMAIL",)` → target `BITBUCKET_EMAIL`.
- `_resolve_bitbucket_secret(...)` mirrors `_resolve_github_secret`: validate `kind == "env"`,
  validate target ∈ {`BITBUCKET_API_TOKEN`,`BITBUCKET_EMAIL`}, resolve source from `source_env`,
  return placeholder pair(s); honor `required`/optional-omitted accounting; reuse the existing
  `_raise`/`_missing` reason-coded paths (`SECRET_LEASE_TARGET_MISMATCH`, `SECRET_LEASE_SOURCE_MISSING`,
  `SECRET_LEASE_TARGET_KIND_MISMATCH`).
- Dispatch in `resolve()` parallel to the github branch; record provider/targets in metadata.
- The agent container's **git** then authenticates to bitbucket.org via the same host-scoped helper.
  The helper config is delivered to the agent through `bitbucket_git_config_entries()` rendered into
  the agent git env (mirroring how GH reaches the agent). **Implementation note / to confirm via
  TDD:** verify whether the agent's GH git config helper today comes from a mounted host `.gitconfig`
  or env; deliver the BitBucket helper by the **same** channel. Default chosen here: emit the helper
  as `GIT_CONFIG_*` env entries alongside the injected `BITBUCKET_*` vars (file-free, host-scoped,
  token only by env reference). Guard against `GIT_CONFIG_COUNT` collision by accumulating onto any
  existing count.

### Redaction (defense-in-depth) — `src/awf/common/token_patterns.py`
Add the Atlassian API-token shape (`ATATT...`) to `KNOWN_TOKEN_PATTERN` and
`STRICT_KNOWN_TOKEN_PATTERN` (e.g. `ATATT[A-Za-z0-9_=.+/-]{8,}`) so a stray token is masked even
though the design never emits it. Existing `_URL_CREDENTIAL_RE` (masks `https://user:pass@`) and
`_TOKEN_ASSIGNMENT_RE` (masks `BITBUCKET_API_TOKEN=…`) already cover the obvious leak shapes.

### Reason catalog
Register `BITBUCKET_GIT_AUTH_NOT_CONFIGURED` text in `service/doctor/reasons.py::_REASON_TEXT`
(likely_cause/action/message) and regenerate `docs/REASON_CATALOG.md` via
`scripts/generate_reason_catalog.py`.

## 6. Risks & mitigations

- **Credential leak (top risk).** Mitigated structurally: token only ever in an **env var**; helper
  config references the var name; clone/push URLs stay plain; `_URL_CREDENTIAL_RE` +
  `_TOKEN_ASSIGNMENT_RE` + new `ATATT` pattern form a redaction safety net. Tests assert the value
  never appears in config/env/args/messages.
- **Regressing the GitHub path.** Bitbucket auth is **host-scoped** and only added when
  `BITBUCKET_*` env is present; explicit regression tests assert GH env/args are byte-identical.
- **`GIT_CONFIG_COUNT` collision** when appending entries in two places (worker + agent). Mitigated
  by always accumulating onto the existing count (`int(env.get("GIT_CONFIG_COUNT","0"))`) — the
  existing `_add_git_config_entries` already does this; reuse it.
- **Hang on missing/invalid creds.** `GIT_TERMINAL_PROMPT=0` + the `ensure_mirror` preflight convert
  hangs/opaque failures into a fast, reason-coded error.
- **Import cycle** (`git_manager` ↔ `git_auth`). Mitigated by keeping `git_auth` dependency-light
  (imports `RepoRef` from `github_client` and, if reused, `GitOperationError`); if `GitOperationError`
  import risks a cycle, raise a local `GitAuthNotConfiguredError` and translate in `git_manager`.
- **File-size guardrail (1500 lines).** `git_manager.py` is large; keep the new logic in `git_auth.py`
  and add only a thin preflight call. Split test files into `_parts/` if needed.
- **Agent-side helper delivery mechanism uncertainty.** The agent's GH git helper channel must be
  confirmed (mounted `.gitconfig` vs env). Mitigation: confirm via TDD before finalizing the agent
  delivery; the **verified blocker (worker clone + push)** is fully addressed by the worker-side
  change independent of this, so #460 unblocks even if the agent channel needs follow-up.

## 7. Assumptions

- Atlassian API token git auth = HTTPS basic (`email:token`) against bitbucket.org (matches
  `BitBucketAuth` basic mode). `x-token-auth` is an alternative but basic+email is the confirmed,
  consistent scheme.
- The worker process already has `BITBUCKET_API_TOKEN`/`BITBUCKET_EMAIL` in its environment (same
  source `BitBucketClient.from_env` reads), so `_service_git_environment` can read them from
  `os.environ`.
- `AsyncioSubprocessRunner` inherits `os.environ` (verified — no explicit `env=`), so applying the
  bitbucket env to `os.environ` covers the executor/monitor push.

## 8. Non-goals

- No changes to GitHub git auth, the REST `ForgeClient`/`BitBucketClient`, PR monitor decision core,

- No SSH-key bitbucket auth (HTTPS basic only).
- No bitbucket **Server/Data Center** support (Cloud / bitbucket.org only, per #345).
- No app-password support (Atlassian API token only, matching existing `BitBucketAuth`).

## 9. Conformance (implemented)

Implemented per the plan. Key deltas from the draft, with rationale:

- **`common/git_auth.py`** — exposes `is_bitbucket_repo`, `bitbucket_git_config_entries`,
  `add_git_config_entries` (shared with the worker), `bitbucket_credentials_present`,
  `apply_bitbucket_git_auth(env, source_env)` (in-place accumulator — replaces the draft's
  standalone `bitbucket_git_auth_env` so the worker composes its `GIT_CONFIG_*` count without a
  collision), `verify_bitbucket_git_auth`, and `GitAuthNotConfiguredError` (local, translated to
  `GitOperationError` in `git_manager` to avoid an import cycle). The helper references env var
  *names* only; no token value is ever written into git env/config.
- **`service/worker.py`** — `_service_git_environment` adds a host-scoped BitBucket block after the
  (unchanged) GitHub block via `apply_bitbucket_git_auth(env, os.environ)`; the local
  `_add_git_config_entries` is replaced by the shared `add_git_config_entries` import. Covers both
  the worker mirror clone (`GitManager(env=...)`) and the executor/monitor push (inherited
  `os.environ`).
- **`node/git_manager.py`** — `ensure_mirror` runs `_bitbucket_auth_preflight` first; a bitbucket.org
  repo with missing creds raises `GitOperationError(reason_code=BITBUCKET_GIT_AUTH_NOT_CONFIGURED)`
  before any `git` runs. GitHub repos are a no-op.
- **`node/secret_mounts.py`** — new `bitbucket` provider injects `BITBUCKET_API_TOKEN` /
  `BITBUCKET_EMAIL` `${VAR}` placeholders into the agent container env (parallel to `github`),
  reusing the existing reason-coded mismatch/missing paths.
- **`common/token_patterns.py`** — added the Atlassian `ATATT…` shape to both known-token patterns
  (defense-in-depth redaction).
- **`service/doctor/reasons.py`** + **`docs/REASON_CATALOG.md`** — registered + regenerated
  `BITBUCKET_GIT_AUTH_NOT_CONFIGURED`.
- **`docker/compose/local-service.yml`** + **`.env.example`** — pass `BITBUCKET_API_TOKEN` /
  `BITBUCKET_EMAIL` / `BITBUCKET_AUTH_MODE` into the control-plane container (mirrors the GitHub
  token passthrough). Without this the worker process never has the creds and the fix is inert —
  required to actually unblock #460. Plan Assumption #2 (creds already in worker env) was therefore
  made true here rather than assumed.
