# Plan: Python/Alembic Migration-Chain Validation

## Goal

Add a narrow, non-mutating validation policy for Python/Alembic profiles. It must detect unsafe Alembic revision graphs before normal validation reports success, emit stable structured reason codes and logs, and reuse the graph-inspection logic needed by the existing target-branch resolver without creating a new auto-fix flow.

## Current Anchors

- `src/awf/service/alembic_resolver.py` already loads Alembic script directories and refuses unsafe graphs before generating target-branch merge revisions.
- `TargetBranchReconcileMonitor` runs `AlembicMergeResolver` as a mutating target-branch resolver after PRs land.
- `ValidationRunner.run_profile_phases()` executes profile commands, health checks, and coverage policy; `ValidationCommandResult` already supports `reason_code`, `policy_failed`, `metadata`, artifacts, and log stream IDs.
- `WorkspaceProfile.validation` is the right profile-owned location for opt-in validation policy fields.
- Executor validation provenance is driven by `_validation_run_command_records()`, `_validation_run_reason_code()`, and `ValidationRunRepository.finish()`.

- `src/awf/runtime/validation_identity.py`
  - Include the new Alembic validation policy fields in environment identity inputs.

No database migration should be needed; validation runs already store commands, reason codes, and log refs in schemaless JSON fields.

## Tests To Write First

1. Graph inspection in `tests/unit/service/test_alembic_resolver.py`:
   - `test_alembic_graph_validation_detects_multiple_heads`: two heads off one base returns failed status, reason code such as `ALEMBIC_MULTIPLE_HEADS`, both head IDs, and no generated file.
   - `test_alembic_graph_validation_detects_missing_down_revision`: a revision pointing to a nonexistent predecessor returns `ALEMBIC_MISSING_DOWN_REVISION` with `missing_down_revisions`.
   - `test_alembic_graph_validation_detects_duplicate_revision_ids`: two files with the same `revision` return `ALEMBIC_DUPLICATE_REVISION` with duplicate IDs and no mutation.
   - `test_alembic_graph_validation_detects_branch_label_anomaly`: duplicate or ambiguous `branch_labels` across revisions returns a specific code such as `ALEMBIC_BRANCH_LABEL_ANOMALY`.
   - `test_alembic_graph_validation_accepts_clean_single_head`: linear `base -> head` returns passed status, `ALEMBIC_GRAPH_OK`, exactly one head, and no findings.

2. Resolver reuse:
   - Existing multi-head resolver tests continue passing.
   - Add a regression proving `AlembicMergeResolver.resolve()` still generates a merge revision for only the multiple-head case but refuses duplicate/missing/branch-label failures from the shared validation helper.

3. Profile schema and identity:
   - A minimal profile defaults Alembic validation to disabled.
   - A profile with `validation.alembic.enabled: true` parses cleanly and preserves path fields.
   - Invalid absolute or parent-traversal policy paths are rejected if path fields are supported.
   - `environment_identity_digest()` changes when Alembic validation is enabled or its config/script settings change.

4. Runtime validation policy:
   - When enabled and the temp repo has multiple heads, `run_profile_phases(..., worktree_path=repo)` returns `all_passed == False`, first failure phase is the policy phase, reason code is `ALEMBIC_MULTIPLE_HEADS`, metadata includes heads/findings, and normal validation commands are not run.
   - Missing `down_revision`, duplicate IDs, and branch-label anomaly each return their own reason code and metadata.
   - Clean single-head graph runs the policy, logs a pass, then executes normal validation commands.
   - Disabled policy does not inspect Alembic and preserves current validation behavior.
   - Enabled policy with no Alembic config is either skipped or failed according to `fail_on_unconfigured`; both branches should have explicit tests if the option exists.

5. CLI/helper surface:
   - If a CLI command is added, assert JSON output includes `status`, `reason_code`, `heads`, and `findings`, and exits nonzero for blocking findings.
   - The CLI must call the same helper as runtime validation.

## Implementation Sequence

1. Add the graph-inspection tests first and confirm they fail against the current resolver-only API.
2. Extract a non-mutating graph inspector:
   - Use the current `_load_script_directory()`, `_safe_heads()`, `_unsafe_loaded_revision_graph()`, and revision reference helpers as the base.
   - Return a new result type that can represent `passed`, `failed`, and `unsupported` without implying a generated merge file.
   - Keep generated-file fields only on `AlembicResolveResult`.
3. Tighten branch-label checks:
   - Detect duplicate labels assigned to more than one revision.
   - Treat branch-label references as valid only when they resolve unambiguously.
   - Include label names and owning revisions in metadata.
4. Rewire `AlembicMergeResolver` to call the inspector:
   - `unsupported` maps to existing `ALEMBIC_NOT_CONFIGURED`.
   - clean single-head maps to existing `ALEMBIC_SINGLE_HEAD`.
   - multiple heads still generates the existing merge revision.
   - all other failures map to refused resolver results with preserved details.
5. Add profile model support for opt-in Alembic validation under `ProfileValidation`.
6. Add the runtime policy hook:
   - Extend `run_profile_phases()` with optional `worktree_path: Path | None = None`.
   - Before phase commands, run the policy when enabled.
   - Write bounded JSON diagnostics to policy stdout/stderr artifacts and durable log streams, matching existing command-result conventions.
   - Return a `ValidationCommandResult` with `policy_failed=True` for blocking graph findings.
7. Update executor integration:
   - Pass the existing `worktree_path` to validation.
   - Add the policy pseudo-command to `_validation_run_command_records()` when enabled so validation provenance has stream refs before execution.
   - Ensure `_validation_run_reason_code()` returns the Alembic reason code for policy failures.
8. Enable the policy only for DB-backed Python/Alembic profiles in this slice, starting with `aira_profile()`. Do not auto-enable for every Python project that merely has `pyproject.toml`.
9. Add the optional CLI helper only after the shared helper and runtime behavior are green; keep it a thin JSON wrapper.

## Risks And Mitigations

- Risk: conflating validation with target-branch auto-fix behavior.
  - Mitigation: put all graph inspection in a non-mutating helper; the resolver remains the only code path that writes merge revisions.
- Risk: Alembic internals differ by version, especially warnings for duplicate revisions or branch labels.
  - Mitigation: inspect loaded `Script` objects directly where possible and assert structured details, not warning text.
- Risk: branch labels are legitimate in some Alembic topologies.
  - Mitigation: fail only on ambiguous or duplicate labels, not on ordinary single-owner labels.
- Risk: policy pseudo-commands could drift from validation provenance stream naming.
  - Mitigation: reuse the existing phase-index/label pattern and add tests for command records and log stream refs.
- Risk: enabling the policy on generic Python projects may create false failures.
  - Mitigation: default disabled; enable only in DB-backed Alembic profiles or explicit repo profiles.
- Risk: coverage pressure from new branches.
  - Mitigation: add focused branch coverage for success, unsupported, failure, and disabled-policy paths before running the full coverage gate.

## Assumptions

- Python DB-backed profiles can opt into this policy through profile JSON/YAML rather than implicit file detection.
- The first implementation can validate the Alembic script graph on disk without connecting to Postgres; applying migrations remains the job of profile setup/validation commands such as `alembic upgrade head`.
- Existing `ValidationCommandResult` and `ValidationRun` JSON fields are sufficient for structured reason codes/logs; no schema migration is required.
- `aira_profile()` is the only built-in profile that should be enabled by default for this slice.

## Explicit Non-Goals

- No new Alembic auto-fix, merge revision generation, rebase flow, or PR monitor repair behavior.
- No changes to target-branch branch management, pushing, or merge policy.
- No automatic enablement for all Python repositories.
- No live database migration execution, downgrade validation, or schema diff/autogenerate validation beyond chain graph integrity.
- No lowering of coverage thresholds, validation tiers, ruff, mypy, or test quality gates.
- No implementation-file, test, config, migration, lockfile, or unrelated doc edits during this planning phase.
- No branch switch, push, rebase, force-push, or commit during this planning phase.
