# Issue 307 Plan: Remonitor Operator Hint Freeze

## Scope

Fix GitHub issue #307: a past-settle `POST /v1/workspaces/{id}/remonitor` with a free-text operator `reason` currently succeeds without making that reason actionable, allowing auto-merge to win before the monitor processes the hint.

This planning artifact is the only file changed in the planning phase. During implementation, also create the repository-required `plans/ISSUE_307_PLAN.md` before source edits and `plans/ISSUE_307_VALIDATION.md` after validation.

## Risks And Mitigations

- Risk: storing hint text in `monitor_threads_addressed` could make the JSON state map carry non-verdict values.
  - Mitigation: use namespaced keys and helper accessors so ordinary comment verdict logic ignores hint keys; add regression coverage around stale state cleanup.
- Risk: clearing settle `done` markers incorrectly could restart reviewer grace for normal remonitor-before-settle behavior.
  - Mitigation: test before-settle and after-settle paths separately and only re-arm when helper confirms settle already elapsed.
- Risk: cooldown could expire while hint is still pending and allow merge.
  - Mitigation: pure `decide()` merge gate blocks on pending hint independently of wall-clock cooldown.
- Risk: a new response warning field may break contract tests or MCP parity.
  - Mitigation: default `warnings=[]`, update shared schema tests, and compare REST/MCP structured content.
- Risk: runner files may exceed the 1500-line maintainability guard.
  - Mitigation: place new helper behavior in existing helper/lifecycle modules or a small sibling module if any touched runner file approaches the guard.

## Assumptions

- `reason` remains optional and capped by existing request validation; empty/whitespace reasons do not create a repair hint.
- The existing `monitor_threads_addressed` JSON state is acceptable for pending operator-hint metadata unless implementation proves a dedicated column is clearer.
- The operator-hint freeze should use existing PR monitor timing machinery and reason-code/event patterns, with no project-specific assumptions.
- The response warning should use the existing public warning-array style. If the codebase standardizes on `warning_code`, use that; if the issue requires `code`, preserve compatibility by documenting the chosen field and tests.
