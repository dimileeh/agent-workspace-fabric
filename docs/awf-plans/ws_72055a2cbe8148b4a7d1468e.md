## Implementation Approach

Prove cross-client alignment with a single, data-driven contract harness rather
than scattered ad-hoc tests. The harness is a registry of **contract
capabilities** — each entry names a REST endpoint, an MCP tool, a CLI
invocation (where present per the parity matrix), the request payload, the
expected backend service call, and the expected error envelopes. The harness
exercises every entry through real REST+MCP+CLI clients backed by the same
database state, then asserts that every layer produced the same operator-
visible contract.

The harness must encode the parity matrix's published gaps as explicit, named
expectations (e.g., "REST exposes `If-Match`, MCP currently does not — assert
the matrix Status row for this capability is `MCP partial` with backlog
`TODO§P1-if-match-parity`"). That keeps the contract test honest today and
lets the future If-Match-parity slice flip a single registry flag instead of
rewriting the suite.

Strict TDD: all new contract tests are written first and fail, then the
smallest safe surface drift is fixed to make them pass. Surface drift fixes
in scope here are only **bug-level** divergences (e.g., one layer omits
`detail` on an `ErrorResponse`, one layer rounds an enum differently, an MCP
tool wraps the response under an extra envelope key). Substantive features
like adding `expected_version` to MCP control tools or new MCP tools/CLI
commands belong to the sibling slices and remain out of scope here.

Coverage strategy: every new contract test module must contribute focused
assertions on touched code, and the suite must keep AWF self-development at
99%+ branch coverage. Existing parity tests are extended where reasonable;
new modules are added under `tests/unit/contracts/` for the cross-client
matrix and under `tests/unit/api/` / `tests/unit/mcp/` / `tests/unit/cli/` for
single-layer follow-ups discovered while writing the harness.

### Contract Dimensions Per Capability

For every registered capability the harness asserts the following dimensions
(adjusted per the capability's row, since some don't apply to read-only or
out-of-scope rows):

1. **Request payload shape:** REST request body, MCP tool input properties,
   and CLI option set hydrate the same backend call. Tested by capturing the
   service-layer call signatures (using a recording fake or real
   `WorkspaceService`) and asserting each layer produces equivalent
   normalized arguments.
2. **Response payload shape:** REST 2xx body and MCP `structuredContent` are
   byte-identical (after stripping volatile timestamps where the existing
   operator-surface tests already strip them). For CLI, the printed JSON,
   when parsed, equals the REST body — proving the CLI does not mutate or
   reshape responses.
3. **Reason codes:** every named error condition produces the same
   `error_code` across REST `detail.error_code` and MCP
   `structuredContent.error_code`. The codes are also already cross-checked
   against source by the matrix `test_parity_matrix_error_codes_*` test —
   the new harness adds *behavioral* parity on top of the existing
   *declarative* parity.
4. **Idempotency keys:** `Idempotency-Key` replays return the same operation
   identifier, status, and message on REST and MCP; mismatched payloads
   under the same key return `IDEMPOTENCY_CONFLICT` on both layers.
   Idempotency-key requirement (REST cancel/stop/destroy/remonitor/validate
   demand the header) maps to MCP's required-arg shape today.
5. **`If-Match` / workspace-version concurrency:** REST endpoints accept
   `If-Match`, return `VERSION_CONFLICT` with structured
   `expected_version`/`actual_version` detail when stale, and never mutate
   when stale. MCP control tools currently do not accept an
   `expected_version`; the harness asserts the parity-matrix row Status is
   `MCP partial` with backlog `TODO§P1-if-match-parity`, so the gap remains
   visible and load-bearing for the next slice. CLI flag `--if-match` for
   `awf workspace remonitor` is verified to forward as `If-Match`.
6. **Auth failures:** REST returns 401 `UNAUTHORIZED` on missing/wrong
   bearer; 503 `API_TOKEN_NOT_CONFIGURED` when no token is set. CLI
   propagates the body and exits non-zero when REST returns 401. MCP runs
   in-process locally, does not enforce the bearer, and does not expose token
   values; the harness asserts MCP responses never include the configured
   token literal (negative test using the existing redaction layer) and the
   parity-matrix Security Boundary column says `require_api_token` for the
   capability.
7. **Structured error envelope:** every error path on REST uses
   `ErrorResponse{error_code, message, detail?}` (under `detail` of an
   HTTPException JSON for FastAPI handlers and as a top-level body for direct
   `JSONResponse` returns). MCP error results carry the same fields under
   `structuredContent`. The harness encodes both shapes through one
   normalizer so REST/MCP error parity is one assertion, not two.

### Implementation Gap Drift To Fix Here (Smallest Safe Surface)

While writing the failing tests I expect to find one or more of these
common-class drifts. Anything beyond these is out of scope and remains backlog
work for the named sibling slice.

- An MCP error-result that returns `error_code` but accidentally drops
  `detail` (unifying through `_workspace_error_result` / `_tool_error`).
- A REST endpoint where one branch raises `HTTPException(detail=str)` instead
  of `HTTPException(detail={"error_code", "message"})`.
- A divergent `error_code` between REST and MCP for the same backend
  exception (e.g., service throws a code, MCP wraps it under a different
  envelope).
- A response field present on one layer and missing on the other (e.g., MCP
  pops `runtime_health` when `None` while REST keeps it `null`, or vice
  versa) — bring the two into one normalized contract.
- A CLI command path that drops `Idempotency-Key` or `If-Match` from headers.

If a more substantive drift is discovered (e.g., the only way to make REST
and MCP `awf_remonitor_workspace` agree on a code is to add `expected_version`
to MCP), the contract test must declare the gap and its parity-matrix
backlog row, not silently fix it. This keeps coordination boundaries clean
with the running sibling slices.

## Risks And Assumptions

- The two sibling P1 slices touch overlapping files (`src/awf/cli/main.py`
  for CLI parity, `src/awf/mcp/server.py` for MCP safe operator action
  tools, plus `tests/unit/cli/**`, `tests/unit/mcp/**`, parity matrix doc).
  Stale-rebase recovery may be required. Coordination strategy: the
  contract registry is the only canonical list of capabilities; sibling
  slices add to the registry once their tools/commands land, and the
  contract suite re-runs without churn. Avoid broad refactors that would
  cause merge conflicts.
- AWF's MCP server is process-local (stdio) and does not enforce bearer
  auth. The contract test must not pretend MCP enforces 401; instead it
  asserts the security boundary documented in the parity matrix and the
  redaction guarantee on responses.
- `If-Match` parity on MCP control tools is genuinely a separate slice.
  Adding `expected_version` to MCP would conflict with that slice and
  is therefore explicitly out of scope.
- Some REST routes return errors via `JSONResponse` (top-level error body)
  while others raise `HTTPException` with structured `detail`. The contract
  envelope normalizer must accept both shapes and prove they carry the same
  `error_code`, `message`, `detail` fields. If a route diverges in a way
  that cannot be normalized, fix the route to use `ErrorResponse(...).
  model_dump()` consistently.
- Some MCP read tools strip optional fields when `None` (e.g., `runtime_health`
  on the runtime tool). Bring the two layers into one normalized contract;
  prefer keeping the field as `null` to match REST `Pydantic`-rendered output
  unless that has downstream operator-console implications I can verify.
- AWF self-development coverage gate is 99%. New contract tests must add
  meaningful assertions, not boilerplate. If a contract dimension cannot be
  expressed without a fake test, document the gap and skip it as
  gap-tracked rather than weakening the assertion.
- The contract registry must validate against the parity matrix at test
  collection time. If the matrix is malformed (e.g., missing required
  columns) the harness fails fast — that is intentional and protects the
  contract from silently rotting.

## Explicit Non-Goals

- Do not add new MCP tools (refresh, rebase, artifact-download, global-events)
  or new CLI commands beyond what the parity matrix already lists. Sibling
  slices `ws_1f89a8c10b1d497d9c912ccb` (MCP safe operator actions) and
  `ws_e7365dffc3a243a2b8f7e775` (CLI command coverage alignment) own that
  work.
- Do not add `expected_version` / `If-Match` parity to MCP control tools —
  that is the explicit `TODO§P1-if-match-parity` backlog slice.
- Do not enforce API tokens in the MCP server. MCP runs locally over stdio
  and trusts the parent process; that contract is documented in the parity
  matrix and trust model.
- Do not flip parity-matrix Status rows without a corresponding behavioral
  fix landing in this slice. Contract tests assert today's reality first.
- Do not introduce a Python SDK or programmatic client — REST + CLI + MCP
  are the supported v0.1 client surfaces.
- Do not lower coverage, validation, or quality gates to make the new tests
  pass.
- Do not rewrite unrelated Active/Completed Slices ledger rows.
- Do not add Aira-specific assumptions to AWF core contract tests; every
  capability in the registry must be project-generic.
