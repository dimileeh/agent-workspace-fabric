# Plan: Reusable Restricted Egress Allowlist Templates (P1 Security Slice)

## Goal
Add reusable restricted-egress allowlist template categories for common local engineering destinations, surface them in onboarding / preview / doctor / status output, and document why the AWF self-dogfood profile stays `open` — all without falsely enforcing destination-level network policy that local Docker cannot yet implement.

## Files to Touch

1. **src/awf/profiles/models.py**
   - Add `EgressAllowlistTemplate` enum (`github`, `model_providers`, `package_registries`, `os_mirrors`, `documentation`).
   - Add `allowlist_templates: list[EgressAllowlistTemplate]` to `ProfileEgress` (default `[]`).
   - Add `open_explanation: str | None` to `ProfileEgress` (default `None`, max_length 512).

2. **src/awf/node/egress_policy.py**
   - In `local_egress_plan`, preserve `allowlist_templates` in `LocalEgressPlan.details` when mode is `restricted` (no behavioral change; local backend stays `internal: true`).

3. **src/awf/service/profile_metadata.py**
   - Add `egress_allowlist_templates_from_profile_snapshot(profile)` to extract the template list from a resolved-profile JSON snapshot.

4. **src/awf/profiles/onboarding.py**
   - Define `_DEFAULT_RESTRICTED_ALLOWLIST_TEMPLATES` as the full set of common templates.
   - In `_profile_for_template`, explicitly set `security.egress.allowlist_templates` on every draft profile so new projects default to restricted with useful templates.

5. **src/awf/service/status.py**
   - In `_network_posture_check_payload`, include `active_restricted_templates` (aggregated from active restricted workspace snapshots) and a `deferred_enforcement_note` in the check payload so the CLI pretty-print and doctor surfaces it.

6. **src/awf/service/doctor/__init__.py**
   - In `_service_status_diagnostics` for the `network_posture` check, pass through the new metadata from the status payload.

7. **.awf/workspace.yml**
   - Add `security.egress.open_explanation` documenting why AWF self-dogfood is intentionally open.

## Risks and Assumptions

- **No local enforcement change**: destination-level filtering remains deferred. The templates are metadata/intent only. `local_egress_plan` for `restricted` still returns `internal: true`.
- **Backward compatibility**: existing profiles without `allowlist_templates` or `open_explanation` parse fine because both fields have safe defaults.
- **Schema safety**: `ProfileEgress` uses `extra="forbid"`; adding typed fields is safe as long as we don't break existing YAML consumers. The new fields are optional with defaults.
- **Overlap risk**: `src/awf/service/profile_metadata.py` and `tests/unit/service/**` are actively edited by `ws_738700a49275436b9b96ec7e`; `src/awf/profiles/onboarding.py` and `tests/unit/profiles/**` are actively edited by `ws_0da5b57348cb49d198db9ee2`. Coordination is advisory; stale policy may require revalidation if those branches land first.

## Explicit Non-Goals

- Do **not** add a new `EgressMode` such as `allowlist` or `mirrored`; the README explicitly rejects these in local schema validation and the PRD says they are a future security slice.
- Do **not** implement cloud `NetworkPolicy`, iptables rules, transparent proxies, or package registry mirrors.
- Do **not** change the default `EgressMode` away from `restricted`.
- Do **not** refactor the onboarding template list or diagnostics beyond adding the egress template fields.
- Do **not** modify the console app (`apps/console`).
