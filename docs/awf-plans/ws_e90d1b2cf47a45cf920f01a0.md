# Plan: Auto-prune git worktrees for completed and merged workspaces

## Summary

AWF today deletes filesystem pressure directories (worktree checkout, compose,
auth) for terminal workspaces via `src/awf/service/gc.py`, but it does **not**
call `git worktree remove` + `git worktree prune` on the associated bare mirror.
This leaves stale worktree administrative metadata in `$GIT_DIR/worktrees/` that
accumulates across runs and can corrupt concurrent `git worktree add` operations
on the same mirror. The task is to extend the GC path to also remove the git
worktree (via `GitManager.remove_worktree`) and release resource reservations
for eligible completed-and-merged workspaces, while protecting active, failed-
preserved, and unmerged-PR workspaces from pruning.

## Current State

### What exists

- **`src/awf/service/gc.py`**: Full filesystem GC for terminal workspaces.
  Plans candidates, classifies preserved reasons, deletes `work_dir/git/worktrees/<id>`,
  `work_dir/compose/<id>`, `work_dir/auth/<id>`, revokes secret leases, and
  produces dry-run evidence. Does **not** call `GitManager.remove_worktree` or
  release resource reservations.
- **`src/awf/node/git_manager.py`**: `GitManager.remove_worktree()` already
  idempotently runs `git worktree remove --force` + `git worktree prune` under
  the per-mirror lock. This is the correct primitive.
- **`src/awf/node/cleanup.py`**: `WorkspaceCleaner.cleanup()` orchestrates
  compose-down + git worktree remove for the explicit destroy path. Not used
  by the GC path today.
- **`src/awf/db/models.py`**: `Workspace` has `pr_url`, `pr_number`,
  `pr_merge_sha`, `repo_url`, `resource_reservations`. `ResourceReservation`
  has `released_at`.
- **`src/awf/db/repositories.py`**: `ResourceReservationRepository.release_active_for_workspace()`
  releases all active reservations for a workspace.
- **`src/awf/service/status.py`**: `collect_workspace_cleanup_status()` surfaces
  GC plan as a status check (dry-run evidence).
- **`src/awf/cli/main.py`**: `awf service gc` CLI wraps `run_terminal_workspace_gc`.

### What is missing

1. GC does not remove the git worktree via `GitManager.remove_worktree()`;
   it only `shutil.rmtree`'s the filesystem directory. The bare mirror's
   `worktrees/` admin metadata is never cleaned up.
2. GC does not release resource reservations for candidates.
3. No predicate checks whether a completed workspace's PR has actually landed
   (i.e. `pr_merge_sha` is set or merge candidate status is `completed`/`merged`).
   Current default policy only checks `pr_url`/`pr_number` existence, not merge
   status.
4. Cleanup/doctor/status surfaces do not expose worktree-prune-specific reason
   codes or evidence in the GC result payload.

#### 2B. Worktree removal in GC execution

**File**: `src/awf/service/gc.py`

- Add `worktree_prune` field to `WorkspaceGCPathOutcome` / `WorkspaceGCResult`:
  actually, the worktree is already one of the three `WorkspaceGCPath` targets
  (kind="worktree"). The missing piece is calling `GitManager.remove_worktree`
  _before_ `shutil.rmtree` on the worktree path. This matters because:
  1. `git worktree remove --force` handles the `.git` link file and mirror
     admin cleanup atomically.
  2. `shutil.rmtree` on the checkout directory alone leaves stale metadata.
  3. After `git worktree remove`, the directory no longer exists, so the
     existing `rmtree` path becomes an `already_removed` no-op — idempotent.

- Add an optional `worktree_remover` callback (similar to
  `compose_teardown`) to `run_terminal_workspace_gc` and
  `run_workspace_filesystem_gc`. When provided, it is called for each
  candidate before filesystem deletion. The CLI provides a concrete
  implementation that calls `GitManager.remove_worktree`.

- New dataclass `WorkspaceGCWorktreeRemoveResult`:
  ```python
  @dataclass(frozen=True)
  class WorkspaceGCWorktreeRemoveResult:
      status: Literal["succeeded", "failed", "skipped"]
      reason_code: str
      error: str | None = None
  ```

- Add `worktree_removes: dict[str, WorkspaceGCWorktreeRemoveResult]` to
  `WorkspaceGCResult`. Wire into `to_dict()` under each candidate.

- In `_delete_gc_plan_paths`, before the existing per-path loop, call the
  `worktree_remover` if provided. If it fails, skip the worktree path
  deletion (still try compose and auth), and record a `WorkspaceGCDeleteError`
  for `worktree_remove`.

#### 2C. Resource reservation release in GC execution

**File**: `src/awf/service/gc.py`

- After filesystem deletion (and worktree removal), call

## Risks and Assumptions

- **Assumption**: `Workspace.pr_merge_sha` is reliably set when a PR is merged.
  If it is `None` for some merged PRs (e.g. release-PR monitors that never merge),
  those workspaces will be preserved until the field is populated or manually
  destroyed. This is the conservative/safe default.
- **Assumption**: `GitManager.remove_worktree` requires `repo_url` to resolve
  the mirror path. We store `repo_url` on every `Workspace` row. The GC
  candidate already carries it via the workspace model.
- **Risk**: `remove_worktree` requires access to the bare mirror on disk.
  If the mirror has been deleted (rare, but possible in disaster recovery),
  the call will fail. The GC path already handles partial failures; this is
  a new failure mode that falls into the existing `partial` status pattern.
- **Risk**: Running `git worktree prune` inside the per-mirror lock may
  contend with concurrent workspace provisioning. This is already the design
  in `GitManager.remove_worktree` (lock is held for both remove + prune);
  no new contention is introduced.
- **Risk**: Resource reservation release after GC might race with the
  state-machine transition path that also releases on terminal transitions.
  Since `release_active_for_workspace` is idempotent (`released_at` set
  check), double-release is a no-op.

## Explicit Non-Goals

- GKE/cloud worktree cleanup — out of scope for this slice.
- Bulk mirror compaction or orphan mirror detection — out of scope.
- New CLI commands beyond wiring into existing `awf service gc`.
- New DB migrations or columns — `pr_merge_sha` already exists.
- Deleting workspace rows or audit events — GC is filesystem/resource-only.
- Modifying the PR monitor loop's post-merge cleanup (it already calls
  `run_workspace_filesystem_gc` today; the worktree removal will happen
  as part of that existing call).
