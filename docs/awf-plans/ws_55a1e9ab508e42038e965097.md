# Plan: Console Dark Theme and Accessibility Controls

**Workspace:** ws_55a1e9ab508e42038e965097

## Goal

Add an operator-focused theme/accessibility control surface to the AWF Next.js console. The console should support light and dark themes, high contrast mode, and larger font sizing; persist those choices in browser local storage; preserve keyboard/focus-visible usability; and prove the dashboard, workspace details, logs, and merge queue in desktop/mobile browser screenshots.

This is a console-only slice. No backlog ledger edits are planned; `TODO/pre-gke-industrial-readiness.md` was read for context only.

## Implementation Approach

1. Implement `operator-preferences.ts` as a small pure module. Keep browser APIs out of the pure functions so unit tests stay fast and deterministic under `node:test`.

2. In `layout.tsx`, add a small inline or `next/script` before-hydration script that reads the same localStorage key and sets HTML data attributes. The script must catch storage/JSON errors and avoid logging preference contents.

3. In `ConsoleDashboard`, initialize preference state after mount, apply attributes to `document.documentElement`, write normalized preferences to localStorage, and render a compact `PreferenceControls` section in the existing `TopBar`. Use segmented/icon buttons or checkbox-style toggles with clear `aria-label`/`aria-pressed` states.

4. Update `globals.css` with semantic CSS variables for background, panels, muted panels, borders, text, accent/focus, terminal, and status colors. Because the current dashboard uses many Tailwind color utilities directly, add scoped dark/high-contrast overrides for the common existing classes (`bg-white`, `bg-slate-50`, `border-slate-*`, `text-slate-*`, and status tone classes) rather than rewriting the whole dashboard.

5. Strengthen focus-visible styles for `button`, `input`, `select`, and `a`; ensure high contrast uses a thicker, clearly visible ring. Make large font sizing root-based so existing `rem` layout scales without custom per-control font math.

6. Add Playwright browser coverage with mocked data rather than requiring a live AWF API. Keep screenshots as test artifacts, not committed golden images, unless the implementation reveals a need for deterministic snapshot baselines.

7. Fix responsive layout issues found by the screenshots, especially fixed-height controls or narrow mobile top-bar wrapping under large font mode.

## Risks and Mitigations

- **Hard-coded Tailwind colors may leave dark-theme gaps.** Mitigate with scoped utility overrides plus browser screenshots across the required panels.
- **Large font mode can stress fixed-height controls.** Mitigate with responsive screenshots, overflow checks, and targeted height/wrapping adjustments in the top bar and logs controls.
- **Before-hydration theme application can cause React warnings.** Mitigate with `suppressHydrationWarning` on `<html>` and keeping the script limited to data attributes.
- **Playwright may require browser binaries not present in the container.** Mitigate by documenting/running the install step only if needed and keeping the test command explicit.
- **Parallel workspace overlap warnings mention console-related test paths.** This plan keeps changes in `apps/console` and avoids Python `tests/**/console*`; re-check target branch changes before implementation edits.

- Existing operational-console density and navigation remain the baseline design language.
