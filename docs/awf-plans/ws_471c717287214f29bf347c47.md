# Issue #337 Plan: PR Monitor Pre-Commit Autofix Retry

## Scope

Resolve GitHub issue #337 in the PR monitor comment-repair commit path. The monitor currently returns `False` after a failed `git commit` when a pre-commit auto-fixer modifies files, leaving those edits dirty for the next monitor pass. The next pass correctly trips `_pre_existing_dirty_repair_worktree_result` with `PRE_EXISTING_DIRTY_WORKTREE`; the fix is to complete the commit handshake upstream.

This plan is intentionally limited to planning. No implementation files are changed in this phase.

## Intended Files and Modules to Touch

  - Update `_commit_dirty_worktree` after the existing failed `git commit` branch.
  - Classify pre-commit output using the existing executor classifier instead of duplicating hook regexes/lists.
  - If the failed commit output indicates `files were modified by this hook`, inspect the now-dirty worktree, prove dirty paths are limited to the current operation's autofixable/deterministic scope, re-stage those paths, and retry the commit once.
  - Preserve the existing ownership repair calls and existing `monitor.dirty_commit_failed` behavior when retry is unsafe or fails.
  - Do not weaken `_pre_existing_dirty_repair_worktree_result`.

  - Prefer reusing `_classify_post_agent_commit_failure` directly from the monitor path if dependency direction is acceptable.

## Tests to Write First

1. `test_commit_dirty_worktree_restages_precommit_autofix_and_retries_commit`
   - Simulate a dirty comment-repair worktree.
   - Queue `git add -A`, cached diff dirty, then `git commit` failure with pre-commit output containing:
     - hook id `end-of-file-fixer` or `trailing-whitespace`;
     - `files were modified by this hook`;
     - `Fixing tests/unit/service/test_workspace_host_port_conflict.py`.
   - Queue post-failure `git status --porcelain` showing only that path dirty.
   - Assert the monitor re-stages the autofixed path, retries `git commit` once, returns `True`, and the next guard check can observe a clean status instead of producing `PRE_EXISTING_DIRTY_WORKTREE`.

2. `test_commit_dirty_worktree_autofix_retry_still_fails_returns_false`
   - Same setup as the success case, but the retry commit also fails.
   - Assert the retry happens once, `_commit_dirty_worktree` returns `False`, and the failure is not masked as success.
   - Verify command ordering so future changes cannot silently skip the retry or loop indefinitely.

3. `test_commit_dirty_worktree_does_not_retry_unowned_or_non_autofix_dirty_paths`
   - Simulate pre-commit output that mentions an autofixed file, but post-failure status includes an additional dirty path not reported by the classifier or not present in the initial operation dirty set.
   - Assert the monitor does not re-stage/retry that unsafe dirty set.
   - Assert the existing dirty-worktree guard still returns `PRE_EXISTING_DIRTY_WORKTREE` for the leftover path on the next pass.

4. Optional classifier regression, only if shared classification is extracted:
   - Preserve current executor classifier expectations for `end-of-file-fixer`, `trailing-whitespace`, `awf-ruff-check`, and `awf-ruff-format-check` in `tests/unit/control/test_executor_post_agent_commit_classifier.py`.

## Implementation Approach

1. Keep the first `git add -A`, cached diff check, and initial `git commit -m <message>` behavior unchanged.

2. On commit failure, after the existing post-failure ownership repair succeeds, classify the commit result with the executor pre-commit classifier.

3. Treat an autofix retry as eligible only when all of these are true:
   - combined stdout/stderr includes `files were modified by this hook`;
   - classifier output identifies deterministic/autofixable paths, such as `normalizer_repair_files`, `format_repair_files`, or `autofix_repair_files`;
   - a fresh `git status --porcelain` after the failed commit succeeds;
   - current dirty paths are non-empty and are a subset of the classifier-reported repair paths;
   - current dirty paths are also within the paths dirty at the start of the operation, so unrelated workspace changes cannot be committed.

4. If eligible, run a bounded restage, preferably `git add -- <dirty paths>` rather than a broad second `git add -A`.

5. Retry `git commit -m <message>` exactly once.

6. On retry success, log a clear monitor event and continue through the existing successful post-commit ownership repair path.

7. On retry failure, status inspection failure, restage failure, or unsafe dirty path scope, return `False` through the existing failed-commit path. The next monitor pass should still be protected by `_pre_existing_dirty_repair_worktree_result`.

8. Do not change the reason code or safety semantics of `_pre_existing_dirty_repair_worktree_result`.

## Risks and Mitigations

- Risk: accidentally committing unrelated dirty files during the retry.
  - Mitigation: retry only when post-failure dirty paths are a subset of classifier-reported autofix paths and the initial operation dirty paths; use `git add -- <paths>` for the bounded set.

- Risk: introducing a monitor/runtime dependency on executor-specific naming.
  - Mitigation: reuse existing classifier behavior first; extract to a small shared helper only if needed, while preserving executor imports/tests.

- Risk: commit retry loops or repeated hook mutation.
  - Mitigation: retry at most once and preserve existing failed-commit behavior if the retry fails.

- Risk: weakening the conservative dirty-worktree guard.
  - Mitigation: do not change `_pre_existing_dirty_repair_worktree_result`; add negative regression coverage proving the guard still fails unsafe dirty worktrees.

- Risk: broad validation conflicts with AWF provenance rules in this workspace.
  - Mitigation: run only focused tests/lint/type checks locally and document that full validation is handled by AWF/GitHub.

## Assumptions

- Pre-commit output for normalizer hooks continues to include `files were modified by this hook` and `Fixing <path>` lines.
