# Plan: Issue #327 — Post-agent commit fails when agent self-commits

## Problem

When an AWF coding agent runs `git commit` itself during its run, the
post-agent commit step fails the workspace with
`reason_code=POST_AGENT_COMMIT_FAILED` (surfaced as
`infrastructure_failure`) — even though the agent's work is fully
committed and the branch is ahead of base.

**Root cause**: In `src/awf/control/executor/execution_flow.py`, when
`git commit` (line 831) returns non-zero, lines 837-863 classify the
failure and either run repair or raise `_PostAgentCommitStepError`. When
the commit fails with "nothing to commit, working tree clean" (the
agent already committed everything), the classifier returns
`repair_strategy="none"` and the code raises the error at line 858
instead of falling through to the rev-list check at line 864 that would
discover the branch is ahead of base and proceed normally.

## Files to touch

1. **`src/awf/control/executor/execution_flow.py`** — Main fix: after
   `git commit` fails, detect "nothing to commit" and fall through to
   the rev-list check instead of raising `_PostAgentCommitStepError`.
2. **`src/awf/control/executor/quality_gates.py`** — Add a helper
   `_is_nothing_to_commit` predicate to detect the benign case from the
   `CommandResult`. Keep the classifier unchanged (it still returns
   `POST_AGENT_COMMIT_FAILED` for observability), but the executor uses
   the new predicate to decide whether to raise or fall through.
3. **`tests/unit/control/test_executor_post_agent_commit_parts/`** — New
   test part file for the self-commit regression tests.

## Tests to write first (TDD)

1. **Agent self-commits → proceeds**: Simulate agent having committed
   (clean worktree, branch ahead of base). Assert workspace proceeds to
   push/PR instead of failing `POST_AGENT_COMMIT_FAILED`.

2. **Clean worktree + not ahead → agent_failure**: Clean worktree AND
   branch NOT ahead of base still fails as no-work/`agent_failure`.

3. **Real git commit error → still fatal**: A genuine `git commit` error
   (not "nothing to commit") still raises `_PostAgentCommitStepError` /
   `POST_AGENT_COMMIT_FAILED`.

4. **Nothing-to-commit + orphan history → reattached**: A self-committed
   branch that is also orphaned is still caught by the orphan-history
   guard and reattached.

5. **Unit test for `_is_nothing_to_commit`**: Predicate correctly
   distinguishes "nothing to commit" output from real errors.

## Implementation approach

### Step 1: Add `_is_nothing_to_commit` predicate in `quality_gates.py`

```python
_NOTHING_TO_COMMIT_PATTERN = re.compile(
    r"nothing to commit|working tree clean",
    re.IGNORECASE,
)

def _is_nothing_to_commit(result: CommandResult) -> bool:
    """Return True when git commit exited non-zero specifically because
    there is nothing to commit (working tree clean). The "no changes
    added" variant is intentionally excluded to avoid dirty-tree false
    positives. This is benign — the agent may have already committed
    its work."""
    if result.ok:
        return False
    combined = (result.stdout or "") + (result.stderr or "")
    return bool(_NOTHING_TO_COMMIT_PATTERN.search(combined))
```

### Step 2: Modify commit-failure handling in `execution_flow.py` (~line 837)

Current code (lines 837-863):
```python
if not commit_result.ok:
    classification = _classify_post_agent_commit_failure(commit_result)
    if classification.repair_strategy in {"deterministic", "agent"}:
        await self._run_post_agent_commit_repair(...)
    else:
        raise _PostAgentCommitStepError(...)
```

New code:
```python
if not commit_result.ok:
    if _is_nothing_to_commit(commit_result):
        _log.info(
            "executor.post_agent_nothing_to_commit",
            workspace_id=workspace_id,
            reason="agent already committed; falling through to rev-list check",
        )
    else:
        classification = _classify_post_agent_commit_failure(commit_result)
        if classification.repair_strategy in {"deterministic", "agent"}:
            await self._run_post_agent_commit_repair(...)
        else:
            raise _PostAgentCommitStepError(...)
```

When `_is_nothing_to_commit` returns True, we skip the error and fall
through to the existing rev-list check at line 864. The rev-list check
already handles both cases correctly:
- rev-count > 0 → proceed (agent already committed)
- rev-count == 0 → agent_failure / no-work

### Step 3: Improve no-work message clarity

In the rev-count == 0 block (~line 874), append a clarifying note if
the nothing-to-commit path was taken (optional, for debuggability):
the existing message is already clear ("agent exited without producing
any commits on the feature branch").

### Step 4: Add regression tests

## Risks / assumptions / non-goals

### Risks
- **False positive matching**: `_is_nothing_to_commit` could
  accidentally match real errors that happen to contain "nothing to
  commit" in unrelated output. Mitigated by checking for `returncode=1`
  (git's specific exit code for this) AND the pattern, and by only
  applying this in the commit (not `git add`) failure path.

- **Test realism**: The `FakeCommandRunner` must correctly simulate the
  git exit code and output for the "nothing to commit" case. It already
  supports this.

### Assumptions
- Git's "nothing to commit" exit code is always 1 (documented behavior).
- The `_is_nothing_to_commit` check is applied ONLY to `git commit`
  results, not `git add` results (git add failures are still always
  fatal).
- The rev-list check at line 864 is the correct single source of truth
  for "did work actually happen?" — which the existing comment at line
  475 confirms.

### Non-goals
- Changing the `_classify_post_agent_commit_failure` classifier itself
  (it should still classify the output the same way for observability;
  the fall-through decision is a separate concern at the call site).
- Changing the `_mark_post_agent_commit_failed` handler or the
  exception-to-reason-code mapping.
- Adding new reason codes or changing the FailureReason enum.
- Changing the retry/resume/repair flow beyond the focused fix.
- Updating `openapi.json` (no schema changes).
