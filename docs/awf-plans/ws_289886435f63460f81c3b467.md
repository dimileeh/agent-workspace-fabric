# Plan — Issue #361 / WS-B1: make AWF's GC reclaim engine actually reclaim disk

**Workspace:** `ws_289886435f63460f81c3b467`
**Branch:** `awf/ws_289886435f63460f81c3b467`
**Issue:** #361 (WS-B1 of a 4-part fix — the *reclaim engine*).

## Problem recap (three coupled defects, one PR)

1. **Deletion runs as the wrong user (P1#1).** `awf service gc` runs the gc engine
   **in the host CLI process as uid 1000** (`run_terminal_workspace_gc` invoked directly
   from `cli/service_commands.py:462`). The per-workspace **auth** dirs are root-owned
   (created in-container by the root worker), so the host-side `shutil.rmtree`
   (`_delete_gc_path`, `gc.py:1459`) cannot remove them. Worse, a path that does not exist
   is reported as `already_removed` **success** (`_delete_gc_path_outcome`, `gc.py:1088`),
   so a permission no-op can read as "reclaimed".
2. **Post-merge reclaim defers a week (P1#2).** `_gc_completed_workspace_filesystem`
   (`runtime/pr_monitor_runner/lifecycle.py:634`) runs in the root worker (ownership is
   fine) but calls `run_workspace_filesystem_gc` with the **default 168 h retention**.
   `_classify_workspace_for_gc` (`gc.py:1299`) preserves a freshly-merged workspace because
   `updated_at > cutoff_at` → reclaims **nothing** on merge; the ~1.7 GB pressure dirs
   survive for a week (in practice forever).
3. **Docker volumes leak (the docker leak).** Per-workspace volumes
   (`awf-ws_<id>-dind_data` / `-postgres_data`) leak. The CLI's host-side compose teardown
   (`cli/common.py:163`, `_run_terminal_workspace_compose_teardown`) runs
   `docker compose down --remove-orphans` **without `-v`/`--volumes`**, so the terminal-gc
   path never reaps volumes. `compose_manager.down_project(remove_volumes=True)` and
   `remove_project_by_label` already exist but are not wired into the terminal-gc engine
   with volume removal.

## Locked design (from the engineering review — do not re-litigate)

- **FIX 1:** route the actual deletion **through the root control-plane**. Add a service
  entrypoint + a thin REST route on the `api` container (which runs as **root** and mounts
  the host work-dir + docker socket — see `docker/compose/local-service.yml:125-148`). The
  `awf service gc` CLI becomes a **thin httpx trigger** over REST (matching the documented
  "cli is a thin httpx client over REST" contract). Replace the silent `already_removed`
  success-on-permission-failure with a **loud, reason-coded failure** so a no-op is never
  reported as success.
- **FIX 2:** on a successful PR merge, reclaim the **pressure dirs** (auth, git worktree,
  compose stack) **immediately**, bypassing the 168 h retention window. The retention
  window keeps protecting only the **durable record** — the `Workspace` row, its
  `WorkspaceEvent` audit log, and logs — which gc already never deletes.
- **FIX 3:** wire a real `compose_teardown` callback into the gc execution path that calls
  `compose_manager.down_project(remove_volumes=True)` (fallback
  `remove_project_by_label(remove_volumes=True)`) so per-workspace volumes are reaped.
  **Do not touch image pruning** — companion/runtime images are global and already
  age-pruned.

## Architectural facts confirmed during planning

- Both `api` and `worker` services run as **root**, mount `${AWF_HOST_WORK_DIR}` at the
  same path inside the container, and mount `/var/run/docker.sock`
  (`docker/compose/local-service.yml`). So a gc run inside the `api` container can both
  delete root-owned dirs and drive `docker compose`.
- gc **only ever deletes filesystem pressure dirs** (worktree / companion_worktree /
  compose / auth — see `_is_safe_gc_path`, `gc.py:1475`). It never deletes the DB row or
  events. So "preserve the durable record" for FIX 2 is satisfied by construction; the only
  change needed is to stop *deferring* the pressure-dir reclaim.
- The reason-code catalog (`docs/REASON_CATALOG.md`) is generated from
  `awf.service.doctor.reasons._REASON_TEXT`, **not** from the gc string constants, so a new
  gc reason code does not force a catalog regen (optional operator-doc entry only).

## Intended files/modules to touch

Source (scope-locked to WS-B1):

1. `src/awf/service/gc.py`
   - **FIX 1 (loud failure):** add reason code `PATH_DELETE_PERMISSION_DENIED`. In
     `_delete_gc_path`, catch `PermissionError` (and `OSError` with `errno in {EACCES,
     EPERM}`) **specifically** and return a distinct sentinel so `_delete_gc_path_outcome`
     emits `status="failed"` with the new reason code (never `already_removed`). Ensure an
     **existing-but-undeletable** path can never collapse to `already_removed` (that branch
     stays strictly the not-exists case).
   - **FIX 2 (immediate reclaim):** add a parameter to `run_workspace_filesystem_gc`
     (e.g. `ignore_retention: bool = False`) threaded into `_classify_workspace_for_gc`
     (new keyword, default `False`) so that for a **completed + PR-merged** workspace the
     `updated_at > cutoff_at` deferral at `gc.py:1299` is skipped and the workspace becomes
     a `_candidate_for_workspace(... reason_code=COMPLETED_PR_RETENTION_EXPIRED)`
     immediately. Retention behavior for **failed/superseded/without-PR/not-merged**
     workspaces is unchanged (still preserved). Default `False` keeps every existing caller
     and test path identical.
   - **FIX 3 (teardown wiring):** provide the root-control-plane gc entrypoint
     (new `async def run_service_workspace_gc(...)` or similar) that builds a
     `ComposeManager`-backed `compose_teardown` callback and calls
     `run_terminal_workspace_gc(..., compose_teardown=<callback>)`. The callback removes
     **volumes** (`down_project(remove_volumes=True)` with `remove_project_by_label`
     fallback) and is idempotent / tolerant of an already-down stack.
2. `src/awf/node/compose_manager.py` — **only** to expose a small teardown convenience the
   gc callback calls (e.g. `async def teardown_project(*, project_name, compose_file,
   workspace_id, remove_volumes=True) -> <result>` that does `down_project` then falls back
   to `remove_project_by_label` on failure, returning a structured ok/reason_code). No
   behavior change to provisioning paths.
3. `src/awf/runtime/pr_monitor_runner/lifecycle.py` — `_gc_completed_workspace_filesystem`
   passes `ignore_retention=True` to `run_workspace_filesystem_gc`, and (FIX 3) wires the

   `--volumes`; confirm we do not double-tear-down in a way that turns a benign

   request/response schemas to `src/awf/api/schemas.py` (reused by MCP per the contract;

6. `src/awf/cli/common.py` — the host-side `_run_terminal_workspace_compose_teardown`

## Risks & assumptions

- **Assumption (FIX 1 interpretation):** the "silent `already_removed` success" the issue
  cites manifests as a permission no-op being treated as benign. We make permission
  failures **loud and reason-coded** (`PATH_DELETE_PERMISSION_DENIED`) *and* move deletion
  to root so it actually succeeds. We keep the genuine not-exists → `already_removed` path
  (it is correct — nothing to reclaim).
- **Risk — REST entrypoint vs exec-into-container:** chosen design is a REST route on the
  root `api` container (most testable, matches the cli-over-REST contract). Confirmed the
  `api` container is root and mounts the work-dir + docker socket, so it can delete
  root-owned dirs and run compose teardown. Long-running deletion is synchronous; acceptable
  for local alpha Core with the default batch limit (50). If this proves too coarse later,
  it can move to the async `Operation` model — out of scope here.
- **Risk — double compose teardown in the post-merge path:** lifecycle already calls
  `_teardown_compose_stack` (`--volumes`) before gc. Wiring a volume-removing
  `compose_teardown` into the gc call must remain **idempotent** so an already-down stack
  yields `skipped`/ok, not `partial`. Tests assert this.
- **Risk — ComposeManager construction:** `ComposeManager.__init__` requires
  `work_dir` + `template_path`; teardown (`down_project` / `remove_project_by_label`) does
  not actually need the template, but the constructor does — resolve `template_path` from
  settings/the provisioner's default at the entrypoint. Verify during implementation.
- **Risk — OpenAPI drift + MCP lockstep:** new schemas must regenerate `openapi.json` and
  stay consistent with the MCP server's reuse of `api/schemas.py`.
- **Risk — CLI behavior change:** `awf service gc` now needs a running API
  (`awf serve`/control-plane up). This is the documented model for cli-over-REST commands;
  update `--help`/error messaging so an operator without a running API gets a clear hint.

## Reason-code flow (invariant compliance)

`PATH_DELETE_PERMISSION_DENIED` flows: `_delete_gc_path` sentinel → `WorkspaceGCPathOutcome`
/`WorkspaceGCDeleteError` (`reason_code`) → `_gc_result` `status="partial"` →
structured log fields in `_gc_completed_workspace_filesystem` (`monitor.filesystem_gc_failed`
`delete_errors`) and the REST/CLI payload. No bare `except`; catch `PermissionError`/
`OSError` specifically. No secrets logged.
