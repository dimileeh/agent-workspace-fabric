# Plan: PR Monitor Merge Completion Observability and Persistence

## Scope

Fix two PR monitor issues observed after PR #220 merged:

1. Add explicit structured observability around the built-in pre-merge settle wait that happens after `monitor.merge_critical_section_entered` and before the final PR recheck/merge.
2. Ensure a successful merge SHA recorded by monitor operations is also persisted to `Workspace.pr_merge_sha`, including the completion path where the workspace row is already terminal when the monitor terminal callback runs.

## Intended Files / Modules To Touch

- `src/awf/runtime/pr_monitor_runner.py`
  - Add structured pre-merge settle start/completion logging in the merge critical section.
  - Reuse the existing monitor log sink pattern so the same events land in `monitor.log` when present.
  - Adjust `_terminate_completed` so a provided successful `pr_merge_sha` is persisted before returning from an already-terminal/completed workspace path.

- `tests/unit/runtime/test_pr_monitor_runner.py`
  - Add real-Postgres regression coverage for `pr_merge_sha` persistence when `_terminate_completed` is called with a merge SHA but the workspace has already reached `completed` with `pr_merge_sha` still null.
  - Optionally add the pre-merge settle log regression here if it is cleaner to exercise `_execute` directly with `structlog.testing.capture_logs`.

- `tests/unit/runtime/test_monitor_action_logging.py`
  - Preferred location for the pre-merge settle observability regression because it already covers monitor structured logs and durable monitor log behavior with real Postgres.

No schema migration, API schema, CLI, merge coordinator, merge policy, or workspace display changes are expected. `Workspace.pr_merge_sha` already exists and workspace detail should show it once persistence is fixed.

## Tests To Write First

1. `test_pre_merge_settle_emits_started_and_completed_logs`
   - Use the existing real Postgres fixture from monitor runner tests.
   - Seed a `monitoring_pr` workspace.
   - Configure `pre_merge_settle_seconds=5` and initial/non-check settle values so the test enters the pre-merge settle path immediately.
   - Queue the existing clean pre-merge recheck commands and merge command responses.
   - Capture structlog records with `structlog.testing.capture_logs()`.
   - Assert the captured events include, in order after `monitor.merge_critical_section_entered`:
     - `monitor.pre_merge_settle_started`
     - `monitor.pre_merge_settle_completed` or `monitor.pre_merge_settle_elapsed`
   - Assert both events include `workspace_id`, `pr_number`, `base_branch`, full `head_sha`, and `wait_seconds`.
   - Assert the completed/elapsed event includes `elapsed_seconds` and that it is numeric and non-negative.
   - If using a `LogStore`, also assert the same event names appear in the durable `monitor.log` stream.
   - Expected initial failure: these events are absent today; only the sleep happens after entering the critical section.

2. `test_terminate_completed_persists_merge_sha_when_workspace_already_completed`
   - Use `seed_monitoring_workspace(...)` with real Postgres and `pr_merge_sha=None`.
   - Manually transition the workspace from `monitoring_pr` to `completed` without setting `pr_merge_sha`, simulating the stale/terminal callback path seen in production observability.
   - Call `PullRequestMonitorRunner._terminate_completed(workspace_id, pr_merge_sha="MERGESHA", repo_url=None, base_branch=None, compose_project=None, compose_file=None)`.
   - Assert the workspace remains `completed` and now has `pr_merge_sha == "MERGESHA"`.
   - Assert the ignored terminal callback event behavior is preserved if the existing helper records one for non-`monitoring_pr` rows.
   - Expected initial failure: `_terminate_completed` currently returns before assigning `ws.pr_merge_sha` when status is not `monitoring_pr`.

## Implementation Steps

1. Add the failing tests and run only those focused test nodes to confirm they fail for the expected reasons.
2. In `PullRequestMonitorRunner`, add a small helper for pre-merge settle events, likely mirroring `_record_merge_coordination_event` but with extra fields:
   - `workspace_id`
   - `repo_url`
   - `base_branch`
   - `pr_number`
   - full `head_sha`
   - `wait_seconds`
   - optional `elapsed_seconds`
3. In the merge critical section, wrap only the existing `await self._deps.sleep(self._config.pre_merge_settle_seconds)` call:
   - record `monitor.pre_merge_settle_started` immediately before sleeping;
   - capture `time.monotonic()` before sleep;
   - record `monitor.pre_merge_settle_completed` after sleep with elapsed seconds.
   - Do not add or remove any waits, rechecks, queue checks, gate checks, or merge calls.
4. In `_terminate_completed`, persist a provided `pr_merge_sha` before the early return for non-`monitoring_pr` rows, preferably only filling a blank value or preserving an identical existing value. Keep the existing ignored callback recording and commit behavior.
5. Re-run the focused tests, then the broader touched runtime tests.

## Risks / Assumptions

- Assumption: `awf workspace show` already surfaces `Workspace.pr_merge_sha`; the observed `null` value was caused by persistence, not response serialization. If the new persistence regression passes but workspace detail still omits the value, add the narrowest response/CLI regression and serializer fix.
- Assumption: the relevant production race is the already-terminal completion path in `_terminate_completed`; it matches the code path that can record merge operation success while returning before writing `pr_merge_sha`.
- Risk: `RecordedSleep` does not advance `time.monotonic()`. The log test should assert `elapsed_seconds >= 0` or monkeypatch `time.monotonic` in a controlled way.
- Risk: overwriting an existing non-null, different `pr_merge_sha` could hide a deeper data conflict. The smallest safe persistence fix should fill null values and leave mismatches visible unless tests or requirements show an overwrite is necessary.
- Risk: adding logs inside the merge critical section must not introduce extra DB writes or operation rows that could perturb merge ordering. Prefer structlog plus existing monitor log sink only.

## Explicit Non-Goals

- Do not change merge eligibility, merge queue ordering, merge critical-section locking, pre-merge settle duration, retry behavior, or PR monitor decision policy.
- Do not add schema migrations or new workspace fields.
- Do not change branch management, pushing, rebasing, or PR creation behavior.
- Do not broaden this into cleanup/GC behavior beyond making `pr_merge_sha` accurately persistent after successful monitor completion.
