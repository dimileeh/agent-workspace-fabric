## 1. Goal & context

Add a new `src/awf/host_setup/providers.py` module that **orchestrates provider
setup** on top of the foundations already merged:

- **T04** (PR #332) gave `awf setup` a validated, repeatable `--provider`
  selector, the `build_setup_readiness_payload` aggregation, and an explicit
  placeholder dispatch point in `setup_commands._run_setup` where selected
  providers currently raise `INTERACTIVE_INPUT_REQUIRED` via
  `_require_provider_interactive` (`src/awf/cli/setup_commands.py:248-269`).
- **T06** (PR #333) gave `host_setup/credentials.py` the credential backend
  abstraction: `store_provider_credential(...) -> CredentialRef`,
  `CredentialRef.to_provider_config_fields(status=...)`, host-capability
  gating for plain files, and the `INTERACTIVE_INPUT_REQUIRED` /
  `CREDENTIAL_*` reason codes. `host_setup/config.py` already models
  `ProviderConfig(credential_ref, backend, source, status)` inside
  `HostSetupConfig.providers` and round-trips `~/.awf/config.yml` without
  storing raw secrets.

The probing engine already exists: `src/awf/service/provider_readiness.py`
(`collect_agent_readiness`, `selected_provider_readiness_preflight`,
`validate_provider_names`, `ProviderReadinessError`) probes GitHub (`gh auth
status`, 5s timeout), Codex, Claude Code, Cursor, Gemini, OpenCode/Ollama
(bounded 2s HTTP probe), Grok, and Docker, redacting all secrets and returning
per-provider `{ok, status, reason, message, credential_sources, ...}` results.

T07 is the **orchestration layer** that ties capture → ref → recheck →
renderable summary together, treating GitHub as first-class, and wires it into
the existing setup dispatch placeholder.

### Reason codes — already present (no new codes needed)

`PROVIDER_SETUP_AUTH_INVALID` and `SETUP_PROVIDER_UNKNOWN` already exist in
`host_setup/rendering.py`, are registered in `FIRST_RUN_CREDENTIAL_REASON_CODES`
/ `FIRST_RUN_SETUP_REASON_CODES`, exported from `host_setup/__init__.py`, and
have catalog entries in `src/awf/service/doctor/reasons.py` + generated
`docs/REASON_CATALOG.md`. T07 **consumes** these; it does not invent new codes.
If a genuinely new operator-facing failure surfaces during implementation, add
it via the established 3-step pattern (constant in `rendering.py` → `_REASON_TEXT`
entry in `reasons.py` → export + `FIRST_RUN_*` tuple) and regenerate the catalog.

### Name-surface bridge (the central design decision)

The two provider vocabularies differ and must be bridged explicitly:

- `KNOWN_SETUP_PROVIDERS` (setup CLI) = `{github, codex, claude_code, cursor,
  gemini, opencode, grok, awf_cloud}` — includes `awf_cloud`, **no** `docker`.
- `PROVIDER_NAMES` (readiness) = `{github, codex, claude_code, cursor, gemini,
  opencode, grok, docker}` — includes `docker`, **no** `awf_cloud`.

`providers.py` owns a single explicit mapping from setup-provider →
readiness-provider (identity for the seven shared names) plus stub/slot handling:

- `awf_cloud` → **stub**: always returns a deterministic
  `status="not_configured"`, `reason="AWF_CLOUD stub"` result; never probes the
  network; documented as a reserved future slot (backend out of scope per
  backlog "NOT In Scope").
- Future provider slots → a small ordered registry so new providers are one
  table entry, not a code change scattered across files.
- `docker` is infrastructure, not an agent provider selector, so it stays out
  of the setup-provider orchestration surface (it is already covered by system
  checks / readiness elsewhere).

## 2. Files / modules to touch

### New

- `src/awf/host_setup/providers.py` — the orchestration module. Contents:
  - A frozen provider registry (ordered tuple of provider specs) describing each
    setup provider: canonical name, whether it is GitHub-first-class, the
    readiness provider it maps to (or `None` for stub slots), and its preferred
    env-ref variable name(s) (e.g. GitHub → `GH_TOKEN`/`GITHUB_TOKEN`,
    Codex → `OPENAI_API_KEY`, Claude → `ANTHROPIC_API_KEY`, Gemini →
    `GEMINI_API_KEY`, OpenCode → `OLLAMA_API_KEY`).
  - `ProviderSetupResult` (Pydantic `frozen` model, `extra="forbid"`): per
    provider `name`, `status` (`ready` | `warning` | `unavailable` |
    `not_configured`), `reason_code`, `summary`, `backend` (ref backend kind or
    `None`), `credential_ref` (the **safe** ref string only — never a value),
    `configured` (bool), `rechecked` (bool). No raw-secret fields by construction.
  - `ProviderSetupSummary` (Pydantic `frozen` model): `mode`
    (`all_providers` | `targeted_recheck`), `selected` (ordered names, empty for
    all), `providers` (ordered tuple/dict of `ProviderSetupResult`),
    `overall_status`, and a `to_details()` helper returning the status-only,
    secret-free dict that `build_setup_readiness_payload` details and
    `start_commands._providers_summary` can render.
  - `orchestrate_provider_setup(...)` — the entry point. Signature shape:
    `(settings, *, selected_providers: Sequence[str], config: HostSetupConfig,
    allow_plain_secrets: bool, non_interactive: bool, environ=None,
    capture: ProviderSecretCapture | None = None, run_subprocess=None,
    http_get=None) -> tuple[ProviderSetupSummary, HostSetupConfig]`.
    Returns the renderable summary **and** an updated `HostSetupConfig` (with
    `ProviderConfig` refs filled for configured providers) so the caller persists
    it via the existing `_persist_safe_config` path. Pure orchestration: all
    I/O (subprocess/http/secret capture) is injected for testability.
  - `render_provider_summary(...)` — produces the status-only dict for setup +
    start summaries, reusing `provider_readiness` redaction guarantees (status
    strings only, no refs/tokens in the surfaced summary).
  - GitHub first-class helper: marks GitHub ready when either `gh auth status`
    succeeds (bounded probe, reuse the injected `run_subprocess` and the existing
    5s `provider_readiness` GitHub timeout semantics) **or** an env ref
    (`GH_TOKEN`/`GITHUB_TOKEN`) is configured — **without** storing a raw token.
  - Credential→ref conversion: when a secret is captured/discovered for a
    provider, call `store_provider_credential(CredentialRequest(...), preferred,
    capabilities=detect_host_credential_capabilities(...), allow_plain_secrets,
    plain_file_consent=config.consent.plain_file_secrets)` and fold the resulting
    `CredentialRef.to_provider_config_fields(status="ready")` into
    `ProviderConfig`. Env-only providers store an `env://NAME` ref (no value).
  - Recheck: after refs are set, call `collect_agent_readiness(settings,
    environ=..., strict_providers=[<mapped readiness names>], run_subprocess=...,
    http_get=...)` (or per-provider equivalent) so the summary reflects the
    real, bounded probe outcome. Map readiness `ok/status/reason` →
    `ProviderSetupResult`. **Targeted mode**: when `selected_providers` is
    non-empty, only those providers are configured/probed; unselected providers
    are neither mutated in config nor probed, and the summary `mode` is
    `targeted_recheck`.
  - Non-blocking failure isolation: each provider is orchestrated independently;
    a failure (missing/invalid credential, probe failure) sets that provider to
    `unavailable` with `PROVIDER_SETUP_AUTH_INVALID` (or the readiness reason)
    and never aborts the others. `overall_status` aggregates but a single failed
    provider does **not** mark the run blocked.

### Modified (narrow)

- `src/awf/host_setup/__init__.py` — export the new public symbols
  (`orchestrate_provider_setup`, `ProviderSetupSummary`, `ProviderSetupResult`,
  `render_provider_summary`, registry accessor) and add to `__all__`.
- `src/awf/cli/setup_commands.py` — replace the T04 placeholder so that, on a
  non-dry-run path with selected (or, for an all-provider setup, all
  configurable) providers, `_run_setup` calls `orchestrate_provider_setup`,
  folds the returned `ProviderSetupSummary` into the readiness payload
  `details["providers"]` (labelled `targeted_recheck` vs `all_providers`), and
  persists the returned `HostSetupConfig`. The existing
  `_require_provider_interactive` guard is preserved for the genuine
  non-interactive-needs-capture case (when a selected provider needs a secret
  that can only be entered interactively); orchestration that can complete from
  `gh`/env refs alone must **not** raise it. Keep the change minimal — reuse the
  existing payload-merge and persistence helpers.
- `src/awf/service/provider_readiness.py` — **only if** a narrow integration
  seam is required (e.g. a thin helper that maps a single setup provider to its
  redacted readiness result, or accepts a resolved env-ref override so a
  configured ref is probed). Prefer reusing the existing public API
  (`collect_agent_readiness` with `strict_providers`) and add the seam **only**
  if reuse is insufficient. No behavior change to existing readiness callers.
- `src/awf/cli/start_commands.py` — only if needed to render the new summary
  shape. `_providers_summary` already extracts status-only data from
  `service_status["agent_readiness"]`; prefer keeping `providers.py`'s summary
  shape compatible with it so **no** start change is required. Touch only if a
  compatibility gap is proven by a test.

## 3. Tests to write first (strict TDD)

Test-first ordering: write each failing test, then the smallest green change.

### `tests/unit/service/test_host_setup_providers.py` (new — primary suite)

Inject fakes for subprocess/http (mirror `test_provider_readiness_parts`
`_completed`/`_ollama_ok` style) and fake credential backends (reuse
`tests/unit/service/test_host_setup_credentials_parts/_helpers.py`
`FakeKeyringModule`, `_secret`, `_FAKE_GH_TOKEN`). No real keychain, network, or
`gh`. Cases:

1. **Provider success** — a provider with a captured secret is stored as a ref
   and rechecks `ready`; `ProviderConfig.credential_ref` is a safe `keyring://`
   / `env://` ref; summary status is `ready`.
2. **Missing credential** — no secret/env present → provider `unavailable` /
   `not_configured` with a stable reason; run does not raise; config unchanged
   for that provider.
3. **Invalid credential** — secret present but readiness recheck fails (fake
   `gh`/probe returns non-zero) → `unavailable` + `PROVIDER_SETUP_AUTH_INVALID`;
   no raw token in result/summary.
4. **Mixed-provider partial readiness** — one ready, one missing, one invalid in
   a single all-provider run → each independent; `overall_status` reflects mixed
   without blocking; the ready provider stays ready.
5. **Selected-provider isolation (configure)** — `selected=["codex"]` with other
   providers pre-populated in config: only `codex` is configured/probed; the
   other providers' `ProviderConfig` entries are byte-for-byte unchanged; the
   injected `run_subprocess`/`http_get` are asserted to be called only for the
   selected provider's probe (unselected providers are never probed); summary
   `mode == "targeted_recheck"`.
6. **Selected-provider recheck (no mutation)** — `selected=["github"]` already
   configured: rechecks GitHub only, mutates nothing, labels targeted recheck.
7. **GitHub via `gh`** — fake `gh auth status` returns 0 with no env token →
   GitHub `ready`, no raw token stored, `backend`/`credential_ref` reflect a
   non-secret state (gh-managed, env ref, or none-with-ready).
8. **GitHub via env ref** — `GH_TOKEN`/`GITHUB_TOKEN` set, `gh` absent → GitHub
   marked ready via `env://GH_TOKEN` ref; raw token value never in ref/summary.
9. **AWF Cloud stub** — `awf_cloud` selected → deterministic `not_configured`
   stub result, no subprocess/http calls (assert injected probes untouched).
10. **Bounded probes** — every injected `run_subprocess`/`http_get` receives a
    positive `timeout` kwarg (assert `timeout > 0`), proving probes are bounded.
11. **No raw secret in summary/results** — feed `_FAKE_GH_TOKEN` and token-shaped
    env values; assert the token string appears in **no** field of
    `ProviderSetupSummary.model_dump()` / `to_details()` / any result.
12. **Non-interactive capture-needed** — selected provider needs interactive
    secret under `non_interactive=True` and no env/gh fallback → orchestration
    signals `INTERACTIVE_INPUT_REQUIRED` (so the CLI guard fires), while other
    providers in the same run still resolve independently.

## 5. Risks & mitigations

- **Name-surface drift** (setup vs readiness vocabularies). Mitigation: one
  explicit mapping table in `providers.py`, unit-tested for every
  `KNOWN_SETUP_PROVIDERS` member (each maps to a readiness name or is a declared
  stub/slot); a test asserts no setup provider is silently unmapped.
- **Secret leakage** into refs/summaries/logs/snapshots. Mitigation: results and
  summaries carry only safe ref strings by construction (Pydantic `extra=forbid`,
  no value fields); reuse `provider_readiness` redaction for any probe text; an
  explicit "no token in dump" test (case 11) guards regressions. Persistence
  flows only through `ProviderConfig` (which already rejects secret-shaped refs).
- **Coupling setup_commands more tightly** to orchestration. Mitigation: keep
  the CLI change to a single dispatch call + payload merge + existing
  persistence; orchestration logic and I/O live in `providers.py`, keeping
  `setup_commands` thin and the diff small.
- **Touching the large `provider_readiness.py`** (near coverage thresholds).
  Mitigation: prefer reuse of its public API; add a seam only if proven
  necessary, with its own focused test, and no change to existing callers.
- **Targeted-recheck must not mutate unselected providers.** Mitigation: case 5
  asserts unselected `ProviderConfig` entries are unchanged and their probes are
  never invoked.
- **GitHub readiness without raw-token storage.** Mitigation: GitHub-first-class
  path proves both `gh` and env-ref routes mark ready while asserting the token
  value is absent from every persisted/surfaced field.
- **Coverage gate (99%).** Mitigation: drive each branch from the test list
  above; for any genuinely unreachable defensive branch, add a justified
  `# pragma: no cover` rather than a hollow test.
