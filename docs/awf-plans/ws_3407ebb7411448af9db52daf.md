# Plan: P0 operator console recovery controls

## Objective

Add non-destructive operator controls to the AWF console workspace detail view
for PR remonitoring, drift refresh, and validation recovery. The browser must
call console BFF routes only; the BFF will proxy to the existing AWF recovery
APIs with the server-side `AWF_API_TOKEN`.

Workspace remains the primary operator concept. Merge-candidate and validation
data should only explain when a workspace is eligible for an action.

## Current Code Context

- Console UI is concentrated in
  `apps/console/components/console-dashboard.tsx`.
- Console server-side AWF proxy helpers live in `apps/console/lib/awf-server.ts`.
  The existing catch-all `/api/awf/[...path]` proxy can forward POST requests,
  but it does not add recovery-specific request validation or idempotency
  headers.
- Workspace detail already loads the selected workspace, runtime, events,
  operations, streams, overview, and merge queue snapshot.
- Existing TypeScript API types already include `Workspace`, `WorkspaceOverview`,
  `MergeQueueItem`, `Operation`, validation freshness, stale reasons, and
  recovery summaries.
- Backend recovery APIs already exist:
  - `POST /v1/workspaces/{id}/remonitor`
  - `POST /v1/workspaces/{id}/refresh`
  - `POST /v1/workspaces/{id}/validate`
- Backend routes require API auth and `Idempotency-Key`; `refresh` and
  `validate` also accept `If-Match` and return `OperationResponse` with 202.
  `remonitor` returns `WorkspaceControlResponse`.

## Implementation Approach

1. Add BFF route helper and tests.
   - Define supported actions: `remonitor`, `refresh`, and `revalidate`.
   - Validate route params and JSON body with small explicit checks:
     `reason?: string`, `workspace_version?: number`, `requested_tier?: 1|2|3`,
     and optional non-secret `idempotency_key`.
   - Create `Idempotency-Key` from the browser-provided key when valid or a
     server-generated `crypto.randomUUID()` fallback.
   - Forward `If-Match` from `workspace_version` so backend version conflicts
     remain structured.
   - Never read or forward browser `Authorization`; always use `awfHeaders()`
     from `AWF_API_TOKEN`.
   - Preserve AWF status codes, content type, and structured error bodies.

2. Add explicit BFF route files.
   - Keep route files thin: export `runtime = "nodejs"`,
     `dynamic = "force-dynamic"`, and delegate to the tested helper.
   - Use `/api/operator/workspaces/{id}/...` to keep these routes explicit and
     separate from the broad `/api/awf/[...path]` proxy.

3. Add console control helpers.
   - Compute visible/enabled state from `WorkspaceOverview`, optional
     `Workspace`, optional selected `MergeQueueItem`, and current `Operation[]`.
   - Treat active operation as a global disable for these recovery buttons.
   - Eligibility policy:
     - Remonitor: PR-backed `monitoring_pr` or failed-with-PR workspace.
     - Refresh: merge-candidate or stale context; never for destroying or
       destroyed workspaces.
     - Revalidate: PR-backed `monitoring_pr` workspace with validation recovery
       indicated by `required_next_action === "validate"`,
       `validation_insufficient_tier`, or stale validation freshness.
   - Return compact reasons suitable for a dense panel: examples are
     `active operation`, `no PR`, `not monitorable`, `no merge candidate`,
     `validation fresh`, and `not PR-monitoring`.

4. Wire UI in `ConsoleDashboard`.
   - Add a separate `operatorActionState` rather than overloading existing retry
     state.
   - Place restrained controls in the `WorkspaceSummary` panel action area or
     immediately below the recovery/validation block, preserving the current
     dense grid and mobile wrapping behavior.
   - Use lucide icons already imported or available: `Radio`/`GitPullRequest`
     for remonitor, `RefreshCw` for refresh, and `CheckCircle2` for revalidate.
   - Show disabled buttons only when the action is relevant enough to explain;
     hide irrelevant actions to preserve density.
   - On submit, call the new BFF endpoint with reason, workspace version,
     idempotency key, and requested tier where needed.
   - On success, display operation id/status and refresh selected workspace,
     operations, overview, merge queue, failure summary, workspace summary, and
     resource saturation data.
   - On failure, display the structured code/message in a compact error callout
     and leave the console usable.

5. Update operation/type formatting as needed.
   - Add `WorkspaceControlResponse` to `types.ts`.
   - Add or reuse an `OperationResponse` shape; the existing `Operation` type is
     likely sufficient for refresh/revalidate responses.
   - Add operation labels so the operation panel and success callout avoid raw
     lowercase names where possible.

## Risks

- The existing catch-all AWF proxy still exists and can forward other AWF paths.
  This slice should use explicit operator routes for the new controls, but full
  BFF hardening is outside this task unless requested.
- Component-level DOM testing is not currently set up with jsdom or Testing
  Library. To keep the slice scoped, console behavior should be covered through
  pure helper tests and type checks unless a DOM harness is already added for
  another reason.
- `remonitor` returns a different response shape than `refresh` and
  `validate`; UI success formatting must handle both.
- Backend eligibility is broader for `refresh` than the requested UI surface.
  The console should intentionally restrict refresh visibility to
  merge-candidate or stale contexts while still preserving backend structured
  errors.
- Active operation detection may come from overview, recovery summary, or the
  operations list. Tests should cover all three so the UI does not allow double
  submits.
- If the selected merge queue snapshot is stale between polls, the backend may
  reject an action. The console must show that structured failure and refresh
  data instead of assuming the frontend eligibility check is authoritative.

## Assumptions

- The stable AWF recovery APIs are the source of truth for final authorization,
  idempotency, and state validation.
- `AWF_API_TOKEN` must remain server-only; browser requests may carry
  non-secret idempotency keys and workspace versions.
- The selected workspace detail response includes enough version information to
  send `If-Match`.
- Revalidate should be labeled as an operator action in the console but should
  proxy to AWF's existing `validate` operation.
- Existing dense panel styles, button sizing, and responsive flex/grid patterns
  in `console-dashboard.tsx` should be reused rather than introducing a new
  layout system.

## Explicit Non-Goals

- No destructive controls such as cancel, stop, delete, destroy, or force merge.
- No backend API redesign, database migrations, or changes to recovery service
  semantics.
- No broad hardening or removal of the existing catch-all `/api/awf/[...path]`
  proxy in this slice.
- No role-based authorization, audit UI, or operator confirmation modals beyond
  the existing backend operation audit payloads.
- No rebase button in this slice, even though backend rebase recovery exists.
- No lowering of lint, typecheck, test, coverage, or quality thresholds.
