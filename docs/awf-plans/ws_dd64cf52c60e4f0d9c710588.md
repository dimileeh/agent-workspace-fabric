# Plan — Issue #411: pre-push fix-pass ALWAYS re-parents (stop discriminating)

Workspace: `ws_dd64cf52c60e4f0d9c710588`

## Problem & locked design

The PR-monitor pre-push validation **fix pass** lets a fix-agent self-commit a repair. When
the agent rewrites the tip (`git commit --amend`) the new HEAD is **not** a descendant of the
pre-fix commit (`fix_start_head`). Today the code tries to discriminate a legit content-modifying
amend from a work-dropping `reset --hard HEAD~1` + recommit via a `git merge-tree` tree-content
check (`_head_preserves_fix_tree`). Those two operations can produce byte-identical trees, so the
discriminator mis-classifies valid amends as work-dropping, rolls them back, orphans the fix, and
the fix pass never converges (the #406-class over-rollback).

**Locked design (owner-approved): STOP DISCRIMINATING — ALWAYS RE-PARENT.** For a non-descendant
HEAD, reconstruct whatever the agent produced as a single commit
`git commit-tree <resulting-tree> -p fix_start_head` and `reset --hard` the ref to it. One rule
covers every case (advance / plain amend / content-modifying amend / reset+recommit):

- `fix_start_head` can never be orphaned — it is the new commit's parent (this also rescues it
  from danglinghood after an amend).
- The agent's fix (the resulting tree) is always kept → the pass converges.
- Any dropped work is visible as `git diff fix_start_head..HEAD` and is **re-validated before
  push** by the existing `_run_pre_push_validation_with_fix_passes` loop (it re-runs validation on
  the new HEAD). No change needed in that loop's re-validation behavior — confirmed by reading the
  loop: after a committed fix pass it `continue`s and calls `_run_pre_push_validation` again.

**Behavior change to document in the PR:** a work-dropping reset+recommit is **no longer rolled
back**; it is preserved as an auditable child of `fix_start_head` and caught by re-validation +
full PR review. This is the intended tradeoff — the over-rollback was the worse failure.

**Add `_reparent_fix_pass_commit`** — pure git plumbing, no DB, catches nothing broad (relies on
`runner.run` returning a result object with `.ok`/`.stdout`/`.stderr`/`.returncode`):

```python
async def _reparent_fix_pass_commit(
    self: Any,
    *,
    workspace_id: str,
    worktree_path: Path,
    fix_start_head: str,
    current_head: str,
    pass_number: int,
) -> tuple[str | None, bool, str | None]:
    """Re-parent the fix agent's resulting tree onto ``fix_start_head``.

    Returns ``(new_head, no_net_change, failure_reason)``:
      - ``(new_sha, False, None)``  -> reconstructed commit; accept against new_sha.
      - ``(None, True, None)``      -> agent produced no net change; signal no-commit.
      - ``(None, False, REPARENT)`` -> infra failure (rev-parse/commit-tree/reset).
    """
```
Steps (each via `git_worktree_command(worktree_path, ...)` through `self._deps.runner.run`):
1. `rev-parse current_head^{tree}` → `current_tree`; on `not ok` or blank → warn
   (`git_step="rev-parse current tree"`, truncated stderr) and return
   `(None, False, REPARENT_FAILED)`.
2. `rev-parse fix_start_head^{tree}` → `start_tree`; same guard.
3. **No-net-change guard:** if `current_tree == start_tree` → return `(None, True, None)`
   (agent produced no net change; caller falls through to the existing rollback).
4. Message derivation: `git log -1 --format=%B current_head`; if `ok` and `.stdout.strip()`,
   use the stripped body; else fall back to `f"awf: pre-push validation fix for {workspace_id}"`.
5. `*git_identity_config_args()` + `commit-tree current_tree -p fix_start_head -m <msg>`
   (identity `-c` args passed as leading `*args` to `git_worktree_command`, which is valid — git
   accepts interleaved global `-C`/`-c` before the subcommand). On `not ok` or blank stdout → warn
   and return `(None, False, REPARENT_FAILED)`. New SHA = `stdout.strip()`.
6. `reset --hard <new_sha>` (moves the ref only; the worktree already equals current's tree). On
   `not ok` → warn and return `(None, False, REPARENT_FAILED)`.
7. Return `(new_sha, False, None)`.

Warnings use `monitor.pre_push_validation_fix_reparent_failed` with `workspace_id`, `pass_number`,
`git_step`, and `stderr=(result.stderr or "")[:400]` (never log secrets; only git stderr,
truncated).

## Risks & mitigations
- **git `-c` placement:** identity `-c` args are passed as leading `*args` to
  `git_worktree_command`, producing `git -c safe.directory=… -C <path> -c user.name=… -c
  user.email=… commit-tree …`. Git accepts multiple interleaved global options before the
  subcommand. A focused commit-tree test asserts the exact arg vector.
- **Multi-line commit message via `-m`:** `git log -1 --format=%B` may yield a multi-line body;
  `commit-tree -m <body>` handles it as a single `-m`. Acceptable; matches design.
- **Re-validation reliance:** the loop already re-runs `_run_pre_push_validation` on the new HEAD
  after a committed fix pass (verified by reading `_run_pre_push_validation_with_fix_passes`); the
  loop-level test (#3) guards this so a dropped-work reparent is caught before push.
- **Maintainability line cap:** new tests go to part_003 to keep every `_parts` file < 1500 lines;
  `test_core_decomposition_maintainability.py` is in the focused test run.
- **Reason-code propagation:** `PRE_PUSH_VALIDATION_REPARENT_FAILED` flows constant → re-export →
  fix-pass return → loop label/`reason_code` → `_PrePushValidationResult.reason_code` →
  `_GitPushResult.reason_code`/`details`, matching the existing end-to-end pattern. No swallowed
  reason codes; warnings carry `git_step` + truncated stderr.
