# Plan: public refresh and validate workspace operations

## Objective

Add authenticated, idempotent operator API endpoints for workspace refresh and validate requests:

- `POST /v1/workspaces/{workspace_id}/refresh`
- `POST /v1/workspaces/{workspace_id}/validate`

Use `validate` rather than `revalidate` because the PRD and current `OperationType` vocabulary already use `validate`. The endpoints should create or return an active operation record for the same workspace/action/reason, preserve structured payload reason/source data for later console display, and avoid launching a full coding agent for validate-only recovery.

## Intended Files And Modules To Touch

- `src/awf/api/routes/controls.py`
  - Add `refresh_workspace` and `validate_workspace` route handlers under the existing sensitive workspace-control router.
  - Keep `require_api_token`, `Idempotency-Key`, and `If-Match` behavior aligned with existing cancel/stop/remonitor/destroy endpoints.
  - Return `OperationResponse` with HTTP `202 Accepted` for newly requested or replayed active operations.
  - Extend `_http_error` mapping for refresh/validate policy errors.

- `src/awf/api/schemas.py`
  - Add a narrow request schema for recovery operations, likely `WorkspaceOperationRequest`, with `reason` and optional `requested_tier`.
  - Reuse existing `OperationResponse`; do not add response URL fields unless the existing operation schema already supports them cleanly.

- `src/awf/service/controls.py`
  - Add `request_refresh_workspace` and `request_validate_workspace`.
  - Add policy error classes such as `WorkspaceRefreshStateError` and `WorkspaceValidateStateError`.
  - Add active-operation coalescing by workspace, operation type, source, reason, and request parameters so duplicate calls return the same pending/running operation even if the caller uses a fresh idempotency key.
  - Preserve strict idempotency-key conflict detection when the same key is replayed with a different action payload.
  - Emit request events with reason codes such as `OPERATOR_REFRESH` and `OPERATOR_VALIDATE`.
  - For validate-only on `monitoring_pr`, create a pending `validate` operation with payload `source="operator_api"` and `recovery_mode="validate_only"`, then transition `monitoring_pr -> ready` with a dedicated reason code so the worker can resume validation without a full agent run.
  - Reject `destroying` with 409 and `destroyed` with 404 or 409 using an actionable structured error. Reject `completed` validate with a clear policy error unless the current state model supports a safe re-entry path.

- `src/awf/db/repositories.py`
  - Add an `OperationRepository` helper for finding active matching operations (`pending` or `running`) by workspace/type and payload identity.
  - Add small helpers for marking pending operations running only if needed by the worker-side refresh implementation.

- `src/awf/control/executor.py`
  - Generalize the current PR-monitor recovery discriminator so validate-only operations from `source="operator_api"` also skip planning, full agent execution, post-agent commits, and PR creation.
  - Keep existing `source="pr_monitor"` behavior unchanged.
  - Ensure operator validate-only operations are started and finished through the existing pending validate operation finalization path.

- `src/awf/control/worker.py` and `src/awf/service/worker.py`
  - Touch only if refresh operations need a worker-side processor in this slice.
  - The minimal refresh path should request recomputation by enqueuing a `refresh` operation and never dispatch the coding executor.
  - If implemented now, process pending `refresh` operations by recomputing inspectable runtime/merge/staleness state through existing services and finishing the operation with a structured result.

- `src/awf/service/staleness.py`, `src/awf/service/scope_policy.py`, or `src/awf/service/target_branch_monitor.py`
  - Touch only to expose a small reusable workspace-refresh helper if the operation processor needs one. Avoid changing stale-policy semantics.

- Tests:
  - `tests/unit/api/test_workspace_controls_idempotency.py` or a new `tests/unit/api/test_workspace_recovery_operations.py`
  - `tests/unit/service/test_controls_lifecycle.py`

## Tests To Write First

1. API auth and request validation
   - Missing or invalid `Authorization` on `/refresh` and `/validate` is rejected like other sensitive controls.
   - Missing `Idempotency-Key` is rejected if the endpoint follows the current sensitive-control contract.
   - Malformed `If-Match` returns the existing structured 400 error.

2. Missing and invalid workspace states
   - Missing workspace returns 404 `NOT_FOUND`.
   - `destroying` returns 409 with an error code such as `WORKSPACE_STATE_NOT_REFRESHABLE` or `WORKSPACE_STATE_NOT_VALIDATABLE`.
   - `destroyed` returns an actionable 404/409 policy response and does not create an operation.
   - `completed` validate returns a clear policy error unless implementation proves a safe state-machine path exists.

3. Refresh operation creation and idempotency
   - A refresh request for an eligible workspace creates one pending `refresh` operation.
   - The response is an `OperationResponse` containing id, workspace_id, type, status, payload, and timestamps.
   - A duplicate request with the same workspace/action/reason while the first operation is pending/running returns the same operation id.
   - The payload preserves `source="operator_api"`, the operator `reason`, and a reason code for console display.
   - No workspace execution state is changed in a way that could launch the coding agent.

4. Validate operation creation and idempotency
   - A validate request for a `monitoring_pr` workspace with a PR URL creates one pending `validate` operation and transitions the workspace to `ready` for validate-only recovery.
   - A duplicate validate request with the same workspace/action/reason returns the same active operation id without duplicate rows.
   - Same idempotency key with a different reason/requested tier returns `IDEMPOTENCY_CONFLICT`.
   - Payload preserves `source="operator_api"`, `reason`, `recovery_mode="validate_only"`, and requested tier if provided.

5. Validate-only execution does not launch a full agent
   - Extend existing executor recovery tests so an active operator validate operation skips planning, the full agent adapter run, post-agent commit, and PR creation.
   - Verify existing PR-monitor recovery tests still pass unchanged for `source="pr_monitor"`.

6. Existing behavior preservation
   - Existing cancel, stop, remonitor, and destroy idempotency tests remain unchanged.
   - Operation listing endpoints include the new operation rows through the existing list/get APIs.

## Implementation Steps

1. Add failing API and service tests for refresh/validate operation creation, duplicate active-operation replay, missing workspace, invalid terminal states, payload reason/source preservation, and auth.

2. Add repository support for active operation lookup.
   - Match only `pending` and `running`.
   - Use operation type plus stable payload identity fields, not the entire result or timestamps.
   - Keep PostgreSQL portability; filtering a bounded set in Python is acceptable if JSON querying would complicate portability.

3. Add service-layer request methods.
   - Reuse `_prepare_operation` patterns for idempotency locks and `If-Match`.
   - Check idempotency-key replay conflicts before active-operation coalescing.
   - Check workspace state policy before creating new operation rows.
   - Create request events with stable reason codes.
   - For validate-only, perform only the minimal state transition needed for the existing worker/executor path.

4. Add API routes.
   - Wire the new schema, `Idempotency-Key`, `If-Match`, auth, structured error mapping, and `OperationResponse`.
   - Keep status code `202` for accepted operation requests.

5. Generalize executor validate-only recovery.
   - Accept operator validate operations as validate-only recovery operations.
   - Keep PR-monitor-specific logging/event names where they are truly monitor-specific, but avoid requiring `source="pr_monitor"` for operation lifecycle finalization.
   - Prove with tests that no full agent path is entered.

6. Implement refresh execution only to the extent supported by current services.
   - If a lightweight, worker-safe recompute path can be wired without broad refactor, process pending refresh operations and finish them with structured runtime/merge/staleness summaries.
   - If the existing service model is not ready for refresh execution, leave refresh as a pending request operation with clear payload/action semantics and document the follow-up in code comments/tests without pretending it completed.

7. Run focused and broad validation, then fix only regressions caused by this slice.

## Risks

- The current executor only recognizes PR-monitor recovery by `payload.source == "pr_monitor"`. Generalizing that check must not accidentally classify ordinary validate operations as validate-only recovery.
- `completed` workspaces cannot currently transition back to `ready`; accepting completed validate without changing the state model would create stuck or misleading operations.
- Refresh semantics span runtime inspection, merge candidate readiness, stale reasons, and policy findings. A narrow API slice must avoid marking refresh operations succeeded unless those recomputations actually ran.
- Active-operation coalescing can conflict with strict idempotency-key semantics. The service should first reject same-key/different-payload replays, then coalesce equivalent active operations.
- Operator-triggered validate transitions `monitoring_pr -> ready`; stale monitor or executor callbacks must not move destroyed/cancelled workspaces forward. Existing state rechecks should be preserved and extended where needed.

## Assumptions

- These endpoints are sensitive operator controls and should use the existing bearer-token dependency.
- `OperationType.refresh` and `OperationType.validate` already exist, so no enum migration is required.
- Operation payload JSON is the right place for this slice's reason/source fields.
- `OperationResponse` is sufficient for the API response; clients can poll `GET /v1/operations/{operation_id}`.
- `monitoring_pr` is the first safe validate target because the state machine already allows `monitoring_pr -> ready`, and the executor has a validate-only recovery path to return to monitoring.

## Explicit Non-goals

- Do not implement `/v1/workspaces/{workspace_id}/rebase` in this slice.
- Do not add console controls, CLI commands, or MCP tools unless implementation proves REST cannot be tested otherwise.
- Do not change cancel, stop, remonitor, or destroy behavior except for shared helper extraction with preserved tests.
- Do not lower coverage thresholds, `.awf/workspace.yml` gates, `pyproject.toml` `fail_under`, or quality checks.
- Do not add migrations unless implementation discovers a real schema requirement.
- Do not launch a full coding agent for refresh or operator validate-only operations.
- Do not manually push, rebase, switch branches, or commit as part of this planning phase.
