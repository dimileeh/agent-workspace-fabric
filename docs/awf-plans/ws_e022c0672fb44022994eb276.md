# Provider Credential Readiness Security Slice Plan

## Starting Point

AWF already has a local readiness surface in `src/awf/service/provider_readiness.py`
and threads its payload through `awf service status` and `/readyz` as
`agent_readiness`. The current provider set is GitHub, Claude Code, Gemini, and
OpenCode/Ollama. Auth mount isolation for service-created workspaces already
lives in `src/awf/node/auth_mounts.py`: Codex, Claude, Gemini, OpenCode, and
Ollama file auth are copied into per-workspace auth directories, while selected
base Git/GitHub/SSH/GCloud paths are mounted read-only.

This slice should extend that existing shape instead of introducing a new
secret broker or changing workspace admission policy. Missing optional
providers and observable least-privilege downgrades should remain warnings by
default in local mode; explicit strict provider selection should continue to
turn unusable or missing provider readiness into a failure.

## Intended Files and Modules to Touch

Primary implementation files:

1. `src/awf/service/provider_readiness.py`
   - Add `codex` and `docker` to `ProviderName`, `PROVIDER_NAMES`, validation,
     and readiness collection.
   - Add provider-specific credential source classification without reading file
     contents:
     - declared or service-managed per-workspace copy candidates;
     - read-only host path signals;
     - static environment token fallbacks;
     - broad Docker host/socket or Docker registry auth signals where observable.
   - Add stable structured fields to each provider result, preserving existing
     reason codes where practical:
     - `credential_sources`: list of redacted source descriptors;
     - `credential_scope`: `isolated_workspace`, `read_only_host_path`,
       `static_env_token`, `docker_host_control`, `not_observed`, etc.;
     - `isolation`: `per_workspace_copy`, `read_only_bind`, `service_env`,
       `host_daemon`, or `none`;
     - `warnings`: list of `{reason, message, severity}` entries for
       least-privilege downgrades such as `STATIC_TOKEN_FALLBACK` or
       `DOCKER_HOST_BROAD_CONTROL`;
     - top-level `security` summary with warning counts and provider reason
       codes.
   - Ensure redaction covers new static token env keys, including Codex/OpenAI
     env fallbacks and Docker auth env fallbacks.

2. `src/awf/profiles/compose.py`
   - If Codex env auth is classified as a supported fallback, add the same
     env names to `AGENT_AUTH_ENV_VARS` so readiness does not report an auth path
     that the workspace launcher drops.
   - Keep values as Compose placeholders only, never raw env values.

3. `scripts/run_awf.py`
   - Mirror any Codex env passthrough additions made in
     `src/awf/profiles/compose.py`, because this script still has its own
     local driver helpers.

4. `src/awf/api/routes/health.py`
   - Accept the expanded provider set through existing validation.
   - Keep `/readyz` response backward-compatible while allowing the richer
     `agent_readiness.security` and per-provider fields to pass through.
   - Update tests if the expected provider set or readyz response shape changes.

5. `src/awf/service/status.py`
   - Prefer no behavior change if the enriched `agent_readiness` payload passes
     through cleanly.
   - Touch only if service status needs a small compatibility shim for the new
     `security` summary or provider set.

6. `src/awf/cli/main.py`
   - Update operator help text for `awf service status --provider` and
     `awf service bootstrap --provider` to include `codex` and `docker`.

7. Documentation only if implementation changes operator-visible behavior:
   - `README.md` local service readiness section, with no secret examples beyond
     variable names and no expanded setup flow.

## Implementation Sequence

1. Extend provider validation and collection with `codex` and `docker`.
2. Introduce small internal helpers in `provider_readiness.py` for source
   descriptors and warning descriptors. Keep them data-only and deterministic.
3. Add Codex checks:
   - prefer `~/.codex` file auth as an isolated per-workspace-copy source;
   - treat static env auth as usable but warned;
   - missing auth remains warn by default and fail only when strict.
4. Enrich existing GitHub, Claude, Gemini, and OpenCode/Ollama checks with the
   same source/warning metadata while preserving existing reason codes where
   possible.
5. Add Docker provider diagnostics:
   - classify configured Docker host/socket as a broad-control local resource
     warning;
   - classify Docker registry auth env/path presence by signal only;
   - rely on existing Docker CLI/daemon/image `/readyz` checks for actual
     resource readiness.
6. Add the top-level `security` summary to the readiness payload.
7. Add Codex env placeholders to workspace launch environment helpers only if
   the readiness implementation recognizes those env fallbacks.
8. Update CLI help text and any response-shape expectations.
9. Update README only after tests pass, if the new operator-visible contract
   needs documentation.

## Risks

- Existing tests and downstream users may rely on current provider reason
  strings. Mitigation: add new source/warning fields and preserve current reason
  codes for existing success/failure cases unless a new classification requires
  a new code.
- Docker is both a resource dependency and a credential/security boundary.
  Mitigation: keep daemon/image health under existing `checks.docker_*` and use
  the Docker provider entry only for credential/security-surface diagnostics.
- Adding Codex env fallback diagnostics without launcher passthrough would be a
  false positive. Mitigation: update `AGENT_AUTH_ENV_VARS` and the legacy script
  helper in the same slice or do not classify that env path as usable.
- Static env token warnings could be misread as hard failures. Mitigation:
  represent them as warning descriptors while keeping provider `status` `ok`
  when the provider is otherwise usable.
- File existence checks can accidentally broaden into secret reads. Mitigation:
  use `exists()`, `is_file()`, or `is_dir()` only and assert secret contents never
  appear in serialized payloads.

## Assumptions

- Local service mode remains the compatibility target for this slice.
- The existing `ServiceAuthMountResolver` behavior is the source of truth for
  which file credentials are isolated into per-workspace auth directories.
- Environment variable names are safe to report; environment values are not.
- Path labels such as `~/.codex` or `~/.docker/config.json` are acceptable
  operator diagnostics, but absolute paths should be used sparingly and never
  paired with file contents.
- Strict provider selection is an operator opt-in readiness gate; default local
  status and readyz should not block on optional providers or on least-privilege
  downgrade warnings.

## Explicit Non-Goals

- Do not implement a cloud secret broker, lease issuer, token minting service,
  or database schema for `secret_lease`.
- Do not change workspace admission, scheduling, merge policy, or PR monitor
  behavior based on these warnings.
- Do not read, parse, log, or hash secret file contents.
- Do not mount the whole host home directory or add new broad credential mounts.
- Do not make local development fail solely because a static env token fallback
  or Docker host socket is being used.
- Do not add a frontend/dashboard change in this slice unless a later explicit
  task asks for it.
