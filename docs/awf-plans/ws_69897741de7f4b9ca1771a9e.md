# Issue #335 Plan: Companion Image Launch Revalidation

## Problem Statement

GitHub issue #335 reports a race in `src/awf/node/stack_launcher.py`: `CompanionImageBuilder.ensure()` can return a cache-hit companion image tag, then `awf service gc --execute` can prune that old tag before `docker compose up` starts the stack. The rendered companion then has only `image:` plus `pull_policy: never`, so compose fails instead of rebuilding.

The required approach is a point-of-use defense in the launch/render path. Do not change GC behavior. Immediately before the stack starts, revalidate pre-built companion image tags and fall back to inline `build:` rendering for any tag that disappeared.

## Intended Files / Modules To Touch

- `src/awf/node/companion_images.py`
  - Add a small image-existence helper on `CompanionImageBuilder`, likely `companion_image_exists(tag: str) -> bool`, delegating to `ComposeManager.companion_image_exists`.
  - Catch Docker probe `ComposeOperationError` distinctly from a confirmed missing image and preserve/log the reason code.
  - Keep `ensure()` cache-hit semantics otherwise unchanged.

- `src/awf/node/stack_launcher.py`
  - After `WorkspaceComposeSpec` is assembled and before `self._compose.up(spec, wait=True)`, revalidate companions whose rendered service has an `image` and a configured companion image builder.
  - If a tag still exists, leave that `CompanionService` unchanged so `ComposeManager` continues rendering `image:` plus `pull_policy: never`.
  - If a tag is confirmed absent, replace that one companion service with `image=None` so the existing renderer emits the inline `build:` stanza.
  - If the probe errors for a reason other than confirmed absence, propagate a specific failure rather than treating it as missing.

- `tests/unit/node/test_companion_images.py`
  - Add helper tests for the new existence probe success and not-found branches.
  - Add a probe-error test if the helper catches/logs/re-raises `ComposeOperationError` explicitly.

- `tests/unit/node/test_stack_launcher_companion_images.py` or `tests/unit/node/test_stack_launcher_parts/*`
  - Add launch-path regression coverage for the race: `ensure()` returns a tag, launch-time revalidation reports absent, and the `WorkspaceComposeSpec` handed to compose has that companion rendered for inline build (`image is None`).
  - Add/keep normal cache-hit coverage where launch-time revalidation reports present and the companion still carries the image tag.
  - Preserve existing `tests/unit/node/test_compose_manager.py::TestComposeManager::test_companion_prebuilt_image_pins_pull_policy_never` behavior unchanged.

- `plans/ISSUE_335_PLAN.md`
  - During implementation phase, create the mandatory repository plan from this planning artifact before coding, per `plans/PLAN_EXECUTION_PROTOCOL.md` and the task instructions.

- `plans/ISSUE_335_VALIDATION.md`
  - During validation phase, record requirement-by-requirement status and focused evidence.

1. `test_launch_revalidates_prebuilt_companion_image_and_falls_back_to_build_when_missing`
   - Use a recording compose fake whose `up()` captures the `WorkspaceComposeSpec`.
   - Use a fake builder where `ensure()` returns a deterministic tag but launch-time `companion_image_exists(tag)` returns `False`.
   - Assert `compose.up()` is still called, the captured companion has `image is None`, and existing build context/dockerfile data is preserved so compose can build inline.

2. `test_launch_keeps_prebuilt_companion_image_when_revalidation_succeeds`
   - Same setup, but launch-time existence returns `True`.
   - Assert the captured companion still has the prebuilt image tag. The renderer test for `pull_policy: never` remains the source of truth for the emitted YAML.

3. `test_companion_image_exists_returns_true_when_tag_present`
   - Exercise the new builder/helper against the existing fake compose with `exists=True`.

4. `test_companion_image_exists_returns_false_when_tag_missing`
   - Exercise the helper with `exists=False`.

5. `test_companion_image_exists_preserves_probe_error_reason_code` if the helper wraps/logs probe errors
   - Make fake compose raise `ComposeOperationError(reason_code="DOCKER_UNAVAILABLE")` from `companion_image_exists`.
   - Assert the same exception/reason is not converted into a missing-image fallback.

## Implementation Steps

1. Create `plans/ISSUE_335_PLAN.md` from this artifact as the first implementation-phase file change.
2. Write the focused failing regression tests listed above.
3. Add the `CompanionImageBuilder` image-existence helper in `companion_images.py`.
4. Add a small revalidation helper in `stack_launcher.py`, likely private to `ComposeStackLauncher`, that:
   - no-ops when no companion image builder is configured;
   - iterates rendered `CompanionService` entries;
   - skips services without `image`;
   - checks the tag at point of use;
   - replaces only confirmed-missing images with `replace(service, image=None)`.
5. Call that revalidation helper after `WorkspaceComposeSpec` is built and before `self._compose.up(spec, wait=True)`. If any companion changed, replace the frozen spec with an updated `companions` tuple.
6. Keep `ComposeManager` rendering unchanged. Do not add a permanent `build:` stanza alongside `image:` for normal prebuilt companions.
7. Update docstrings/comments only where needed to explain the launch-time race defense.
8. Create `plans/ISSUE_335_VALIDATION.md` after implementation with evidence and any gaps.

## Risks And Mitigations

- Risk: treating Docker probe errors as image absence could hide daemon or permission failures. Mitigation: only fall back on a clean `False` from the existence helper; let `ComposeOperationError` propagate with its reason code.
- Risk: revalidating too early would leave the same prune window. Mitigation: call revalidation after spec construction and immediately before `compose.up()`.
- Risk: changing normal cache-hit rendering could break `pull_policy: never`. Mitigation: do not alter `ComposeManager`; only clear `image` when the tag is confirmed absent.
- Risk: concurrent companion pre-build behavior could regress. Mitigation: leave `_build_companion_services()` concurrency intact and add only a later serial/async revalidation pass over the already-rendered services.
- Risk: file-size maintainability guard. Mitigation: add concise tests to existing focused companion-image test modules; if a guard flags a test file size issue, split along existing `test_stack_launcher_parts` patterns instead of disabling the guard.

## Assumptions

- `ComposeManager.companion_image_exists(tag)` is the canonical host-daemon probe and already distinguishes missing tags by returning `False`.
- Setting `CompanionService.image` back to `None` is sufficient for `ComposeManager` to render the existing inline `build:` fallback with no `pull_policy: never`.
- The companion service still has the original `build_context` and `dockerfile` after pre-build tagging, so no additional metadata is needed for fallback.
- The launch path can afford one final existence probe per prebuilt companion immediately before `compose.up()`.

## Explicit Non-Goals

- Do not modify GC or make it workspace-aware.
- Do not change companion image retention policy.
- Do not add `build:` alongside `image:` for normal prebuilt companions.
- Do not retry `compose.up()` after failure as the primary fix.
- Do not switch branches, push, rebase, stage, commit, or run broad validation during the agent phase.
- Do not hard-code project-specific companion behavior into AWF core.
