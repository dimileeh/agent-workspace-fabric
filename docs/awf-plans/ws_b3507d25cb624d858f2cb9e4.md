# P0 Cleanup Reliability Slice Plan

## Goal

Make workspace cleanup retry-safe and observable when Docker cleanup only
partially succeeds. Cleanup must keep durable workspace logs and artifacts while
removing only runtime pressure paths after the configured retention window.

## Intended Files and Modules

Planning phase touch:

- `docs/awf-plans/ws_b3507d25cb624d858f2cb9e4.md` only.

Tests to write or update first:

- `tests/unit/service/test_gc.py`
  - Retention-based filesystem cleanup behavior.
  - Compose teardown partial failure behavior for `run_terminal_workspace_gc`
    and `run_workspace_filesystem_gc`.
  - Idempotent reruns after paths have already been removed.
- `tests/unit/service/test_controls.py`
  - Explicit destroy cleanup behavior through `WorkspaceControlService`.
  - Operation result and workspace event payloads for cleanup success, partial
    cleanup, and retry.

Likely production files:

- `src/awf/service/gc.py`
  - Keep pressure-directory cleanup idempotent.
  - Ensure compose teardown failures produce structured partial results and
    skipped path outcomes.
  - Preserve the current dictionary shape while adding result detail only in
    existing result fields.
- `src/awf/node/cleanup.py`
  - Represent cleanup step outcomes with reason codes and error details while
    continuing later cleanup steps after a compose failure.
  - Preserve compatibility for callers by normalizing legacy list-style failure
    results if needed.
- `src/awf/service/controls.py`
  - Record cleanup details in `Operation.result` and workspace events during
    destroy.
  - Keep `WorkspaceControlResponse` unchanged.
- `src/awf/node/compose_manager.py`
  - Touch only if tests show compose down failure details are not specific
    enough for actionable cleanup results.

No migrations, public API schema changes, lockfile changes, or broad cleanup
refactors are planned.

## TDD Sequence

1. Add failing GC tests in `tests/unit/service/test_gc.py`.
   - Compose teardown returns a failed result on the first cleanup run. Assert
     the GC result is `partial`, includes the compose teardown reason code and
     error, marks pressure paths as `skipped`, and leaves worktree, compose, and
     auth directories in place.
   - Retry with compose teardown succeeding. Assert runtime pressure paths are
     deleted and status is `succeeded`.
   - Run cleanup a third time for the same workspace. Assert it succeeds with
     no deleted paths, no errors, and per-path `already_removed` outcomes.
   - Add a single-workspace variant through `run_workspace_filesystem_gc` so the
     PR-monitor cleanup path gets the same guarantees.
   - Add or strengthen assertions that files under `<work_dir>/logs` and
     `<work_dir>/artifacts` survive execution, while `<work_dir>/git/worktrees`,
     `<work_dir>/compose`, and `<work_dir>/auth` are removed only when retention
     policy allows cleanup.

2. Add failing destroy-control tests in `tests/unit/service/test_controls.py`.
   - Use a recording cleaner that first returns a structured partial cleanup
     result for compose down failure and one successful later step. Assert the
     destroy operation fails with `cleanup_failure`, and `Operation.result`
     contains actionable cleanup details such as status, failed step, reason
     code, error message, and completed steps.
   - Assert a workspace event is recorded with the same cleanup detail in its
     existing payload structure.
   - Retry cleanup for the same workspace with the cleaner succeeding. Assert
     the workspace reaches `destroyed`, a new destroy operation succeeds, and
     the operation result records cleanup success.
   - Assert destroying an already-clean or already-destroyed workspace remains
     safe and observable without invoking destructive work unnecessarily.

3. Confirm each new test fails for the expected missing detail or behavior
   before production edits.

4. Implement the smallest production changes.
   - In `src/awf/service/gc.py`, ensure the result model consistently includes
     compose teardown details, delete errors, skipped path outcomes, and
     `already_removed` outcomes. Treat missing paths as success, not failure.
   - In `src/awf/node/cleanup.py`, introduce structured cleanup step/result
     helpers if needed. Compose failure should not prevent worktree cleanup, and
     every failure should carry a stable reason code.
   - In `src/awf/service/controls.py`, normalize cleanup results into
     `Operation.result["cleanup"]` and event payload cleanup detail while keeping
     `WorkspaceControlResponse` fields unchanged.
   - Preserve legacy fake cleaners that still return `list[str]` by translating
     those entries into failed cleanup step details.

5. Re-run the narrow tests. If any existing tests assert exact operation result
   dictionaries, update only those assertions to include the newly required
   cleanup detail, because this task explicitly asks to surface cleanup details
   through operation/event structures.

## Risks and Mitigations

- Exact `Operation.result` assertions already exist. Keep new cleanup detail
  nested under a stable key such as `cleanup` so existing top-level status and
  error fields remain compatible.
- Changing `WorkspaceCleaner.cleanup` from `list[str]` to a structured object
  could ripple through tests and fakes. Add a normalization helper that accepts
  both structured results and legacy failure lists.
- Retention cleanup must never delete durable logs or artifacts. Tests should
  create real files under `logs` and `artifacts` and assert they remain after
  cleanup.
- Compose teardown failures can mask path cleanup if deletion is skipped. The
  result should make that explicit with skipped path outcomes and the compose
  reason code.
- Idempotent reruns can look like no-ops. Record `already_removed` path outcomes
  so operators can distinguish safe replay from unobserved work.

## Assumptions

- Runtime pressure paths are limited to worktrees, compose project directories,
  and auth directories under the service `work_dir`.
- Durable logs and artifacts live under `<work_dir>/logs` and
  `<work_dir>/artifacts` and are outside GC targets.
- Existing operation and event JSON payloads are acceptable places to add
  cleanup result detail without changing the public `WorkspaceControlResponse`
  model.
- Cleanup retry is modeled by a later cleanup operation over the same
  workspace, not by mutating a completed operation in place.
- Compose `down` failure is the main Docker partial-failure case for destroy and
  retention GC; direct `docker stop` behavior remains covered by existing stop
  command tests unless new failures reveal a gap.

## Non-Goals

- Do not add a new cleanup API endpoint.
- Do not change branch, push, PR, or merge behavior.
- Do not change retention defaults or workspace coverage thresholds.
- Do not delete database rows, workspace events, durable log streams, logs, or
  artifacts.
- Do not introduce asynchronous background cleanup scheduling in this slice.
- Do not broaden cleanup to orphan Docker resources beyond the workspace paths
  already modeled by service GC.
