# Issue 311 Plan: Add Official xAI Grok Build Runtime

## Scope

Add xAI's official Grok Build CLI as a new AWF `AgentRuntime` named `grok`, mirroring the existing `gemini` and `opencode` adapter wiring without changing existing adapter behavior. The integration must target the official xAI Grok Build docs and installer, not the unrelated community `superagent-ai/grok-cli` package.

Authoritative docs to cite in code comments/docstrings where relevant:

- `https://docs.x.ai/build/cli/headless-scripting` for `grok -p`, `--always-approve`, `--no-alt-screen`, `--no-auto-update`, `-m/--model`, and `--output-format`.
- `https://docs.x.ai/build/enterprise` for `XAI_API_KEY` headless authentication and installer/network notes.
- `https://docs.x.ai/developers/models/grok-build-0.1` and `https://docs.x.ai/developers/models` for the default coding model choice. The current documented coding model is `grok-build-0.1`, with aliases including `grok-code-fast-1` and `grok-code-fast`; the plan is to use `grok-build-0.1` unless implementation discovers the CLI requires an alias form.

The current planning phase is constrained to this artifact only. During implementation, if the standard repository Plan-and-Validate workflow is still required, create/update `plans/ISSUE_311_PLAN.md` before source edits and `plans/ISSUE_311_VALIDATION.md` after implementation.

## Intended Files and Modules to Touch

Core runtime registration:

- `src/awf/db/enums.py`: add `AgentRuntime.grok = "grok"` with a docstring describing official xAI Grok Build headless mode.
- `src/awf/adapters/grok.py`: new `GrokAdapter(AgentAdapter)` registered with `@register_adapter`.
- `src/awf/adapters/registry.py`: import `grok` alongside `codex`, `claude_code`, `gemini`, and `opencode`.
- `src/awf/adapters/defaults.py`: add `AgentRuntime.grok: AgentDefaults(model="grok-build-0.1", effort="xhigh")` with a comment citing the xAI model docs.
- `src/awf/adapters/base.py`: update registry-population comments only if needed.

Adapter contract:

- `src/awf/adapters/grok.py` should build a non-interactive argv equivalent to `grok -p <prompt> --always-approve --no-alt-screen --no-auto-update -m <model> --output-format plain`.
- Follow AWF runner conventions from existing adapters: inspect whether prompt should be delivered through stdin or argv to avoid leaking large prompts into process args. If AWF requires stdin, use a small shell wrapper that writes stdin to a temporary prompt file/string and invokes `grok -p "$prompt"`; cover that wrapper in unit tests.
- `get_provider()` returns `"xai"`.
- Reasoning effort mapping should be documented as model-based/no-op: Grok Build docs do not expose a portable thinking-level flag in the CLI. For now, `high`, `xhigh`, and `max` keep the documented coding model unless a documented higher-reasoning Grok Build model variant is found during implementation; no undocumented flags will be invented.

Provider failures and recovery:

- `src/awf/adapters/provider_failures.py`: classify xAI/Grok auth, quota/capacity, rate limit, and transient failures using existing provider-specific patterns and redaction helpers.
- `src/awf/service/provider_recovery.py`: add `grok -> xai` to provider mapping and include defaults/fallback handling where current runtime maps are enumerated.

Provider readiness, doctor, and smoke surfaces:

- `src/awf/service/provider_readiness.py`: add `grok` to provider literals, default provider lists, runtime-to-provider maps, CLI executable maps, reason-code prefixes, and selected-agent preflight. Add `_check_grok` requiring both the runtime binary (`command -v grok` via the same runtime-container probe path as Gemini/OpenCode) and an `XAI_API_KEY` signal.
- `src/awf/service/provider_readiness_helpers.py`: add helpers only if the existing helper split requires them; keep the main readiness shape consistent with nearby `gemini`/`opencode` code.
- `src/awf/service/doctor/__init__.py`, `src/awf/service/doctor/reasons.py`, `docs/REASON_CATALOG.md` if generated/maintained manually, and related doctor tests: add Grok credential labels and reason guidance without exposing secrets.
- `src/awf/service/smoke.py`: include Grok wherever agent/runtime smoke support is enumerated.

Auth and secret injection:

- `src/awf/node/auth_mounts.py`: inject `XAI_API_KEY` into the agent container via the existing env-secret mechanism; do not add a keyring or credential-dir mount. Ensure repr/log paths remain redacted through existing secret handling.
- `src/awf/node/compose_manager.py` and stack launcher/provisioner code only if env-secret propagation requires enum/list updates outside `auth_mounts.py`.
- `docker/compose/local-service.yml` only if local service sidecar auth mounts/env declarations enumerate provider credentials and need Grok parity.

Runtime image:

- `docker/agent-runtime.Dockerfile`: install official xAI Grok Build using `curl -fsSL https://x.ai/cli/install.sh | bash`, not npm. Add an `ARG`/comment analogous to version pins if the installer exposes a documented version pin; otherwise document that the image tracks the official installer. Verify `grok --version || true` next to other CLIs.

CLI, API, profiles, usage, monitor surfaces:

- `src/awf/cli/workspace_commands.py`: ensure `awf workspace create --agent grok` and `adopt-pr --agent grok` parse through `AgentRuntime` validation.
- `src/awf/cli/service_commands.py`: include `grok` in provider strictness help text.
- `src/awf/api/schemas.py` only if examples or schema enum snapshots need explicit updates.
- `src/awf/profiles/*`: update runtime/auth lint allowlists and sample profiles only where `gemini`/`opencode` are currently enumerated.
- `src/awf/service/usage_store.py` and `src/awf/service/usage_collection.py`: add a Grok mapping if `ccusage` or AWF usage accounting can represent it; otherwise add an explicit unsupported/no-op path with tests and no failures.

## Tests to Write First

Adapter tests (`tests/unit/adapters/test_adapters.py` or a new focused `tests/unit/adapters/test_grok_adapter.py` if that matches line-length guardrails):

1. `GrokAdapter.get_provider()` returns `"xai"`.
2. Default invocation includes the Docker exec prefix and Grok argv with `grok`, `-p`/`--single`, `--always-approve`, `--no-alt-screen`, `--no-auto-update`, `--output-format plain`, and the default/custom model via `-m` or `--model`.
3. Prompt delivery follows the chosen AWF runner convention and is asserted explicitly: if the final implementation keeps prompts off argv, assert the prompt is sent on stdin and the wrapper reads it; if using `-p <prompt>` directly, assert the exact argv and document why this is acceptable for Grok.
4. Invocation without model omits the model flag while retaining required headless hygiene flags.
5. Effort mapping covers `None`, `low`, `medium`, `high`, `xhigh`, and `max`; high effort should not add undocumented flags.
6. Registry lookup returns `GrokAdapter` for `AgentRuntime.grok`.
7. Defaults include `AgentRuntime.grok` with model `grok-build-0.1` and effort `xhigh`.

Provider failure/recovery tests:

1. `provider_failures` classifies common xAI/Grok auth/rate/capacity messages with provider `xai`, model retained, retryability preserved, and no secret leakage.
2. `provider_recovery` maps `grok` to provider `xai` and uses Grok defaults when fallback/recovery metadata references the runtime.

Readiness/doctor tests:

1. Provider name validation accepts `grok` and includes it in default readiness provider sets.
2. Selected Grok preflight succeeds only when both `command -v grok` succeeds through the runtime CLI probe and `XAI_API_KEY` is present.
3. Missing binary yields a Grok binary-missing reason.
4. Missing `XAI_API_KEY` yields a Grok auth-missing reason.
5. Probe stderr/stdout containing an API key value is redacted from readiness details.
6. Doctor diagnostics include `provider.grok` with usable/missing credential statuses and reason guidance.

Auth/env tests:

1. `auth_mounts`/stack launcher propagates `XAI_API_KEY` to the agent environment when present.
2. `repr()`/serialized compose specs do not include the raw `XAI_API_KEY` value.
3. No Grok auth directory mount is created.

CLI/profile/usage tests:

1. CLI tests accept `--agent grok` for workspace creation and adopt-pr payload construction.
2. Service strict provider parsing/help accepts `grok`.
3. Profile lint allowlists accept Grok env secrets if profiles enumerate allowed auth signals.
4. Usage-store mapping handles Grok consistently with current runtime provider accounting, or explicitly records no `ccusage` source if unsupported.

Dockerfile tests:

1. If a Dockerfile text test exists, add assertions that the official installer URL is present and no community/npm Grok package is used.
2. Avoid invoking the real `grok` binary in unit tests.

## Risks and Mitigations

- Official Grok installer pinning may not be documented. Mitigation: document installer tracking in the Dockerfile and avoid pretending to pin a version that the installer cannot pin.
- Prompt delivery is subtle because Grok documents `-p <PROMPT>` while AWF adapters often keep prompts on stdin to avoid argv leakage. Mitigation: inspect `AgentAdapter.run()` and choose the least-leaky runner-compatible wrapper, then test the exact contract.
- xAI docs include both `XAI_API_KEY` and, on a getting-started page, a Grok-specific env example. Mitigation: follow the issue and enterprise/headless docs by wiring `XAI_API_KEY`; do not add extra env names unless implementation finds existing AWF env-secret patterns require aliases.
- Readiness may need to probe the agent-runtime container rather than the API container. Mitigation: mirror selected Gemini/OpenCode preflight probe paths so `awf workspace create --agent grok` checks the right image.
- `ccusage` may not support Grok. Mitigation: make usage wiring explicit and non-fatal, with tests documenting unsupported collection if necessary.
- A parallel `cursor` runtime may add nearby enum/import/list changes. Mitigation: scan before editing and make additive changes without reordering unrelated runtime entries.
- New reason codes may require generated reason catalog updates. Mitigation: follow existing doctor/reason catalog patterns and run the focused generator/check only if the repository already requires it for such edits.
- Secrets could leak through readiness subprocess stderr/stdout or compose reprs. Mitigation: add regression tests that include fake `XAI_API_KEY` values and assert redacted output.

## Assumptions

- `AgentRuntime` enum values are sufficient for CLI/API validation, so `--agent grok` should work once the enum and schema surfaces are updated.
- AWF already has an env-secret mechanism suitable for `XAI_API_KEY`; no new secret broker or credential mount abstraction is required.
- `grok-build-0.1` is an acceptable default because xAI documents it as the Grok Build coding model, with `grok-code-fast*` aliases available.
- Grok Build's `--always-approve` is appropriate because AWF containers are the sandbox boundary, matching the existing approval-bypass posture for other agent runtimes.
- Real Grok CLI execution is not available in this sandbox and must not be required for unit tests.

## Non-goals

- Do not modify existing `codex`, `claude_code`, `gemini`, or `opencode` adapter semantics.
- Do not integrate the community `superagent-ai/grok-cli` or any npm package named `grok`; use the official `https://x.ai/cli/install.sh` installer only unless official docs provide a documented fallback.
- Do not add persistent `~/.grok` credential mounts, keyring support, browser login, or device-code login for AWF workspaces.
- Do not implement Grok ACP/session resume support; AWF will use one-shot headless execution.
- Do not invent undocumented reasoning or permission flags.
- Do not run the real Grok CLI in tests.
- Do not run broad AWF/GitHub-owned validation during the agent phase under the current workspace contract.
- Do not switch branches, push, rebase, force-push, or commit during this planning-only phase.
