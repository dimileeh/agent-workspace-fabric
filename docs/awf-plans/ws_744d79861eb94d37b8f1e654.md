# Plan: PR Monitor Transient GitHub Retry State Preservation

## Goal

Implement the P0 PRD slice so transient GitHub failures in the PR monitor cause a conservative wait/retry cycle without losing monitor state, mutating operation state, failing the workspace, escalating to humans, or merging from an unknown GitHub snapshot.

The retry behavior must apply only where retry is safe:

- PR status fetch and comment reads through `GitHubClient.fetch_pr_status`.
- Merge-gate status rechecks before merge.
- Merge attempts rejected by transient GitHub/network errors.
- Human notification/comment posting when the monitor is already in a wait state.
- Comment-settle re-polls inside `AddressComments`.
- Inline thread resolve failures after a push, where the next monitor poll can safely retry resolution or re-queue the open thread.

Permanent auth, permission, repository-not-found, validation, review, policy, stale, and branch-protection failures must continue to use the existing terminal/fallback paths.

## Implementation Steps

1. Add test helpers as needed.
   - Add a tiny operation seeding helper in `_monitor_runner_fixtures.py` or local test helpers.
   - Add an assertion helper for retry events on `Workspace.events`.
   - Keep fixtures SQLite-backed so state, events, operations, and lifecycle are exercised through real repositories.

2. Write the failing tests above before implementation.
   - Run the narrow test command after adding each cluster to confirm red.
   - Avoid weakening existing tests that assert permanent failures.

3. Introduce a single retry-recording helper in `PullRequestMonitorRunner`.
   - Candidate shape: `_record_transient_github_retry(exc, workspace_id, pr_number, context, wait_seconds, monitor_log)`.
   - It should write:
     - structlog warning: `monitor.github_transient_error_retrying`
     - monitor log event: `monitor.github_transient_error_retrying`
     - workspace event: same event type, reason code `GITHUB_TRANSIENT_RETRY`
   - Payload should include `context`, `operation`, `returncode`, bounded/sanitized message or stderr, `pr_number`, and `wait_seconds`.

4. Keep classification narrow.
   - Preserve explicit non-transient markers for auth, bad credentials, not found, repository/node resolution failures, and ordinary branch-protection/review-required messages.
   - Treat 5xx, timeouts, connection resets/refusals, EOF, secondary rate limit, abuse detection, and "try again" style GitHub responses as transient.
   - Do not classify validation failures, unresolved comments, failed checks, stale candidates, or policy blockers as transient GitHub failures.

5. Wire retry helper at safe boundaries.
   - Main `run()` status fetch: transient -> record event, sleep `poll_interval_seconds`, continue outer loop; permanent -> existing workspace failure.
   - Pre-merge recheck: transient -> record event, sleep, return `False`; permanent -> existing failure path.
   - `merge_pr`: transient -> record event, sleep, return `False`; permanent -> existing NotifyHuman/branch-protection fallback.
   - `NotifyHuman`/post comment: transient -> record event, sleep, return `False` without marking notification state; permanent -> existing raise/failure behavior.
   - Fix-cycle settle status fetch: transient -> record event and leave the monitor in a retryable state without pretending comments are known.
   - Resolve-thread mutation: transient -> record event and remove that thread ID from addressed state so the next poll reconsiders it; permanent behavior remains warning/requeue, unless tests reveal a stricter existing contract.

6. Preserve merge gates.
   - Do not call `decide()` with partial or unknown status.
   - Do not call `merge_pr` after any failed status fetch or pre-merge recheck.
   - Keep initial review grace, async reviewer settle, branch freshness, merge queue, stale validation/candidate checks, policy refresh, and final settle ordering unchanged.

7. Preserve state intentionally.
   - Retry paths should not increment `iter_count` unless the existing action actually completed.
   - Retry paths should not create recovery operations, change existing operation status, transition to `ready`, transition to `failed`, write notification dedupe markers, or run compose teardown.
   - Persist only intentional wait markers/events/logs. Existing monitor state such as addressed thread IDs, last push SHA, and grace/settle markers must survive.

8. Run narrow and broad validation, then commit in the implementation phase.
   - This planning phase will not run validation or commit.

## Risks

- Misclassifying a permanent GitHub denial as transient could loop forever. Mitigation: keep auth/not-found/review-required/branch-protection markers non-transient and preserve existing permanent failure/fallback tests.
- Retrying after an unknown comment/status snapshot could accidentally merge from stale green data. Mitigation: tests assert no merge when status fetch or pre-merge recheck is unknown.
- Retrying inside fix-cycle after the agent has committed local changes can duplicate work or lose thread resolution state. Mitigation: keep local state explicit, avoid marking unresolved GitHub threads as complete after resolve failure, and rely on the next outer poll to re-read GitHub.
- Adding durable retry events could spam the event log during a long outage. Mitigation: payloads are compact and bounded; if needed, dedupe by context/head/operation in a follow-up, but do not hide retries for this P0 slice.
- Backoff changes can make unit tests brittle. Mitigation: use injected `RecordedSleep` and start with existing `poll_interval_seconds`; introduce exponential backoff only if it can be deterministic under test.

## Assumptions

- GitHub transient errors surface as `GitHubClientError` from the `gh`/GraphQL boundary or as stderr text from `gh` commands, not arbitrary exception types.
- The safest retry unit is the PR monitor poll interval; no new DB schema is required for this slice.
- Workspace events are the right durable place for reason codes because existing monitor code already writes `WorkspaceEventCreate` entries for monitor decisions.
- Existing AWF branch, push, PR creation, and merge ownership rules remain unchanged.
- This phase is a planning-only phase, so the implementation commit requested by the task belongs to the later implementation phase, not this plan file turn.

## Explicit Non-Goals

- Do not change PR monitor decision ordering or merge policy.
- Do not bypass unresolved comments, failed/pending checks, stale validation, branch freshness, review grace, async reviewer settle, merge queue, policy refresh, or final settle checks.
- Do not add new migrations or persistent retry counters unless tests prove the existing workspace event/state fields are insufficient.
- Do not retry deterministic validation failures, policy blockers, branch-protection denials, bad credentials, missing repositories, or closed PRs.
- Do not push, rebase, switch branches, or modify AWF branch-management behavior.
- Do not change console code, API contracts, lockfiles, coverage thresholds, or validation requirements.
- Do not add broad abstractions outside the PR monitor runner/GitHub boundary.
