# Plan: First-Class AWF PR Monitor Adoption For Existing GitHub PRs

## Objective

Add a supported AWF control-plane path for adopting an already-open GitHub PR
into the normal service-managed PR monitor lifecycle. An operator should be able
to provide either:

- `repo_url` or GitHub repo slug plus `pr_number`, or
- a full GitHub PR URL.

AWF will resolve the PR metadata, reject terminal PRs with structured reason
codes, and create or attach a workspace/task attempt/merge candidate that reaches
`monitoring_pr` without running the original implementation agent. The existing
service worker and PR monitor should own the adopted PR afterward, including
review comments, CI repair, base sync, auto-merge or manual merge policy,
validation freshness reporting, durable events, operations, and `monitor.log`.

## Current Findings

- The legacy path is `scripts/attach_feature_pr_monitor.py` plus
  `awf.runtime.feature_pr_sync`; it writes a spec and detaches `scripts/run_awf.py`
  for `sync_feature_pr` work.
- The service stack already has first-class `Task`, `TaskAttempt`,
  `MergeCandidate`, validation freshness summaries, monitor log streams, monitor
  claim recovery, and auto-merge/manual monitor selection through
  `workspace.auto_merge`.
- The normal service provisioner currently checks out `workspace.branch_base`.
  Adopted PRs need to check out the PR head ref while preserving the PR base ref
  as the merge target.
- The executor currently has normal feature-branch and monitor-recovery paths,
  but the service path does not yet have a `sync_feature_pr` skip-agent/skip-push
  execution branch equivalent to the legacy `run_awf.py` implementation.
- `WorkspaceRepository.transition(..., to=monitoring_pr)` already creates or
  updates the open merge candidate when `pr_url` is present and the workspace has
  a task attempt.

  - Request fields: `repo_url` or `repo_slug`, `pr_number`, `pr_url`, `agent`,

    `initial_review_grace_period_seconds`, optional title/prompt overrides, and

  - Response fields: workspace id/status/version, task id/attempt id, candidate

  - Add a reusable repo parser that accepts both GitHub URL forms and
    `owner/repo` slugs.
  - Add a PR-adoption metadata fetcher or shared parser that returns PR number,

    ref, head SHA, and base SHA.

  - Create or attach a workspace with `task_kind="sync_feature_pr"`, persisted
    PR adoption metadata in `task_policy`, task/attempt lineage, reservation and
    queue decision records, monitor policy, and no initial implementation agent
    execution.
  - Return existing adoption rows for the same normalized repo/PR instead of

- `src/awf/service/workspaces.py`
  - Add `WorkspaceService.adopt_pull_request_monitor(...)` that wraps the new
    adoption service for MCP and other non-FastAPI callers.

- `src/awf/node/provisioner.py`

  - Persist `remote_push_branch` as the PR head ref so monitor fix commits push

- `src/awf/control/executor.py`

## Tests To Write First

1. Service adoption creates the right lineage and monitor-owned request
   - Fake PR metadata fetcher returns an open PR with head/base refs and SHAs.
   - Call `WorkspaceService.adopt_pull_request_monitor` or the lower-level
     adoption service.
   - Assert one workspace, one task, one task attempt, reservation, queue
     decision, and adoption event/operation are persisted.
   - Assert task kind/policy identify `sync_feature_pr`, `auto_merge` is stored,
     `pr_url`, `pr_number`, head/base refs, and SHAs are recorded.

2. Service adoption is idempotent per repo/PR
   - Call adoption twice with equivalent identities, for example slug plus PR
     number and then full PR URL.
   - Assert the second call returns `attached_existing=true`, the same workspace
     id, and no duplicate task attempt or merge candidate.

3. Service adoption rejects terminal PRs with structured reason codes
   - Closed PR returns `PR_ALREADY_CLOSED`.
   - Merged PR returns `PR_ALREADY_MERGED`.
   - Missing/invalid repo or PR identity returns `PR_ADOPTION_INPUT_REQUIRED` or
     `INVALID_GITHUB_REPO`.
   - Assert no workspace rows are created on these failures.

4. Monitor policy conflict regression
   - First adoption uses `auto_merge=false`.
   - Replay for the same repo/PR with `auto_merge=true` returns a structured
     conflict, unless the implementation explicitly supports a separate policy
     update operation. The test should lock in the chosen behavior.

5. Provisioner checks out the PR head ref for adopted workspaces
   - Seed a `sync_feature_pr` workspace with adoption metadata.
   - Use a fake `GitManager` and assert `add_worktree(... base_branch=head_ref,
     new_branch=<service branch>)` is called.
   - Assert `remote_push_branch` is persisted as the PR head ref while
     `branch_base` remains the PR base ref.

6. Executor skips original implementation work
   - Seed a ready `sync_feature_pr` workspace with PR metadata and a fake monitor.
   - Assert the agent adapter is not invoked, validation runner is not invoked,
     and PR creator is not invoked.
   - Assert state reaches `monitoring_pr`, the merge candidate is open and
     canonical, and candidate `head_sha`/`base_sha` match adoption metadata.

7. Executor/monitor integration records durable monitor logs
   - Run the adopted workspace through the monitor handoff with a `LogStore`.
   - Assert `monitor.log` is listed for the workspace and contains a
     `monitor.start` frame.
   - Assert operations/events include adoption/monitor reason codes and do not
     contain secret values.

8. Validation freshness appears for adopted PRs
   - After candidate creation with no validation runs, assert workspace,
     merge-queue, and adoption responses expose validation freshness as
     unavailable/stale according to the existing freshness contract rather than
     omitting the field.
   - If a validation run is later attached to the adopted attempt, assert the
     freshness summary scopes to that attempt.

9. REST endpoint contract
   - `POST /v1/workspaces/adopt-pr` accepts repo slug plus PR number.
   - It also accepts full PR URL without separate repo fields.
   - It requires the configured API token.
   - It returns the adoption response, structured terminal-PR errors, and the
     same idempotency behavior as the service test.

10. CLI contract
    - `awf workspace adopt-pr --repo owner/repo --pr 123` posts the expected
      JSON to the REST endpoint with bearer token headers.
    - `--pr-url` form derives identity client-side only enough to build the
      request; server remains authoritative.
    - `--no-auto-merge` persists manual monitor policy.
    - API error bodies are relayed without leaking `AWF_API_TOKEN`.

11. MCP contract
    - `awf_adopt_pull_request_monitor` calls the shared service and returns the
      same structured payload as REST.
    - Terminal PR errors are `is_error=true` tool results with reason codes.
    - Tool schema is bounded and does not expose shell, Docker exec, secret, or
      filesystem inputs.

12. Legacy script wrapper
    - Existing script tests are updated to assert the script calls the supported
      adoption endpoint/CLI path instead of spawning `run_awf.py`.
    - Existing flags such as `--repo`, `--pr`, `--agent`, and `--no-auto-merge`
      are mapped to the new request.
    - Idempotent repeated invocation no longer depends on `pgrep` for detached
      process detection; service idempotency is authoritative.

## Implementation Approach

1. Add the shared metadata and identity helpers first, with pure parser tests.
2. Add the adoption service and service-level tests before any API/CLI/MCP code.
3. Extend provisioner/executor support for service-managed `sync_feature_pr`,
   proving the initial coding agent path is not entered.
4. Add REST, CLI, and MCP adapters as thin wrappers around the shared service.
5. Wrap the legacy detached script so there is one supported adoption path.
6. Update docs and TODO only after the code and tests are green.

The preferred idempotency mechanism is a deterministic adoption key stored in
`workspaces.idempotency_key`, backed by the existing unique constraint. If tests
show older rows without that key need attachment, add a repository lookup by
normalized repo slug and PR number before creating a new row.

## Risks And Assumptions

- Assumption: new adoption requests can follow AWF's existing asynchronous
  workspace lifecycle. The request returns an accepted/adopted workspace, and
  the service worker provisions it and moves it to `monitoring_pr` without an
  implementation-agent run.
- Assumption: adopted PRs should still have a managed worktree and compose stack
  so the existing PR monitor can fix comments, CI, and base drift. A DB-only
  monitor row is not sufficient.
- Assumption: `auto_merge` is immutable for an existing repo/PR adoption. A
  later policy flip should be a separate explicit operator action, not an
  idempotent replay side effect.
- Risk: GitHub metadata shape differs between `gh pr view --json` and GraphQL.
  Keep metadata fetching behind one fakeable helper and parse defensively.
- Risk: checking out a PR head ref while preserving the base branch as merge
  target crosses provisioner/executor boundaries. Tests must prove both the git
  source branch and merge-candidate base metadata are correct.
- Risk: concurrent adoption requests for the same repo/PR can race. The
  deterministic idempotency key should make the database the final authority.
- Risk: legacy detached script behavior may be used by operators outside the
  service stack. The wrapper should fail with an actionable message when the
  AWF API is unreachable rather than silently falling back to detached
  `run_awf.py`.
- Risk: the TODO file and docs are high-overlap paths. Keep updates limited to
  implementation-backed evidence for this slice.

## Explicit Non-Goals

- Do not rerun the original coding agent when adopting a PR.
- Do not auto-resolve GitHub review comments at adoption time; the existing PR
  monitor loop owns that after `monitoring_pr`.
- Do not add Aira-specific repo, branch, database, pgvector, Alembic, or service
  assumptions to AWF core.
- Do not implement arbitrary shell/Docker/file/secret MCP tools.
- Do not rewrite the merge queue, validation provenance model, or PR monitor
  decision core beyond the hooks required for adopted PR workspaces.
- Do not remove or rewrite unrelated Active/Completed Slices ledger rows.
