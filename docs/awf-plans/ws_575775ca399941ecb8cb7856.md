## Part A (#469) — `require_ci` operator flag + explicit "no checks observed" signal

### Problem (verified in code)
- `parse_check_state([])` → `CheckState.PENDING` (`bitbucket_client_parsing.py:268`); GitHub
  defaults a missing rollup to `PENDING` (`github_client.py:561`).
- `decide()` gate 6 (`pr_monitor.py:944`) maps `PENDING → WaitForCI("pending_checks")` with no
  escape. A BitBucket repo with **no Pipelines** therefore never merges even when clean.
- For a clean OPEN BitBucket PR: `mergeable_state_for` → `MERGEABLE`, `merge_state_status_for`
  → `CLEAN` (`bitbucket_client_parsing.py:219,231`). So the `unknown_mergeable_state` gate
  (`pr_monitor.py:946-950`) is **not** hit — once gate 6 is bypassed, `decide()` reaches
  `Merge()`. **No mapping fix is required**; only a proving test (point 7).

### Design decisions
- **New PRStatus field**: `no_checks_observed: bool = False`.
  - Default `False` is the SAFE value: "checks may exist → do NOT skip WaitForCI". A forgotten
    assignment can never enable an unsafe merge (mandatory invariant).
  - Set `True` **only** when the client authoritatively fetched the check/status set and that
    set is EMPTY. Never inferred from `len(status.checks)` (parse/pagination/transient-window
    bug could empty it while real CI exists).
- **MonitorConfig.require_ci: bool = True** (default = today's behavior; opt-in only).
- **decide() gate 6**: skip `WaitForCI("pending_checks")` **only** when
  `not config.require_ci AND status.no_checks_observed`. One-line semantics comment.

## Part B (#468) — BitBucket `workspace.pr_number` persists as `None` at handoff

### Problem (verified in code)
- BitBucket `create_pull_request` returns only a web URL (`bitbucket_client.py:250,270`);
  `PullRequestMetadata.number` is `None` for BitBucket.
- The release-sync handoff persists the raw `metadata.number`
  (`monitor_handoff_sync.py:319` log, `:356` persist, `:370`/`:393` event payloads), so
  `pr_number` lands `None`.
- The forge-neutral `_extract_pr_number` / `_PR_NUMBER_RE` (`executor/helpers.py:192`,
  `executor/constants.py:163`; regex already handles `/pull-requests/<n>`) is applied in the main
  feature path (`execution_flow.py:1389`) and recovery, but NOT in this handoff.

### Design decision
- Resolve the number **once** at handoff with a URL fallback, mirroring the existing
  `persisted.pr_number or _metadata_int(...)` seam (`monitor_handoff_sync.py:580-587`). ONE
  resolution path — compute a single local `pr_number = metadata.number or _extract_pr_number(metadata.url)`
  immediately after `metadata` is available (before the `release_pr_sync.pr_ready` log at ~line 314),
  then use that local at the log (319), persist (356), and both event payloads (370, 393). Do NOT
  inline the fallback twice.
- GitHub behavior is unchanged: GitHub `metadata.number` is populated, so `or`-fallback is inert.

### Files to touch (Part B)
- `src/awf/control/executor/monitor_handoff_sync.py`:
  - Import `_extract_pr_number` from `awf.control.executor.helpers` (alongside existing
    `_metadata_int` import at line 40).
  - Add local `pr_number = metadata.number or _extract_pr_number(metadata.url)` near line 314.
  - Replace `metadata.number` usages at 319, 356, 370, 393 with that local.
  - Leave the recovery seam at 580-587 as-is (it already resolves; the `or` pattern is what we
    mirror). Optionally factor a tiny module-level helper if it reads cleaner, but keep it ONE path.

### Tests first (Part B)
- Extend the `_extract_pr_number` unit tests (`tests/unit/control/test_executor_parts/...` —
  see `test_executor_part_005.py`) with real URL shapes:
  - BitBucket `.../pull-requests/7`, with trailing slash, with `?query`, with `#frag` → `7`.
  - GitHub `.../pull/7` → `7` (regression).
  - Malformed → `None`.
- Add a handoff-level test (under the release-sync handoff suite,
  `tests/unit/.../test_release_pr_sync*` / executor handoff parts) asserting that with a BitBucket
  `metadata.number=None` + BitBucket `metadata.url=".../pull-requests/7"`, the persisted
  `workspace.pr_number == 7`; and a GitHub case (`metadata.number=7`) still persists `7`.

## Risks & assumptions
- **Safe-default invariant**: `no_checks_observed` defaults `False`; gate 6 requires BOTH
  `not require_ci` and the signal. Any populate-site omission fails safe (keeps waiting).
- **GitHub `totalCount`**: adding `totalCount` to the GraphQL `contexts` connection is additive
  and harmless; if GitHub returns `null` rollup for no-CI commits, `rollup is None` already covers
  it — `totalCount` only hardens the present-but-empty edge.
- **BitBucket KNOWN mergeable**: confirmed clean OPEN BB PRs map to `MERGEABLE`/`CLEAN`, so the
  `unknown_mergeable_state` gate does not block — `Merge()` is reachable. No mapping change needed;
  proven by an explicit `decide()` test.
- **Single factory wiring**: `worker._pr_monitor_factory` feeds feature/release/handoff monitors,
  so one `monitor_kwargs` addition covers all live paths; the `runner.py:103` `MonitorConfig()`
  fallback stays default-True by design.
- **Coverage**: each new branch (signal set true/false in both clients; gate-6 bypass true/false;
  URL fallback hit/miss) gets a direct test. No coverage-theater.
