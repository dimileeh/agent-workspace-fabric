## 1. Problem and goal

`packaging/install.sh` already ships a hosted, inspected, jq-free one-line
installer with an `--uninstall` lane that removes an **AWF-managed** uv/pipx
package install and refuses an unmanaged `awf` (`UNINSTALL_REFUSED_UNMANAGED`).
There is no symmetric hosted **uninstaller** one-liner, and the existing
`--uninstall` lane intentionally does *not* clean local AWF runtime/config/state
(`docs/UNINSTALL.md` documents that gap as manual work).

T21 adds `packaging/uninstall.sh`: a standalone, hosted
`curl -fsSL … | bash`-style uninstaller with a conservative, AWF-managed cleanup
contract. It must:

1. **Preserve user and agent credentials by default** — never touch provider
   secrets (keyring entries, env refs, plain-file secrets) or `gh`/agent auth.
   There is no flag that removes credentials.
2. **Remove only AWF-managed installs and explicitly selected AWF
   runtime/config/state** — the managed uv/pipx package removal (reusing the
   `install.sh --uninstall` behavior), plus opt-in cleanup of an allowlisted set
   of non-secret AWF state paths under `~/.awf`.
3. **Refuse or no-op on unmanaged `awf` executables** — an `awf` not installed by
   uv/pipx is never deleted (`UNINSTALL_REFUSED_UNMANAGED`); nothing-installed is
   a clean no-op.
4. **Support clear dry-run / plan output** — `--dry-run` enumerates every action
   a real run would take and mutates nothing.
5. **Require explicit non-interactive flags for destructive cleanup** —
   destructive filesystem deletes (state/config purge, uv removal) need an
   interactive confirmation or an explicit `--yes`; in non-interactive mode
   without `--yes` they fail closed with `CONFIRMATION_REQUIRED`.
6. **Offer uv removal only when an AWF ownership marker proves AWF bootstrapped
   uv** — `--remove-uv` removes uv only when the marker written by
   `install.sh`'s `bootstrap_uv` is present; otherwise it refuses
   (`UV_REMOVAL_REFUSED_UNOWNED`) so a user's own uv is never removed.

Out of scope: the Python first-run error catalog, `src/awf/host_setup`,
`src/awf/cli`, MCP, and any non-installer runtime/CLI behavior. Like `install.sh`,
`uninstall.sh` emits **shell-level** reason tokens only and does not depend on the
Python reason catalog, so no `docs/REASON_CATALOG.md` / `src/awf/...` changes.

## 2. Design

### 2.1 Self-contained, not a sourced library

`install.sh` is deliberately fully self-contained (bash 3.2, jq-free,
dependency-light) so the hosted `curl | bash` lane works with no sibling files.
A hosted `uninstall.sh` has the same constraint: a piped one-liner cannot
`source` a `packaging/lib/*.sh` helper that was never downloaded, and re-deriving
`install.sh`'s manifest+fetch machinery just to delegate package removal would be
*more* code than the small, well-tested removal helpers it would reuse.

Decision: `uninstall.sh` is **self-contained** and embeds the managed uv/pipx
removal helpers, mirrored from `install.sh` verbatim (same hardened logic:
token-anchored `grep -E "^${PACKAGE}( |$)"`, drain-the-stream instead of
`grep -q` to avoid the SIGPIPE-under-`pipefail` false-negative, dual-manager
probe-then-remove, `UV_TOOL_BIN_DIR`/`PIPX_BIN_DIR` re-export on `--install-dir`,
and the unmanaged refusal). A focused **parity test** guards against drift rather
than a runtime cross-script dependency. The "shared installer/uninstaller shell
helpers" allowance is satisfied by this mirrored-and-parity-guarded reuse; a
sourced library is explicitly rejected because it breaks the hosted contract.

### 2.2 Reason tokens (shell-level)

Reused names (identical semantics to `install.sh`):
`UNSUPPORTED_PLATFORM`, `MISSING_DEPENDENCY`, `BAD_USAGE`,
`UNINSTALL_REFUSED_UNMANAGED`, `INSTALL_METHOD_FAILED`.

New tokens (documented in the header comment and `usage()`):

- `CONFIRMATION_REQUIRED` — a destructive cleanup lane (state/config purge or uv
  removal) was requested in non-interactive mode without `--yes`, or an
  interactive confirmation was declined.
- `UV_REMOVAL_REFUSED_UNOWNED` — `--remove-uv` requested but no AWF uv-ownership
  marker is present, so AWF refuses to remove a uv it did not bootstrap.
- `STATE_CLEANUP_FAILED` — an authorized state/config removal failed (e.g. a
  path exists but cannot be removed), surfaced non-zero rather than masked.

### 2.3 Flags

```
uninstall.sh [options]

  --dry-run            Plan every action and mutate nothing.
  --non-interactive    Never prompt; destructive lanes then require --yes.
  --yes                Explicit consent for destructive cleanup (state/config/uv).
  --install-dir <path> Bin dir the matching install used (forwarded to uv/pipx
                       removal so neither manager orphans the awf entrypoint).
  --purge-config       Remove the non-secret host setup config (~/.awf/config.yml).
  --purge-state        Remove AWF host runtime/state (~/.awf/service).
  --remove-uv          Also remove uv, only when an AWF ownership marker proves
                       AWF bootstrapped it (else UV_REMOVAL_REFUSED_UNOWNED).
  --all                Convenience: managed package + --purge-config + --purge-state
                       (NOT credentials, NOT uv unless --remove-uv is also given).
  --shell <name>       Override shell detection for any PATH-related advice.
  --help               Print help and exit 0 (no mutation).
```

Default action (no purge/uv flags): managed uv/pipx package removal only —
behaviorally equal to `install.sh --uninstall`. Managed package removal alone is
**not** gated by `--yes` (parity with `install.sh`); only the new destructive
filesystem lanes are.

Parse-time guards (mirroring `install.sh`'s meaningless-combo rejections):

- `--remove-uv` with no other effect is fine; but `--yes`/`--non-interactive`
  remain accepted broadly (harmless no-ops where nothing destructive runs).
- Unknown flag → `BAD_USAGE` (exit 2). `--help` exits 0 with no mutation.
- `--install-dir ''` (explicit empty) → `BAD_USAGE`, matching `install.sh`'s
  `require_install_dir`.

### 2.4 Platform guard

`detect_platform` (mirrored) runs before any mutation: unsupported OS/arch aborts
with `UNSUPPORTED_PLATFORM` before touching uv/pipx or the filesystem.

### 2.5 Interactivity + confirmation gate

Mirror `install.sh`'s `stdin_is_interactive` with an uninstaller-local seam name
`AWF_UNINSTALL_FORCE_INTERACTIVE` (the harness runs under a piped, non-TTY
stdin):

```sh
stdin_is_interactive() {
    [ "$NON_INTERACTIVE" -eq 1 ] && return 1
    [ "${AWF_UNINSTALL_FORCE_INTERACTIVE:-0}" = "1" ] && return 0
    [ -t 0 ]
}

# Returns 0 only when the destructive lane is authorized.
confirm_destructive() {              # confirm_destructive "<what>"
    [ "$ASSUME_YES" -eq 1 ] && return 0
    if [ "$DRY_RUN" -eq 1 ]; then return 0; fi   # dry-run plans, never mutates
    if stdin_is_interactive; then
        printf '%s' "Remove $1? This cannot be undone. [y/N] " >&2
        local reply=""; IFS= read -r reply || reply=""
        case "$reply" in y|Y|yes|YES|Yes) return 0 ;; *) return 1 ;; esac
    fi
    return 1   # non-interactive + no --yes -> caller fails CONFIRMATION_REQUIRED
}
```

Each destructive lane consults `confirm_destructive`; a `return 1` becomes
`fail CONFIRMATION_REQUIRED "<lane> requires --yes (non-interactive) or interactive confirmation"`.

### 2.6 Managed package removal (mirrored from `install.sh`)

Embed `uv_lists_package`, `pipx_lists_package`, `resolve_awf_path`,
`uninstall_via_uv`, `uninstall_via_pipx`, and `uninstall_awf` verbatim from
`install.sh` (lines ~1137–1272). This preserves: dual-manager removal, the
`UV_TOOL_BIN_DIR`/`PIPX_BIN_DIR` re-export under `--install-dir`, the
drain-the-stream SIGPIPE fix, substring-fork safety, dry-run preview, the
unmanaged refusal, and the nothing-installed no-op. This lane is not `--yes`
gated (parity with `install.sh --uninstall`).

### 2.7 uv-ownership marker (producer change in `install.sh`)

The uv-removal-gated-by-marker contract needs a producer. Add a **minimal,
scoped** change to `install.sh`'s `bootstrap_uv`: after a successful bootstrap,
write a deterministic (no timestamp) ownership marker so the uninstaller can
prove AWF installed uv.

- Marker path: `${HOME}/.awf/uv-bootstrap.marker`
  (constant `AWF_UV_MARKER="${HOME}/.awf/uv-bootstrap.marker"`).
- Contents: two stable lines, `installed_by=awf` and `uv_bin_dir=<dir>`.
- Written only on a real bootstrap (never under `--dry-run`, which already
  returns before mutation in `bootstrap_uv`). `mkdir -p "${HOME}/.awf"` first.
- Document the marker in `install.sh`'s header alongside the existing seams.

`uninstall.sh` consumes the marker:

```sh
remove_uv() {
    [ "$REMOVE_UV" -eq 1 ] || return 0
    if [ ! -f "$AWF_UV_MARKER" ]; then
        fail UV_REMOVAL_REFUSED_UNOWNED "refusing to remove uv: no AWF ownership marker at ${AWF_UV_MARKER}; AWF only removes a uv it bootstrapped"
    fi
    confirm_destructive "uv (AWF-bootstrapped)" || fail CONFIRMATION_REQUIRED "uv removal requires --yes (non-interactive) or interactive confirmation"
    if [ "$DRY_RUN" -eq 1 ]; then
        plan "remove uv via 'uv self uninstall' and delete ${AWF_UV_MARKER}"
        return 0
    fi
    if command -v uv >/dev/null 2>&1; then
        uv self uninstall >/dev/null 2>&1 || warn "uv self uninstall reported a problem; continuing"
    fi
    rm -f "$AWF_UV_MARKER"
    say "Removed AWF-bootstrapped uv."
}
```

The marker location is overridable via `AWF_UV_MARKER` env so install/uninstall
tests share a hermetic path (and the marker stays under the temp `$HOME` anyway).

### 2.8 AWF state/config cleanup (opt-in, credential-preserving)

Cleanup targets an **explicit allowlist** of non-secret subpaths under
`${AWF_HOME:-$HOME/.awf}` (env seam `AWF_HOME` for tests; default `$HOME/.awf`,
matching `src/awf/host_setup/config.py` and `src/awf/cli/init_ops.py`):

- `--purge-config` → remove the file `${AWF_HOME}/config.yml` only.
- `--purge-state`  → remove the dir  `${AWF_HOME}/service` only.

It **never** removes `${AWF_HOME}` itself, nor any other entry under it, so a
credential/secrets directory (e.g. a plain-file secret store) survives. Each lane
is `confirm_destructive`-gated, dry-run previews the exact path, and a removal
failure on a present path raises `STATE_CLEANUP_FAILED`. A missing target is a
benign no-op ("nothing to remove").

**Docker is advisory only.** Per `CLAUDE.md` ("Do not `rm` workspace state from
the host shell — use `awf service gc`"), `uninstall.sh` does not delete Docker
volumes/stacks; it prints a one-line pointer to stop/clean Compose state before
uninstalling. This keeps destructive host-side Docker ops out of scope.

### 2.9 Orchestration (`main`)

```
parse_args → detect_platform
  → remove_uv            (if --remove-uv; marker-gated, confirm-gated)
  → purge_state/config   (if requested; allowlist, confirm-gated)
  → uninstall_awf        (managed package removal; unmanaged refusal/no-op)
  → advisory Docker/credential-preserved note
```

Ordering note: uv removal and state purge run before package removal so an
explicit, authorized cleanup is not blocked by the package lane's unmanaged
refusal. Each lane is independent; a refusal/failure in one is surfaced with its
own token and non-zero exit.

### 2.10 `usage()` / `--help`

Self-contained help listing every flag and a short "Trust" paragraph: credentials
are preserved by default; destructive cleanup needs `--yes` or interactive
confirmation; uv is removed only with a proven AWF ownership marker; unmanaged
`awf` is never removed.

## 6. Risks, assumptions, non-goals

Assumptions:

- **`~/.awf` layout** — config at `~/.awf/config.yml`, host state at
  `~/.awf/service` (confirmed in `src/awf/host_setup/config.py` and
  `src/awf/cli/init_ops.py`). The cleanup allowlist targets exactly these; if a
  future layout adds state paths, they are simply not purged (safe default) until
  added to the allowlist. `AWF_HOME` overrides the base for hermetic tests.
- **uv removal mechanism** — assumes the official uv supports `uv self uninstall`.
  A non-zero result warns and continues (the marker is still removed and the run
  succeeds); the contract being tested is the *marker gate*, not uv's internals.
  Tests pin this via the stub, not a real uv.
- **Marker producer coupling** — the positive uv-removal path only fires in
  production once `install.sh` writes the marker (the minimal `bootstrap_uv`
  change). Tests cover both halves: install.sh writes it; uninstall.sh refuses
  without it and removes with it.
- **Interactivity in tests** — real `[ -t 0 ]` cannot be exercised under
  subprocess pipes, so `AWF_UNINSTALL_FORCE_INTERACTIVE` stands in (mirroring
  `install.sh`'s `AWF_INSTALL_FORCE_INTERACTIVE`); the true-TTY branch is covered
  indirectly by the non-interactive default.
- **`set -euo pipefail` discipline** — mirrored `read`/pipeline code reuses the
  `|| reply=""` and drain-the-stream patterns already proven in `install.sh` to
  avoid SIGPIPE-under-`pipefail` and `set -e` aborts with no reason token.
- **Docs drift tests** — `tests/unit/docs/test_public_docs_status.py` asserts
  specific UNINSTALL.md strings; edits are additive and preserve them. Risk
  surfaced by running the focused docs test above.

Risks:

- **Helper drift** between the mirrored managed-removal in `uninstall.sh` and
  `install.sh`. Mitigated by the parity test and by copying the helpers verbatim.
- **Accidental credential deletion** — mitigated by the strict allowlist (only
  `config.yml` and `service/`, never `${AWF_HOME}` or a secrets dir) plus a test
  that seeds a secret path and asserts it survives every purge lane.

Non-goals:

- No changes to the Python reason catalog, `host_setup`, CLI, or MCP.
- No credential-removal capability (credentials are always preserved).
- No host-side Docker volume/stack deletion (advisory pointer to `awf service gc`
  / `docker compose down` only).
- No changes to `install.sh` install/verify/checksum/manifest/uninstall logic
  beyond writing the uv ownership marker in `bootstrap_uv` and the header doc.
- No real network calls, real releases, or real uv in tests.
