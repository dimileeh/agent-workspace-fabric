# Plan — Lease fencing via `execution_claim_epoch` (issue #421)

Workspace: `ws_df9a6ea504114ab2b46e6e14` · Branch: `awf/ws_df9a6ea504114ab2b46e6e14`

## Problem

Stale-lease recovery can run two provisions of the **same** workspace concurrently
(split-brain). The execution lease is time-based only; `Workspace.version` bumps on every
status transition so it cannot serve as a fencing token. In the overlap window a stale worker
can `rmtree` a bind source the new claimant just created (the #421 / #418–419 lineage race).

## Locked design (build THIS)

A dedicated monotonic **`execution_claim_epoch`** column. Each claim of `requested ->
provisioning` strictly increments the epoch. The worker reads its epoch back at provision start
and CAS-checks every heartbeat / release against it. A later claimant always holds a strictly
higher epoch, so the stale worker is fenced (CAS updates 0 rows) on its next heartbeat write and
aborts before any destructive filesystem op. No filesystem lock, no provisioning stall.

Design decisions D1–D8 from the issue are authoritative; this plan implements them.

  (`dispatch_methods._safely_provision_claimed`). The legacy `provision()` (self-claiming) path
  has **no production callers**, so the epoch parameter threaded through

  path and all existing tests.
- Worker `_refresh_execution_claim` / `_release_execution_claim` are **shared** by the
  provisioning path (`_safely_provision_claimed`) and the execution path
  (`_safely_execute_claimed`). The execution lease is established by the *executor*, which is
  **out of scope** (not in the FILES list). We therefore scope epoch fencing to the
  **provisioning** claim: the repo epoch parameters are optional, and the worker passes
  `self._execution_claim_epochs.get(workspace_id)` (present only for provisioning, `None`
  otherwise). This keeps the executor untouched while still fixing the same-worker

- Reason codes for the catalog come from a curated dict

  and the catalog generator is unaffected.

## Implementation detail notes

### Epoch increment (claim, D8)
In `claims.py`, a single helper sets ownership and increments using a **SQL-side expression** so
monotonicity holds regardless of in-memory staleness:
```python
def _apply_execution_claim(self, ws, *, owner_id):
    ws.execution_claimed_by = owner_id
    ws.execution_claim_expires_at = self._execution_claim_expires_at()
    ws.execution_claim_epoch = Workspace.execution_claim_epoch + 1
    if self._config.node_id is not None:
        ws.node_id = self._config.node_id
```
Used by both `_claim_requested_capacity_candidates` (after `transition_if_current`, ~L385) and
`_claim_requested_for_provisioning` (~L454). The row is row-locked / freshly atomically
transitioned, so the increment is safe. The concrete value is read back later via
`_read_execution_claim_epoch` (D2), so the in-memory SQL-expression placeholder is never read
within the claim txn.

### Repo refresh / release CAS (D6)
Add optional `execution_claim_epoch: int | None = None`. When not `None`, append
`Workspace.execution_claim_epoch == execution_claim_epoch` to the `WHERE`. `release` returning 0
rows means a newer claimant intervened — release no longer clobbers it.

### `read_execution_claim_epoch` (D2)
`SELECT execution_claim_epoch WHERE id=:id AND execution_claimed_by=:owner` -> `int | None`.
`None` ⇒ not ours (or row gone) ⇒ worker aborts the provision before starting.

### Recovery-clear epoch bumps (D3)
At each site that clears `execution_claimed_by`/`execution_claim_expires_at`, also set
`ws.execution_claim_epoch = Workspace.execution_claim_epoch + 1`:
- `recovery_stale._fail_stale_active_execution` (~L793)
- `recovery_stale._fail_stranded_workspace` (~L868)
- `recovery_stale._record_recoverable_runtime_stranding` (~L936)
- `workspace_repo.claim_monitoring_pr` stale-execution-claim `case(...)` (~L1042): bump epoch in
  the same `case` guarded by `stale_execution_claim`.

Decision (documented, minimal): the generic `transition` /
`transition_if_current` provisioning→terminal clears (cancel/stop/destroy via
`_transition_releases_provisioning_execution_claim`) already null the owner, so a stale worker's
owner-keyed refresh CAS fails there regardless — **no epoch bump added** to those generic paths.
The claim-time increment (the core fence) already covers same-owner re-dispatch.

### Abort-on-fence wiring (D4/D7, `dispatch_methods._safely_provision_claimed`)
```python
epoch = await self._read_execution_claim_epoch(workspace_id)
if epoch is None:
    _log.warning("worker.execution_claim_fenced", workspace_id=..., reason_code=EXECUTION_CLAIM_FENCED)
    return
self._execution_claim_epochs[workspace_id] = epoch
provision_task = asyncio.create_task(
    self._provisioner.provision_claimed(workspace_id, execution_claim_epoch=epoch), ...)
heartbeat = asyncio.create_task(
    self._refresh_execution_claim_loop(workspace_id, on_claim_lost=provision_task.cancel), ...)
try:
    await provision_task
except asyncio.CancelledError:
    _log.warning("worker.execution_claim_fenced", workspace_id=..., reason_code=EXECUTION_CLAIM_FENCED)
except Exception:
    _log.exception("worker.provision_failed", ...)
finally:
    heartbeat.cancel(); suppress+await
    await self._release_execution_claim(workspace_id)   # CAS on stored epoch
    self._execution_claim_epochs.pop(workspace_id, None)
```
`_refresh_execution_claim_loop` gains an optional `on_claim_lost` callback invoked when
`refresh` returns `False` (default `None` preserves the execution path's current behavior). The
fenced provision task is cancelled mid-flight; the heartbeat-cancel + D7 are the backstops for
the residual ms-scale gap between the pre-launch verify and the `rmtree` inside `to_thread`.

### Pre-launch verify (D4, provisioner)
Immediately before `stack_paths = await self._stack_launcher.launch(...)` (~L471):
```python
if execution_claim_epoch is not None and not await self._verify_execution_claim_epoch(
    workspace_id, execution_claim_epoch
):
    _log.warning("provisioner.execution_claim_fenced", workspace_id=..., reason_code=EXECUTION_CLAIM_FENCED)
    return   # abort WITHOUT transitioning (no _mark_failed)
```
`_verify_execution_claim_epoch` reads the row and returns `False` if missing, not in
`provisioning`, or `execution_claim_epoch != expected`. No sync guard, no
`run_coroutine_threadsafe` (explicit D4 constraint).

### Terminal transition epoch-CAS (D7, provisioner)
Convert the two terminal transitions to `transition_if_current` with the epoch predicate when
`execution_claim_epoch is not None`:
- **`provisioning->ready`** (~L742): replace `repo.transition(persisted, to=ready, ...)` with
  `repo.transition_if_current(workspace_id, from_status=provisioning, to=ready,
  reason_code="PROVISIONING_COMPLETE", extra_conditions=(Workspace.execution_claim_epoch ==
  epoch,))`. If it returns `None` ⇒ fenced/raced ⇒ **do not commit**, log
  `EXECUTION_CLAIM_FENCED`, return.
- **`provisioning->failed`** in `_mark_failed` (~L994): add optional `execution_claim_epoch`
  param, thread from `_provision_claimed_workspace` to every `_mark_failed` call in the pipeline,
  and add the same epoch `extra_conditions`. On `None` ⇒ fenced ⇒ skip commit, log.

**Clobber risk (must verify with tests):** the success/`_mark_failed` paths set placement/failure
metadata on the loaded ORM row *before* the transition. `transition_if_current` re-`SELECT`s the
row (`populate_existing` on PG; fresh `SELECT` on SQLite). SQLAlchemy **autoflushes** pending
writes before that `SELECT`, so the re-read returns the just-flushed values and repopulates the
object identically — no data loss within the txn. If the CAS fails (`None`), the session is not
committed and the flushed-but-uncommitted metadata rolls back (correct: a new claimant redoes
it). Tests below assert the ready/failed row retains its metadata on the happy path.

2. **Model column**: ORM default `0` on insert; column present, non-null.
3. **Repo CAS** (`tests/unit/db/test_repository_coverage_parts/…`): `refresh_execution_claim` /
   `release_execution_claim` — match (epoch+owner) succeeds; wrong epoch fenced (0 rows); wrong
   owner fenced; `release` does **not** clobber a row whose epoch advanced; `epoch=None` keeps
   legacy behavior. `read_execution_claim_epoch` returns the value for the owner and `None`
   otherwise. `claim_monitoring_pr` bumps epoch when it clears a stale execution claim.
4. **Claim increments epoch** (`tests/unit/control/test_worker_parts/…`): both claim blocks
   (`_claim_requested_for_provisioning` and the capacity path) set `execution_claimed_by=me` and
   `execution_claim_epoch == N+1`; backfilled `0` row goes to `1`; re-claim by the **same**
   worker still increments (fences a prior captured epoch).
5. **Recovery clears bump epoch**: a stale `provisioning` row at epoch `N` -> after each recovery
   clear, `execution_claimed_by is None` **and** `execution_claim_epoch == N+1`.
6. **Worker carries its epoch**: `_safely_provision_claimed` stores
   `_execution_claim_epochs[ws]`; refresh/release pass it; epoch cleared in `finally`;
   `_read_execution_claim_epoch` returning `None` aborts before dispatch.
7. **Abort-on-fence wiring**: refresh-CAS failure invokes `on_claim_lost`, cancelling the
   provision task; the fenced worker logs `EXECUTION_CLAIM_FENCED` and does **not** transition the
   row to `failed`/`ready`.
8. **Pre-launch verify + terminal CAS** (`tests/unit/node/test_provisioner_parts/…`): a fenced
   worker (epoch advanced after claim) aborts before `launch()` (stack launcher **not** called)
   and does not transition; a fenced worker's `provisioning->ready` / `->failed` updates 0 rows
   (cannot steal); a normal worker transitions to `ready` with all placement metadata intact
   (clobber assertion) and `_mark_failed` populates failure fields; `epoch=None` path unchanged.
9. **End-to-end fencing** (`tests/integration/` or worker parts): claim -> reclaim (epoch bump)
   -> stale worker fenced -> aborts -> no rmtree of new claimant's bind source -> stale terminal
   transition no-ops; **plus** the normal single-worker provision completes unaffected (no
   stall).

Cover every new line/branch with a focused test or a justified `# pragma: no cover` for

## Risks

- **Metadata clobber on the guarded ready/`_mark_failed` transition** (highest risk). Mitigated
  by the autoflush mechanism above and explicit happy-path metadata-retention assertions in
  test 8. If autoflush proves insufficient, fall back to a row-locked
  `get_for_update` + in-memory epoch check before `repo.transition` (still structurally safe on
  PG via the lock; documented alternative).
- **Shared refresh/release loop** between provisioning and execution paths. Mitigated by the
  optional epoch param defaulting to `None` and `_execution_claim_epochs` being populated only
  for provisioning — execution path behavior is byte-for-byte unchanged.
- **Migration backfill on both dialects**: `batch_alter_table` + `server_default=text("0")`
  ensures existing rows backfill on SQLite and PG. Verified by tests 1 and the PG roundtrip.
- **Dialect symmetry**: `transition_if_current` has a PG `FOR UPDATE` path and a SQLite
  atomic-`UPDATE` path; the epoch `extra_conditions` flows through both. Tests run on both.
- **No stall on the normal path**: the only added work is one cheap indexed point read before
  `launch()` and an epoch predicate on writes; epoch `0->1` at claim, CAS matches forever for
  the live worker. Asserted by test 9's single-worker case.
