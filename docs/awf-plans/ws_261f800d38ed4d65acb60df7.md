# Plan: PR Monitor Merge-Safety Gate

## Goal

Implement the narrow P0 fix so the PR monitor cannot auto-merge an open merge
candidate unless the candidate still points at the canonical attempt, has fresh
required validation provenance for that canonical attempt, and has no active
stale or merge blockers.

The intended integration point is the `Merge` branch in
`src/awf/runtime/pr_monitor_runner.py`, immediately before the existing final
merge path. Existing merge queue ordering, older-candidate blocker semantics,
API response shapes, and PR monitor decision-core behavior should remain
unchanged.

## Intended Files And Modules To Touch

- `tests/unit/runtime/test_pr_monitor_merge_safety.py`
  - Add a focused unit test module for PR monitor merge-gate behavior using the
    existing PostgreSQL fixture patterns and `_monitor_runner_fixtures.py`.
  - Keep setup helpers local and minimal.

- `tests/unit/runtime/test_merge_queue_ordering.py`
  - Add or minimally extend one focused regression proving an older same
    repo/base candidate still blocks a later eligible candidate after the new
    gate is present.

- `src/awf/runtime/pr_monitor_runner.py`
  - Add a small candidate readiness/validation guard in the `Merge` action path
    before calling `gh.merge_pr`.
  - Reuse the existing stale recovery dispatch behavior where the blocker is
    validation insufficiency or another stale reason.
  - Preserve existing transient GitHub error handling unless the implementation
    touches that path.

- `src/awf/runtime/merge_eligibility.py`
  - Add the smallest helper or parameter needed to evaluate validation
    sufficiency against the candidate's canonical attempt, not merely any
    workspace validation run.
  - Preserve existing `compute_stale_reason(workspace)` behavior for callers
    that do not opt into candidate-attempt-specific validation.

- `src/awf/db/repositories.py`
  - Add a narrow repository loader if needed to fetch the open candidate for a
    workspace with `attempt`, `workspace.operations`, `workspace.validation_runs`,
    and policy/stale inputs loaded without async lazy loads.

## Tests To Write First

1. Add a failing validation-provenance test:
   - Seed a `monitoring_pr` workspace, task, canonical attempt, and open merge
     candidate.
   - Make the task require tier 2 validation, then add only insufficient
     provenance for the canonical attempt, such as a tier 1 run or a tier 2 run
     attached to a different attempt.
   - Execute `PullRequestMonitorRunner._execute(Merge())`.
   - Assert `gh pr merge` is not called, the monitor dispatches the existing
     PR-monitor validation recovery operation, and the blocker reason is
     `validation_insufficient_tier`.

2. Add a failing active-blocker test:
   - Seed an otherwise mergeable canonical candidate with sufficient validation.
   - Add an active stale reason or persisted candidate stale flag for that
     candidate.
   - Execute `Merge`.
   - Assert the runner does not call `gh pr merge` and routes through the
     existing stale/recovery wait path instead of completing the workspace.

3. Add an eligible-candidate test:
   - Seed a canonical open candidate with sufficient successful validation
     provenance attached to the same attempt and no active stale/policy blockers.
   - Queue the normal fake GitHub merge and merge-sha lookup results.
   - Execute `Merge`.
   - Assert the merge command is called and the workspace/candidate reach the
     existing completed/merged path.

4. Add an older-candidate regression:
   - Seed an older eligible candidate and a later eligible candidate on the same
     repo/base.
   - Execute `Merge` for the later candidate.
   - Assert the later monitor waits with
     `MERGE_QUEUE_WAITING_FOR_OLDER_CANDIDATE`, does not call `gh pr merge`, and
     does not notify a human.

5. Add a transient GitHub regression only if the production change touches
   transient error handling or moves existing merge/pre-merge recheck error
   paths.

## Implementation Steps

1. Add the focused failing tests and confirm they fail for the expected reason:
   the current runner can reach `gh pr merge` without checking the open
   candidate's canonical-attempt validation/blocker state.

2. Add a candidate merge-gate helper in `PullRequestMonitorRunner` or a nearby
   small private dataclass/function. The helper should load the workspace's open
   merge candidate and return either "eligible" or a structured blocker:
   `validation_insufficient_tier`, active stale reason, `not_canonical`,
   `policy_blocked`, missing candidate, or other non-ready state.

3. For validation sufficiency, evaluate successful validation runs for the
   candidate's attempt:
   - status must be `succeeded`;
   - tier must satisfy the required task-class tier;
   - post-rebase validation must be newer than the latest successful rebase;
   - validation attached to a different attempt must not satisfy the canonical
     attempt's requirement.

4. For active blockers, consult existing persisted candidate state and active
   stale/policy inputs rather than inventing a separate queue model:
   - `candidate.stale` / active stale reasons block merge;
   - `candidate.policy_blocked` or blocking policy findings block merge;
   - non-canonical or non-open candidates block merge;
   - existing older-candidate blockers remain handled by
     `list_merge_queue_blockers_for_workspace`.

5. Wire the helper into the `Merge` branch before the final merge attempt. If
   the blocker is validation insufficiency or stale, feed it into the existing
   grace/recovery dispatch behavior. If the blocker is policy/non-canonical/no
   candidate, stop before merge with the least disruptive existing wait/notify
   behavior and an explicit reason.

6. Keep the existing queue-blocker checks before and inside the merge critical
   section. Do not change queue ordering or older-candidate blocker selection.

7. Run focused tests, then the required validation commands until green.

## Risks And Assumptions

- Validation runs with `attempt_id=None` are legacy or workspace-level
  provenance. For merge safety, the new PR monitor gate should prefer blocking
  and redispatching validation over treating ambiguous provenance as sufficient
  for a canonical attempt.

- Existing `compute_stale_reason(workspace)` treats workspace validation as a
  workspace-level signal. To avoid broad behavior changes, the candidate-specific
  validation check should be opt-in for the PR monitor merge gate.

- Active target-branch freshness is expected to be represented by existing
  stale reason/candidate stale state. This fix should not add a new target
  branch provider fetch in the final merge path unless a failing test proves the
  existing surfaces cannot represent the blocker.

- The runner may need to persist refreshed candidate readiness after loading the
  candidate. That should be scoped to the open candidate for the current
  workspace and should not alter merge queue API shape.

- There is a race between a pre-merge readiness check and the actual GitHub
  merge. The narrow fix should at least gate immediately before merge, and it
  should preserve the existing queue recheck inside the serialized merge
  critical section.

## Explicit Non-Goals

- Do not rewrite merge queue ordering or older-candidate blocker semantics.
- Do not change API response shapes for merge queue, tasks, validation, or stale
  reasons unless a focused failing test requires it.
- Do not lower coverage thresholds, `fail_under`, workspace coverage
  requirements, or PRD quality gates.
- Do not mark reachable behavior as `no-cover`.
- Do not touch migrations or lockfiles for this narrow fix.
- Do not switch branches, push, rebase, open a PR, or manually perform AWF
  lifecycle actions.
