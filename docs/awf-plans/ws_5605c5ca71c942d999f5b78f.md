# P0 Pre-GKE Orphan Resource Detection Plan

## Intended Files and Modules to Touch

1. `src/awf/service/orphan_resources.py` (new)
   - Centralize AWF orphan detection for Docker containers, Docker networks, Docker volumes, and managed worktrees.
   - Reuse the existing workspace lifecycle classification already present in `src/awf/service/status.py`: active workspace ids are expected; terminal or missing workspace ids are orphan candidates.
   - Preserve the AWF compose project conventions `awf_<workspace_id>` and legacy `awf-<workspace_id>`.
   - Expose typed dataclasses and `to_dict()`/payload helpers for:
     - per-resource records (`kind`, `workspace_id`, `name`/`id`/`path`, `compose_project`, classification, reason);
     - aggregate counts by kind;
     - cleanup readiness (`ready`, `status`, `reason`, `action`, `dry_run_only`);
     - bounded actionable examples.
   - Run Docker inventory as read-only list/inspect operations only:
     - `docker ps -a --filter label=com.docker.compose.project ...`
     - `docker network ls --filter label=com.docker.compose.project ...`
     - `docker volume ls --filter label=com.docker.compose.project ...`
   - Scan worktrees read-only under `<AWF_WORK_DIR>/git/worktrees`, considering only directory names that look like AWF workspace ids (`ws_*`).

2. `src/awf/service/status.py`
   - Replace or wrap the current container-only `_build_orphan_check` path with the new all-resource detector.
   - Keep backward compatibility for the existing `checks.orphan_workspaces` payload if needed by current tests/operators, but add the new primary `checks.orphan_resources` payload.
   - Ensure `collect_service_status()` remains testable with injected subprocess and workspace lookup dependencies, and that Docker/resource scan failures degrade to structured `unavailable` data instead of tracebacks.

3. `src/awf/api/routes/health.py`
   - Add `orphan_resources` to `/readyz` checks using the same detector and the route's existing `AsyncCommandRunner` injection pattern.
   - Return structured reason codes such as `NO_ORPHANS`, `ORPHAN_RESOURCES_PRESENT`, `DB_UNAVAILABLE`, `DOCKER_RESOURCE_SCAN_UNAVAILABLE`, and `WORKTREE_SCAN_UNAVAILABLE`.
   - Treat confirmed orphan resources as readiness failure (`503`) because the node is not cleanup-ready for more work; treat unavailable orphan classification as non-authoritative while existing DB/Docker checks report the root dependency failure.

4. `src/awf/service/metrics.py`
   - Add an `OrphanResourceMetrics`/summary field to `ResourceSaturationSummary`.
   - Keep metrics read-only and deterministic: counts by resource kind, total orphan count, terminal-vs-missing classification counts, and cleanup readiness reason/action.

5. `src/awf/api/routes/metrics.py`
   - Extend `/v1/metrics/resources/saturation` response schema with `orphan_resources`.
   - Add an app-state injection seam for tests, similar to the existing disk check provider, so API tests do not require a Docker daemon.

6. Tests:
   - `tests/unit/service/test_orphan_resources.py` (new focused detector tests).
   - `tests/unit/service/test_status.py` (service status integration and existing orphan-container regression coverage).
   - `tests/unit/api/test_health.py` (`/readyz` contract).
   - `tests/unit/service/test_metrics.py` and/or `tests/unit/api/test_metrics.py`/`tests/unit/api/test_metrics_capacity.py` (metrics serialization and summary behavior).
   - `tests/unit/cli/test_service_cli.py` only if CLI output or exit-code behavior needs an explicit regression beyond `collect_service_status()`.

No migrations, lockfiles, frontend files, config files, cleanup executors, Docker Compose templates, or unrelated docs should be touched.

## Tests to Write First

1. Detector unit tests in `tests/unit/service/test_orphan_resources.py`
   - `test_orphan_summary_reports_all_resource_kinds`: feed fake Docker/container/network/volume rows plus fake worktree paths for one terminal workspace and assert `orphan_count`, `orphan_counts_by_kind`, examples, and cleanup readiness action.
   - `test_active_workspace_resources_are_expected`: resources for an active workspace id do not fail readiness and are counted as expected.
   - `test_missing_workspace_resources_are_orphans`: resources whose `workspace_id` is absent from the DB view are classified with a stable missing-workspace reason.
   - `test_db_unavailable_makes_classification_unknown`: scanner examples are still returned, but cleanup readiness is `unknown` and not destructive.
   - `test_docker_scan_unavailable_is_structured`: non-zero Docker list result or missing Docker binary returns an `unavailable` scanner section without crashing.
   - `test_worktree_scanner_ignores_non_workspace_entries`: non-`ws_*` directories/files are ignored and paths are reported without deletion.
   - `test_docker_templates_include_compose_project_labels`: guard that container/network/volume listing uses Compose labels, not fragile name parsing.

2. Service status tests in `tests/unit/service/test_status.py`
   - Add or update a failing test proving `collect_service_status()` exposes `checks.orphan_resources` with containers, networks, volumes, and worktrees.
   - Assert confirmed orphan resources set top-level status to `fail`.
   - Assert no-orphan resources keep status `ok`.
   - Preserve current container-only regressions either by adapting them to the new payload or by keeping a compatibility alias.

3. Health tests in `tests/unit/api/test_health.py`
   - Update the all-ok `/readyz` shape test to include `orphan_resources`.
   - Add a failing test where fake Docker resource listings include a terminal/missing AWF resource and `/readyz` returns `503` with actionable `ORPHAN_RESOURCES_PRESENT`.
   - Add a test where DB or Docker classification is unavailable and `/readyz` returns structured orphan readiness data without a 500.

4. Metrics tests
   - In `tests/unit/service/test_metrics.py`, add a direct summary test that injects an orphan-resource summary and verifies `ResourceSaturationSummary.orphan_resources`.
   - In the metrics API tests, assert `/v1/metrics/resources/saturation` serializes the same counts and cleanup readiness fields using the app-state fake provider.

5. CLI test if needed
   - Add a focused `awf service status --format pretty` or JSON test proving the new nested orphan resource fields are emitted and a confirmed orphan exits non-zero.

Each test should fail against the current container-only implementation before implementation begins.

## Implementation Approach

1. Extract the status module's current workspace id view and compose-project parsing into the new orphan-resource module with minimal compatibility shims.
2. Add parser functions for Docker container, network, and volume JSON-line output. Invalid rows should be skipped; valid AWF rows should be grouped by `workspace_id` and resource kind.
3. Add a worktree scanner that reads only `<work_dir>/git/worktrees` and returns existing directory entries named `ws_*`.
4. Build one aggregate orphan summary from:
   - Docker scanner results;
   - worktree scanner results;
   - active and terminal workspace id sets from the control-plane DB.
5. Wire `collect_service_status()` to run the expanded scanner alongside existing API/DB/Docker/image/disk/provider checks.
6. Wire `/readyz` through the existing async command runner seam, keeping all subprocess calls bounded.
7. Extend resource saturation metrics with the detector summary through an injectable provider to keep tests isolated from Docker.
8. Keep all cleanup recommendations as text/status only. Do not add or call `docker rm`, `docker network rm`, `docker volume rm`, `git worktree remove`, `shutil.rmtree`, or `awf service gc --execute` from this slice.

## Risks

- Docker CLI `--format` fields differ slightly across Docker versions. Use Compose labels and JSON-line parsing, tolerate missing optional fields, and test the exact command templates.
- A Docker resource may have a valid AWF compose label even if the compose project no longer has containers. Networks and volumes must be scanned independently rather than inferred from `docker ps`.
- Worktree directories can be stale even when Docker resources are gone. Worktree detection must not depend on Docker availability.
- Making `/readyz` fail on confirmed orphans may affect operators using readiness as a pure dependency probe. Keep dependency failures separately reasoned so the response remains actionable.
- Adding Docker scans to metrics/health could increase latency. Keep checks bounded and use the existing command-runner timeout/concurrency patterns.

## Assumptions

- AWF-owned Docker resources are identifiable by `com.docker.compose.project` labels with project names matching `awf_<workspace_id>` or `awf-<workspace_id>`.
- Managed worktrees live under `<AWF_WORK_DIR>/git/worktrees/<workspace_id>`, matching `GitManager` and service worker setup.
- Active/destroying workspace rows are not orphaned; terminal rows with remaining resources are cleanup candidates; resources for missing workspace rows are cleanup candidates.
- Reporting an action string is sufficient for this P0 slice; actual destructive cleanup remains a later, separately gated change.
