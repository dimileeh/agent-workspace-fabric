# P0 Stale-Policy Fix Plan

## Scope

Implement a focused stale-policy fix so target-branch changes that only touch
workspace-specific AWF plan/conformance artifacts under `docs/awf-plans/**` are
visible as advisory context but do not make an otherwise mergeable candidate
stale. Preserve blocking behavior for real source, test, dependency, build,
schema, and migration overlaps.

## Intended Files And Modules To Touch

- `src/awf/service/staleness.py`
  - Add a small plan-artifact path predicate for `docs/awf-plans/**`.
  - Extend `StalenessFinding` with an advisory/blocking distinction, likely
    `blocks_merge: bool` and/or `severity`.
  - Emit advisory findings for plan-artifact owned-path overlaps.
  - Mark candidates stale only when at least one finding blocks merge or
    validation provenance is stale.
  - Avoid `STALE_TARGET_ADVANCED` for non-lenient tasks when the only target
    changes are plan artifacts.

- `src/awf/db/models.py`
  - Add compatibility properties on `StaleReason` such as `blocks_merge` and
    `severity` so API responses can distinguish blocking stale reasons from
    advisory overlap risks without requiring existing rows to change.

- `src/awf/api/schemas.py`
  - Add the advisory reason code and severity/blocking fields to
    `StaleReasonResponse`.
  - Keep existing fields stable for API/console compatibility.

- `src/awf/api/routes/merge_queue.py`
  - When choosing stale recovery actions, consider only blocking stale reasons.
  - Continue returning advisory stale findings in `stale_reasons` for operator
    context.

- `src/awf/runtime/pr_monitor_runner.py`
  - Filter active stale reasons to blocking ones before triggering rebase,
    validation, abort, or human escalation logic.

- `src/awf/runtime/merge_eligibility.py`
  - If useful, add a tiny helper for classifying stale reason codes as blocking
    vs advisory, and test it here to keep merge-gate callers consistent.

- `apps/console/lib/types.ts`, `apps/console/lib/merge-queue-format.ts`,
  `apps/console/lib/merge-queue-format.test.mjs`, and possibly
  `apps/console/components/console-dashboard.tsx`
  - Update console types and summaries to display advisory stale findings as
    advisory context, not as blocking stale work.
  - Keep existing stale display behavior for blocking reasons.

- No expected migration unless implementation chooses a durable DB column for
  `severity`/`blocks_merge`. Preferred first pass is computed compatibility
  properties keyed by reason code to keep the patch smaller and avoid schema
  churn.

## Tests To Write First

Write or update failing tests before implementation.

- `tests/unit/service/test_staleness.py`
  - Add a pure `evaluate_staleness` test where a candidate owns
    `docs/awf-plans/**`, the target advanced only by
    `docs/awf-plans/ws_other.md` or
    `docs/awf-plans/ws_other.conformance.json`, and the result contains only
    an advisory finding with no blocking stale reason.
  - Add a service refresh test showing plan-artifact-only target changes create
    an active advisory finding but leave `MergeCandidate.stale` false and
    `candidate.stale_reason` unset when validation is otherwise satisfied.
  - Add a source-overlap regression showing `src/...` owned-path overlap still
    emits blocking `STALE_OVERLAP`.
  - Add a mixed regression where changed paths include a plan artifact and a
    source overlap; the plan artifact remains advisory, but the source overlap
    blocks and the candidate is stale.

- `tests/unit/api/test_merge_queue.py`
  - Add a queue/API regression where plan-artifact-only target branch changes
    leave the queue item mergeable:
    `merge_blocker_reason == "ready_to_merge_or_waiting_for_github"`,
    `required_next_action is None`, and `readiness.stale is False`.
  - Assert the advisory finding is still returned with explicit fields such as
    `severity == "advisory"` and `blocks_merge is False`.
  - Add or extend a mixed plan+source test showing the queue still reports
    `merge_blocker_reason == "stale"` because of the source blocker, while both
    advisory and blocking findings remain visible.

- `tests/unit/runtime/test_merge_eligibility.py`
  - Add helper-level tests that advisory stale reason codes do not require a
    stale recovery action, while existing stale codes remain blocking.

- `tests/unit/runtime/test_pr_monitor_runner.py`
  - Add a focused merge-gate regression, if feasible, proving an active
    advisory stale reason alone does not dispatch rebase/validation recovery or
    set `candidate.stale`.

- `tests/unit/api/test_stale_reasons.py`
  - Update response-shape coverage so stale reason payloads include the new
    advisory/blocking fields and existing blocking reasons default to blocking.

- Console tests, if console files are touched:
  - `apps/console/lib/merge-queue-format.test.mjs`: add a case showing
    advisory stale reasons are counted/displayed separately from blocking stale
    reasons, and do not make the stale summary read like a required recovery.

## Implementation Sequence

1. Add the failing service-level tests for pure staleness evaluation and
   persistence behavior.
2. Add the failing API/merge-queue tests that assert advisory findings are
   visible but not blocking.
3. Add merge eligibility and PR monitor tests if the helper/filtering is needed
   outside the API route.
4. Implement the smallest staleness model change:
   - introduce an advisory reason code, e.g.
     `ADVISORY_PLAN_ARTIFACT_OVERLAP`;
   - add `blocks_merge`/`severity` to `StalenessFinding`;
   - classify `docs/awf-plans/**` target changed paths as advisory;
   - compute candidate stale state from blocking findings only.
5. Update API schemas and route logic to expose all findings but choose
   required actions from blocking findings only.
6. Update PR monitor stale-reason selection to ignore advisory-only reasons.
7. Update console types/summaries if the API adds new response fields consumed
   by the console.
8. Run narrow tests, then the requested broader validation.

## Risks

- Advisory rows in the existing `stale_reasons` table must not accidentally
  drive merge recovery through older call sites that still use the first active
  stale reason. The PR monitor and merge queue route need explicit filtering.
- If only `evaluate_staleness` changes, non-lenient tasks may still become
  stale via the default `STALE_TARGET_ADVANCED` path. The implementation must
  suppress that default only when all target changed paths are plan artifacts.
- Existing API consumers may assume every active `stale_reasons` row blocks
  merge. Adding explicit `severity`/`blocks_merge` fields should make the new
  contract clear while preserving existing fields.
- The preferred no-migration approach depends on advisory reason codes being
  enough to classify old and new rows. If future arbitrary advisory stale
  reasons are required, a durable DB column and Alembic migration may be needed.
- Console updates may be required to prevent advisory context from looking like
  an operator-required stale recovery.

## Assumptions

- `docs/awf-plans/**` is AWF-generated workspace plan/conformance artifact
  space; changes under that tree are advisory-only for staleness unless other
  changed paths trigger real blocking policy.
- Source/test/dependency/build/schema/migration changes keep existing blocking
  semantics.
- Launch-time owned-path overlap is already advisory via
  `workspace.owned_path_overlap_risk` events and should not be converted into a
  workspace admission blocker.
- Existing stale reason rows without advisory reason codes should be treated as
  blocking for backward compatibility.

## Non-Goals

- Do not change branch management, pushing, PR creation, or merge monitor
  ownership.
- Do not relax validation tier, coverage, policy finding, queue ordering, or
  canonical-attempt gates.
- Do not make all docs changes advisory; this fix is limited to AWF
  plan/conformance artifacts and does not exempt ordinary docs overlaps unless
  existing policy already does.
- Do not change launch-time owned-path overlap warnings except to preserve their
  current warning-only behavior.
- Do not introduce broad stale-policy refactors beyond the targeted
  advisory/blocking split needed for this P0.
