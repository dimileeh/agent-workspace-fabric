## Problem statement

`_run_pre_push_validation_fix_pass` in
`src/awf/runtime/pr_monitor_runner/pre_push_validation.py` handles the case where a
fix-pass agent self-commits its repair (so `_commit_dirty_worktree` finds a clean
worktree and returns `committed=False`).

- PR #407 (issue #406): if the new HEAD **advances** on top of `fix_start_head`
  (`git merge-base --is-ancestor fix_start_head current_head` exits 0), it is accepted
  as a committed repair instead of being rolled back.
- Regression `e05b47b6c`: if HEAD moved **but does not descend** from `fix_start_head`
  (e.g. `git reset --hard HEAD~1`), it is rolled back to `fix_start_head` so we never
  push the wrong revision.

The deferred gap: a fix-pass agent that self-commits via `git commit --amend` (or
otherwise rewrites the tip) produces a HEAD that is **not** a descendant of
`fix_start_head`, so today it is wrongly rolled back — dropping a valid repair.

**The trap (must not reopen):** `git commit --amend` and the work-dropping
`git reset --hard HEAD~1` + recommit are **topologically indistinguishable** — both
leave HEAD as a new commit whose parent is `fix_start_head`'s parent. So topology alone
(merge-base / ancestry) cannot separate "good amend" from "bad work-dropping recommit".

## Locked design — tree-preservation check (not a topology tweak)

Accept a non-descendant rewritten self-commit **only when its resulting tree preserves
the work that was in `fix_start_head`'s tree**; otherwise keep rolling back.

Discriminate by **tree content** using a three-way merge:

- `git merge-tree --write-tree <current_head> <fix_start_head>` performs a real
  three-way merge using the merge-base of the two commits. In **both** the amend and
  the reset+recommit case, `current_head` and `fix_start_head` share the same parent
  (`fix_start_head`'s parent), so the merge-base is exactly that shared parent — the
  correct base for asking "does `current_head` still contain `fix_start_head`'s work?".
- Compare the merged tree OID (first stdout line on a clean merge, exit 0) to
  `current_head`'s own tree OID (`git rev-parse <current_head>^{tree}`).
  - **Equal trees ⇒ work preserved (amend):** `current_head` already contains every
    change `fix_start_head` introduced; re-merging `fix_start_head` adds nothing.
    → accept.
  - **Different trees ⇒ work dropped (reset+recommit hole):** re-merging
    `fix_start_head` would re-introduce content `current_head` is missing.
    → reject, fall through to rollback.
  - **Merge conflict (non-zero exit) or any merge-tree/rev-parse failure or empty
    output ⇒ treat as NOT preserved** → rollback. Rollback restores the known-good
    `fix_start_head`, so defaulting to rollback on any ambiguity is the safe choice and
    never pushes a wrong revision.

Git 2.39.5 is present in the workspace and supports `merge-tree --write-tree`.

Ordering: keep the cheap `_head_descends_from` (advance, #406) check first; only run the
tree-preservation merge for the non-descendant rewrite case (#408). Both accept paths
share the existing `_cleanup_committed_pre_push_validation_fix_pass` + `return True`
behavior.

## Risks & mitigations

- **Reopening the work-dropping hole.** Mitigated by the tree-OID equality check: a
  reset+recommit that drops `fix_start_head`'s work yields a re-merged tree ≠
  `current_head`'s tree → rejected. The extended regression test (#2) locks this in.
- **Edge: merge-base ≠ shared parent.** In the amend/reset cases analyzed, both commits
  share `fix_start_head`'s parent, so merge-base is that parent. If git ever picks a
  different merge-base, an amend that genuinely preserves work still yields
  merged_tree == current_tree (its tree already contains everything reachable), and any
  divergence still defaults to rollback. Safe either way.
- **`merge-tree --write-tree` availability.** Requires git ≥ 2.38; workspace has 2.39.5.
  Non-ok exit (older git / unexpected failure) is treated as "not preserved" → rollback,
  preserving today's safe behavior rather than crashing.
- **stdout parsing.** On a clean merge the tree OID is the first stdout line; parse via
  `splitlines()[0].strip()` and guard empty output → `False`.
- **Catch specifics / no hidden failures.** New helper uses explicit `result.ok` checks
  and early `return False`; no bare `except`, no swallowed reason codes; existing rollback
  logging/reason-code flow is preserved end-to-end.

## Assumptions

- `git_worktree_command` builds an argv list (no shell), so `^{tree}` needs no escaping.
- `self._deps.runner.run` returns a result with `.ok`, `.stdout`, `.returncode` (matches
  `_head_descends_from` usage and `FakeCommandRunner`).
- A fix-pass amend keeps `current_head`'s parent equal to `fix_start_head`'s parent
  (true for `git commit --amend` without extra history surgery).
