# Implementation Plan: Durable PR Monitor Operation Visibility

## Scope

Implement the remaining P0 PR monitor observability slice by making important
PR monitor states visible as durable `operations` rows, listed through the
existing operation endpoints and summarized in the console Operations panel.

The change should preserve the existing API response shape. New state should
travel through existing operation fields (`type`, `status`, `payload`, `result`,
and the already-derived audit fields such as `owner`, `source`, `action`,
`reason`, and `reason_code`) rather than adding response fields.

## Intended Files and Modules to Touch

### Runtime and DB

1. `src/awf/db/enums.py`
   - Add one generic operation type, likely `monitor_state = "monitor_state"`.
   - Keep the database schema unchanged because `operations.type` is already a
     string column, not a database enum.
   - Avoid adding many one-off operation types; use `payload.action` to
     distinguish `grace_wait`, `check_wait`, `merge_ready`, `merge`,
     `completed`, and similar monitor states.

2. `src/awf/runtime/pr_monitor_operations.py`
   - Add small helper(s) for monitor transition operations that reuse existing
     redaction and finish semantics:
     - build a monitor transition payload with `owner="pr_monitor"`,
       `source="pr_monitor"`, `action`, `requested_action`, `reason`,
       `reason_code`, PR metadata, head/base SHA metadata, branch metadata, and
       optional `extra` fields such as `wait_seconds` or blocker details;
     - begin a running operation for active waits/side effects;
     - record an immediate succeeded operation for instantaneous monitor
       milestones;
     - finish running wait operations with `succeeded` or `failed` while
       preserving structured `error_code` / `error_message`.
   - Reuse `redact_monitor_operation_value` for payloads and results.

3. `src/awf/runtime/pr_monitor_runner.py`
   - Instrument the monitor runner at the existing action boundaries:
     - `WaitForCI`: create a running `monitor_state` operation with
       `action="check_wait"` before sleeping; finish it after the sleep.
     - Initial review grace in `_handle_merge_gate_blocker`: create a running
       `monitor_state` operation with `action="grace_wait"` before sleeping;
       include stale deferral fields when grace is delaying stale recovery.
     - Existing comment handling, sync-base, CI repair, human wait, validate-only
       recovery, and rebase-only recovery already create operation rows; keep
       those paths and ensure their payloads remain concise and monitor-owned.
     - Merge queue / reviewer settle waits: record `monitor_state` wait
       operations where the monitor is merge-ready but deliberately sleeping or
       waiting for an older candidate/reviewer window.
     - Merge readiness: record an immediate `monitor_state` operation with
       `action="merge_ready"` after comments, checks, freshness, policy, and
       queue gates are clean and before entering the serialized merge section.
     - Merge execution: record a running `monitor_state` operation with
       `action="merge"` around the GitHub merge attempt; finish with
       `merge_sha` on success or a structured error on non-transient failure.
     - Completion: record an immediate `monitor_state` operation with
       `action="completed"` for both successful merge completion and
       `ShortCircuitCompleted`.
   - Keep operation creation best-effort only where losing observability must
     not prevent monitor progress, but do not hide actual merge/recovery
     failures behind retries.

     - `GET /v1/workspaces/{workspace_id}/operations`.
   - Include a `?type=monitor_state` filter test once the enum value exists.
   - Add/keep a legacy compatibility assertion for operations with `payload=None`

5. `src/awf/api/routes/operations.py`, `src/awf/service/workspaces.py`, and

   - Touch only if tests expose that the new enum value is not accepted by the

     a small compatibility fix.

### Console

6. `apps/console/lib/types.ts`
   - Extend `Operation` to include the optional fields already emitted by the
     API schema: `owner`, `source`, `action`, `pr_number`, `pr_url`,
     `source_head_sha`, `source_base_sha`, `reason`, `reason_code`,
     `failure_code`, `failure_message`, `log_stream_refs`, and
     `log_stream_ids`.
   - Keep all new fields nullable/optional enough for legacy rows.

7. `apps/console/lib/operation-format.ts` (new)
   - Add pure formatting helpers for concise operation display:
     - title/label, for example `Monitor: waiting for checks`,
       `Monitor: initial review grace`, `Monitor: ready to merge`,
       `Monitor: merging`, `Monitor: completed`, `Validate-only recovery`,
       `Comment repair`;
     - detail line using `reason`, `reason_code`, PR number, wait seconds, stale
       reason, and short SHAs when present;
     - fallback behavior for legacy rows with no payload/action/reason.

8. `apps/console/lib/operation-format.test.mjs` (new)
   - Add Node test coverage for monitor operation labels and legacy fallback
     formatting before wiring the component.

9. `apps/console/lib/types-contract.test.ts`
   - Add a type-level assertion that the console `Operation` type includes the
     API-derived monitor fields as nullable/optional fields.

10. `apps/console/components/console-dashboard.tsx`
    - Update `OperationsPanel` to use `operation-format` helpers.
    - Show concise monitor entries with:
      - primary label from action/type;
      - status badge;
      - timestamp;
      - short operation id;
      - compact detail/reason line;
      - error/failure line using `failure_message ?? error_message`.
    - Keep the existing `No operations recorded.` empty state for legacy
      workspaces with no operation rows.

## Implementation Approach

1. Add `OperationType.monitor_state` and the failing API filter test.
2. Add monitor operation helper tests, then implement the smallest helper
   surface in `pr_monitor_operations.py`.
3. Instrument the runner in narrow slices:
   - grace wait;
   - check wait;
   - merge-ready / merge / completed;
   - queue/reviewer waits.
4. After each slice, run the focused runtime test(s) for that slice.
5. Update exact-list assertions in existing tests only where new observability
   rows are expected by the acceptance criteria.
6. Add console formatting tests and helpers, then wire `OperationsPanel`.
7. Run the required Python and console validation commands.

## Risks

- Operation volume can grow if every poll creates a row. Mitigation: record the
  important wait spans requested by the task, keep payloads compact, and avoid
  adding per-log-line operations.
- Some existing tests assert exact operation lists. Those tests need filtering
  or updated expectations so they continue to verify their original invariant
  while allowing observability rows.
- A monitor crash during a wait could leave a `monitor_state` row in `running`.
  That is still more truthful than having no durable state, but stale-running
  monitor operation cleanup is not part of this slice.
- Adding an enum value changes the OpenAPI enum set for operation type filters.
  This is additive and should not break existing clients, but clients with
  closed local enums may need to tolerate the new string.
- Console formatting must not assume payload fields exist; old rows and
  operator-created rows can have `payload=null` or non-monitor payloads.

## Assumptions

- `operations.type` remains a free string column, so no migration is needed for
  `monitor_state`.
- Existing operation list endpoints are the intended API surface; no new route
  is needed.
- The API already serializes derived audit fields from operation payloads, and
  this task should use those fields instead of adding new response fields.
- Existing durable operation paths for `comment_repair`, `sync_base`,
  `ci_repair`, `human_wait`, `validate_only`, and `rebase_only` count toward
  the requested monitor observability once the console can summarize them.
- The console operation panel is workspace-scoped and already handles the
  no-operation legacy case with `No operations recorded.`

## Explicit Non-Goals

- Do not add database migrations or change the `operations` table shape.
- Do not add new operation list endpoints or change existing response envelope
  shape.
- Do not build a full monitor timeline UI; this slice only improves the
  existing Operations panel.
- Do not change PR monitor decision policy, merge eligibility, review grace
  semantics, retry behavior, or merge queue ordering.
- Do not implement stale-running operation cleanup.
- Do not lower coverage, quality gates, or workspace validation requirements.
- Do not switch branches, push, rebase, force-push, manually merge PRs, or
  commit during the planning phase.
