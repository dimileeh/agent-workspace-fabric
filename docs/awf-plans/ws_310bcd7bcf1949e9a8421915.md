# Implementation Plan: Coverage-Wrapped Pytest Failure Classification

## Goal

Implement the narrow reschedule-required slice for workspace `ws_0d9b0d2e6b1d48149c0c5291`: when AWF runs pytest through a coverage command, classify real pytest/test failures separately from true coverage-threshold failures. If coverage is already at or above the configured threshold, AWF should guide the agent to fix the failing tests, while still preserving observed coverage facts. If coverage is below threshold, preserve current coverage-failure behavior. If both are true, surface both facts and make the primary action fix tests first.

This is limited to validation/result classification and retry guidance. It does not implement provider circuit breakers, delayed fallback, or fallback attempts.

## Current Code Context

- `src/awf/runtime/validation.py`
  - `ValidationRunner._collect_coverage()` executes `profile.validation.coverage.command` and appends the command result to validation results.
  - `_coverage_reason_code()` currently returns `COVERAGE_COMMAND_FAILED` when a coverage command exits non-zero even if a usable coverage percentage was parsed and meets the threshold.
  - `ValidationCoverageResult.as_metadata()` stores coverage facts, including existing gap metadata, under `ValidationRun.log_stream_refs.coverage` through the executor.
  - `ValidationResult.first_failure` currently prefers command failures before coverage failure, but `_validation_run_reason_code()` in the executor currently prioritizes failed coverage over command failures.

- `src/awf/control/executor.py`
  - `_validation_run_reason_code()` chooses the persisted validation run reason code.
  - `_validation_run_coverage_metadata()` forwards coverage facts into validation run and operation metadata.
  - `_validation_failure_message()` builds the operator-visible failure message.
  - The validation fix loop builds `ValidationFixContext` and calls `build_fix_prompt()` for retry guidance.

- `src/awf/control/validation_fix_cycle.py`
  - `ValidationFixContext` carries command output tails and coverage fields into retry prompts.
  - `build_fix_prompt()` currently includes coverage context but has no structured failing-test list.

- `src/awf/api/validation_runs.py` and `src/awf/api/schemas.py`
  - Validation summaries expose coverage percent, threshold, status, reason code, and gaps.
  - There are no first-class fields for failing pytest node IDs or fallback failing-test evidence.

## Implementation Steps

1. Add failing-test evidence parsing in `src/awf/runtime/validation.py`.
   - Prefer pytest summary lines beginning with `FAILED ` or `ERROR `.
   - Extract node IDs conservatively; do not parse arbitrary coverage table rows as tests.
   - Cap node IDs and evidence to keep metadata small.
   - Add unit tests before implementing the helper.

2. Extend `ValidationCoverageResult` metadata.
   - Add defaulted fields for failing-test node IDs/evidence.
   - Include them in `as_metadata()` only when non-empty.
   - Preserve existing metadata keys and coverage gap behavior.

3. Split coverage policy from test command failure classification.
   - In `_collect_coverage()`, parse percent, gaps, and pytest failure evidence from the same stdout/stderr paths.
   - If command returned non-zero with pytest evidence and coverage meets threshold, treat coverage policy as OK and command failure as `PYTEST_TEST_FAILURE`.
   - If command returned non-zero with pytest evidence and coverage is below threshold, preserve `COVERAGE_BELOW_THRESHOLD` in coverage metadata while making the command/primary validation reason test-focused.
   - If command returned non-zero with no pytest evidence, keep existing `COVERAGE_COMMAND_FAILED` behavior.

4. Update executor classification and messages.
   - Prefer `PYTEST_TEST_FAILURE` in `_validation_run_reason_code()` when coverage metadata has failing-test evidence.
   - Add a helper to format failing-test evidence for `_validation_failure_message()`.
   - Keep the existing coverage-only message exactly or very close when there is no failing-test evidence.

5. Update retry prompt context.
   - Add failing-test fields to `ValidationFixContext`.
   - Populate them from `val_result.coverage` in the executor.
   - Render a concise failing-tests block before coverage context in `build_fix_prompt()`.

6. Update API-visible summary extraction.
   - Add schema fields with default empty lists.
   - Extract fields from persisted metadata safely, ignoring malformed non-list values.
   - Reuse the same fields in validation summary and provenance item responses.

7. Keep persistence additive.
   - Store new details in existing JSON metadata under `log_stream_refs.coverage`, and in operation results through the existing coverage dict path.
   - Avoid database migrations unless implementation proves impossible without them.

## Risks and Assumptions

- Assumption: the narrow target is explicit AWF coverage commands such as `pytest --cov=awf --cov-report=term`, where pytest failures and coverage facts appear in the same stdout/stderr artifacts.
- Assumption: adding optional fields to API response models is acceptable JSON/API compatibility because existing keys are preserved and new fields default to empty lists.
- Assumption: `PYTEST_TEST_FAILURE` is an acceptable new structured reason code for the primary failure. If the implementation finds an existing test-failure reason code, use that instead.
- Risk: pytest output formats vary. The parser must be conservative: prefer clear `FAILED tests/...::node` and `ERROR tests/...` lines, and fall back to capped evidence rather than over-classifying unrelated command failures as pytest failures.
- Risk: changing primary reason selection can affect operation error codes and metrics. Tests should assert coverage-only failures still report `COVERAGE_BELOW_THRESHOLD`.
- Risk: metadata growth in `log_stream_refs.coverage`. Cap failing test IDs and evidence to a small bounded list.
- Risk: baseline coverage ratchet interacts with below-threshold coverage. Keep current baseline-debt behavior for coverage policy while preserving failing-test evidence in metadata.
- Risk: console visibility may depend on existing API fields only. Additive summary/provenance fields should be enough for console-visible data without implementing a frontend slice.
