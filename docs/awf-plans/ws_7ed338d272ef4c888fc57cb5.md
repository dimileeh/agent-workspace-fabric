## Problem (verified in tree)

`PullRequestCreator.push_and_open` (`src/awf/runtime/pr_creator.py:95`) does a
forge-neutral `git push` (lines 129–164) then a **GitHub-only** `gh pr create`
(lines 174–208) and extracts the URL with `_PR_URL_PATTERN` (a `github.com/.../pull/\d+`
regex, line 34). #443 opened the executor forge gate for BitBucket Cloud, so a BitBucket
*feature* workspace now clears `unsupported_forge_error` and would reach `push_and_open`.
Today it is stopped earlier by `new_pr_unsupported_forge_error`
(`src/awf/control/executor/forge_gate.py:57`, called at `execution_flow.py:325`), which
fails BitBucket new-PR creation fast with `PR_CREATE_FORGE_NOT_SUPPORTED`.
`BitBucketClient.create_pull_request` already exists
(`src/awf/common/bitbucket_client.py:357`) but is bypassed.

To let a BitBucket workspace actually open its PR we must (a) route the PR-open step
through the resolved `ForgeClient` instead of `gh pr create`, and (b) stop tripping the
new-PR fail-fast gate.

## Verified facts the design relies on

- `ForgeClient.create_pull_request(*, repo: RepoRef, base, head, title, body) -> str`
  — `src/awf/common/forge.py:147`.
- `GitHubClient.create_pull_request` runs `gh pr create --repo repo.slug() --base --head
  --title --body` and returns `result.stdout.strip()`; on failure raises
  `GitHubClientError(operation="gh pr create", returncode, stderr)` with `stderr`
  redacted in the constructor — `src/awf/common/github_client.py:1191`, `:49`.
- `BitBucketClient.create_pull_request` returns the PR web URL (`links.html.href`); on
  failure raises `BitBucketClientError(operation, status: int|None, body, reason_code)`
  with `body` redacted in the constructor — `src/awf/common/bitbucket_client.py:357`, `:178`.
  Note the field names differ from GitHub: `status` (not `returncode`), `body` (not `stderr`).
- `RepoRef.from_url` parses ssh/https/bare-slug and host-detects the forge —
  `src/awf/common/github_client.py:358`.
- `make_forge_client(forge, runner)` is I/O-free for github (`GitHubClient(runner)`);
  for bitbucket it calls `BitBucketClient.from_env()` (reads env, no network) and supports
  `async with ... as client:` via `aclose`/`__aenter__`/`__aexit__` — `forge.py:274`, `:183`.
- Caller wiring pattern to reuse (from #443): `make_forge_client(concrete_forge_for_repo(
  profile.forge, repo_url), self._runner)` — see `service/worker.py:230`,
  `monitor_handoff_sync.py:251`.
- The executor `execute()` body is one function (`execution_flow.py:131`, `self: Any`); at
  the push step (~1208) `profile` (WorkspaceProfile, set at `:283`), `ws`, `workspace_id`,
  `self._runner`, `self._pr_creator` are all in scope. `ws.repo_url` carries the repo URL.
- The existing `except PullRequestError` / `except Exception` handlers around the
  `push_and_open` call (`:1243`, `:1293`) already map failures to `infrastructure_failure`
  and audit via `exc.operation != "git push"`.

## Change detail

### A. `src/awf/runtime/pr_creator.py`

- Add imports: `from awf.common.forge import ForgeClient`,
  `from awf.common.github_client import GitHubClientError, RepoRef`.
  Keep `import re` (still used by `_URL_CREDENTIAL_PATTERN`/`_redact_credentials`).
- **Remove** `_PR_URL_PATTERN` (line 34) and its doc comment — D7: no github-shaped regex.
- `push_and_open(...)` signature (D1 = per-call injection, keep `PullRequestCreator`
  forge-agnostic/stateless — NOT constructor injection): add two keyword-only params after
  `body`:
  - `forge_client: ForgeClient`
  - `repo_url: str` — needed to build the `RepoRef`; the locked `RepoRef.from_url(remote_url
    or repo_url)` expression references it (`remote_url` is `None` on the new-PR path, so this
    is `ws.repo_url` in practice). Required keyword so typing stays sound.
- Keep unchanged: pre-push diagnostics (`_log_pre_push_diagnostics`), the `git push` block
  (129–164), the `existing_pr_url` reuse early-return (166–172). The reuse path returns
  BEFORE the create step → it must never call `forge_client.create_pull_request`.
- Replace the `gh pr create` block (174–208) with:
  ```python
  from awf.common.bitbucket_client import BitBucketClientError  # lazy: avoid httpx on hot path
  repo = RepoRef.from_url(remote_url or repo_url)
  try:
      url = await forge_client.create_pull_request(
          repo=repo, base=base_branch, head=branch_name, title=title, body=body,
      )
  except GitHubClientError as exc:
      raise PullRequestError(operation=exc.operation, returncode=exc.returncode,
                             stderr=exc.stderr, head_sha=head_sha) from exc
  except BitBucketClientError as exc:
      raise PullRequestError(operation=exc.operation,
                             returncode=exc.status if exc.status is not None else 0,
                             stderr=exc.body, head_sha=head_sha) from exc
  if not url:                                  # D7: empty-string guard only, no regex
      raise PullRequestError(operation="create_pull_request (no URL)", returncode=0,
                             stderr="forge returned an empty PR URL", head_sha=head_sha)
  _log.info("pr.created", branch=branch_name, url=url)
  return PullRequestResult(url=url, branch=branch_name, head_sha=head_sha)
  ```
  - D2 error mapping: catch the two **specific** client errors and re-raise as
    `PullRequestError`, preserving structured `returncode`/`status` + already-**redacted**
    `stderr`/`body` + `head_sha`. Preserve `exc.operation` (e.g. `"gh pr create"` /
    `"bitbucket create_pull_request"`) — never `str(exc)` — so the executor's
    `exc.operation != "git push"` audit branch keeps working and nothing unredacted leaks.
  - `BitBucketClientError` imported lazily inside the method (mirrors `forge.make_forge_client`)
    so the GitHub path keeps its `httpx`-free import cost; it must be imported before the
    `try` so the `except` can name it.
- Update the module + class docstrings (currently GitHub/`gh`-specific) to describe
  forge-neutral PR creation via the injected `ForgeClient`.
- GitHub repo-targeting preserved: `GitHubClient.create_pull_request` uses `--repo
  repo.slug()` against the just-pushed `head=branch_name` on origin — behavior-equivalent to
  the old cwd-based `gh pr create`.

## Risks & mitigations

- **Dead code / scope tension (flag for review).** Removing the `new_pr_unsupported_forge_error`
  *call* leaves the function in `forge_gate.py` and `PR_CREATE_FORGE_NOT_SUPPORTED` in
  `forge.py` unused by production. They stay **covered** by `test_executor_forge_gate.py`
  (function tested directly) and the reason catalog stays valid, so no gate fails. Deleting
  them cleanly would touch `forge_gate.py` / `forge.py` / `test_executor_forge_gate.py` +
  regenerate the reason catalog + `doctor/reasons.py` — out of the locked "ONLY pr_creator.py
  + execution_flow.py + their tests" scope and risks conflict with sibling Cluster B.
  Decision: leave them; recommend a follow-up issue to remove the now-dead gate.
- **Most executor-test `push_and_open` fakes use `**kwargs`/`**_kwargs`** (verified across
  `test_executor_error_paths_part_00*.py`, `..._recovery_part_002.py`, `test_final_polish.py`)
  so the new `forge_client`/`repo_url` kwargs flow through harmlessly. Mitigation: scan every
  fake; update any with an explicit signature that would reject the extra kwargs.
- **`make_forge_client` for bitbucket calls `from_env()`** which can raise
  `BitBucketClientError` (missing creds) at the reuse path too. Mitigation: it is inside the
  existing `try`, so it degrades to `infrastructure_failure` rather than an uncaught crash —
  consistent with the monitor-handoff wiring.
- **GitHub URL behavior change:** old code regex-extracted the URL tolerating leading noise;
  new code uses `GitHubClient`'s `stdout.strip()` (D7). Real `gh pr create` prints the URL as
  the sole stdout line, so this is behavior-equivalent in practice. Documented as a deliberate
  D7 decision; the leading-noise test is removed, not preserved.
- **`httpx` import cost on the GitHub hot path:** `BitBucketClientError` imported lazily inside
  `push_and_open`, mirroring `forge.make_forge_client`.

## Assumptions

- `ws.repo_url` is always populated for a workspace reaching the push step (it is used to
  resolve the forge upstream and by `concrete_forge_for_repo`).
- `profile` is bound (set at `execution_flow.py:283`) on every path reaching the push step
  (profile setup at `:358` already depends on it).
- BitBucket credentials are provided via env for a real BitBucket workspace; unit tests
  monkeypatch `make_forge_client` and never hit the network or real `from_env()`.
