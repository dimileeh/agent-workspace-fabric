# AWF Init Onboarding Slice Plan

## Goal

Create a narrow P1 onboarding operator slice that adds a first-run `awf init` command and smoke-workspace guidance, building on existing onboarding primitives so first-time users get clear next steps before touching services or creating workspaces.

## Intended Files / Modules to Touch

- `src/awf/cli/main.py`
  - Add new root command `awf init`.
  - Keep command behavior local-first: preview/onboarding + local prerequisite checks; do not call the REST API.
  - Use existing `awf.profiles.onboarding.preview_project_onboarding` and `awf.profiles.onboarding.write_workspace_profile` where practical.
  - Reuse existing local prerequisite helpers: `awf.service.status.collect_service_status` and `awf.service.doctor.collect_doctor_report`/`render_doctor_pretty`.
- `src/awf/profiles/onboarding.py`
  - Add any minimal helper object/renderer needed for init-specific output (e.g., structured guidance payload, smoke workspace command hints) while staying compatible with current onboarding models.
- `tests/unit/cli/test_profile_init.py`
  - Extend for `awf init` behavior and idempotence guidance coupling if preferred.
- `tests/unit/cli/test_init.py` (new)
  - Add dedicated command-level behavior tests for `awf init`.
- `tests/unit/profiles/test_project_onboarding.py`
  - Add/adjust unit checks for non-Aira defaults and smoke request generation shape expected by init guidance.
- `docs/PROJECT_ONBOARDING.md`
  - Add `awf init` first-run path and copy-paste next-steps text, including explicit references to `awf profile init`, `awf profile preview`, and the smoke request flow.

## Tests To Write First (Strict TDD)

1. CLI command existence and safety
   - `tests/unit/cli/test_init.py`
     - `test_init_command_exists`
     - `test_init_is_safe_by_default_and_idempotent`
       - Running twice should return zero exit and no `.awf/workspace.yml` mutations by default.
2. `awf init` plain-language guidance and onboarding pointers
   - `tests/unit/cli/test_init.py`
     - `test_init_prints_clear_next_steps`
       - Output must include `awf profile init`, `awf profile preview`, and `--include-smoke-request` guidance.
3. Local prerequisite check integration
   - `tests/unit/cli/test_init.py`
     - `test_init_runs_status_and_doctor_checks`
       - Stub/mocks `collect_service_status` and `collect_doctor_report` and assert both are invoked as part of init flow.
     - `test_init_reports_local_prerequisite_failures_without_api_calls`
       - Force fail status and assert command surfaces human-readable output plus non-zero exit handling where appropriate.
     - `test_init_does_not_submit_workspace_request`
       - Patch CLI `_call` and ensure it is not invoked by `awf init`.
4. Onboarding payload/message behavior (smoke path and no Aira assumptions)
   - `tests/unit/profiles/test_project_onboarding.py`
     - `test_smoke_request_uses_generic_profile_when_default`
     - `test_preview_smoke_request_does_not_imply_aira_profile`
   - `tests/unit/cli/test_init.py`
     - `test_init_includes_smoke_workspace_hints`
       - Ensure command points to smoke workspace generation and states it is optional / non-executing.

## Implementation Steps (after tests are red)

1. Add/shape onboarding helper in `src/awf/profiles/onboarding.py` if needed for init output.
2. Add `awf init` root command in `src/awf/cli/main.py` with default idempotent preview behavior and optional explicit write flags if needed.
3. Integrate local status checks via existing service helpers.
4. Compose plain-language output that always includes next-step commands and smoke request guidance.
5. Ensure init command delegates onboarding path work through existing profile-init code and preserves existing preview JSON shape.
6. Extend docs in `docs/PROJECT_ONBOARDING.md`.

## Risks

- Local prerequisite checks can be environment-dependent and flaky; keep output robust even if checks fail or are partially unavailable.
- Guidance text must remain generic and should not assume Aira-specific environment, secrets, or providers.
- Minimal command behavior should avoid over-coupling to profile-preview test fixtures to reduce brittle snapshots.

## Assumptions

- Existing `awf profile init` behavior remains stable and usable for preview/write.
- `awf profile preview` output and onboarding draft model are already representative for first-run guidance.
- Existing local doctor/status helpers are the canonical source for local service readiness checks in CLI.

## Explicit Non-Goals

- No workspace creation, no API submission, and no service launch from `awf init`.
- No GKE implementation.
- No REST API changes in this slice (CLI operator convenience only).
- No MCP parity work.
- No package publication or dependency/version migration.
