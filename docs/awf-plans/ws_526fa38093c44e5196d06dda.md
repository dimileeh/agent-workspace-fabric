## Goal

Add client-integration helpers that register AWF's local stdio MCP server into the
**Claude Code** and **Codex** client config, plus the narrow `awf setup --client …`
dispatch needed after T04. The helpers must: prefer the official client CLI when
present, fall back to structured JSON/TOML parsing, show a diff, write a backup before
mutating, detect/refuse ambiguous conflicts, support `--dry-run`, preserve unrelated
existing client config, and never read/accept/store/return provider tokens.

## Design

### New module: `src/awf/host_setup/clients.py`

A self-contained, mostly-pure helper layer (mirrors `credentials.py` shape). No secret
handling — the only value threaded through is the **env-file path** (a path, never the
file's contents).

Public surface (re-exported from `host_setup/__init__.py`):

- Constants: `KNOWN_SETUP_CLIENTS = ("claude", "codex")`; a `_CLIENT_ALIASES` map
  (`claude_code`/`anthropic` → `claude`, `openai` → `codex`) consistent with the existing
  provider aliasing. Server entry key constant `AWF_MCP_SERVER_KEY = "awf"`.
- `normalize_client(name) -> str` / `normalize_clients(names) -> list[str]` — mirror
  `normalize_provider(s)`; raise `SetupCheckError(reason_code=SETUP_CLIENT_UNKNOWN, details={"client": name, "known_clients": [...]})` for unknown names. (Reused from
  system_checks pattern; lives in `clients.py` to keep client logic together.)
- A `ClientDescriptor` (frozen dataclass): `key`, display `label`, config format
  (`"json"` | `"toml"`), default config path builder (under `home`), the official CLI
  binary name (`claude` / `codex`) and the add-command argv builder, and the desired
  server-entry builder. A `CLIENT_DESCRIPTORS: Mapping[str, ClientDescriptor]` registry.
- `ClientConfigAction = Literal["create", "update", "no_change", "conflict"]`.
- `ClientConfigPlan` (frozen pydantic model or dataclass): `client`, `method`
  (`"official_cli" | "file"`), `config_path`, `action`, `diff` (unified-diff text),
  `backup_path` (only when an existing file would be replaced), `conflict_detail`
  (non-secret), `desired_entry`/`existing_entry` summaries. Carries no token-shaped data.
- `ClientWriteResult` (frozen): `client`, `method`, `config_path`, `backup_path`,
  `action`, `wrote` (bool).
- `build_client_config_plan(client, *, env_file, home, which, now) -> ClientConfigPlan`
  — pure read+compute:
  1. Resolve descriptor + config path. Read existing file via **structured** parse
     (`json.loads` / `tomllib.loads`). Unparseable existing config → `conflict` (ambiguous; refuse) with a non-secret `conflict_detail`.
  2. Compute the desired `awf` server entry from `env_file`.
  3. Diff existing vs. merged desired (preserving unrelated server entries and unrelated
     top-level keys) → unified diff text.
  4. Decide `action`: absent server entry → `create`/`update` (update when the file
     already exists with other content); identical entry → `no_change`; an `awf` entry
     that exists but differs in command/args in an ambiguous way → `conflict`.
  5. Choose `method`: `official_cli` when `which(<cli>)` resolves, else `file`.
- `apply_client_config_plan(plan, *, run, now) -> ClientWriteResult` — performs the
  mutation (never called under dry-run):
  - `conflict` → raise `SetupCheckError(reason_code=CLIENT_CONFIG_CONFLICT)`; no mutation.
  - `no_change` → return result with `wrote=False`.
  - `official_cli` → invoke the add-command argv via `run`; non-zero/None result →
    `SetupCheckError(reason_code=CLIENT_CONFIG_WRITE_FAILED, details={...stderr summary...})`.
  - `file` → back up the existing file first (copy to
    `<path>.awf-backup-<ts>` using injected `now`), then atomic structured write
    (temp file + `chmod 0o600` + `os.replace`, dirs created `0o700`). `OSError` →
    `CLIENT_CONFIG_WRITE_FAILED`.
- `setup_client(client, *, env_file, dry_run, home, which, run, now) -> FirstRunPayload`
  — orchestrator the CLI calls: builds the plan; on `dry_run` returns a payload carrying
  the diff + planned action (no mutation); otherwise applies and returns a success/blocked
  payload. Conflicts/write failures are folded into reason-coded `FirstRunPayload`s via
  the T03 builders (consistent with `setup_commands._reason_coded_payload`).

### `tests/unit/service/test_host_setup_clients.py`

Use fakes/temp dirs; no real `claude`/`codex`/keychain/network. Inject `which`,
`CommandRunner` (capturing fake), `home` (tmp), and a fixed `now` clock.

`build_client_config_plan` (claude=JSON and codex=TOML, matrixed):
- Config file missing → `action="create"`, diff shows the added `awf` server entry, no
  `backup_path`.
- Existing file with an identical `awf` entry → `action="no_change"`, empty/`None` diff.
- Existing file with a **conflicting** `awf` entry (different command/args) →
  `action="conflict"`, non-secret `conflict_detail`, no write planned.
- Existing file with unrelated server entries + other top-level keys → preserved in the
  merged/desired diff; `action="update"`.
- Malformed existing JSON/TOML → `action="conflict"` (ambiguous; refuse).
- `which` resolves the CLI → `method="official_cli"`; otherwise `method="file"`.

`apply_client_config_plan`:
- File-fallback write creates a timestamped backup of the existing file, writes the
  merged config, preserves unrelated entries, leaves perms `0o600`.
- `create` (no prior file) → writes, no backup.
- `conflict` plan → raises `SETUP_CLIENT_UNKNOWN`'s sibling `CLIENT_CONFIG_CONFLICT`; file
  untouched.
- Unwritable path / `OSError` → `CLIENT_CONFIG_WRITE_FAILED`; no partial/temp file left.
- Official-CLI path: fake `run` returns rc=0 → invoked with expected argv, no file write;
  rc≠0 / `None` → `CLIENT_CONFIG_WRITE_FAILED`.

`normalize_client(s)`:
- Canonicalizes aliases; unknown → `SetupCheckError(SETUP_CLIENT_UNKNOWN)` with
  `known_clients` in details; de-dupes while preserving order.

Security:
- Pass an `env_file` path whose name/string contains a token-shaped substring → it is
  redacted in `render_first_run_*` output of the payload.
- The helper never opens/reads the env-file contents (point `env_file` at a file holding a
  token-shaped string; assert it is not read and never appears in plan/payload).
- `setup_client(dry_run=True)` performs no mutation (file unchanged, no backup, `run`
  never invoked).

## Risks & mitigations

- **Codex TOML round-trip fidelity.** `tomllib` is read-only (stdlib); writing TOML needs
  a serializer. Mitigation: write a minimal, deterministic TOML emitter scoped to the
  `[mcp_servers.awf]` table (string/array/int values only) rather than adding a dependency,
  and preserve unrelated content by re-emitting parsed tables; if fidelity for arbitrary
  pre-existing TOML is unsafe, treat unrepresentable existing content as `conflict` and
  defer to the official `codex` CLI / manual edit. Confirm no `tomli-w`/`tomlkit` dep is
  introduced without need (keep core generic).
- **Conflict semantics too strict/loose.** Define "ambiguous conflict" precisely: an
  existing `awf`-keyed server entry whose command/args differ from the desired entry.
  Identical → `no_change`; absent → create/update. Cover each branch with a test.
- **Official CLI side effects.** The official CLI may itself prompt or write elsewhere.
  Mitigation: only invoke it in non-dry-run apply, with a bounded `run` seam; dry-run
  always uses the structured diff path so it stays read-only.
- **Coverage drift.** New module + new branches must be covered by the focused tests
  above; defensive/unreachable branches (e.g. a `Protocol`/lazy-import guard) get a
  justified `# pragma: no cover` rather than hollow tests.
- **Touching shared `setup_commands.py`.** Risk of regressing T04. Mitigation: additive
  `--client` branch that returns before the readiness path; leave existing code paths
  unchanged and keep all current setup tests green.

## Assumptions

- Config locations are `~/.claude.json` (Claude Code) and `~/.codex/config.toml` (Codex),
  per `docs/MCP_SETUP.md`; the helper reads only these known paths (no home-dir scanning).
- The registered server points at the resolved `docker/compose/.env` (source checkout) or
  the packaged/default `.env`, matching `awf mcp serve --env-file` guidance; the env file
  need not exist for a dry-run diff.
- `home`, `which`, `run`, and `now` are dependency-injected for hermetic tests, defaulting
  to real implementations in production (lazy/bounded, like the system-check probes).
- `SETUP_CLIENT_UNKNOWN` is the agreed new reason code; if a reviewer prefers reusing an
  existing code, the change is localized to `clients.py` + rendering/reasons.
