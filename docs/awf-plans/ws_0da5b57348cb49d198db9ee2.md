# Plan: One-Command `awf init` Local Bootstrap For New Engineers

## Objective

Make first-run AWF setup absurdly easy. After installing AWF, a new engineer
should be able to run `awf init` once and have a healthy local control plane:

- Docker availability checked.
- AWF host state directory (`${AWF_HOST_WORK_DIR:-${HOME}/.awf/service}`)
  guidance printed and, when missing, created.
- Safe local defaults written when appropriate (copy `.env.example` to `.env`
  only when `.env` does not exist).
- Local Postgres + migrate + API + worker stack started or validated through
  the existing `awf service bootstrap` mechanism.
- Concise next steps printed (set `AWF_GITHUB_TOKEN`, run
  `awf service status`, optionally `awf init <path>` for project onboarding).

`awf init` already exists today and runs project-onboarding readiness checks
when given a repository path. That behavior must remain compatible. The new
service-bootstrap behavior is selected when `awf init` is invoked without a
path argument (the natural shape of "set up AWF on this machine").

`awf project/profile init`, `awf service bootstrap`, and `awf doctor/status`
must keep their current contracts.

## Intended Files And Modules To Touch

### Production (owned)

- `src/awf/cli/main.py`
  - Make the `path` argument optional on the existing `app.command("init")`
    handler.
  - When `path is None`, run the new service-bootstrap-aware first-run flow:
    1. Resolve service settings.
    2. Run an early Docker availability check (delegating to existing
       `awf service doctor` diagnostic helpers — extract a small reusable
       `docker_diagnostic` if needed; do not duplicate Docker probing).
    3. Compute and ensure the host state directory; print guidance line such
       as `state directory: <path>` and `created: true|false`.
    4. Optionally seed `.env` from `.env.example` (gated by `--write-env`
       which is `True` by default in service-bootstrap mode); never
       overwrite an existing `.env`.
    5. Invoke `awf.service.bootstrap.run_service_bootstrap()` with options
       composed from new CLI flags (`--timeout-seconds`,
       `--poll-interval-seconds`, `--skip-agent-runtime-build`,
       `--provider`).
    6. On bootstrap success, print concise next steps and return exit 0.
    7. On `ServiceBootstrapError`, emit the structured failure dict and
       exit 1, matching the existing `awf service bootstrap` failure
       rendering. Do not print Python tracebacks.
    8. On unknown provider arguments, exit 2 with `error: unknown
       provider(s): <names>` (already supported by
       `validate_provider_names`).
  - Add a small helper such as `_run_init_service_bootstrap()` so the path
    branch and the bootstrap branch each stay short and testable.
  - Keep the existing path-based branch and its return semantics unchanged.
  - Do not import `awf.service.bootstrap` at module top-level; keep imports
    inside the command body, matching the existing pattern.

- `src/awf/cli/main.py` flag surface added to `init` (only active when
  bootstrap mode is selected; ignored or rejected with a clear message if
  combined with a path):
  - `--bootstrap-service / --no-bootstrap-service` (default `True` when no
    path; default `False` when path given).
  - `--write-env / --no-write-env` (default `True` when bootstrap mode;
    default `False` when path given).
  - `--timeout-seconds`, `--poll-interval-seconds`,
    `--skip-agent-runtime-build`, `--provider` (mirroring
    `awf service bootstrap`, same defaults).
  - `--format json|pretty` (mirrors existing service commands; pretty stays
    the default human-friendly view, JSON unlocks scripting).

- `src/awf/profiles/onboarding.py`
  - Read-only in this slice unless tests prove a tiny adjacent change is
    required (for example, separating the bootstrap-mode banner string from
    the project-mode banner). If needed, extract a small shared helper for
    the "next steps" rendering rather than duplicating echo lines in the
    CLI module. Document any such adjacent edit in the PR.

### Tests (owned)

- `tests/unit/cli/test_init.py`
  - Add new tests around the bootstrap-mode behavior (see "Tests To Write
    First").
  - Keep all existing project-onboarding tests passing without modification
    where possible.

- `tests/unit/cli/test_init_bootstrap.py` (new, optional)
  - If `test_init.py` becomes too long, split bootstrap-mode tests into a
    focused new file. Decide during implementation; default is to extend
    the existing file.

### Docs (owned)

- `README.md`
  - In the "Setup" section, promote `awf init` as the recommended local
    bootstrap path:
    1. Install AWF (package-manager path will follow in a separate
       backlog item; for now, `git clone` + `uv sync --extra dev` remains
       the contributor path).
    2. Run `awf init` to bootstrap the local service.
    3. Run `awf service status --format pretty` to verify.
  - Keep "Clone and Install", "Build the Agent Runtime Image", and
    "Configure Environment" subsections accurate, but link them as
    contributor/development setup rather than the primary path.
  - Reference `awf init <path>` in the Project Onboarding section so the
    two `awf init` shapes are explicit.

- `docs/PROJECT_ONBOARDING.md`
  - Add one short note that `awf init` (no path) is the new
    AWF-on-this-machine bootstrap, and `awf init <path>` remains the
    project-onboarding pass.
  - Do not change existing copy-paste prompts unless a test proves a
    documentation drift; this slice is about the local bootstrap, not the
    onboarding prompt set.

### Out Of Owned Paths (do not edit)

- `src/awf/service/bootstrap.py` — orchestration helper. Reuse as-is.
  Tiny adjacent edits are allowed only if a CLI test proves they are
  required (for example, to thread a new option down). Any such edit is
  called out in the PR.
- `src/awf/service/doctor/__init__.py` — readiness helpers. Reuse the
  Docker check by calling `collect_doctor_report` (or a more focused
  helper if introduced). Do not duplicate the Docker probe inside the
  CLI.
- `src/awf/service/status.py` and `src/awf/service/config.py` — used as
  read-only callers.
- `src/awf/api/**`, `apps/console/**`, `migrations/**` — unrelated.

## Tests To Write First

All new tests are unit-level Typer `CliRunner` invocations. They mock
`awf.service.bootstrap.run_service_bootstrap`, `collect_doctor_report`,
and `collect_service_status` rather than touching real Docker or
Postgres. Follow the existing patterns in `tests/unit/cli/test_init.py`
and `tests/unit/cli/test_service_cli.py`.

1. `test_init_without_path_runs_service_bootstrap`
   - Stub `run_service_bootstrap` to return a successful
     `ServiceBootstrapResult`.
   - Invoke `app, ["init"]`.
   - Assert exit code 0, the bootstrap helper was called exactly once,
     the output mentions "AWF init: local service bootstrap", the
     resolved state directory is printed, and concise next steps are
     printed.

2. `test_init_without_path_seeds_env_when_missing`
   - Use `tmp_path` with an `.env.example` and no `.env`.
   - Override the working directory or pass an explicit `--repo-root`
     flag (decide during implementation; the simpler option is
     `monkeypatch.chdir(tmp_path)`).
   - Stub bootstrap as above.
   - Assert `.env` is created with byte-equivalent content to
     `.env.example` and the output mentions `wrote .env`.

3. `test_init_without_path_does_not_overwrite_existing_env`
   - Pre-write `.env` with custom content.
   - Stub bootstrap as above.
   - Assert `.env` is unchanged and the output mentions `kept existing
     .env` (or equivalent), and no error.

4. `test_init_without_path_no_write_env_flag_skips_seeding`
   - With `--no-write-env`, `.env` is not created even if `.env.example`
     exists.

5. `test_init_without_path_runs_docker_availability_check_first`
   - Stub doctor to return a `fail` Docker diagnostic.
   - Assert `run_service_bootstrap` is not called and the CLI exits with
     code 1, output mentions Docker is not available.

6. `test_init_without_path_passes_strict_provider_options_to_bootstrap`
   - Invoke `app, ["init", "--provider", "github", "--provider",
     "opencode"]`.
   - Assert `run_service_bootstrap` was called with
     `options.strict_providers == frozenset({"github", "opencode"})`.

7. `test_init_without_path_passes_skip_agent_runtime_build_flag`
   - Invoke `app, ["init", "--skip-agent-runtime-build"]`.
   - Assert `options.skip_agent_runtime_build is True`.

8. `test_init_without_path_handles_bootstrap_failure_without_traceback`
   - Stub bootstrap to raise `ServiceBootstrapError(reason_code=
     "SERVICE_BOOTSTRAP_TIMEOUT", message="...", last_status=...)`.
   - Assert exit code 1, output is parseable JSON when `--format json`
     is set, includes `reason_code`, and contains no `Traceback`.

9. `test_init_without_path_rejects_unknown_provider_without_traceback`
   - Invoke with `--provider bogus`.
   - Assert exit code 2 and the error message matches the existing
     contract `error: unknown provider(s): bogus`.

10. `test_init_without_path_ensures_state_directory_and_prints_path`
    - Set `AWF_HOST_WORK_DIR` env to a `tmp_path / "state"`.
    - Stub bootstrap as success.
    - Assert the directory exists after the call and the printed output
      contains the resolved absolute path.

11. `test_init_with_path_keeps_existing_project_onboarding_behavior`
    - Re-run a representative existing test (or add a focused regression
      assertion) that proves `awf init <tmp_path>` still emits the
      "AWF init: local onboarding readiness check" banner, suggested
      next steps, and exit code 0 when status/doctor are ok.

12. `test_init_with_path_does_not_invoke_service_bootstrap`
    - Stub `run_service_bootstrap` with an `AssertionError`-raising
      double.
    - Run `app, ["init", str(tmp_path)]`.
    - Assert the bootstrap stub was not called.

13. `test_init_with_path_rejects_bootstrap_only_flags`
    - Invoke `app, ["init", str(tmp_path), "--skip-agent-runtime-build"]`.
    - Assert exit code 2 and a clear error message that bootstrap-only
      flags require the path-less form, OR confirm the flags are
      silently ignored if implementation chooses that path. Decide
      during implementation; pick the option that produces the cleanest
      operator UX, document the choice in the test name.

14. README/docs regression tests in `tests/unit/cli/test_service_cli.py`
    style:
    - `test_readme_recommends_awf_init_for_local_bootstrap` — README
      contains a section that recommends `awf init` as the bootstrap
      path and references both `awf init` and `awf init <path>` shapes.
    - `test_project_onboarding_doc_distinguishes_init_modes` — the
      onboarding doc explicitly explains the no-path vs path forms.

Run these tests first to confirm red, then implement the CLI changes.

## Implementation Steps

1. Write the new failing tests above; confirm reds.
2. In `src/awf/cli/main.py`, change `init` to accept an optional
   `path: Path | None = typer.Argument(None, ...)`. Add the new options.
3. Branch on `path is None`:
   - Bootstrap mode: run the doctor Docker check, ensure/create the
     state directory, optionally seed `.env`, call
     `run_service_bootstrap`, render the result, and emit next-steps
     guidance.
   - Project mode: keep the existing logic verbatim.
4. Add a small `_resolve_state_directory(settings)` helper if it makes
   the state-dir handling testable in isolation; otherwise inline.
5. Update the CLI banner and "next steps" copy to match the bootstrap
   mode (mention `awf service status --format pretty`,
   `export AWF_GITHUB_TOKEN`, and `awf init <path>` for project
   onboarding).
6. Update README setup section and `docs/PROJECT_ONBOARDING.md` per the
   docs scope above.
7. Re-run focused validation, then broader Python validation, then
   coverage.

## Risks And Assumptions

- Assumption: making `awf init`'s `path` argument optional is a
  backward-compatible change. Typer's argument default of `None`
  preserves the existing positional behavior; existing scripts that
  pass a path are unaffected.
- Assumption: the existing `run_service_bootstrap` helper is the right
  bootstrap orchestration boundary. Reusing it avoids duplicating
  Docker stage logic and keeps `awf service bootstrap` and
  `awf init` consistent.
- Assumption: the state directory we surface is
  `${AWF_HOST_WORK_DIR:-${HOME}/.awf/service}`, which matches the
  Compose stack default and the existing README guidance.
- Assumption: `.env` seeding is safe to perform from `.env.example`.
  The example file contains placeholders only and is documented as
  "copy to .env and fill in".
- Risk: the bootstrap call shells out to `docker` and `docker compose`.
  In unit tests we must stub `run_service_bootstrap` directly (matching
  `test_service_bootstrap_cli_*` patterns) so no real Docker is
  invoked.
- Risk: combining bootstrap-only flags with a path could surprise
  callers. Mitigation: either reject the combination with a clear
  error and exit code 2, or document that the flags are accepted but
  ignored in project-onboarding mode. Test 13 above pins whichever
  choice we make.
- Risk: README and onboarding doc churn. Mitigation: the docs slice is
  intentionally tight (one new bootstrap section in README; one short
  paragraph in onboarding doc); doc-regression tests prevent drift.
- Risk: coverage regression. The new branch in `init` adds significant
  code; mirror existing CLI test coverage patterns to keep coverage at
  or above 99% per `.awf/workspace.yml`. If a small slice of the CLI
  branch cannot be covered without a real Docker invocation, lift the
  uncovered piece into a `bootstrap.py` helper that already has
  service-side tests, rather than dropping coverage.
- Risk: scope creep. Tempting adjacent items — package-manager install
  path, smoke-workspace command, MCP parity tools, copy-paste agent
  prompts — are all out of scope for this slice and remain on the P1
  backlog.

## Explicit Non-Goals

- Do not change the behavior or contract of `awf service bootstrap`,
  `awf service status`, `awf service doctor`, `awf profile init`, or
  `awf workspace ...`.
- Do not implement the package-manager install path
  (`uv tool install aira-awf`); leave that as a separate backlog item.
- Do not add a smoke-workspace command, copy-paste onboarding prompts,
  new MCP tools, or new REST endpoints.
- Do not change `.env.example` content, profile templates, or the
  Compose stack composition.
- Do not lower coverage targets or relax lint, mypy, ruff, or test
  rules.
- Do not run real Docker from unit tests. Bootstrap and Docker probes
  must be mocked.
- Do not modify `apps/console/**`, `migrations/**`, or `apps/**`
  unrelated to bootstrap.
- Do not change branch management; AWF owns the branch and PR. Commits
  stay on the current AWF-managed branch.
- Do not manually merge the resulting PR; AWF auto_merge is enabled
  for this non-`main` target branch and will handle merge gating.
