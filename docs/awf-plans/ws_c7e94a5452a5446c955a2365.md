# Plan: Fix #452 — Permanent Docker Pull Errors Must Not Borrow Nearby Timeouts

## Problem Statement

`_log_shows_docker_registry_timeout` in `src/awf/runtime/pr_monitor.py` identifies
transient CI failures worth a silent rerun. It works by:
1. Building a set of "evidence lines" that evidence a Docker pull *failure* (e.g. the
   self-evident `"docker pull failed"` line, a daemon-error line with `/v2/` + timeout marker,
   or a corroborated `"failed to pull image"` line).
2. Declaring a log transient when any registry-timeout phrase (`"context deadline exceeded"`,
   `"request canceled while waiting for connection"`, etc.) sits within
   `_CI_DOCKER_TIMEOUT_EVIDENCE_WINDOW` (2) lines of an evidence line.

**Bug**: `"docker pull failed"` is treated as a self-evident evidence line *regardless* of
whether the pull was temporary (network timeout) or permanent (access-denied, image not found,
manifest unknown). When the pull is permanent, a nearby *unrelated* `"context deadline exceeded"`
from a later test step can sit within the 2-line window of the `"docker pull failed"` line and
cause the failure to be classified transient → `RerunTransientCI`. The image will never appear,
so this burns rerun budget without hope of recovery.

**Canonical bug scenario**:
```
Error response from daemon: pull access denied for myimage
Docker pull failed with exit code 1          ← evidence line (self-evident)
context deadline exceeded                    ← unrelated timeout within window → wrongly rerun
```

**Reviewer's original suggestion** ("require a timeout on the pull-failed line itself") was
rejected because it would break the existing regression
`test_docker_pull_failed_wording_anchors_request_canceled_rerun`, which correctly handles:
```
/usr/bin/docker pull postgres:16
net/http: request canceled while waiting for connection   ← timeout on DIFFERENT line
Docker pull failed with exit code 1                       ← must still → RerunTransientCI
```
The `"request canceled"` line is legitimately within the 2-line window of `"docker pull failed"`
and the pull IS transient (network cancel, not a permanent auth/image error).

## Fix Design

### New constant: `_CI_DOCKER_PERMANENT_PULL_ERROR_MARKERS`

```python
_CI_DOCKER_PERMANENT_PULL_ERROR_MARKERS = (
    "access denied",
    "denied:",
    "no such image",
    "manifest unknown",
    "not found",
    "unauthorized",
    "repository does not exist",
)
```

These are real Docker CLI / OCI registry strings that appear on permanent (non-retryable) pull
errors. They are checked on narrow targets (an evidence line or an adjacent daemon-error line),
so terms like `"not found"` and `"unauthorized"` don't generate false positives in practice.

### New helper: `_evidence_line_is_permanent_pull_failure(index, lines)`

Returns `True` when a pull-failure evidence line (one from `evidence_line_indexes`) represents
a permanent, non-retryable pull error:

1. The evidence line itself contains any permanent marker, OR
2. Any line within `_CI_DOCKER_TIMEOUT_EVIDENCE_WINDOW` of this evidence line that also
   contains `_CI_DOCKER_DAEMON_ERROR_MARKER` ("error response from daemon") has a permanent
   marker.

Condition 2 covers the canonical scenario: the daemon-error line carries the permanent error
text, and `"Docker pull failed with exit code 1"` is a summary on the next line.

### Modification to `_log_shows_docker_registry_timeout`

After collecting `evidence_line_indexes`:

```python
transient_evidence_line_indexes = [
    index
    for index in evidence_line_indexes
    if not _evidence_line_is_permanent_pull_failure(index, lines)
]
if not transient_evidence_line_indexes:
    return False
```

Then in the final `any(...)` expression, replace `evidence_line_indexes` with
`transient_evidence_line_indexes` for the distance check:
```python
and any(
    abs(index - evidence_index) <= _CI_DOCKER_TIMEOUT_EVIDENCE_WINDOW
    for evidence_index in transient_evidence_line_indexes  # was evidence_line_indexes
)
```

`evidence_line_set` (used for the uncorroborated-proximity-exclusion bypass) **stays unchanged**
— it includes all evidence lines (both transient and permanent) and is correct for determining
whether a timeout line is itself a pull-failure evidence line.

## Risks and Assumptions

### Risks

1. **False positive in permanent-marker detection**: terms like `"not found"` could match
   application log lines that happen to appear near a "docker pull failed" line and contain
   "not found". Mitigated by: the check requires the permanent marker to be on a daemon-error
   line (contains `"error response from daemon"`) within the window of an evidence line — a
   very narrow target.

2. **Window boundary change**: using the same `_CI_DOCKER_TIMEOUT_EVIDENCE_WINDOW` (2) for
   both the uncorroborated exclusion and the permanent-failure detection maintains consistency
   but means a daemon error on line N and "docker pull failed" on line N+3 (just outside window)
   would not be flagged as permanent. This is acceptable — if they're more than 2 lines apart,
   the daemon error is likely unrelated to the pull failure line.

3. **New `transient_evidence_line_indexes` empty-check placement**: the early-return `if not
   transient_evidence_line_indexes: return False` must come AFTER the existing `if not
   evidence_line_indexes: return False` check to avoid changing behavior when there are no
   evidence lines at all.

### Assumptions

- Docker CLI consistently prints the daemon error before `"Docker pull failed with exit code 1"`,
  within 2 lines. This is the standard Docker CLI output format.
- The permanent error markers listed are comprehensive for the common OCI registry error strings
  (Docker Hub, GHCR, GCR, ECR, Quay). Additional registries may use similar auth/image-not-found
  wording.
- The `_CI_DOCKER_DAEMON_ERROR_MARKER` check in the adjacency scan is sufficient context to
  scope "not found", "unauthorized", etc. to daemon errors and not application log noise.

### Non-Goals

- This fix does NOT change the behavior of the `_is_docker_pull_failure_line` function itself —
  "docker pull failed" still counts as a pull-failure evidence line. The change is in whether
  that evidence line anchors transient-timeout attribution or not.
- This fix does NOT add permanent-error detection for the `"failed to pull image"` or
  `"error response from daemon + /v2/"` evidence paths — those already have tighter guards.
- This fix does NOT address any scenario outside the docker-pull / transient-CI classification.
- No migrations, schema changes, CLI changes, or API changes are needed.
- No 1500-line guardrail concern: `pr_monitor.py` is already ~1401 lines; adding ~25 lines of
  production code + helper stays well below that limit.
