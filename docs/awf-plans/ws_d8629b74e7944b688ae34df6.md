# Plan: Deterministic Sensitive Stale Reasons

## Goal

Implement the P0 PRD slice for deterministic stale reasons when the target branch
advances across sensitive paths. The implementation should make merge candidates
stale with structured active/resolved reasons for dependency, build-config, and
schema/model drift, while preserving mergeability for non-overlapping docs/test
changes when policy permits.

## Current Anchors

- Core stale evaluation and persistence belongs in `src/awf/service/staleness.py`.
- Target-branch reconciliation and candidate refresh orchestration belongs in
  `src/awf/service/target_branch_monitor.py`.
- Durable stale reasons are stored through `StaleReasonRepository` in
  `src/awf/db/repositories.py` and `StaleReason` in `src/awf/db/models.py`.
- Merge queue exposure is in `src/awf/api/routes/merge_queue.py` and response
  models in `src/awf/api/schemas.py`.
- Workspace stale-reason exposure is in
  `src/awf/api/routes/workspaces.py`.
- PR monitor stale recovery wording is in
  `src/awf/runtime/pr_monitor_runner.py`.

## Tests To Write First

1. Pure stale-policy tests in `tests/unit/service/test_staleness.py`:
   - `migration_task` + target change under `migrations/versions/**` emits
     `STALE_SCHEMA` with `trigger_type="schema_changed"`.
   - `migration_task` + target change under an ORM/model path emits
     `STALE_SCHEMA`.
   - `dependency_task` + target change to `pyproject.toml`, `uv.lock`,
     `package.json`, or `package-lock.json` emits `STALE_DEPENDENCY`.
   - `build_config_task` + target change to Docker/CI/build config paths emits
     `STALE_BUILD_CONFIG`.
   - Non-overlapping `docs_task` and `test_task` candidates remain fresh for
     unrelated docs/test changes when policy does not mark those paths sensitive.
   - A custom policy can make dependency/build-config changes invalidate a
     candidate, proving the behavior is policy-driven.

2. Persistence tests in `tests/unit/service/test_staleness.py`:
   - Refreshing a candidate with each sensitive finding creates an active
     `stale_reasons` row and marks the merge candidate stale.
   - Refreshing the same candidate against a target snapshot with no matching
     trigger resolves the prior reason and clears stale state unless another
     stale source, such as validation tier, remains active.
   - Re-running refresh with the same finding is idempotent and does not create
     duplicate active rows.

3. Target-branch refresh tests in
   `tests/unit/service/test_target_branch_monitor.py`:
   - After reconcile succeeds, open merge candidates for the repo/base branch
     are refreshed and summaries include the sensitive stale reason.
   - Candidates with no `base_sha` are summarized without failing the whole
     refresh pass.

4. API tests:
   - `/v1/merge-queue` exposes the active sensitive reason in `stale_reasons`,
     preserves `readiness.stale`, and reports `required_next_action="rebase"`.
   - `/v1/workspaces/{id}/stale-reasons` returns active rows by default and
     includes resolved rows with `include_resolved=true`.
   - Existing queue item shape remains unchanged aside from populated
     `stale_reasons`.

## Implementation Sequence

1. Add the failing pure evaluator tests first.
2. Add failing persistence and API tests for active/resolved behavior and merge
   queue/workspace exposure.
3. Update `StalePolicy` and `evaluate_staleness()` to classify target changed
   paths into dependency, build-config, and schema/model groups and return
   deterministic `StalenessFinding` records.
4. Update `StalenessRefreshService.refresh_candidate()` only as needed so the
   newly returned findings persist through `StaleReasonRepository`, update
   candidate stale state, and emit existing workspace events.
5. Thread the policy into target-branch refresh orchestration if the evaluator
   change requires it.
6. Update API schema literals and PR monitor message maps only if the reason
   codes/triggers are not already represented.
7. Run focused tests, then lint/typecheck/broader unit validation.

## Risks

- Path matching can under-match or over-match sensitive files. Keep the matcher
  deterministic and covered with representative dependency, build, migration,
  schema, and model paths.
- Candidate `stale_reason` is a legacy single string while `stale_reasons` can
  hold multiple structured active rows. Preserve the existing merge queue
  contract and avoid losing validation-tier stale reasons.
- Over-broad default sensitivity could make docs/test work stale too often.
  Tests must cover non-overlapping docs/test freshness.
- Target-branch refresh failures must remain per-candidate in summaries and not
  hide successful reconciliation.
- API literal updates can become breaking if response names change. Only add
  the requested reason codes/triggers and preserve existing field names.

## Assumptions

- P0 can use AWF's in-process `StalePolicy` defaults and injected policy in
  tests; full repository-profile stale-policy configuration is not required
  unless existing code already has a natural profile slot.
- `rebase` remains the required next action for these branch-drift stale
  reasons.
- Structured stale reasons are candidate-scoped and workspace-visible through
  the existing stale reason table and endpoints.
- Owned-path overlaps remain advisory at launch; overlap risk must not become
  a hard workspace admission blocker.

## Explicit Non-Goals

- Do not add hard launch blocking for owned-path overlap.
- Do not implement future exclusive resource locks for schema, dependency, or
  build resources.
- Do not add new API envelopes or rename merge queue/stale-reason fields.
- Do not implement redispatch policy, automated conflict resolution, or new
  validation tier orchestration beyond marking freshness invalid.
- Do not hard-code Aira-specific schema, migration, dependency, or build paths
  into AWF core beyond generic defaults and this repository's existing AWF
  defaults.
- Do not push, rebase, switch branches, or commit during this planning phase.
