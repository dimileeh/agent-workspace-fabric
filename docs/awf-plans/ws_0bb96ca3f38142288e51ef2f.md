# Plan: Advisory Overlap Graph For Running And Queued Workspaces

## Objective

Add an operator-visible overlap graph that explains advisory owned-path overlap
among currently queued and running workspaces. The graph must make overlap risk
easy to inspect, include reason codes and affected workspace ids, and preserve
the existing product rule that ordinary owned-path overlap is never a launch
blocker.

## Intended Files And Modules To Touch

### Production

- `src/awf/db/repositories.py`
  - Add a small public helper such as `owned_path_overlap_match(left, right)`
    that returns structured match details while reusing the existing
    `_normalize_owned_path` / wildcard-prefix logic.
  - Keep `owned_paths_overlap(left, right)` behavior unchanged, likely by
    delegating to the new helper.
  - Do not add schema changes or migrations.

- `src/awf/service/overlap_graph.py` (new)
  - Build the compact graph from `Workspace` rows.
  - Define queued statuses as `requested` and `ready`, matching current
    provision/execution queue semantics in `src/awf/service/metrics.py`.
  - Define running statuses as `provisioning`, `running`, `validating`,
    `pushing`, and `monitoring_pr`.
  - Exclude terminal and teardown states: `completed`, `failed`, `cancelled`,
    `destroying`, and `destroyed`.
  - Group candidates by `(repo_url, branch_base)`, compare only within a group,
    and emit deterministic nodes and edges.
  - Offload the pairwise path comparison with `asyncio.to_thread`, following
    the existing `src/awf/service/locks.py` pattern.

- `src/awf/api/schemas.py`
  - Add response models for:
    - overlap graph node;
    - path match explanation;
    - overlap graph edge;
    - graph summary/counts;
    - top-level graph response.

- `src/awf/api/routes/locks.py`
  - Add `GET /v1/locks/overlap-graph`.
  - Support compact filters: `repo_url`, `base_branch`, `task_class`,
    `queue_state=queued|running|all`, `limit`.
  - Return `reason_code="OWNED_PATH_OVERLAP_RISK"`, `severity="advisory"`,
    `blocks_launch=false`, and `affected_workspace_ids` on every edge.

- `apps/console/lib/types.ts` and
  `apps/console/components/console-dashboard.tsx` (only if the API/service
  slice stays small)
  - Add a compact "Overlap Graph" panel using existing `Panel`, `Fact`,
    `MutedLine`, compact id, and tone helpers.
  - Show node count, edge count, affected workspace count, and the first few
    advisory edges with workspace ids, reason code, and matching path pairs.
  - Use the existing `/api/awf/[...path]` proxy; no new Next route should be
    needed.

### Tests

- `tests/unit/service/test_overlap_graph.py` (new)
  - Focused service and helper tests for graph construction, status filtering,
    path-match explanations, deterministic ordering, and no-blocking fields.

- `tests/unit/api/test_overlap_graph.py` (new) or
  `tests/unit/api/test_locks.py`
  - API response shape, query filters, enum validation, and serialized reason
    code / affected workspace ids.

- `tests/unit/api/test_workspaces.py`
  - Add or extend a creation test proving overlapping high-risk owned paths are
    still admitted while the graph reports the relationship as advisory.

## Tests To Write First

1. `test_overlap_graph_builds_advisory_edges_for_same_repo_base`
   in `tests/unit/service/test_overlap_graph.py`
   - Seed two workspaces on the same repo/base with overlapping paths:
     one queued (`requested` or `ready`) and one running.
   - Assert the graph has two nodes and one edge.
   - Assert the edge includes `reason_code == "OWNED_PATH_OVERLAP_RISK"`,
     `severity == "advisory"`, `blocks_launch is False`, and
     `affected_workspace_ids == [<sorted ids>]`.

2. `test_overlap_graph_filters_to_running_and_queued_workspaces`
   - Seed overlapping terminal and teardown rows alongside active rows.
   - Assert `completed`, `failed`, `cancelled`, `destroying`, and `destroyed`
     are excluded from nodes and cannot produce edges.
   - Assert same-path workspaces on a different repo or base branch do not
     produce an edge.

3. `test_overlap_graph_path_match_explanations_cover_exact_ancestor_and_wildcard`
   - Exercise exact path, ancestor path, wildcard-to-file, and wildcard-to-
     wildcard overlaps.
   - Assert each match includes both owned paths, both workspace ids, a stable
     match reason code such as `OWNED_PATH_EXACT_MATCH`,
     `OWNED_PATH_ANCESTOR_MATCH`, or `OWNED_PATH_WILDCARD_MATCH`, and a concise
     explanation string.

4. `test_overlap_graph_queue_state_filter_limits_nodes_before_edges`
   - Seed queued-only, running-only, and mixed overlaps.
   - Assert `queue_state=queued` returns only queued nodes and queued-queued
     edges, `queue_state=running` returns only running nodes and running-running
     edges, and `queue_state=all` returns mixed edges.

5. `test_overlap_graph_deterministic_and_compact`
   - Seed several workspaces with multiple matching paths.
   - Assert nodes are ordered by `created_at desc, workspace_id desc`, edges use
     a deterministic sorted workspace-id pair, and duplicate path matches do not
     duplicate edge records.

6. `test_get_overlap_graph_serializes_reason_codes_and_affected_workspace_ids`
   in the API test file
   - Call `GET /v1/locks/overlap-graph`.
   - Assert top-level counts, nodes, edges, `affected_workspace_ids`, path
     match explanations, and advisory/no-blocking fields serialize as expected.

7. `test_overlapping_owned_paths_remain_admitted_and_show_in_overlap_graph`
   in `tests/unit/api/test_workspaces.py`
   - Create an existing `migration_task` with `owned_paths=["migrations/**"]`.
   - Create a new overlapping `migration_task` targeting a concrete migration
     file.
   - Assert the create response is still `202`, the queue decision remains
     `decision="admitted"` / `reason_code="ADMITTED_LOCAL"`, and the overlap
     graph reports an advisory edge rather than any blocking state.

## Implementation Steps

1. Add the focused service and API tests above and run them to confirm red
   failures before implementation.
2. Add the structured path-match helper in `src/awf/db/repositories.py` and
   keep the existing boolean `owned_paths_overlap()` API compatible.
3. Implement `src/awf/service/overlap_graph.py` with typed dataclasses:
   `WorkspaceOverlapNode`, `WorkspaceOverlapPathMatch`,
   `WorkspaceOverlapEdge`, and `WorkspaceOverlapGraph`.
4. Query candidate workspaces from the DB using the queued/running status sets,
   optional filters, and a bounded `limit + 1` read for `has_more`.
5. Build graph edges only within matching `(repo_url, branch_base)` groups.
   Each edge should aggregate all matching path pairs between the same two
   workspaces and expose a sorted `affected_workspace_ids` pair.
6. Add Pydantic response models in `src/awf/api/schemas.py` and expose
   `GET /v1/locks/overlap-graph` in `src/awf/api/routes/locks.py`.
7. If the backend diff remains small, add the console panel and types. Keep it
   summary-only and avoid new dependencies or lockfile changes.
8. Re-run the focused tests, then the broader Python validation. Run console
   checks only if console files were touched.

## Risks And Assumptions

- Assumption: queued means `requested` plus `ready`; running means
  `provisioning`, `running`, `validating`, `pushing`, and `monitoring_pr`.
  This matches current resource saturation queue/in-use semantics.
- Assumption: ordinary owned-path overlap should continue to use
  `OWNED_PATH_OVERLAP_RISK`; any future explicit exclusive lock must be modeled
  separately.
- Assumption: a graph computed at read time is sufficient for this P1 slice;
  creation-time warning events and queue-decision summaries remain the durable
  admission breadcrumbs.
- Risk: pairwise path matching is O(workspaces^2 * paths^2). Keep the API
  bounded by `limit`, group by repo/base before comparison, and offload the
  comparison thread as the lock service already does.
- Risk: path specificity is nuanced. This slice should explain why two paths
  matched, not attempt to rank stale severity beyond the existing advisory
  reason code.
- Risk: adding a console panel may grow the diff. Keep frontend work limited to
  a compact read-only summary, or defer it if the backend implementation is no
  longer narrow.

## Explicit Non-Goals

- Do not make owned-path overlaps block workspace launch, provisioning,
  execution, validation, or queue admission.
- Do not implement explicit exclusive resource locks.
- Do not add migrations, new tables, or durable graph snapshots.
- Do not change stale detection, merge queue ordering, merge eligibility, PR
  monitor behavior, or resource admission policy.
- Do not modify agent branch management, push behavior, or AWF PR ownership.
- Do not lower coverage targets or quality gates.
- Do not touch lockfiles or unrelated documentation.
- Do not commit during this planning phase.
