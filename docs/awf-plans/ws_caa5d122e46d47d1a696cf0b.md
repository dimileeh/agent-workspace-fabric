# Plan: P0 Terminal-State Callback Safety

## Scope

Implement a narrow terminal-state safety slice for stale asynchronous callbacks.
For this slice, `cancelled`, `destroyed`, `failed`, and `completed` are
terminal for executor, validation, cleanup, and PR-monitor callbacks even though
some of them still allow explicit operator lifecycle actions such as destroy or
remonitor. A stale callback must not advance the workspace, must not run the
next callback side effect, and must leave durable audit data explaining that it
was ignored.

The existing state machine only treats `destroyed` as structurally terminal.
Keep that public transition model intact; add a separate callback-terminal
concept instead of redefining all lifecycle terminal states.

## Intended Files And Modules To Touch

Production modules:

- `src/awf/control/state_machine.py`
  - Add a small helper such as `is_callback_terminal(state)` or
    `is_attempt_terminal(state)` for `{cancelled, destroyed, failed, completed}`.
  - Do not change existing allowed transitions or `is_terminal()` semantics,
    because `completed` / `failed` / `cancelled` can still move to
    `destroying`, and failed PR workspaces may be explicitly remonitored.

- `src/awf/db/repositories.py`
  - Add a shared durable audit helper for ignored stale callbacks, for example
    `WorkspaceRepository.record_ignored_stale_callback(...)`.
  - Persist a `WorkspaceEvent` with a stable event type such as
    `workspace.stale_callback_ignored`, reason code
    `STALE_CALLBACK_IGNORED`, and payload fields:
    `callback_source`, `callback_action`, `expected_status`,
    `actual_status`, optional `requested_status`, optional `operation_id`, and
    optional `reason_code`.
  - Preserve existing event shapes where current tests assert exact payloads;
    add the new event only where it does not break compatibility, or update
    tests deliberately when the old event was the only stale-callback audit.

- `src/awf/control/executor.py`
  - Use the callback-terminal helper in `_recheck_status`,
    `_transition_if_current`, `_mark_failed`, recovery dispatch finalization,
    PR persistence, and validation completion paths.
  - If a validation or recovery callback returns after a callback-terminal
    status, skip push / PR creation / monitor handoff and do not overwrite
    workspace status or failure metadata.
  - Finish pending/running validate or monitor-recovery operations with a
    non-success terminal outcome such as `OperationStatus.cancelled` and a
    stale-callback result payload when the operation belongs to the ignored
    callback.
  - Keep existing public API response fields unchanged.

- `src/awf/service/controls.py`
  - Guard the cleanup finalization path in `destroy_workspace` after
    `cleaner.cleanup(...)` returns. If the workspace is no longer in the
    expected destroy phase for this operation, do not transition it to
    `destroyed` or `failed`.
  - Record the ignored callback event and finish the destroy operation with a
    durable ignored/cancelled result.
  - Do not block explicit operator destroy requests for already completed,
    failed, or cancelled workspaces.
  - Preserve `_reset_failed_workspace_for_remonitor(...)` as the explicit
    exception that can reopen a failed PR workspace to `monitoring_pr`.

- `src/awf/runtime/pr_monitor_runner.py`
  - Reuse the shared ignored-callback event helper from
    `_terminate_completed` / `_terminate_failed`.
  - Add a status recheck before monitor-created recovery operations transition
    `monitoring_pr -> ready`; if the workspace is now callback-terminal, do not
    create recovery operations or run repair side effects.
  - Keep the existing explicit remonitor/recovery behavior intact once a
    remonitor request has legitimately reset a failed workspace to
    `monitoring_pr`.

- `src/awf/runtime/pr_monitor_operations.py`
  - Touch only if operation-result redaction or a small helper is needed for
    ignored monitor operations. Avoid changing idempotency semantics unless a
    failing test requires it.

Tests:

- `tests/unit/control/test_state_machine.py`
  - Cover the new callback-terminal helper.
  - Assert `WorkspaceStateMachine.is_terminal()` still only reports

- `tests/unit/control/test_executor_monitor_recovery.py`
  - Extend the existing stale recovery tests beyond `cancelled` and
    `destroyed` to include `completed` and `failed`.
  - Assert stale recovery operations are not marked succeeded, workspace state

  `tests/unit/control/test_executor.py`
  - Add a validation-callback race: after a validation run starts, mutate the

  - Assert validation completion does not transition to `pushing`,
    `monitoring_pr`, `completed`, or `failed` again; no PR creator or monitor

- `tests/unit/service/test_controls_lifecycle.py`
  - Add cleanup-finalizer races where a destroy cleanup callback returns after
    the workspace has become `cancelled`, `destroyed`, `completed`, or
    `failed`.
  - Assert cleanup finalization does not overwrite that state, failure metadata,
    or PR metadata, and records an ignored stale-callback operation/event.
  - Add/keep tests proving an explicit destroy request for a completed/failed/
    cancelled workspace still works.
  - Add/keep tests proving `remonitor_workspace` can explicitly reopen a failed
    workspace with a PR URL to `monitoring_pr` and reopen the merge candidate.

- `tests/unit/runtime/test_pr_monitor_runner_coverage_edges.py`
  - Extend stale monitor terminal callback coverage from
    `cancelled` / `destroying` / `destroyed` to also include `completed` and
    `failed`.
  - Assert `_terminate_completed` and `_terminate_failed` do not set
    `pr_merge_sha`, failure metadata, compose teardown calls, filesystem GC, or
    target-branch reconciliation after stale terminal state.
  - Add a monitor recovery-dispatch race test where the monitor decides to
    validate/rebase but the workspace is terminal before dispatch persistence;
    assert no recovery operation is created and an ignored callback event is
    recorded.

## Risks

- `completed`, `failed`, and `cancelled` are terminal for stale callbacks but
  not terminal for every lifecycle action. A helper name and call-site usage
  must make that distinction explicit to avoid blocking valid destroy or
  remonitor operations.
- Existing tests assert exact event payloads for some stale-action paths. The
  implementation should avoid changing those payloads unless the matching tests
  are intentionally updated.
- Validation runs have a limited public status vocabulary. Prefer a compatible
  failed/cancelled operation result plus reason code over introducing a new
  validation status that would surface as `unknown`.
- Cleanup is partly irreversible once the cleaner has started. This slice can
  prevent stale cleanup finalization from moving state forward, but it cannot
  undo filesystem/container work already performed by an older cleanup attempt.
- The monitor already has some ignored terminal callback handling. The new work
  should consolidate and extend it without weakening existing merge and review
  grace behavior.

## Assumptions

- A "callback" means a delayed executor, validation, cleanup, or PR-monitor
  completion/finalization path that was valid when started but returns after the
  workspace has entered a callback-terminal state.
- Durable audit can be represented by workspace events and operation results;
  no schema migration is required.
- Explicit operator actions (`destroy`, `remonitor`, `validate`, `rebase`) are
  not stale callbacks when their eligibility check succeeds against the current
  state.
- Public API response compatibility means no new required response fields and
  no change to existing enum values exposed by schemas.
- Existing PR monitor recovery tests cover most legitimate recovery behavior;
  this slice only adds regression tests around terminal-state races.

## Explicit Non-Goals

- Do not redesign the workspace state machine or remove valid transitions from
  `completed`, `failed`, or `cancelled` to `destroying`.
- Do not disable explicit failed-workspace remonitoring for PR workspaces.
- Do not add database migrations or new operation/status enum values unless a
  failing test proves there is no compatible alternative.
- Do not change API response shapes or require clients to understand new
  response fields.
- Do not broaden this slice into provisioning, scheduling policy, merge queue
  redesign, or target-branch stale detection.
- Do not lower coverage thresholds, quality gates, workspace coverage
  requirements, or validation requirements.
- Do not switch branches, push, rebase, force-push, or manually manage AWF PR
  lifecycle.
