# Plan: P1 External Operator Callback Foundation

## Objective

Implement the narrow local-service foundation for external operator callbacks
from `TODO/pre-gke-industrial-readiness.md`.

The slice should add durable callback subscription registration and listing,
plus a safe delivery path for sanitized workspace, merge, and operation event
envelopes. Delivery must be at-least-once, retry-aware, and idempotent per
subscription/source event. Disabled or failing callbacks must only affect
callback delivery records; they must not mutate workspace, merge candidate, or
operation state.

## Current Code Context

- `docs/awf_prd_v2.2.md` lists `POST /v1/callbacks` as the callback
  registration endpoint and requires mutating endpoint idempotency.
- Existing event storage is `workspace_events`, exposed by `GET /v1/events`.
  There is no external callback model, route, or delivery service yet.
- `operations` already stores durable operation status, payload, result, and
  idempotency key. Public operation responses intentionally include operation
  payload/result today, but callback envelopes should not forward those raw
  internals.
- `merge_candidates` is the current durable merge queue/candidate table. It
  does not currently emit a separate event table, so this slice should synthesize
  a narrow merge envelope from allowlisted candidate fields when asked to enqueue
  merge events.
- The current Alembic head is `4f2b9c8d7e6a`; any new schema migration should
  build from that head and keep the migration graph single-headed.

    `callback_delivery_initial_backoff_seconds`.
  - Keep defaults safe for local development.

- `src/awf/service/callbacks.py` (new)
  - Add `CallbackService` for registration/listing.
  - Add `CallbackDeliveryService` for enqueueing sanitized envelopes and
    draining due delivery attempts through an injectable async HTTP poster.
  - Envelope builders:
    - Workspace envelope from `WorkspaceEvent`: allowlist event id/type,
      workspace id, old/new state, reason code, occurred timestamp, and
      callback delivery metadata. Do not forward raw `WorkspaceEvent.payload`.
    - Operation envelope from `Operation`: allowlist operation id, workspace id,
      type, status, error code/message, created/started/finished timestamps,
      and callback delivery metadata. Do not forward raw operation `payload`,
      `result`, or API idempotency key.
    - Merge envelope from `MergeCandidate`: allowlist candidate id,
      workspace id, task/attempt ids, status, readiness booleans, stale
      reason, updated timestamp, and callback delivery metadata. Do not forward
      raw policy findings or arbitrary candidate internals.
  - Delivery behavior:
    - Send JSON with only `Content-Type`, a stable AWF user agent, and a
      delivery `Idempotency-Key`.
    - On 2xx response, mark the delivery `succeeded`.
    - On non-2xx response or request exception, record `error_code`,
      bounded `error_message`, response status when present, increment attempt
      count, and either schedule the next retry or mark terminal `failed`.
    - If a subscription is disabled before send time, mark the delivery
      `skipped` with `CALLBACK_DISABLED` and do not call the target.
    - Never raise delivery failure into workspace/control-plane state mutation.

## Tests To Write First

1. API registration contract.
   - `POST /v1/callbacks` without `Idempotency-Key` returns the existing
     structured invalid-request style error.
   - Valid registration returns `201`, a `cb_` id, persisted target URL,
     `event_types`, `enabled`, retry config, and timestamps.
   - Response contains no secret/header fields.
   - Invalid URL schemes, URL userinfo, blank event types, unknown event types,
     and extra fields return `422` or structured `400` as appropriate.

2. API registration idempotency.
   - Same key and same request body returns the original subscription and does
     not insert a second row.
   - Same key and different target URL, event list, or enabled flag returns
     `409 IDEMPOTENCY_CONFLICT`.

3. API listing.
   - `GET /v1/callbacks` returns a pagination envelope.
   - Listing includes disabled subscriptions and can filter by `enabled` if the
     route adds that filter.
   - Limit bounds match the existing list API pattern.

4. Repository persistence.
   - `CallbackSubscriptionRepository.create_idempotent` persists the request
     hash, detects exact replay, and rejects changed payloads.
   - `CallbackDeliveryRepository.enqueue_once` uses
     `(subscription_id, dedupe_key)` to prevent duplicate delivery rows for the
     same source event.
   - Due delivery queries return only pending rows whose `next_attempt_at` is
     due, ordered oldest first.

5. Workspace event envelope delivery.
   - Seed a workspace and `workspace_events` row with a raw payload containing
     fields that must not leave the system, such as `task_prompt`, `env`, or a
     fake token.
   - Enqueue delivery for an enabled subscription and assert the stored/sent
     envelope contains only allowlisted workspace event fields plus delivery
     idempotency/retry metadata.
   - Exact enqueue replay returns the same delivery id and stable delivery
     idempotency key.

6. Operation event envelope delivery.
   - Seed an operation with raw `payload`, raw `result`, and API
     `idempotency_key`.
   - Enqueue an `operation.state_changed` envelope and assert none of those raw
     internals are sent; only allowlisted operation status fields and delivery
     metadata are present.

7. Merge event envelope delivery.
   - Seed task/attempt/workspace/merge candidate rows.
   - Enqueue a merge candidate envelope and assert it includes candidate id,
     workspace id, attempt/task ids, public status/readiness/stale fields, and
     delivery metadata without raw internal payloads.

8. Successful delivery.
   - Use an injected fake HTTP poster returning 2xx.
   - Assert one POST call, JSON body equals the sanitized envelope, headers
     contain the delivery idempotency key and no authorization/secret headers,
     and the delivery row becomes `succeeded`.

9. Disabled callback handling.
   - A subscription created with `enabled=false` should not enqueue new
     deliveries.
   - If a pending delivery's subscription is disabled before send time, the
     service marks the delivery `skipped` with `CALLBACK_DISABLED` and does not
     call the poster.
   - Workspace, operation, and merge candidate rows are unchanged.

10. Failing callback handling.
    - HTTP non-2xx and request exceptions record bounded failure detail and
      retry metadata.
    - Attempts below `max_attempts` become pending again with a future
      `next_attempt_at`.
    - Attempts at the retry limit become terminal `failed`.
    - Failures do not change AWF workspace status, operation status, merge
      candidate status, or existing event rows.

## Risks And Assumptions

- Assumption: this slice provides local foundation and explicit service methods
  for queueing/draining callback deliveries; wiring a continuous background
  dispatcher into the worker loop can be a later slice if not required to make
  the focused tests pass.
- Assumption: delivery semantics are at-least-once, not exactly-once. The stable
  delivery `Idempotency-Key` lets receivers deduplicate retries.
- Assumption: registration is a mutating endpoint and therefore requires
  `Idempotency-Key`, even though the PRD endpoint summary only says
  `POST /v1/callbacks`.
- Risk: the word "callback" is already used for internal stale async callbacks.
  New code and tests should use names such as `CallbackSubscription`,
  `CallbackDelivery`, or `external callback` when clarity matters.
- Risk: callback URLs are an outbound network surface. This slice should limit
  accepted URL shapes and send no secrets, but broader egress allowlisting or
  SSRF policy can remain future work.
- Risk: raw event, operation, and merge payloads may contain sensitive data or
  internal implementation details. Envelope builders must be allowlist-based,
  and tests should seed obviously sensitive fake values to catch leaks.
- Risk: adding schema tables requires keeping Alembic single-headed and making
  SQLite test metadata match the migration intent.
- Risk: changing shared schemas or app routing can inadvertently affect OpenAPI
  or existing route tests. Keep new schemas additive and do not modify existing
  response models.

## Explicit Non-Goals

- Do not send bearer tokens, signing secrets, custom user-provided headers, raw
  operation payloads/results, raw workspace event payloads, task prompts,
  environment values, provider config, or repository credentials.
- Do not add a cloud secret broker, webhook signing, per-tenant auth, egress
  policy enforcement, or operator console UI in this slice.
- Do not expose a broad delivery management API unless tests prove it is needed;
  registration and listing are the public API target for this slice.
- Do not change existing `GET /v1/events`, `GET /v1/operations`, workspace,
  merge queue, or control endpoint response shapes.
- Do not make callback delivery failure fail, cancel, retry, or otherwise move
  AWF workspace, operation, or merge-candidate state.
- Do not implement inbound GitHub webhooks or release watcher webhooks.
- Do not lower coverage, lint, mypy, or quality thresholds.
- Do not switch branches, push, rebase, force-push, create a PR, merge a PR, or
  commit during the planning phase.
