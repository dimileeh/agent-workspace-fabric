# Plan: P1 Structured Control-Plane Audit Events

## Goal

Implement a narrow auditability slice using the existing `operations` and
`workspace_events` tables. The slice should produce durable, structured audit
events for:

- initial git push / branch publication and PR creation or reuse;
- PR-monitor branch pushes during comment, CI, sync-base, and rebase recovery;
- merge attempts and merge results;
- PR comment/thread resolution outcomes;
- destructive control operations: cancel, stop, and destroy.

This is not a new audit database and should not require schema changes. Events
must remain query-compatible through the existing event endpoints, with stable
`event_type`, top-level `reason_code`, and compact JSON payloads.

## Current Context From Inspection

- `src/awf/db/models.py` already defines append-only `WorkspaceEvent` rows and
  free-form JSON `Operation.payload` / `Operation.result` fields.
- `WorkspaceRepository.add_event()` and `add_events()` are the current write
  path for workspace events.
- `OperationResponse` in `src/awf/api/schemas.py` already derives audit-like
  fields from operation payload/result: owner, source, action, PR number/URL,
  source/base SHAs, reason codes, failure fields, and log stream refs.
- PR-monitor operations already use `src/awf/runtime/pr_monitor_operations.py`
  to create redacted operation payloads for `comment_repair`, `ci_repair`,
  `sync_base`, `human_wait`, and monitor-state actions.
- Runtime monitor logs already have durable stream IDs via `LogStore`; audit
  payloads should refer to these IDs instead of copying raw command output.
- `src/awf/service/controls.py` already creates operation rows for cancel,
  stop, remonitor, refresh, validate, rebase, and destroy. Cancel/stop/destroy
  are the destructive subset for this task.

## Audit Event Shape

Use stable event types with a common payload schema. Candidate event types:

- `workspace.audit.git_push`
- `workspace.audit.pr_created`
- `workspace.audit.merge_attempt`
- `workspace.audit.merge_result`
- `workspace.audit.comment_resolution`
- `workspace.audit.control_operation`

Common payload keys:

- `schema`: `"control_audit.v1"`
- `actor`: `"executor"`, `"pr_monitor"`, or `"operator_api"`
- `source`: same source vocabulary used by operation payloads
- `action`: narrow action name, such as `git_push`, `pr_create`, `merge`,
  `resolve_thread`, `cancel`, `stop`, or `destroy`
- `outcome`: `attempted`, `succeeded`, `failed`, `skipped`, `reused`, or
  `requeued`
- `reason_code`: same value as the row `reason_code`
- `operation_id`: included when an operation row exists
- `operation_type`: included when available
- `pr_number` and `pr_url`: included when available
- `source_head_sha`, `source_base_sha`, `target_branch`, `remote_branch`, and
  `branch_name`: included when relevant
- `evidence`: compact safe refs such as `log_stream_refs`, `log_stream_ids`,
  PR URL, candidate ID, cleanup step names/statuses, or bounded redacted error
  codes/messages

Do not include raw stdout/stderr, prompts, PR comment bodies, review excerpts,
tokens, authorization headers, secret names with raw values, or host-home
paths unless they are already safe durable log stream identifiers.

## Risks and Mitigations

- Duplicating operation data in workspace events can make audit payloads noisy
  and harder to query. Mitigation: keep operation rows primary for long-running
  actions and put compact event payloads with `operation_id` refs in the event
  stream.
- Adding event writes inside PR-monitor hot paths can create duplicate events
  during retries. Mitigation: use operation idempotency where available and keep
  retries either idempotent or explicitly marked as `requeued/skipped`.
- Comment audit can accidentally persist review text. Mitigation: tests assert
  only thread/comment IDs, counts, verdicts, and safe evidence refs are stored.
- Push audit can accidentally copy raw stderr that contains credentials.
  Mitigation: shared redaction tests include URL credentials, bearer headers,
  GitHub tokens, API keys, and long strings.
- Merge audit must not weaken merge policy. Mitigation: instrumentation should
  sit around existing merge gates and should not change decision ordering,
  queue checks, stale checks, final settle, or branch-protection fallback.
- Destructive operation replay semantics may be ambiguous. Mitigation: encode
  the desired replay behavior in tests before implementation and keep it
  consistent across cancel, stop, and destroy.
- Full 99% coverage may still depend on unrelated modules. Mitigation: add
  regression tests for every new audit behavior and run the focused plus unit
  suites; do not reduce quality gates.

## Assumptions

- Existing `workspace_events.payload` JSON is sufficient for structured audit
  data; no migration is required.
- Existing operation IDs are available for PR-monitor actions and destructive
  controls, but not necessarily for the executor's initial push/PR creation
  path. Missing operation IDs are acceptable only where no operation exists.
- `actor`/`source` can use the existing source vocabulary:
  `executor`, `pr_monitor`, and `operator_api`.
- Safe evidence means durable links or references, such as PR URL, PR number,
  candidate ID, log stream IDs/refs, cleanup step summaries, and bounded
  redacted error codes/messages.
- Release-PR scheduler/script-only PR creation that has no workspace/session is
  outside this narrow workspace-event slice unless a caller already has a
  workspace row to attach the event to.

## Explicit Non-Goals

- Do not create a new audit table, audit database, migration, event schema
  column, or public API field.
- Do not change PR-monitor decision policy, merge eligibility, stale handling,
  review grace, queue ordering, or branch-protection fallback behavior.
- Do not persist raw tokens, raw secrets, full command output, prompts, review
  bodies, comment excerpts, or unbounded stderr/stdout.
- Do not add broad observability refactors, a search/indexing subsystem, or a
  console UI for audit events in this slice.
- Do not change branch management, push destinations, git refspec invariants,
  or AWF-managed branch rules.
- Do not touch lockfiles, profile config, migrations, console code, or unrelated
  documentation during implementation.
- Do not push, rebase, switch branches, or manually manage the PR; AWF owns
  branch and PR publication after the agent exits.
