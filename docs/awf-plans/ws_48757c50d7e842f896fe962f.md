# Plan: P0 PR Monitor Auto-Merge Gate Hardening

## Goal

Add a focused test-hardening slice proving that auto-merge mode never merges a
PR until every monitor gate has passed: initial review grace, unresolved review
activity, running/pending checks, validation freshness and required tier, stale
blockers, branch freshness/sync-base, async non-check reviewer settle, and the
final pre-merge settle recheck.

This is primarily a regression-test task. Production code should change only if
the new tests expose a real missing guard or an ordering bug in the existing
decision/runner seams.

## Current Anchors

- Pure PR snapshot decisions live in `src/awf/runtime/pr_monitor.py`.
  `decide()` already owns unresolved comments, CI state, branch freshness,
  merge-state status, deferred human feedback, and the final pure `Merge` vs
  `NotifyHuman` decision.
- Runner-side auto-merge gates live in
  `src/awf/runtime/pr_monitor_runner.py`, especially
  `PullRequestMonitorRunner._execute()` for the `Merge` action.
- Candidate validation/stale/canonical policy is checked through
  `_merge_gate_for_workspace()` and `_handle_merge_gate_blocker()`.
- Initial review grace is runner-side through
  `_initial_review_grace_wait_seconds()`.
- Async non-check reviewer settle is runner-side through
  `_non_check_reviewer_settle_decision()`.
- Final pre-merge settle and recheck happen inside the serialized merge
  critical section before `GitHubClient.merge_pr()`.
- Existing lightweight fixtures live in
  `tests/unit/runtime/_monitor_runner_fixtures.py`.

## Intended Files/Modules To Touch

- `tests/unit/runtime/test_pr_monitor.py`
  - Add or extend table-driven pure decision tests proving each snapshot-level
    gate returns a non-`Merge` action in auto-merge mode.
  - Keep the assertions at the decision boundary: expected action type and
    reason where applicable.

- `tests/unit/runtime/test_pr_monitor_runner.py`
  - Add runner-level regressions for gates that are not pure `decide()` logic:
    initial review grace, validation tier/freshness, active stale blockers,
    async non-check reviewer settle, final pre-merge recheck, and the clean
    merge path after every runner gate is satisfied.
  - Reuse `make_runner()`, `seed_monitoring_workspace()`, `RecordedSleep`,
    `FakeAdapter`, `FakeCommandRunner`, and existing DB repositories.

- `tests/unit/runtime/_monitor_runner_fixtures.py`
  - Touch only if a tiny helper is needed to avoid duplicated candidate or
    validation setup in the new tests.

- `src/awf/runtime/pr_monitor.py`
  - Touch only if a new pure decision regression proves a missing snapshot
    guard.

- `src/awf/runtime/pr_monitor_runner.py`
  - Touch only if a runner regression proves a real missing guard, missing
    recheck, or incorrect gate ordering.

## Tests To Write First

1. Pure decision no-merge gate matrix in
   `tests/unit/runtime/test_pr_monitor.py`:
   - Add a parameterized test such as
     `test_auto_merge_does_not_merge_when_any_snapshot_gate_is_open`.
   - Cases should include unresolved inline thread, unresolved top-level review
     comment, blocking policy/checklist review comment, CI pending, CI failure,
     unknown mergeability, unknown merge-state status, base behind count,
     `MergeStateStatus.BEHIND`, `MergeStateStatus.DIRTY`, legacy
     `MergeableState.CONFLICTING`, branch-protection `BLOCKED`/`HAS_HOOKS`,
     and unresolved human-deferred feedback.
   - Assert the exact action class (`AddressComments`, `WaitForCI`,
     `ReportCiFailure`, `SyncBase`, or `NotifyHuman`) and assert it is never
     `Merge`.

2. Runner regression for initial review grace:
   - In `tests/unit/runtime/test_pr_monitor_runner.py`, execute a `Merge()`
     action against an otherwise eligible candidate with
     `initial_review_grace_period_seconds > 0`.
   - Assert the runner sleeps, returns non-terminal, leaves the workspace in
     `monitoring_pr`, records the grace marker in state, and never calls
     `gh pr merge`.

3. Runner regression for validation freshness and required tier:
   - Seed a workspace whose task class requires a higher validation tier than
     the latest passing run has.
   - Execute `Merge()` and assert recovery is dispatched, the workspace moves to
     `ready`, a monitor-owned validation operation is created, and no merge
     command runs.
   - Add a separate active stale-reason case, for example
     `STALE_TARGET_ADVANCED`, proving stale blockers dispatch the required
     recovery and block merge.

4. Runner regression for branch freshness/sync-base:
   - Add focused `decide()` coverage for branch freshness in the matrix above.
   - Add a runner-level loop case if needed: a `BEHIND` or nonzero
     base-behind status should route to `SyncBase` and must not call
     `gh pr merge` during that tick.

5. Regression that would have caught merging while a reviewer/check was still
   pending:
   - Use `pre_merge_settle_seconds > 0` with an initially green `Merge()` action.
   - During the pre-merge recheck, return a fresh status with a pending check
     or a newly arrived reviewer comment.
   - Assert the runner routes to `WaitForCI` or `AddressComments`, sleeps or
     dispatches repair as appropriate, and never calls `gh pr merge`.

6. Runner regression for async non-check reviewer settle:
   - Execute `Merge()` with a configured non-check reviewer such as
     `greptile-apps`, no visible Greptile check/status on the head SHA, and a
     positive settle window.
   - Assert the runner sleeps, marks the head-scoped settle-start key, returns
     non-terminal, and does not merge.
   - Add or reuse a settled/visible-check variant in the clean-path regression
     so the wait is proven to unblock correctly.

7. Clean PR merges only after all gates pass:
   - Seed an eligible canonical candidate with fresh required validation, no
     active stale reasons, no policy blockers, auto-merge enabled, and clean PR
     status.
   - Pre-mark initial review grace elapsed and non-check reviewer settle elapsed
     or provide a visible reviewer check.
   - Enable a final pre-merge settle recheck and make the recheck return the
     same clean status.
   - Assert `gh pr merge` is called only after the recheck path, the workspace
     transitions to `completed`, and the merge candidate is marked merged.

## Implementation Sequence

1. Add the pure decision matrix test first and run the focused monitor test
   file.
2. Add runner gate regressions one at a time, running the two targeted runtime
   test files after each logical batch.
3. If a new test already passes because the guard exists, keep the production
   code unchanged and treat the test as hardening coverage.
4. If a test fails because a guard is genuinely missing, make the smallest
   production change at the existing seam:
   - `decide()` for snapshot-level policy.
   - `_execute(Merge)`, `_merge_gate_for_workspace()`,
     `_handle_merge_gate_blocker()`, or the pre-merge critical-section recheck
     for runner-level policy.
5. Re-run the targeted tests, then run lint, typecheck, and the full unit
   suite.
6. In the implementation phase, commit locally with a conventional commit such
   as `test(runtime): harden pr monitor auto-merge gates` unless production code
   changes require `fix(runtime): ...`. Do not push or switch branches.

## Risks

- Some requested gates already have coverage in sibling files such as
  `test_pr_monitor_merge_safety.py`,
  `test_pr_monitor_non_check_reviewer_settle.py`, and
  `test_pr_monitor_stale_pending_checks.py`. The new tests should harden the
  explicitly requested targeted files without duplicating large integration
  scenarios.
- Runner tests can become brittle if they assert raw `gh` command queues too
  deeply. Prefer state transitions, sleep calls, operation records, action
  outcomes, and absence/presence of `gh pr merge`.
- Pre-merge recheck tests must ensure the recheck uses the same status-fetch
  seam as the main loop, otherwise the test could miss the real race.
- Validation-tier tests must not accidentally change the seeded workspace into
  manual merge mode or a non-canonical candidate case unless that is the gate
  under test.
- Initial review grace and non-check reviewer settle markers use monotonic time
  at runtime and wall-clock persistence. Tests should monkeypatch time or use
  existing helper conversion functions to avoid timing flake.

## Assumptions

- The P0 slice is test-hardening first; passing new tests with no production
  change is an acceptable outcome if the existing guards are already correct.
- Auto-merge means `MonitorConfig.auto_merge=True` and workspace
  `auto_merge=True`; manual/release PR behavior is not the primary subject
  except where needed to prove no behavior regression.
- The existing fake GitHub/command-runner fixtures are sufficient for these
  tests; no network or real GitHub calls are required.
- Existing merge candidate, stale reason, operation, and validation repository
  APIs are the source of truth for runner gate assertions.
- The named validation commands are the required quality bar for the final
  implementation.

## Explicit Non-Goals

- Do not redesign the PR monitor state machine.
- Do not add new retry behavior or hide any failure behind retries.
- Do not change release/manual merge semantics.
- Do not change merge queue policy beyond preserving existing blocker behavior.
- Do not change database schema, migrations, API contracts, or frontend code.
- Do not lower coverage, lint, mypy, or unit-test thresholds.
- Do not push, rebase, switch branches, or commit during this planning phase.
