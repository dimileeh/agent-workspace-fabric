# Review 4590903660 Plan

## Problem Statement And Scope

Address the PR #353 review-level comment about PR monitor merge-method handling:

- avoid classifying GitHub's generic "could not be merged with this method" response as a merge-method mismatch when no specific rejected method is named;
- persist the merge-method blocked state for permanent merge-method preflight failures so later polls short-circuit through `decide()` instead of re-calling the preflight endpoint.

Scope is limited to `src/awf/runtime/pr_monitor_runner/merge_loop.py`, focused regression tests in `tests/unit/runtime/test_pr_monitor_merge_methods.py`, and this plan/validation documentation.

## Requirements Checklist

- [ ] Specific GitHub method policy errors such as "Squash merges are not allowed" still retry allowed alternatives and record a merge-method blocker only after alternatives are exhausted.
- [ ] Generic "could not be merged with this method" errors are treated as regular merge blockers, not merge-method mismatch blockers.
- [ ] Transient merge-method preflight failures still back off without recording a merge-method blocker.
- [ ] Non-transient merge-method preflight failures notify humans and record the per-head merge-method blocked key.
- [ ] Focused tests prove the changed behavior.

## Implementation Steps

1. Update merge-method rejection classification to require a named rejected method.
2. When a permanent preflight failure is about to notify humans, compute the notification reason, mark `_merge_method_blocked_key`, and persist state before posting the notification.
3. Update/add focused tests for generic merge failure classification and permanent preflight blocker persistence.
