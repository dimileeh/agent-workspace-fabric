# Wiki Structure Plan: AWF GitHub Wiki

Generated by /plan-ceo-review on 2026-06-21
Branch: development | Mode: SCOPE EXPANSION
Repo: dimileeh/agent-workspace-fabric

## Goal

Populate the (currently empty) GitHub Wiki at
https://github.com/dimileeh/agent-workspace-fabric/wiki with a complete,
navigable manual for two audiences — **operators** running AWF day-to-day and
**contributors** working on AWF itself — without duplicating the comprehensive
in-repo `docs/` folder.

## Locked Decision: the wiki ↔ docs/ relationship (Approach B — hybrid)

AWF already ships a comprehensive in-repo `docs/` folder (~30 files, ~8k lines:
`CONCEPTS`, `CLI_REFERENCE`, `REST_API_REFERENCE`, `MCP_REFERENCE`,
`REASON_CATALOG`, `TROUBLESHOOTING`, `AWF_CORE_TRUST_MODEL`, …) plus a rich
README. `docs/` is, and stays, the **single source of truth** for reference
material.

The wiki is a **curated manual that owns navigation + narrative +
audience-specific guides** and **links into `docs/`** for deep reference rather
than copying it. This is the core anti-drift rule:

> **DRY rule:** the wiki never re-states reference content that lives in `docs/`.
> Command tables, the full reason catalog, the full REST/MCP surface, the deep
> concepts text — the wiki *links* to those `docs/` files. The wiki's own prose
> is orientation, routing, narrative how-to, playbooks, FAQ — content that does
> NOT exist in `docs/`. If a wiki page starts re-deriving a `docs/` reference,
> that is a defect: replace the prose with a link.

```
WIKI (owns: navigation + narrative + guides)     docs/ (owns: reference, source of truth)
────────────────────────────────────────────     ──────────────────────────────────────────
Home / What is AWF / Pick Your Path
Install & first run        ───────link──────────▶ QUICKSTART, GETTING_STARTED, UPGRADE
Operating AWF (guide)      ───────link──────────▶ CLI_REFERENCE
Core Concepts (narrative)  ───────link──────────▶ CONCEPTS (deep)
PR monitor playbook        ───────link──────────▶ PR_MONITOR_ADOPTION, PLAN_PR_MONITOR
Reference Index (hub)      ───────link──────────▶ REST/MCP/Reason/CLI/Client Surfaces
Troubleshooting / FAQ      ───────link──────────▶ TROUBLESHOOTING, REASON_CATALOG
Contributing               ───────link──────────▶ CONTRIBUTING, AGENTS, SECURITY
```

### Wiki infrastructure
- **_Sidebar.md** — the persistent left-nav: the 7 group headers above, each with its pages in order. This is the primary navigation; GitHub renders it on every page.
- **_Footer.md** — one line on every page: "📖 Reference lives in the repo `docs/` (source of truth) · AWF is alpha · [Repo](…) · [Issues](…) · [Discussions](…) · [License](…/LICENSE)". (This makes the Support + License route explicit on every page.)

## Publishing mechanism (confirmed working)

GitHub has no REST API for wiki pages; the wiki is a git repo. Bootstrap (first
page via the UI) is **done** — the Home page was created, so
`git@github.com:dimileeh/agent-workspace-fabric.wiki.git` now clones.

Build/publish loop (fully programmatic from here):
1. `git clone git@github.com:dimileeh/agent-workspace-fabric.wiki.git`
2. Write/replace the 26 `*.md` page files + `_Sidebar.md` + `_Footer.md`.
   - GitHub wiki page name ↔ file name: spaces → `-`, `.md` extension, e.g.
     "Pick Your Path" → `Pick-Your-Path.md`. Links between pages use the page
     name: `[[Pick Your Path]]` or `[Pick Your Path](Pick-Your-Path)`.
   - Links INTO the repo use absolute URLs to `blob/main/docs/<FILE>` (wiki and
     repo are separate git repos; relative links don't resolve across them).
3. `git add -A && git commit && git push`.

## Maintenance model

- **Reference content is never duplicated** → reference upkeep stays a `docs/`
  concern; the wiki inherits it via links.
- **Wiki-owned prose** (orientation, guides, FAQ, playbooks) is the only thing to
  keep current; it changes far slower than the reference surface.
- The two `⚠` asset/positioning pages (AWF vs Alternatives, Demo & Video Gallery)
  are the only periodic-refresh items; flagged here so they're a conscious choice.

## NOT in scope

- Auto-sync/mirroring of `docs/` into the wiki (Approach C — rejected: drift +
  two rendered copies).
- Case Studies page (no real material yet).
- Governance/RFC process page (premature for alpha).
- Editing the in-repo `docs/` or `README` as part of this work (the wiki links to
  them as-is; any `docs/` gaps surface as separate issues).
